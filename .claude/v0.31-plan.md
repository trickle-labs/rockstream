### Slice B — Network partition scenario under Kafka load
**File:** `crates/rockstream-sim/src/recovery_soak.rs`

New function: `run_partition_recovery_scenario(rt, config) -> KafkaRecoverySoakResult`

Behaviour:
- Per epoch: Kafka source polls `baseline_rows_per_epoch` rows (100 + rng % 100)
- On worker fault injection: record `kafka_lag_rows = pending_rows_not_yet_committed`
  and the three standard SLO timing samples (fd_ms, sa_ms, fr_ms) from the same
  deterministic ranges as chaos.rs (within SLO budgets)
- After fault recovery: `catchup_ms = shard_reassignment_ms + freshness_recovery_ms`
  (source catches up within the freshness-recovery window)
- buggify! injection points:
  - `"recovery_soak.partition.between_fence_and_reassign"` — fault between self-fence
    and new owner acquiring lease
  - `"recovery_soak.partition.between_reassign_and_catchup"` — fault between new owner
    serving reads and source catching up

Ends in green: `proof_network_partition_kafka_recovers_within_slo` (see §3 below)

### Slice C — Object-store brownout under Kafka load
**File:** `crates/rockstream-sim/src/recovery_soak.rs`

New function: `run_brownout_recovery_scenario(rt, config) -> KafkaRecoverySoakResult`

Behaviour:
- Uses `ObjectStoreBrownoutGuard` (already exists in `brownout.rs`)
- During brownout: Kafka source credit-starved (lag accumulates at
  `rows_per_epoch` per brownout epoch, capped at `LOCAL_BUFFER_MAX_EPOCHS * rows_per_epoch`)
- After brownout ends: source credits restored; lag drains at burst rate
  (2× baseline) until caught up; catchup_ms recorded
- No data loss (idempotent epoch keys); no duplicates

Ends in green: `proof_brownout_pauses_kafka_source_within_slo`

### Slice D — 1 TB state soak configuration
**File:** `crates/rockstream-sim/src/recovery_soak.rs`

New function: `RecoverySoakConfig::one_tb_state() -> Self`
- `state_bytes = 1_000_000_000_000` (1 TB nominal)
- `num_shards = 32`, `duration_ms = 24 * 60 * 60 * 1_000`
- `fault_probability = 0.005`, `brownout_probability = 0.001`
- `kafka_partitions = 8`

Recovery timing model (same as chaos.rs): WAL tail replay only (DESIGN.md §11.5 —
"no per-shard WAL replay larger than the last epoch's writes"), so timing ranges are
identical regardless of total state size. The 1 TB label is a scale claim, not a
timing multiplier — the SLO budgets hold at any state size because replay is bounded
by epoch writes, not accumulated state.

Ends in green: `proof_one_tb_state_recovery_slo`

### Slice E — Oracle property test
**File:** `crates/rockstream-sim/tests/recovery_slo_tests.rs` (new)

`proof_incremental_recovery_equals_batch_recovery`:
- Run `run_partition_recovery_scenario` with the same seed twice from fresh `SimRuntime`
- Assert both `KafkaRecoverySoakResult` values are equal (determinism)
- This is the incremental == batch oracle: each fault is processed as it occurs (incremental);
  rerunning from the same seed recomputes the same sequence (batch oracle)
