# v0.65 Plan — Complete Standalone Recovery, Backup, and Restore

## Scope and Boundary

Roadmap reference (`ROADMAP.md` §11: `v0.65 — Complete Standalone Recovery, Backup, and Restore`):
> **Focus**: Make standalone RockStream a genuinely durable database deployment.
> **User outcome**: The supported local deployment can be crashed, backed up, restored elsewhere, and verified.
> **Required Proof**:
> At minimum:
> - hard kill during ordinary write
> - hard kill during view maintenance
> - hard kill during checkpoint
> - hard kill during catalog DDL
> - hard kill during backup
> - restore to new filesystem path
> - verify exact view multiset
> The restored instance must have no dependency on files outside the backup.

Committed implementation plan reference: `docs/implementation-plans/v0.65.md`.
Apply the shared implementation and evidence rules: `docs/implementation-plans/README.md`.

v0.65 establishes complete standalone recovery, point-in-time backup, and clean-path restore:

1. **Standalone Recovery Contract & 8-Category Ownership (`crates/rockstream-runtime/src/recovery.rs`, `shard_actor.rs`, `crates/rockstream-storage/src/shard_db.rs`)**:
   - Enumerate durable ownership and deterministic recovery order across all eight mandatory state categories:
     1. `catalog`: databases, namespaces, tables, columns, materialized views, compiled plans, indexes, roles (`CatalogStore`)
     2. `base-table state`: durable heap tables and primary key unique indexes (`ShardDb`, `WriteBuffer`)
     3. `operator state`: dirty-key incremental state for aggregates, joins, distinct, and windows (`AggregateOp`, `JoinOp`, etc.)
     4. `view output`: queryable view result multisets and row arrangements (`CatalogStore`, `DataRowEncoder`)
     5. `frontier/epoch`: monotonic committed epoch sequence, high-water mark, publisher lease (`FrontierAggregator`, `FrontierLeaseStore`)
     6. `indexes`: secondary indexes and key arrangement index tables (`IndexArrangeOp`, `CatalogStore`)
     7. `source cursors`: connector checkpoint offsets and resume tokens (`ConnectorOffset`, `SourceCoordinator`)
     8. `idempotency metadata`: client transaction sequence numbers and deduplication keys (`Session`, `WriteBatch`)
   - Zero mandatory state may exist solely in volatile process memory.
   - Define exact acknowledgment contract: a write is durable only after storage flush and sync acknowledgment; uncertain outcomes are resolved via idempotency metadata without duplicate side effects.

2. **Formal Recovery State Machine (`crates/rockstream-runtime/src/recovery.rs`, `crates/rockstream-types/src/lifecycle.rs`)**:
   - Sequence startup through 6 explicit, observable lifecycle states:
     ```text
     OpeningStorage
         ↓
     RecoveringCatalog
         ↓
     RecoveringEpoch
         ↓
     RecoveringOperators
         ↓
     ValidatingState
         ↓
     Ready
     ```
   - Management readiness probe returns `false` (`is_ready() == false`) during all pre-Ready recovery phases.
   - Any corruption, missing dependency, or restore failure transitions directly to `Fatal` with explicit diagnostic error codes; fallback to empty state is strictly prohibited.

3. **Multi-Page Bounded Scan Continuation (`crates/rockstream-storage/`, `crates/rockstream-ops/`)**:
   - Audit all recovery and restore scan loops to ensure complete pagination.
   - Use bounded memory buffers (`MAX_RESTORE_SCAN_PAGE_ROWS = 1,024`, `MAX_RECOVERY_SCAN_BUFFER_BYTES = 32 MiB`).
   - Paginate scans to completion across aggregate, arrangement, index, sink, cursor, and deduplication records; never treat a bounded first page as complete recovery.
   - Expose scan progress and handle cancellation cleanly.

4. **Point-in-Time Consistency & File Pinning (`crates/rockstream-control/src/checkpoint.rs`, `checkpoint_store.rs`, `checkpoint_export.rs`)**:
   - Capture a consistent logical recovery point consisting of exactly:
     `catalog_revision + checkpoint_id + frontier`.
   - Prevent mixing metadata from one revision with data or frontier from another.
   - Pin referenced files during backup copying; coordinate retention and compaction so concurrent writes or background compactions cannot unlink active backup files.

5. **Backup Manifest Specification & Compatibility Rules (`crates/rockstream-control/src/manifest.rs`, `checkpoint_export.rs`)**:
   - Standardize backup manifest JSON structure:
     ```json
     {
       "format_version": 1,
       "catalog_revision": 192,
       "checkpoint_id": 81,
       "frontier": 8412,
       "storage_format": 3,
       "files": [
         {
           "path": "shards/0/wal/000081.wal",
           "byte_len": 4194304,
           "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
         }
       ],
       "checksum": "a1b2c3d4e5f6..."
     }
     ```
   - Write and finalize manifest atomically only after all referenced payload files are durably fsync'd/uploaded.
   - Partial, interrupted, or damaged backup runs never publish a valid manifest.
   - Strict version compatibility: reject incompatible format versions (`RS-3617`) and unsupported storage formats.

6. **Admin Backup and Restore CLI Operations (`crates/rockstream-cli/`)**:
   - Implement CLI command family:
     - `rockstream admin backup create <destination>`: Create full point-in-time backup to LFS directory or S3/MinIO bucket.
     - `rockstream admin backup inspect <destination>`: Inspect backup manifest, inventory, catalog revision, and consistency metadata without writing.
     - `rockstream admin backup verify <destination>`: Cryptographically verify file integrity against per-file SHA-256 checksums and manifest checksums.
     - `rockstream admin restore <source> [--target <destination>] [--yes]`: Restore backup into fresh or explicitly replaceable destination.
   - Destination safety guard: restore only into an empty directory or explicitly replaceable path (`--yes`); reject non-empty destinations without authorization (`RS-2401` / `RS-0005`).
   - Validate backup integrity before restoring; rollback to initial state on any restore error.
   - Bound copy concurrency (`MAX_BACKUP_COPY_CONCURRENCY = 4`), pending bytes (`MAX_BACKUP_PENDING_BYTES = 64 MiB`), and retry attempts.

7. **Fail-Closed Corruption Detection (`crates/rockstream-runtime/`, `crates/rockstream-control/`)**:
   - Detect and fail closed on:
     - Missing files referenced in manifest (`RS-3615`)
     - Checksum mismatch on manifest or data files (`RS-3616`)
     - Incompatible manifest format or storage layout version (`RS-3617`)
     - Incomplete or unfinalized manifest (`RS-3615`)
     - Broken catalog references or orphan objects (`RS-3618`)
   - Startup fails closed with diagnostic error codes; readiness remains false.
   - `inspect` reports structural errors but never marks an invalid backup valid.

8. **Crash-Injection Matrix & Zero-Dependency Standalone Restore (`crates/rockstream-gateway/tests/`, `crates/rockstream-cli/tests/`)**:
   - Hard kill (`SIGKILL`) injection across 5 critical boundaries:
     1. During ordinary base-table writes
     2. During incremental view maintenance
     3. During periodic checkpoint execution
     4. During catalog DDL transaction commit
     5. During backup file copying and manifest generation
   - Standalone restore proof: restore complete backup to a brand-new directory, make original storage inaccessible (`chmod 000` or delete), launch fresh `rockstream` process, assert bit-identical base rows, view multisets, secondary indexes, and catalog objects against an independent oracle (`incremental == batch`).

### Non-Negotiable Ground Rules

- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag or config property on the same `rockstream` binary. `main` remains runnable through it.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters, asserted by test.
- Unbounded in-memory accumulation is never acceptable. Every new queue, buffer, or scan window needs a named upper bound, a fill-level metric, and a backpressure or error path.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass. Do not use `--no-verify`. Fix root causes.
- Make only changes this version requires. No speculative features outside IVM engine + Postgres wire layer.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals.**

## 4. Vertical Slices & Test Commitments

### Slice 1: Standalone Recovery State Machine & Multi-Category Ownership (`rockstream-runtime`, `rockstream-types`)
- Define explicit recovery sub-states: `OpeningStorage`, `RecoveringCatalog`, `RecoveringEpoch`, `RecoveringOperators`, `ValidatingState`, and `Ready`.
- Sequence recovery across all 8 mandatory categories in strict order.
- Ensure management readiness returns `false` during recovery and fails closed to `Fatal` on any mandatory error.
- Pre-committed test: `crates/rockstream-runtime/tests/recovery_state_machine_tests.rs::test_recovery_state_machine_traversal_and_readiness_gate`.

### Slice 2: Multi-Page Bounded Scan Continuation for Recovery (`rockstream-storage`, `rockstream-ops`)
- Refactor all state scan loops to paginate to completion rather than stopping at a page boundary.
- Bound memory buffers with `MAX_RESTORE_SCAN_PAGE_ROWS` (1,024 rows) and `MAX_RECOVERY_SCAN_BUFFER_BYTES` (32 MiB).
- Provide progress tracking and cancellation handles.
- Pre-committed test: `crates/rockstream-storage/tests/recovery_scan_pagination_tests.rs::test_multi_page_recovery_scan_continues_to_completion`.

### Slice 3: Point-in-Time Consistent Backup Point & Manifest Generation (`rockstream-control`)
- Formulate unified capture point: `catalog_revision + checkpoint_id + frontier`.
- Pin referenced storage files during copying; prevent compaction or writer unlinking.
- Generate and atomically finalize canonical backup manifest JSON with per-file SHA-256 checksums and overall manifest digest.
- Pre-committed test: `crates/rockstream-control/tests/backup_point_in_time_tests.rs::test_point_in_time_consistency_across_concurrent_writes`.

### Slice 4: Admin Backup CLI Operations (`backup create`, `backup inspect`, `backup verify`) (`rockstream-cli`)
- Wire `rockstream admin backup create <destination>`, `inspect <destination>`, and `verify <destination>` into CLI parsing and execution.
- Implement per-file cryptographic integrity verification against recorded SHA-256 hashes.
- Pre-committed test: `crates/rockstream-cli/tests/admin_backup_cli_tests.rs::test_admin_backup_create_inspect_verify_cli`.

### Slice 5: Admin Restore CLI Operation to Clean/Replaceable Destination (`rockstream-cli`, `rockstream-storage`)
- Wire `rockstream admin restore <source> [--target <destination>] [--yes]` into CLI dispatch.
- Enforce clean destination rule: refuse non-empty destinations without `--yes` (`RS-2401` / `RS-0005`).
- Pre-validate backup integrity before modifying destination; roll back on failure.
- Pre-committed test: `crates/rockstream-cli/tests/admin_restore_cli_tests.rs::test_admin_restore_destination_guards_and_rollback`.

### Slice 6: Fail-Closed Corruption Detection & Incompatible Format Rejection (`rockstream-runtime`, `rockstream-control`)
- Implement strict corruption validation for missing files, bad checksums, incompatible formats, and broken catalog references.
- Enforce explicit error codes (`RS-3615`, `RS-3616`, `RS-3617`, `RS-3618`) and fail closed with zero partial recovery.
- Pre-committed test: `crates/rockstream-control/tests/backup_corruption_detection_tests.rs::test_corruption_detection_fails_closed`.

### Slice 7: Hard Kill Crash-Injection Test Matrix (`rockstream-runtime`, `rockstream-gateway`)
- Inject `SIGKILL` across 5 critical boundaries: ordinary write, view maintenance, checkpoint commit, catalog DDL, and backup creation.
- Assert exact recovery of committed state and clean rejection of uncommitted operations post-restart.
- Pre-committed test: `crates/rockstream-gateway/tests/recovery_crash_injection_tests.rs::test_hard_kill_at_all_five_execution_boundaries`.

### Slice 8: Independent Clean-Path Restore Verification & Zero Original File Dependency (`rockstream-cli`, `rockstream-gateway`)
- Restore complete backup to a fresh filesystem directory.
- Render original storage directory inaccessible (`chmod 000` or delete).
- Launch fresh `rockstream` process against restored directory; assert bit-identical catalog, base tables, and view multisets against an independent oracle (`incremental == batch`).
- Pre-committed test: `crates/rockstream-cli/tests/disaster_recovery_standalone_tests.rs::test_restore_to_new_path_zero_original_file_dependency`.

### Slice 9: Resource Bounding, Copy Concurrency & Scan Limits (`rockstream-control`, `rockstream-cli`)
- Bound copy concurrency (`MAX_BACKUP_COPY_CONCURRENCY = 4`), in-flight memory (`MAX_BACKUP_PENDING_BYTES = 64 MiB`), scan windows (`MAX_BACKUP_SCAN_WINDOW_OBJECTS = 1,024`), and recovery budgets.
- Validate graceful backpressure, observable progress, and explicit error handling on slow storage or timeout.
- Pre-committed test: `crates/rockstream-control/tests/backup_bounding_limits_tests.rs::test_backup_and_restore_resource_bounds_enforced`.
