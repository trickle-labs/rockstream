## 1. Resolved Contract Choices

1. **Canonical Source DDL / API Contract & Authoritative Ownership (Step 1, V069-01)**:
   - **Syntax & Schema**:
     ```sql
     CREATE SOURCE <source_name> TYPE postgres_cdc (
       host = '...',
       port = '5432',
       database = '...',
       publication = '...',
       slot = '...',
       table = '...',
       schema_policy = 'evolve',
       credential_ref = 'vault://...',
       snapshot_policy = 'initial'
     ) FORMAT pgoutput;
     ```
   - **Authoritative Ownership**: The SQL DDL / API path owns the canonical source definition. `rockstream.toml` configuration files supply environment/deployment bindings or generate the definition, but cannot act as an independent mutable source owner.
   - **Seven Roadmap Fields Strictly Enforced**:
     1. Upstream endpoint (`host`, `port`, `database`, `user`)
     2. Publication name (`publication`)
     3. Replication slot name (`slot`)
     4. Table mapping (`table` or relational mapping options)
     5. Schema policy (`schema_policy`: `strict` | `evolve` | `error`; default `evolve`)
     6. Credential reference (`credential_ref` or `secret`; inline credentials such as `password = '...'` are rejected with `RS-4008`)
     7. Snapshot policy (`snapshot_policy`: `initial` [snapshot then stream] | `never` [stream from current LSN] | `always` [resnapshot on restart])
   - **Pre-Ingestion Validation**:
     - Connectivity to upstream PostgreSQL endpoint, existence of publication, validity and state of replication slot, existence of target table(s), credential resolution, and table replica identity (`REPLICA IDENTITY FULL` or primary key) are verified *before* starting ingestion. Missing publication or table fails closed with `RS-4008` / `RS-4001`.
   - **Persisted Source Record Versioning**:
     - Persisted in catalog storage (`ShardDb`) as `SourceRecordV1` with explicit version tag `1`. Records with unknown versions are rejected with `RS-2025` / `RS-4008`.

   - Redacted diagnostics: diagnostics, logs, and `SHOW SOURCE STATUS` never expose raw passwords or secret tokens.

3. **Snapshot and WAL Fence Exact Multiset Guarantee (Step 3, V069-03)**:
   - **Boundary Coordination**:
     - Consistent slot creation: create or attach replication slot via `pg_create_logical_replication_slot(slot_name, 'pgoutput')` returning snapshot identifier and consistent LSN `fence_lsn`.
     - Exported snapshot read: snapshot transaction opened in `REPEATABLE READ` isolation using the exported snapshot ID.
     - Paged snapshot streaming: snapshot rows streamed in bounded pages (1,024 rows / 1 MiB max per page).
     - Streaming cutover: WAL streaming begins from `fence_lsn`. WAL events with `commit_lsn <= fence_lsn` are discarded; events with `commit_lsn > fence_lsn` are applied.
   - **Exact Multiset Invariant**:
     $$\text{Snapshot Rows} + \text{Subsequent WAL Changes} = \text{Exact Upstream History from Boundary}$$
     Zero handoff gap, zero duplicate rows, exact multiplicity preservation.
   - **Crash Replay at Fence**:
     - Crash before fence: snapshot is discarded and restarted from scratch.
     - Crash during snapshot: restart resumes or re-executes snapshot cleanly without duplicate keys.
     - Crash after fence: resumes from durable LSN with zero duplicated or missing rows. If slot is lost or WAL truncated, fails closed with explicit resnapshot procedure.

4. **Upstream Transaction Grouping and Atomicity Barrier (Step 4, V069-04)**:
   - **Grouping**:
     - All row operations between pgoutput `BEGIN` (XID, commit LSN) and `COMMIT` (commit LSN, end LSN) are buffered within `ActiveEnvelope` in `SharedPgOutputCoordinator`.
     - Multi-row and multi-table transactions are preserved as a single transaction group.
   - **Atomicity & Isolation**:
     - Transactions become visible to downstream materialized views only upon `COMMIT` and are assigned to a single durable RockStream epoch.
     - Public readers never observe partial transactions (e.g. 5 of 10 rows inserted).
   - **Bounded Transaction Size & Overflow Behavior**:
     - `max_cdc_transaction_bytes = 64 MiB` (configurable).
     - Transactions exceeding this limit are not fragmented into partial visible states. Instead, ingestion is paused and fails closed with `RS-4014` (`source.bounds_exceeded`) naming the transaction size and required budget adjustment.

5. **Quad-LSN Progress Persistence and Acknowledgment Barrier (Step 5, V069-05)**:
   - **Four Progress Fields Persisted in ShardDb**:
     1. `received_lsn`: highest LSN read from replication stream.
     2. `applied_lsn`: highest LSN decoded and buffered in the coordinator.
     3. `durable_lsn`: highest LSN whose corresponding epoch and all downstream view effects are committed to durable storage (SlateDB).
     4. `published_frontier`: highest LSN whose view effects are visible to pgwire readers.
   - **Upstream Slot Acknowledgment Invariant**:
     $$\text{confirmed\_flush\_lsn} \le \text{durable\_lsn}$$
     Acknowledgement sent to PostgreSQL via `StandbyStatusUpdate` MUST NEVER advance beyond `durable_lsn`.
   - **Crash Between Processing, Persistence, and Ack**:
     - Process kill between epoch commit and slot acknowledgement results in replay from the last acknowledged slot LSN. RockStream deduplicates replayed events up to `durable_lsn` using persisted transaction/LSN tokens.
     - Storage failure halts acknowledgment immediately; slot never advances beyond durable state.

6. **Schema Change Policy Decision Table (Step 6, V069-06)**:
   - Classification of the 5 canonical roadmap examples:
     | Schema Change Example | Classification | Engine Action | Recovery / Isolation Behavior |
     |---|---|---|---|
     | **Add nullable column** | `Compatible` | Auto-applied in memory & recorded in schema history | Pre-existing rows padded with NULL; subsequent WAL events populate new column. Materialized views continue. |
     | **Rename column** | `Requires Rebuild` | Relation blocked; stops applying changes for table | Enters `BLOCKED` status with `RS-4015`. Retains recoverable LSN. Unaffected tables continue. Rebuild CLI command provided. |
     | **Type widening** (`int4` $\to$ `int8`) | `Compatible` | Lossless widening applied; schema version bumped | Arrow schema widened; view maintenance continues seamlessly. |
     | **Drop referenced column** | `Requires Rebuild` | Relation blocked; dependent views invalidated | Enters `BLOCKED` status with `RS-4015`. Dependent views return error. Retains recoverable LSN. |
     | **Primary-key change** | `Unsupported / Requires Rebuild` | Relation blocked immediately | Enters `BLOCKED` status with `RS-4015`. Primary key retraction identity changed. Resnapshot procedure required. |
   - **Isolation**: Changes affecting one table in a publication do not block ingestion of unaffected tables.

7. **Worker Budget, Backpressure, and Truthful Lag (Step 7, V069-07)**:
   - **Named Buffer Bounds**:
     - `max_snapshot_page_buffer_bytes = 16 MiB`
     - `max_cdc_transaction_buffer_bytes = 64 MiB`
     - `max_in_flight_source_epochs = 16`
     - `max_cdc_reconnect_retries = 5` (with bounded exponential backoff: 500ms to 8s)
   - **Truthful Lag Metric**:
     $$\text{source\_lag\_bytes} = \text{pg\_current\_wal\_lsn}() - \text{durable\_lsn}$$
     Reported truthfully in `SHOW SOURCE STATUS` alongside `received_lsn`, `applied_lsn`, `durable_lsn`, buffer fill ratios, and blocked-relation status.
   - **Missing-WAL Recovery**:
     - When PostgreSQL replication slot is invalidated or required WAL segments are purged upstream (Postgres error `55000` / `58P01`), connector transitions to `FAILED` with `RS-4011` / `RS-4016` and outputs an explicit resnapshot recovery procedure.

8. **Roadmap TestContainers Scenario Specification (Step 8, V069-08)**:
   - Complete 15-phase sequential integration test running against real PostgreSQL and real release `rockstream` binary:
     1. Start PostgreSQL 16 container with `wal_level=logical`.
     2. Seed 10,000+ rows into source tables.
     3. Start release `rockstream` binary with `--role all`.
     4. Issue `CREATE SOURCE ... TYPE postgres_cdc FORMAT pgoutput`.
     5. Issue `CREATE MATERIALIZED VIEW ... AS SELECT ...`.
     6. Complete snapshot backfill; verify exact row count and contents.
     7. Execute live `INSERT`s in PostgreSQL $\to$ verify immediate view update.
     8. Execute live `UPDATE`s in PostgreSQL $\to$ verify exact in-place update in view.
     9. Execute live `DELETE`s in PostgreSQL $\to$ verify exact row retraction in view.
     10. Execute multi-row, multi-table transaction in PostgreSQL $\to$ verify atomic view visibility.
     11. Crash RockStream process (`kill -9`).
     12. Restart RockStream process $\to$ verify clean recovery from `durable_lsn` with zero duplicate/missed rows.
     13. Disconnect PostgreSQL network temporarily; reconnect $\to$ verify automatic reconnect and replay catch-up.
     14. Apply compatible schema evolution (`ALTER TABLE ... ADD COLUMN ...`) $\to$ verify view continues.
     15. Apply incompatible schema evolution (`ALTER TABLE ... DROP COLUMN ...`) $\to$ verify relation blocked, error code `RS-4015`, other tables unaffected, resnapshot recovery succeeds.

9. **Connector Performance Envelope, Large State, and Worker Migration (Step 9, V069-09)**:
   - Workload profile: 10,000 msg/s ingestion sustained.
   - Maintained state > configured worker budget (backed by v0.67.1 demand-loaded spillable arrangements).
   - Targets: `freshness_p99 <= 100 ms`, `commit_p99 <= 25 ms`, `read_p99 <= 10 ms`.
   - Worker RSS strictly bounded under continuous CDC stream.
   - Worker shard migration under v0.68 saga coordinator during active CDC stream.
