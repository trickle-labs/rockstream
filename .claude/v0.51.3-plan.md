# v0.51.3 Plan — Gateway↔Runtime Unification: One Data Plane

Roadmap row: `NEW_ROADMAP.md:1011`. Prior version: v0.51.2 (`NEW_ROADMAP.md:1010`,
Query-Time Predicate/Join/Aggregate Execution, Standard EXPLAIN Parity & Real

FizzBee models — it re-runs them unchanged as its coordination proof.

**Scoping decision (documented, not a deferral):** because every existing
view definition across the whole gateway test corpus is `Source →
[Filter] → Project` only, this version's `PlanNode → Operator` compiler
(§3 Slice 3) covers exactly `OpKind`/`PlanNode` variants `Source`, `Filter`,
`Project`, `Map`, `ViewSink` — the shapes `DiffCtx::differentiate` already
handles as "linear" (`rockstream-diff/src/lib.rs:8-9,102-145`) and that
`CreditScheduler`/`LinearPipeline` already execute (both are explicitly
linear-chain-only). `Aggregate`/`Join`/`OuterJoin`/`Window` compilation is
real, unimplemented work but is **not required by this version's Scope** (no
Proof claim, no existing test, exercises a view definition using them) and is
explicitly reserved for whichever future version first introduces a view
definition that needs them — most likely v0.51.4 (incremental maintenance)
or later, which will owe its own test commitments when it lands. This
mirrors v0.51.2's own §2 scoping-decision precedent (deferring real
`IndexArrangeOp` wiring) and is not itself a deferral of this version's Scope,
since nothing in this version's Scope or Proof requires Aggregate/Join view
definitions.

## 3. Vertical Slices

Ordered by dependency: Slice 1 (encoding) blocks everything downstream since
every existing view test uses `TEXT` columns. Slice 2 (shared shard) and
Slice 3 (compiler) are independent of each other but both required before
Slice 4 (CREATE VIEW wiring). Slices 5–6 depend on 1–4. Slice 7 is
regression-only, no new code.

### Slice 1 — Generalize `ViewSinkOp`'s row encoding beyond Int64-only (do first)
- Replace `ViewSinkOp::encode_row`'s hardcoded `Int64Array` downcast
  (`sink.rs:51-62`) and `read_view_output`'s fixed `(num_cols+1)*8`-byte
  decode (`sink.rs:107-150`) with a per-column, schema-driven encoding: for
  each `arrow::datatypes::DataType` in the batch's schema, dispatch to a
  type-tagged variable-width encode (`Int64`, `Utf8`, `Boolean`, `Float64` —
  the types exercised by `type_system_tests.rs`), instead of assuming every
  column is `Int64`. Store the schema itself once (e.g. as an extra
  `ShardPrefix::ViewOutput` sub-key `[op_id]‖SCHEMA`, or pass the expected
  `Vec<DataType>` into `read_view_output` alongside `num_cols`) so decode
  doesn't need per-row type sniffing.
- Keep the function signatures otherwise compatible (`write_epoch`,
  `write_next_epoch`, `read_view_output`) so existing `rockstream-ops`/
  `rockstream-sql` callers (`lfs_pipeline.rs`, `lfs_snapshot.rs`,
  `minio_snapshot.rs`, `lfs_catalog.rs` — the only current callers, confirmed
  via `grep -rln "read_view_output|ViewSinkOp" crates/`) keep working
  unmodified for their existing Int64-only fixtures.
- Exit test: new `rockstream-ops/tests/sink_multi_type_tests.rs` —
  `write_and_read_back_mixed_int64_utf8_row` round-trips a batch with
  `(id: Int64, name: Utf8)` columns through `write_next_epoch` +
  `read_view_output` and asserts byte-identical row content; a second test
  covers `Boolean`/`Float64`.

### Slice 2 — One shared `ShardDb`, no `gateway-shard` directory
- Promote `rockstream-runtime`, `rockstream-plan`, `rockstream-ops`,
  `rockstream-diff` to real (non-dev) dependencies in
  `crates/rockstream-gateway/Cargo.toml` (`rockstream-ops`/`rockstream-oracle`
  already dev-deps; `runtime`/`plan`/`diff` currently absent entirely).
- Change `start_gateway` (`rockstream-cli/src/lib.rs:220-300`) to accept an
  already-open `Arc<ShardDb>` (and its backing `Arc<dyn ObjectStore>` for the
  `ShardReader`) instead of constructing its own `gateway-shard/` directory
  and `ShardDb::builder("gateway", ...)`.
- Change `run_start`'s `--role all` branch (`lib.rs:551-572,591-648`): open a
  single `ShardDb` under `<storage>/shards/0/` (reusing the exact directory
  convention `client.rs:271-273` already uses for leased shards), insert it
  into the worker's `active_shards` map for `ShardId(0)` (replacing the demo
  `ShardId(1)` lease request at `lib.rs:568`, which served no real purpose),
  and pass the **same** `Arc<ShardDb>` into `start_gateway`. `--role gateway`
  (standalone, no worker) keeps opening its own shard, since there's no
  worker to share with in that role — not part of this version's `--role
  all` Proof claim.
- Exit test: new `rockstream-cli/tests/unified_data_plane_tests.rs::
  role_all_creates_exactly_one_shard_directory` — starts `--role all` against
  a temp storage dir, asserts `<storage>/gateway-shard/` does **not** exist
  and exactly one `<storage>/shards/0/` directory exists with a valid
  manifest.

### Slice 3 — `PlanNode` → executable `Operator` chain compiler (independent of Slice 2)
- New function, e.g. `rockstream_ops::compile::compile_plan(plan: &PlanNode,
  db: Arc<ShardDb>) -> Result<(Vec<Arc<dyn Operator>>, ViewSinkOp), CompileError>`
  (new `rockstream-ops/src/compile.rs` — the crate that already owns
  `Operator`/`ViewSinkOp`/`FilterOp`/`ProjectOp`/`MapOp`). Recursively walks
  the **original** `PlanNode` tree (not the field-stripped `OpNode` IR — see
  §2 finding), assigning `OperatorId`s exactly as `DiffCtx::next_op_id`
  already does, matching only `PlanNode::Source`, `Filter{predicate}`,
  `Project{columns}`, `Map{func}`, `ViewSink{view_name, pk, child}` (per the
  §2 scoping decision); any other variant returns a new
  `CompileError::UnsupportedNode` (a real, tested error path, not a silent
  fallback).
- For each variant: `Filter{predicate}` → `Arc::new(FilterOp::new(predicate.clone()))`,
  `Project{columns}` → `Arc::new(ProjectOp::new(named_exprs))` (names sourced
  from the view's already-computed `CatalogView.columns`, matching
  `infer_select_columns`'s existing output), `Map{func}` →
  `Arc::new(MapOp::new(func.clone()))`, `ViewSink{..}` →
  `ViewSinkOp::new(db.clone(), op_id)`. `Source` contributes no operator (the
  chain's input channel/`LinearPipeline` entry point stands in for it).
- Exit test: pre-committed oracle test (§4) — `compile_plan` output driven
  through `LinearPipeline`/`accumulate_ab`-style harness, `incremental ==
  batch` against a hand-computed oracle for representative
  `Source→Filter→Project→ViewSink` plans.

### Slice 4 — Wire `CREATE VIEW`/`CREATE MATERIALIZED VIEW` through the real pipeline
- Add `pub op_id: Option<u64>` to `CatalogView` (`catalog_stubs.rs:151-157`),
  mirroring `CatalogIndexEntry.op_id`'s existing pattern (`:183-192`).
- In `handle_create_view` (`server.rs:2898-3050`): after catalog
  registration, call `SqlFrontend::sql_to_plan_node_with_catalog` (already
  proven, `rockstream-sql/src/frontend.rs:165-206`) on the view's SQL, then
  Slice 3's `compile_plan`, store the resulting `Vec<Arc<dyn Operator>>` +
  `ViewSinkOp` in a new in-process registry (`HashMap<String, CompiledView>`
  on `GatewayServer`, keyed by view name) and persist `op_id` onto
  `CatalogView`. This **replaces** `view_materializer.rs`'s
  `materialize_views` call sites (`server.rs:2988`, `:3933`) for views
  registered through this new path; `view_materializer.rs` itself is deleted
  once every call site is migrated (no dead standalone-DataFusion path left
  behind — ground rules forbid speculative/parallel implementations).
- Exit test: `unified_data_plane_tests.rs::create_view_registers_op_id_and_no_longer_uses_datafusion_materializer` —
  asserts `CatalogView.op_id` is `Some(_)` immediately after `CREATE VIEW`,
  and that the in-process compiled-view registry contains the view.

### Slice 5 — Wire `COMMIT` to drive the compiled operator chain (depends on 1–4)
- In `handle_commit` (`server.rs:3786-3970`), after the base-table
  `WriteBatch` persists (`:3913-3916`), for each view whose dependency set
  overlaps `changed_tables` and that has a compiled pipeline (Slice 4): scan
  the *current* full `view_output/{table}/` content for each source table
  (bounded scan, reusing v0.51.2's `MAX_QUERY_TIME_ROWS` pattern and
  `tsv_to_record_batch`), diff against the previous commit's materialized
  snapshot for that view (retract old rows at weight `-1`, insert new rows at
  weight `+1` — this is the correctness-preserving trick that keeps
  `ViewSinkOp`'s append-only, epoch-summed accumulation (`sink.rs:103-150`
  sums **all** epochs) consistent with "full recompute per commit" per this
  version's explicit non-incremental Scope; true delta computation without a
  full rescan is v0.51.4's job), run the retract+insert batch through
  `LinearPipeline::process` (synchronous — matches `EmbeddedRuntime`'s
  zero-gRPC/zero-shuffle profile, `embedded.rs:1-9`), and call
  `ViewSinkOp::write_next_epoch` on the result. This replaces the
  `materialize_views` call at `server.rs:3920-3941` for compiled views.
- New metric: `COMMIT_COMPILED_VIEW_ROWS_SCANNED_TOTAL` (counter, mirrors
  v0.51.2's `QUERY_TIME_DATAFUSION_ROWS_SCANNED_TOTAL` pattern,
  `server.rs:2098`-style `AtomicU64`) so the bounded re-scan's fill level is
  observable.
- Exit test: `unified_data_plane_tests.rs::insert_commit_select_round_trip_serviced_by_real_operator_dag` —
  live `tokio_postgres` round trip: `CREATE TABLE`, `CREATE MATERIALIZED
  VIEW`, `INSERT`, `COMMIT`, `SELECT` — asserts the returned row matches, and
  (via the new metric or a debug counter on `compile_plan`'s `FilterOp`/
  `ProjectOp` instances) that the real operator chain executed, not
  DataFusion.

### Slice 6 — Wire `SELECT`/`read_view_response` to read `ViewSinkOp` output (depends on 4–5)
- In `read_view_response` (`server.rs:2745-2850`), when `CatalogView.op_id`
  is `Some(id)`, call `rockstream_ops::sink::read_view_output(shard_db, id,
  num_cols)` instead of scanning the gateway-local `view_output/{view_name}/`
  prefix; collapse the returned `(epoch, row_idx, cols, weight)` rows by
  primary key (per `pk` recorded in the `ViewSink` plan node), summing
  weights, and keep only rows with net positive weight (standard Z-set →
  set-semantics materialization, same pattern already used implicitly by
  `handle_commit`'s retract/insert). Column values decode via Slice 1's
  generalized, schema-aware decode.
- Exit test: re-run `mv_immediate_population_durability_lfs_tests.rs` /
  `_minio_tests.rs` (the pre-existing `TEXT`+`BIGINT` view test) unmodified —
  it now exercises the full new path end to end; both must stay green.

## 4. Test Commitments (new operators)

No new IVM/DBSP operator **kind** is introduced — `FilterOp`, `ProjectOp`,
`MapOp`, `ViewSinkOp` all pre-exist and were individually oracle-proven
correct since v0.4–v0.10. What is new is Slice 3's compiler that, for the
first time, derives live operator instances from gateway-submitted SQL text
in production (previously only hand-wired in `sql_engine_e2e.rs`'s oracle
harness). Per the ground rules ("pre-commit to its oracle property test
(`incremental == batch`) before writing the operator"), this version commits
to:

- **New test**: `crates/rockstream-gateway/tests/unified_data_plane_oracle_tests.rs::
  compiled_view_incremental_output_equals_batch_oracle` — for a
  `Source→Filter→Project→ViewSink` view compiled via Slice 3's
  `compile_plan` and driven via Slice 5's commit-time retract/insert
  pipeline across multiple commits (insert, update, delete on the base
  table), the accumulated `read_view_output` result after each commit
  equals a hand-computed oracle (full SQL re-evaluation over the
  accumulated base-table state) — the same "incremental == batch" property
  standard as `sql_engine_e2e.rs`. This is the direct proof that wiring
  live SQL through the real pipeline (rather than DataFusion) is correct,
  not just plumbed.
- **New test**: `rockstream-ops/tests/sink_multi_type_tests.rs` (Slice 1) —
  not an oracle test (no operator semantics involved), but a required
  correctness pre-commitment since the encoding change is a prerequisite for
  every other test in this plan.

## 6. Coordination Slices

No **new** cross-shard/cross-node coordination path is introduced. `--role
all` remains single-process, single-shard (shard `0`, per Slice 2) — the
same boundary v0.51.1/v0.51.2 already documented for gateway-local
operations. Sharing one `ShardDb` between the embedded worker's
`active_shards` map and the gateway touches only shard-*open* plumbing
(`rockstream-cli`), not the lease/fencing/frontier state machines themselves
(`rockstream-control`, `rockstream-runtime/src/fence.rs`, `recovery.rs`).
Per the roadmap's explicit statement, "No new FizzBee model is needed... this
version is proven by re-running the full existing `SimRuntime`/
FizzBee-paired-assertion regression suite against the unified data plane" —
this is Slice 7: a regression re-run, not a new coordination-slice test. No
new `SimRuntime`/`buggify!()` test is owed by this version's own Scope.
Real multi-shard/multi-node DAG execution (workers other than the embedded
`--role all` one actually running compiled pipelines) is out of Scope here
and reserved for whichever future version distributes the compiled-pipeline
execution introduced in Slice 3 across real workers.
