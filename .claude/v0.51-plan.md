# v0.51 Plan — Hot-Path Compute Optimizations

Roadmap row re-read: `NEW_ROADMAP.md:928` — **Hot-Path Compute Optimizations**:
WAL elision for derived intermediate operator shards, and direct coupling from
`max_rows_per_quantum` to network-buffer depth, with proof that throughput on
complex DAGs increases by **>30%**.

Important current-state note before slicing: the 2026-07-11 roadmap review was
correct that this repo historically had no benchmark gate, but the repo has
since gained generic benchmark-gate infrastructure at v0.45.4
(`crates/rockstream-ops/src/bench_regression.rs`,
`crates/rockstream-ops/src/bin/bench_regression_gate.rs`,
`.github/workflows/ci.yml:313-342`, checked-in baseline JSONs). v0.51 should
**reuse and extend that machinery**, because it still does **not** benchmark or
gate the specific hot path this version is claiming.

## Codebase Investigation Findings

### 1. Where WAL writes happen today for derived/intermediate shards

**Lowest-level WAL writers**

- `crates/rockstream-storage/src/shard_db.rs:200-212` — `ShardDb::put()`
- `crates/rockstream-storage/src/shard_db.rs:229-266` — `ShardDb::write_batch()`

Those are the actual SlateDB write entry points behind all higher-level
persistence helpers.

**Live multi-shard hot-path intermediate writes**

- `crates/rockstream-runtime/src/exchange/multiplexer.rs:186-245` —
  `WorkerStreamMultiplexer::send_frame()` persists sender-side
  `shuffle_outbox/` via `persist_outbox()` **before every send** (`:236`).
- `crates/rockstream-runtime/src/exchange/service.rs:169-197` —
  `ShuffleServer::shuffle_stream()` persists receiver-side `shuffle_inbox/`
  via `persist_inbox()` before forwarding the frame to the local inlet.
- `crates/rockstream-runtime/src/exchange/shared_memory.rs:203-240` —
  `deliver_ticket()` persists receiver-side `shuffle_inbox/` for same-host
  shared-memory delivery too.
- `crates/rockstream-runtime/src/exchange/loopback.rs:95-127` —
  `LoopbackRouter::route_loopback()` persists **both** `shuffle_outbox/` and
  `shuffle_inbox/` even though this is the same-worker fast path.
- `crates/rockstream-runtime/src/exchange/multiplexer.rs:359-460` —
  durable object-store fallback uploads a coalesced shuffle object, then
  deletes the local outbox only after upload succeeds.
- `crates/rockstream-runtime/src/exchange/multiplexer.rs:498-569` —
  `catch_up_durable()` rehydrates `shuffle_inbox/` from the durable object.

This is the most important v0.51 finding: the repo’s **live distributed hot
path** is still doing local SlateDB WAL work on fast-path exchange deliveries,
even when delivery succeeds immediately over gRPC or shared memory.

**Other operator-shard WAL writers that exist today**

These are real WAL writers too, but they are helper-layer persistence routines,
not the continuously exercised exchange hot path:

- `crates/rockstream-ops/src/aggregate.rs:681-722` — `persist_agg_state()`
- `crates/rockstream-ops/src/minmax.rs:456-515` — `persist_minmax_state()`
- `crates/rockstream-ops/src/join.rs:479-514` — `JoinOp::persist_state()`
- `crates/rockstream-ops/src/distinct.rs:506-535` — `persist_distinct_state()`
- `crates/rockstream-ops/src/window.rs:566-601` — `persist_window_state()`
- `crates/rockstream-ops/src/time_window.rs:1019-1181` — tumble/hop/session
  window persistence helpers
- `crates/rockstream-ops/src/topk.rs:371-396` — `persist_topk_state()`
- `crates/rockstream-ops/src/recursion.rs:737-753` — `persist_recursion_state()`

They matter as background precedent: “derived/intermediate shard” is already a
real storage concept in the repo. But the **first measurable throughput win**
should target the exchange fast path above, because that code is live today and
already has integration, durability, and simulation coverage to extend.

### 2. Where checkpoint / replay safety lives today

- `crates/rockstream-storage/src/shard_db.rs:530-547` —
  `ShardDb::create_checkpoint()` uses `CheckpointScope::Durable`.
- The doc comment at `crates/rockstream-storage/src/shard_db.rs:537-538`
  explicitly says checkpoints include only **durably flushed** writes,
  “avoiding any dependency on WAL-only entries.”
- `DESIGN.md:1974-2014` defines shard-level epoch commit, and
  `DESIGN.md:2010-2014` makes WAL atomicity the current durability contract.
- `DESIGN.md:2181-2193` makes restart/reassignment recover from the durably
  committed frontier plus WAL replay.

That means v0.51 cannot just “stop writing stuff” casually; it must narrow WAL
elision to data that is explicitly safe to reconstruct from upstream replay /
durable fallback without violating the frontier/checkpoint contract.

### 3. Where `max_rows_per_quantum` and buffer/backpressure live today

**`max_rows_per_quantum`**

- `crates/rockstream-types/src/config.rs:103-105` — `WorkerConfig` defines
  `max_rows_per_quantum`
- `crates/rockstream-types/src/config.rs:188-190` and `:250-252` — defaults
  set to `1000`
- `crates/rockstream-types/src/cost.rs:116-118` — sample config includes it

Repo-wide search found **no runtime use site** beyond those config/default
definitions. Today it is a dead config knob.

**Current backpressure / buffer-depth code**

- `crates/rockstream-ops/src/task.rs:26-31` — `OPERATOR_CHANNEL_CAPACITY = 16`
  for in-process operator-to-operator `mpsc` backpressure
- `crates/rockstream-runtime/src/exchange/flow_control.rs:9-74` —
  `FlowController`, with hardcoded default credits via `or_insert(16)` in both
  `handle_ack()` and `acquire_credit()`
- `crates/rockstream-runtime/proto/shuffle.proto:20-27` — `ShuffleAck` carries
  `credit_grant`
- `crates/rockstream-runtime/src/exchange/service.rs:225-233` and
  `crates/rockstream-runtime/src/exchange/shared_memory.rs:247-250` — both
  currently grant `credit_grant: 1` **per frame**
- `crates/rockstream-types/src/config.rs:115-135` —
  `ExchangeConfig.same_host_shm_segment_bytes` and
  `same_host_shm_segments_per_peer` are the existing named same-host bounds
- `crates/rockstream-runtime/src/exchange/shared_memory.rs:75-141` enforces
  those bounds and updates `shuffle_shm_bytes_used` /
  `shuffle_shm_segments_in_use`

**Critical integration gap**

- `crates/rockstream-runtime/src/exchange/multiplexer.rs` uses the
  `FlowController` only on the ACK side (`:252`, `:312`), but **never** calls
  `acquire_credit()` before sending.

So the current network shuffle path has:

1. a hardcoded credit model (`16`, per-frame),
2. no link to `max_rows_per_quantum`,
3. and no live send-side blocking on credits at all.

That makes the roadmap’s “tight backpressure coupling” a real missing feature,
not just tuning.

## Vertical Slices

### Slice 1 — Direct gRPC fast path stops writing shuffle WAL on success

Restrict fast-path direct delivery so `WorkerStreamMultiplexer::send_frame()`
and `ShuffleServer::shuffle_stream()` no longer persist `shuffle_outbox/` /
`shuffle_inbox/` for a successfully delivered gRPC frame. Keep the durable
object-store fallback path persisted, because that is the explicit recovery
path when the fast path is unavailable.

**Ends green when:** `direct_grpc_fast_path_avoids_shuffle_wal_and_delivers_exact_rows`
passes.

### Slice 2 — Loopback + same-host shared-memory fast paths stop writing shuffle WAL on success

Apply the same policy to `LoopbackRouter::route_loopback()` and
`shared_memory::deliver_ticket()`: successful in-process or same-host delivery
should not write `shuffle_outbox/` / `shuffle_inbox/` keys just to delete or
ignore them immediately afterward. Preserve the existing bounded shared-memory
pool semantics and fallback-to-gRPC behavior.

**Ends green when:** `same_host_shared_memory_fast_path_avoids_shuffle_wal_and_delivers_exact_rows`
passes.

### Slice 3 — Recovery/checkpoint semantics stay correct without fast-path shuffle WAL

Make recovery explicitly rely on the already-designed durable sources of truth:
checkpoint frontier + source replay + durable object-store fallback, not on
fast-path shuffle WAL entries that no longer exist. Prove that
`ShardDb::create_checkpoint()`’s `CheckpointScope::Durable` semantics remain
valid when fast-path shuffle writes are elided, and that restart/replay does
not duplicate or lose rows.

**Ends green when:** `direct_grpc_fast_path_replays_from_frontier_after_lfs_restart_without_shuffle_wal`
passes.

### Slice 4 — `max_rows_per_quantum` becomes the live network row budget

Thread `worker.max_rows_per_quantum` from `rockstream-types::config::WorkerConfig`
into the exchange runtime:

- call `FlowController::acquire_credit()` from `WorkerStreamMultiplexer::send_frame()`
  before sending;
- replace the hardcoded `16` credit window with an explicit row budget derived
  from `max_rows_per_quantum`;
- replace frame-count-based `credit_grant: 1` with row-count-based credit
  release (likely requiring a `row_count` field in `ShuffleFrame` and/or
  `ShuffleAck`, since the current proto only models frame credits);
- expose a named fill-level metric for rows in flight, with sender-side
  backpressure once the budget is exhausted.

This slice is the one that satisfies the repo’s “named upper bound + fill-level
metric + backpressure path” rule for the newly-coupled network queue.

**Ends green when:** `send_frame_blocks_once_rows_in_flight_reach_max_rows_per_quantum`
passes.

### Slice 5 — Faulted/fallback distributed exchange still releases row credits and never duplicates delivery

Because the credit model is now part of cross-worker coordination, add seeded
simulation coverage for row-budget release across fallback and drain scenarios
using the existing exchange simulation harness and `buggify!()` hooks
(`exchange.shm_segment_unavailable`, `exchange.domain_rebuild_during_drain`).

**Ends green when:** `same_host_shared_memory_quantum_budget_falls_back_without_duplication_sim`
passes with a fixed seed and `buggify!()` enabled.

### Slice 6 — Complex-DAG throughput benchmark, checked-in baseline, and CI gate

Add a **v0.51-specific** criterion benchmark that exercises the real exchange
hot path for a multi-hop / multi-operator DAG, with two benchmark IDs in the
same suite:

1. `legacy_wal_on`
2. `wal_elided_quantum_coupled`

Preferred home: extend `crates/rockstream-runtime/benches/exchange_bench.rs`,
because the existing runtime benchmark job and baseline file already live
there. The benchmark should reuse actual runtime exchange helpers
(`WorkerStreamMultiplexer`, `ShuffleServer`, `ExchangeRegistry`, real payload
serialization) rather than a synthetic counter-only loop.

Deliverables in this slice:

- a checked-in baseline JSON for the optimized benchmark IDs
  (new `v0.51` runtime baseline, not just the old `v0.45.4` microbench ids);
- CI wiring in `.github/workflows/ci.yml` using the existing
  `bench_regression_gate`;
- a proof-side ratio check that the optimized benchmark is **≥30% faster**
  than the legacy benchmark on the same benchmark host/config.

The ratio proof is the one-time “roadmap claim is true” check; the checked-in
baseline + CI gate are the ongoing “it never silently regresses” check.

**Ends green when:** `complex_dag_hot_path_wal_elision_is_at_least_30pct_faster_than_legacy`
passes and the benchmark CI step gates the optimized ids against the checked-in
baseline.

## Test Commitments

No new relational operator is being introduced, but v0.51 **does** change
operator-shard behavior on the distributed exchange path. Pre-committed oracle
tests:

| Behavior change | Oracle property test (pre-commit) | Oracle |
|---|---|---|
| Fast-path direct/shared-memory/loopback exchange no longer persists intermediate shuffle WAL | `exchange_fast_path_wal_elision_incremental_equals_batch_for_join_agg_dag` | Final incremental output for a 2-shard `Filter -> Join -> Aggregate` DAG must equal batch recomputation after random INSERT/UPDATE/DELETE sequences and a restart boundary. |
| Row-budget backpressure now rechunks / delays exchange delivery based on `max_rows_per_quantum` | `quantum_coupled_exchange_rechunking_incremental_equals_batch` | Different chunking / suspension points must not change final output: incremental result == batch result for the same logical delta stream. |
| Fast-path failure falling back to durable object-store exchange under row-budget pressure | `durable_fallback_after_fast_path_failure_incremental_equals_batch` | With induced SHM/gRPC failure, fallback delivery plus replay still produces exactly the same final rows as batch recomputation. |

These are intentionally **pipeline-level** oracles, not per-operator unit
oracles, because the changed behavior is transport/persistence/coupling across
existing operators rather than new operator math.
