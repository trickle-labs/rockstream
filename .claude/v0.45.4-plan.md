# v0.45.4 Plan — Performance-Regression CI Gate & Benchmark Coverage Expansion

## Deferred-Item Audit

Scanned every `sign-offs/v*.md`. No prior version left an item marked
deferred/postponed/out-of-scope that overlaps this version's Scope
(benchmark CI gating, storage/runtime/control benches, baseline comparison).
`v0.45.md`'s own body text names the one directly relevant precedent — "turn
the v0.36 Nexmark criterion benchmarks from descriptive-only into a real CI
regression gate" — which was implemented and signed off at v0.45
(`nexmark-regression-gate` job in `ci.yml`, `benches/baseline/v0.36.json`).
That gate is **out of this version's scope**: it already exists and already
passes; v0.45.4's four named subsystems are `rockstream-ops` (the
non-Nexmark `perf_regression` criterion suite: filter/aggregate/join/delta),
`rockstream-storage`, `rockstream-runtime`, and `rockstream-control` — none
of which have any checked-in baseline or CI gate today. `v0.45.2.md` and
`v0.45.3.md` explicitly state "nothing deferred." No other sign-off's
deferred items touch benchmarking, storage/runtime/control performance, or
CI gating.

## Current-State Findings (inform the slices below)

- `crates/rockstream-ops/benches/perf_regression.rs` already exists
  (`bench_filter`, `bench_aggregate`, `bench_join`,
  `bench_delta_propagation_rates`, `bench_filter_delta_rates`) but has **no**
  CI job and **no** baseline — it only runs manually today.
- `crates/rockstream-storage`, `crates/rockstream-runtime`, and
  `crates/rockstream-control` have **no** `[[bench]]` targets and **no**
  `criterion` dev-dependency at all — these three benches are net-new.
- Bench targets exist for storage (`ShardDb::get/put/merge` over
  `object_store::memory::InMemory`, see `shard_db.rs` doctest at line ~792),
  runtime (`exchange::serialization::{serialize_zset,deserialize_zset}` +
  `exchange::flow_control::FlowController::{acquire_credit,handle_ack,
  get_credits}`), and control (`FrontierAggregator::ingest` /
  `cluster_frontier` — DESIGN.md §16.6 names this exact throughput risk:
  "Frontier-aggregator throughput with thousands of shards × hundreds of
  operators").
- The v0.45/v0.36 Nexmark gate (`nexmark_regression.rs` +
  `bin/nexmark_regression_gate.rs`) is the only precedent for "checked-in
  baseline JSON + comparison binary that fails CI on regression" in this
  repo. It is Nexmark-specific (`NexmarkBenchmarkSummary`,
  `[nexmark_summary]` eprintln tag). This version generalizes that exact
  shape — checked-in JSON baseline, `[bench_summary:<tag>]` eprintln line,
  one shared comparison binary — to the four new subsystems, rather than
  inventing a fourth incompatible mechanism or a real `critcmp` CLI
  dependency (no `critcmp` binary or config exists anywhere in the repo
  today; "critcmp-compatible JSON" is satisfied by keeping the schema a flat
  `{benchmark_id: mean_nanos}` map, which is what `critcmp`'s own JSON export
  shape reduces to for comparison purposes).
- No new distributed-coordination protocol is introduced (roadmap's own
  Phase 12.6 table says "no new coordination protocol") and no new
  durability path (commit/replay/checkpoint/compaction/WAL) is introduced —
  the storage bench exercises `ShardDb::get/put/merge`, which are existing,
  already-tested durability primitives being *measured*, not changed. So
  Sections 4 (Durability Slices) and 5 (Coordination Slices) below have no
  new obligations beyond what's already covered by existing LFS/MinIO/SimRuntime
  tests for those primitives.

## Vertical Slices

### S1 — Shared regression-comparator generalization (prerequisite for S2–S5)
Generalize `rockstream-ops/src/nexmark_regression.rs`'s comparator into a new
sibling module `rockstream-ops/src/bench_regression.rs`:
- `BenchmarkSummary(BTreeMap<String, f64>)` — benchmark id → mean nanoseconds.
- `parse_summary_line(text: &str, tag: &str) -> Option<BenchmarkSummary>` —
  scans `criterion`/harness stdout+stderr for a `[bench_summary:<tag>] {...}`
  JSON line (each new bench main prints this once, after all groups finish,
  by reading back `target/criterion/**/new/estimates.json` mean point
  estimates — kept dependency-light with `serde_json`, no new crate).
- `compare_against_baseline(baseline, observed, threshold_pct: f64) ->
  RegressionCheck { passed: bool, failures: Vec<String> }` — flags any id
  present in both where `observed > baseline * (1 + threshold_pct/100)`;
  missing ids in `observed` are also a failure (a removed/renamed benchmark
  must not silently stop being gated).
- New shared bin `rockstream-ops/src/bin/bench_regression_gate.rs`:
  `--baseline <json> --output <bench-stdout-file> --tag <name>
  [--threshold-pct 10]`, reused by all four CI steps (ops/storage/
  runtime/control) instead of one bin per subsystem.
Ends green when: `cargo test -p rockstream-ops bench_regression` passes,
covering (a) exact-match baseline passes, (b) >10%-slower observation fails
with a listed failure per regressed id, (c) a missing id fails, (d) the
existing Nexmark gate is left untouched (no behavior change to
`nexmark_regression.rs`/`nexmark_regression_gate.rs` — pure sibling
addition, not a refactor of working code).

### S2 — `rockstream-ops` gate wiring (closes the gap DESIGN.md/roadmap flag: "descriptive only")
Add a `[bench_summary:ops]` emission to `perf_regression.rs`'s `main`
(criterion's `criterion_main!` macro expands to a real `fn main`, so this is
a small wrapper, not a criterion API change) that reads back
`target/criterion/{filter_performance,aggregate_performance,join_performance,
delta_propagation_cost,filter_delta_cost}/*/new/estimates.json` mean points
and prints the tagged JSON summary line. Record the current measured means as
`crates/rockstream-ops/benches/baseline/v0.45.4-ops.json`.
Ends green when `cargo bench -p rockstream-ops --bench perf_regression --
--noplot | tee ops-bench.out && cargo run -p rockstream-ops --bin
bench_regression_gate -- --baseline
crates/rockstream-ops/benches/baseline/v0.45.4-ops.json --output
ops-bench.out --tag ops` exits 0.

### S3 — `rockstream-storage` bench: SlateDB read/write/merge-operator latency
Add `criterion` dev-dependency + `[[bench]]` `storage_bench` to
`rockstream-storage/Cargo.toml`. New
`crates/rockstream-storage/benches/storage_bench.rs`: build one warm
`ShardDb` over `object_store::memory::InMemory` (mirroring the existing
doctest helper at `shard_db.rs:~792`), then criterion-async-bench (via
`tokio::runtime::Runtime` + `bencher.to_async`) `get` (point read, warm key),
`put` (point write), and `merge` (via `MergeOperatorRegistry`'s
`SumCountMergeOperator`, exercising the actual merge-operator code path) at a
fixed key/value size. Emit `[bench_summary:storage]`. Record baseline at
`crates/rockstream-storage/benches/baseline/v0.45.4-storage.json`.
Ends green: same gate-binary invocation as S2, tag `storage`, exits 0.

### S4 — `rockstream-runtime` bench: exchange/shuffle serialization + credit-flow throughput
Add `criterion` dev-dependency + `[[bench]]` `exchange_bench` to
`rockstream-runtime/Cargo.toml`. New
`crates/rockstream-runtime/benches/exchange_bench.rs`:
`serialize_zset`/`deserialize_zset` round-trip on a representative
`ArrowZSet` (reuse the same batch-construction pattern as
`perf_regression.rs`'s `make_kv_batch`, sized to a realistic shuffle-batch
row count), and `FlowController` credit-flow throughput — a tight
async loop of `acquire_credit` immediately answered by a paired
`handle_ack`, measuring achieved acquire/release pairs per second (the
metric DESIGN.md/roadmap call "credit-flow throughput"). Emit
`[bench_summary:runtime]`. Baseline at
`crates/rockstream-runtime/benches/baseline/v0.45.4-runtime.json`.
Ends green: gate binary, tag `runtime`, exits 0.

### S5 — `rockstream-control` bench: frontier-aggregation throughput at simulated shard/operator counts
Add `criterion` dev-dependency + `[[bench]]` `frontier_bench` to
`rockstream-control/Cargo.toml`. New
`crates/rockstream-control/benches/frontier_bench.rs`: construct a
`FrontierAggregator`, pre-register a simulated fleet — thousands of shards ×
hundreds of operators, i.e. distinct `shard_id`s up to (but not exceeding)
`MAX_REGISTERED_SHARDS` — and bench steady-state `ingest` throughput
(monotonic epoch advances only, matching real traffic — no
retreats/no-ops) plus `cluster_frontier`/`fill_level` read cost under that
load. This directly answers DESIGN.md §16.6's named open risk
("Frontier-aggregator throughput with thousands of shards × hundreds of
operators. The aggregator must be CPU- and memory-bounded, never
blocking"). Emit `[bench_summary:control]`. Baseline at
`crates/rockstream-control/benches/baseline/v0.45.4-control.json`.
Ends green: gate binary, tag `control`, exits 0.

### S6 — `benchmark` CI job + `make bench-baseline-update`
Add one new `benchmark` job to `.github/workflows/ci.yml` (sibling to, not a
replacement for, the existing `nexmark-regression-gate` job — that gate
already passes and is untouched), `timeout-minutes` bounded to a documented
budget (measured locally first; sized generously above the sum of the four
`cargo bench` step wall-clock times plus checkout/build so a slow CI runner
doesn't flake). Steps, per subsystem: `cargo bench -p <crate> --bench
<name> -- --noplot | tee <tag>-bench.out`, then `cargo run -p rockstream-ops
--bin bench_regression_gate -- --baseline
crates/<crate>/benches/baseline/v0.45.4-<tag>.json --output <tag>-bench.out
--tag <tag>`. Add `bench-baseline-update` to `Makefile`: re-runs all four
`cargo bench` commands and overwrites the four baseline JSON files from the
freshly measured means — explicitly **not** invoked anywhere in `ci.yml`
(the roadmap requires it stay an explicit, code-reviewed, human-triggered
step, never automatic).
Ends green when: `benchmark` job is present and green in a local `act`-free
static check (parsed by S7's test) and the Makefile target runs cleanly
once by hand, producing a diff-only change to the four baseline files.

### S7 — Proof-of-gate tests (the "15% slowdown fails, reviewed improvement passes" claim)
1. Unit tests in `rockstream-ops/src/bench_regression.rs` (generic, run once
   — proves the comparator itself, independent of which subsystem calls it):
   `test_regression_gate_passes_on_identical_summary`,
   `test_regression_gate_fails_on_15pct_slowdown` (synthetic baseline vs. a
   synthetic "observed" map with one id inflated by exactly 15%),
   `test_regression_gate_passes_on_9pct_jitter` (under the 10% threshold),
   `test_regression_gate_fails_on_missing_benchmark_id`.
2. `test_bench_regression_gate_reads_baseline_update_makes_it_pass`: after a
   simulated "reviewed improvement" (observed summary faster than baseline),
   the gate still passes, and re-running with that observed summary written
   in as the new baseline (simulating `make bench-baseline-update`) also
   passes on the next run — proving the update path is idempotent and never
   itself fails the gate it just refreshed.
3. `test_benchmark_ci_job_exists_and_covers_four_subsystems` (new test,
   colocated with the existing `test_coverage_gate_config_is_present`-style
   parsing tests in `rockstream-gateway/tests/conformance_doc_tests.rs`, or a
   new sibling file if a more central home fits better): parses `ci.yml`,
   asserts a `benchmark` job exists with a `timeout-minutes` bound, and that
   its steps reference all four `--tag`s (`ops`, `storage`, `runtime`,
   `control`) and all four baseline JSON paths.
4. `test_makefile_has_bench_baseline_update_target_not_invoked_by_ci`:
   parses `Makefile` for a `bench-baseline-update` target and asserts the
   literal string `bench-baseline-update` does not appear anywhere in
   `ci.yml` (never auto-invoked).
Ends green when all of the above pass under `cargo test --workspace`.

## Proof Mapping

Roadmap Proof column, split into checkable claims:

- **P1 — Deliberate 15% slowdown fails the gate, per subsystem.**
  Test: `test_regression_gate_fails_on_15pct_slowdown` (S7.1) proves the
  comparator's threshold logic generically; `bench_regression_gate`'s single
  shared implementation is exercised identically by all four CI steps (S2–
  S5), so proving the comparator once covers all four subsystems without
  four redundant slow `cargo bench` re-runs in the unit-test suite. The
  wiring guarantee — that each subsystem's CI step actually invokes this
  binary with its own tag/baseline — is proven by
  `test_benchmark_ci_job_exists_and_covers_four_subsystems` (S7.3), which
  fails if any of the four `--tag` invocations is missing from `ci.yml`.
- **P2 — A reviewed improvement updates the baseline via `make
  bench-baseline-update`, and the next run passes.**
  Test: `test_bench_regression_gate_reads_baseline_update_makes_it_pass`
  (S7.2) proves the update-then-regate cycle is idempotent and never
  self-fails; `test_makefile_has_bench_baseline_update_target_not_invoked_by_ci`
  (S7.4) proves the update step stays explicit/human-triggered, matching
  "explicit, code-reviewed" in the roadmap wording.
- **P3 — The job completes within a documented, bounded wall-clock budget
  suitable for per-PR execution.**
  Evidence (not a unit test — wall-clock timing is not a meaningful `cargo
  test` assertion, matching the existing Nexmark gate's own precedent of a
  `timeout-minutes: 30` bound with no timing unit test): S6's `benchmark`
  job carries an explicit `timeout-minutes` value, chosen from a locally
  measured sum of the four `cargo bench --noplot` step durations plus
  checkout/build overhead, recorded in `.claude/v0.45.4-evidence.md`.
  `test_benchmark_ci_job_exists_and_covers_four_subsystems` (S7.3)
  additionally asserts the `timeout-minutes` key is present and numeric (a
  job with no bound at all would fail this test).

Every Proof claim has at least one test mapped. Plan is finished.
