## 2. Environment & Platform Classification Engine Verification

Host platform, runtime environment, and external backend tiering are formally evaluated according to Matrix A & B:

- **Host Evaluation (`PlatformClassifier::evaluate_host()`)**:
  - `x86_64` (AMD64) and `aarch64` (ARM64) architectures evaluate to `ClassificationTier::Supported`.
  - 32-bit architectures (`x86`, `arm`) evaluate to `ClassificationTier::Unsupported` with immediate rejection.
  - 64-bit alternative architectures (`riscv64`, `ppc64le`) evaluate to `ClassificationTier::CompatibleUnverified`.
  - Linux (Kernel ≥ 5.4) and macOS (Darwin 20+) evaluate to `ClassificationTier::Supported`.
  - Native Windows evaluates to `ClassificationTier::Unsupported` (POSIX locking and io_uring semantics required).
  - WSL2 evaluates to `ClassificationTier::CompatibleUnverified`.
  - Libc runtime: Glibc ≥ 2.31 and Musl ≥ 1.2.3 evaluate to `ClassificationTier::Supported`; older glibc versions evaluate to `ClassificationTier::Unsupported`.
- **Backend Classification (`PlatformClassifier::evaluate_storage_backend()`, `evaluate_postgres_version()`, `evaluate_kafka_version()`)**:
  - Local NVMe/SSD filesystem (`LFS`), AWS S3, and MinIO evaluate to `ClassificationTier::Supported`.
  - S3-compatible alternatives (Cloudflare R2, GCS S3 API, Ceph) evaluate to `ClassificationTier::CompatibleUnverified`.
  - Network filesystems lacking POSIX write-through locking (NFS/SMB) evaluate to `ClassificationTier::Unsupported`.
  - PostgreSQL 14–18 evaluate to `Supported` (tested against pinned `postgres:18.0`); PostgreSQL 12–13 evaluate to `CompatibleUnverified`; PostgreSQL < 12 evaluates to `Unsupported`.
  - Apache Kafka 3.x and Redpanda 23.x/24.x evaluate to `Supported`; Kafka 2.8+ evaluates to `CompatibleUnverified`; Kafka < 2.8 evaluates to `Unsupported`.

  - `LimitNOFILE=65536` (high file descriptor ceiling for sockets and SST files)
- **Watchdog & Process Management**:
  - `WatchdogSec=30` with systemd notification heartbeat.
  - `Restart=on-failure` with restart delay.

## 8. Volume Persistence, Rolling Upgrades & Clean-Machine Smoke Verification

- **Volume Persistence**: Non-root UID 10001 owns `/data`. SlateDB WAL flushes, memtable syncs, and SST compaction execute cleanly on dedicated mounts across container restarts and Kubernetes pod rescheduling.
- **Zero-Downtime Rolling Upgrade Sequencing**:
  - **Step 1: Control Plane**: Upgraded first in rolling fashion; Raft leader steps down cleanly, transfers leadership, and resumes state synchronization.
  - **Step 2: Workers**: Drained and upgraded one-by-one. Each worker flushes active micro-batch epoch to SlateDB, commits 2PC sink transactions, and explicitly releases shard leases (`ReleaseLease`) to peer workers with zero query downtime.
  - **Step 3: Gateways**: Stateless query gateways upgraded in rolling fashion behind load balancer.
- **Clean-Machine Smoke Workload**: Verified in `clean_machine_smoke_tests.rs`: fresh node startup -> PGWire connection -> `SELECT 1` execution returns expected query rows without errors.
