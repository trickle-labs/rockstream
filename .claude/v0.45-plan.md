# v0.45 Plan — Deep FinOps Optimizations & Cost/Diagnostics Visibility

## Roadmap row (verbatim reference, decomposed)

- **Focus**: Deep FinOps Optimizations & Cost/Diagnostics Visibility.
- **Scope** (NEW_ROADMAP.md line 415, condensed to deliverables):
  1. Route `shard_meta/` to AWS S3 Express One Zone; tier older compacted SSTs
     to S3 Standard-IA; validate the stateless worker pool on Spot/preemptible
     instances.
  2. Wire `EXPLAIN INCREMENTAL` / `VERBOSE` / `ANALYZE` / `ESTIMATE` into the
     gateway's real query dispatch (DESIGN.md §14.8–§14.9), replacing the
     one-line pushdown/index-annotation stub.
  3. Ship `SHOW RESOURCE USAGE` / `SHOW RESOURCE USAGE FOR WORKLOAD <name>` /
     `SHOW CLUSTER RESOURCE USAGE` (§14.19) backed by new
     `rockstream_catalog.view_resource_usage` / `workload_resource_usage`.
  4. Turn the v0.36 Nexmark criterion benchmarks into a real CI regression
     gate (>10% regression fails CI, per the Common DoD rule).
  5. DESIGN.md §12.8 gaps: `SET rockstream.max_staleness` (§12.8.3),
     `rockstream.write_fence()`/`after_fence(:token)` (§12.8, cross-session
     fence), and completing `INSERT ... RETURNING` for server-assigned
     primary keys (§12.8.2).
  6. Decouple `pipeline_id` metrics-cardinality management (§14.15.1) from
     any functional pipeline-count ceiling: LRU/recent-traffic working set of
     256 with `pipeline_id="other"` rollup, cluster accepts >256 pipelines.
  7. `estimated_cost_per_hour` on `view_resource_usage`/`workload_resource_usage`
     and `SHOW RESOURCE USAGE`, computed from a `[pricing]` block in
     `rockstream.toml` applied to already-collected metrics.

- **Proof** (roadmap's literal Proof column, split into checkable claims):
  - **P1**: TCO benchmarks show >50% reduction in steady-state operational
    costs compared to v0.31.
  - **P2**: A per-tier cost-visibility metric ships on `/metrics` and the
    starter Grafana dashboard (visible without re-running the TCO benchmark).
  - **P3**: `EXPLAIN INCREMENTAL my_view` typed into `psql` returns the
    documented operator tree, verified byte-for-byte against
    `explain_incremental_for_sql`'s output (not the old pushdown-only stub).
  - **P4**: `SHOW RESOURCE USAGE` returns live per-workload state-byte/
    memory/SLO figures matching `view_resource_usage`.
  - **P5**: CI fails a nightly Nexmark run that regresses delta-amplification
    or propagation latency by >10% against the v0.36 baseline.
  - **P6**: A cluster that has created >256 materialized-view pipelines over
    its lifetime continues to accept new `CREATE MATERIALIZED VIEW`
    statements; per-worker metrics cardinality is bounded by the LRU
    working-set size, not total pipeline count.
  - **P7**: `SHOW RESOURCE USAGE` / `workload_resource_usage` return a
    non-null `estimated_cost_per_hour` once `[pricing]` is configured, and
    the figure changes visibly when `MEMORY_LIMIT`/shard count changes.
  - **P8** *(from Scope, not spelled out as a one-line Proof clause but
    binding per the Ground Rules — "if Scope requires it, it is implemented
    now, in full")*: DESIGN.md §12.8.3's own checkable claims for
    `max_staleness` — never blocks, emits `RS-2018` NOTICE on staleness
    exceeded, `frontier_age_ms` in response metadata,
    `session_staleness_exceeded_total`/`session_frontier_age_ms` metrics.
  - **P9** *(from Scope)*: cross-session `write_fence()`/`after_fence(:token)`
    — a token obtained in one session gates visibility of a specific write in
    another session, reusing the existing `wait_for` code path.
  - **P10** *(from Scope)*: `INSERT ... RETURNING` reflects back a
    **server-assigned** key (default UUID or sequence), not just literal
    client `VALUES`, per DESIGN.md §12.8.2's constraints table.
- **Backends**: Unit, LFS, MinIO, TC. *(No live-AWS backend — this bounds
  what can be proven for S3 Express One Zone / Standard-IA; see §2 below.)*

## 2. Codebase Reality Check (binding constraints on the plan below)

Direct inspection of the repository (not just DESIGN.md) found several
places where the roadmap's framing is optimistic relative to what exists in
code today. These shape every vertical slice below:

- **`EXPLAIN` stub confirmed.** `crates/rockstream-gateway/src/server.rs:1441-1491`
  is exactly the one-line pushdown/index-annotation stub the roadmap
  describes — it never calls into `rockstream-sql`.
- **Only two of four `EXPLAIN INCREMENTAL` levels exist in the library.**
  `rockstream-sql::explain_incremental()` (`explain_incremental.rs:20`)
  renders the plain Level-1 tree only; its own doc comment says *"the
  live-stats explain ... is deferred to v0.9"* (stale — v0.9 is long past).
  `explain_incremental_estimate_for_sql`/`_text` (`frontend.rs:246-270`)
  cover Level-ESTIMATE. **VERBOSE (merge-law annotations, combiner status,
  shard counts, parallelism, workload memory, frontier timestamps) and
  ANALYZE (live per-operator stats) have no formatter in `rockstream-sql`
  today** — these must be built as new formatting functions in this
  version. This is *not* new planning/cost logic (the roadmap's "no new
  planning logic" framing is correct for that), but it is new code, not pure
  reuse.
- **`collect_operator_stats` is a hardcoded stub.**
  `crates/rockstream-control/src/service.rs:136-147` returns a single
  constant `OperatorStats` regardless of `pipeline_id` — real per-operator
  live-stats collection (rows/s, state reads, RMW ratio, p99, DLQ entries,
  aggregated over the trailing 60s per §14.8 Level 3) does not exist. ANALYZE
  must source from whatever real counters already exist
  (`MetricRegistry`'s per-operator/per-shard maps) rather than inventing a
  new distributed stats-collection RPC — scope-bounding this to "wire
  existing counters through," consistent with "no new distributed
  coordination."
- **No `rockstream_catalog` SQL surface exists.** Only `pg_catalog`/
  `information_schema` stubs exist (`catalog_stubs.rs`). `view_resource_usage`
  / `workload_resource_usage` will follow the exact in-memory
  `CatalogSinkEntry`-list pattern v0.44 established for
  `rockstream_catalog.connectors` — not a general catalog SQL engine.
- **`write_amplification_ratio` and `segment_cache_hit_ratio`/
  `segment_cache_bytes_used` are not live metrics.** The roadmap's Scope
  text claims these are metrics "that already exist," but they are only
  computed ad hoc, once, inside a benchmark test
  (`crates/rockstream-storage/tests/minio_budget.rs:472-528` and
  `:215-285`) — they are never emitted continuously via `MetricRegistry`
  (`crates/rockstream-types/src/metrics.rs` has no such fields; only
  `workload_memory_bytes` and `state_budget_bytes`, confirmed at
  `metrics.rs:63-70`, are real running counters). These two metrics must be
  added as genuine live `MetricRegistry` fields, updated on the compaction
  and segment-cache hot paths, since `view_resource_usage` needs real
  numbers, not one-off test math.
- **`pipeline_id` does not exist as a metric label anywhere in code.**
  Grepping the entire workspace for `pipeline_id` finds exactly one hit — an
  unused function parameter (`service.rs:138`) — not a label on any emitted
  metric. DESIGN.md §14.15.1's framing ("today's `MetricRegistry` stores
  each per-label map as a plain `HashMap` with no eviction API") implies a
  retrofit; in reality there is nothing to retrofit. This **simplifies**
  Slice D: the bounded LRU-working-set design is built once, from scratch,
  for whichever metric(s) get a `pipeline_id` label in this version — it is
  never unbounded even transiently.
- **No pipeline creation ceiling exists anywhere** (confirmed: no `256` near
  `pipeline` in any catalog/control-plane code) — P6's "continues to accept
  new `CREATE MATERIALIZED VIEW` beyond 256" is already true today; the
  actual work is bounding the *metrics* cardinality without introducing a
  ceiling as a side effect.
- **No `[pricing]` config parsing exists.** `rockstream.toml` today has only
  `[cluster]`/`[worker]`/`[connector]` (confirmed, `rockstream.toml:1-15`);
  no `pricing` string appears in any `crates/` Rust file.
- **No object-store tiering/multi-backend routing exists.** Every shard
  today is constructed with exactly one `Arc<dyn object_store::ObjectStore>`
  (`rockstream-storage/src/shard_db.rs:80-143`,
  `rockstream-runtime/src/recovery.rs:231-260`,
  `rockstream-cli/src/lib.rs:150-178`). `ShardPrefix::ShardMeta`
  (`rockstream-storage/src/keys.rs:6-13`) is a key-namespace byte, not a
  storage-backend selector. There is no internal SST "tier to cheaper
  storage" mechanism distinct from the v0.44 cold-tier sink (which exports
  to Iceberg/Delta, not internal SST tiering).
- **`object_store` v0.12.5 (workspace-pinned, `Cargo.lock:4233`) exposes
  `Attribute::StorageClass`** (confirmed via docs.rs) settable per-`put_opts`
  call — sufficient to request `STANDARD_IA` on a normal S3 bucket. **S3
  Express One Zone is architecturally different**: it requires a distinct
  "directory bucket" (per-AZ, session-auth, different endpoint semantics),
  not a per-object storage-class attribute on a standard bucket. Given the
  Backends column for this version is Unit/LFS/MinIO/TC — **no live-AWS
  backend** — a real Express One Zone directory bucket cannot be exercised
  end-to-end by this test matrix (MinIO does not emulate directory buckets).
  **Plan decision**: build a generic prefix-routed multi-backend
  `TieredObjectStore` wrapper whose *routing logic* (send `shard_meta/*` to
  backend A, send aged compacted SSTs to backend B) is fully proven on
  LFS + MinIO (two different `ObjectStore` instances standing in for two
  tiers), while the AWS-specific `storage_class`/Express-One-Zone
  *configuration construction* is proven with a unit test that asserts the
  correct `AmazonS3Builder`/`Attribute` values are produced for a given
  `rockstream.toml` tier config — the same "config-is-correct, not
  live-cloud-integration-tested" pattern already used for `catalog = glue`
  in v0.44.
- **No Spot/preemptible-specific code exists**, but the underlying recovery
  primitives this version needs to *validate* (not build) already exist:
  lease fencing/renewal (`rockstream-control/src/shard.rs:80-177`),
  worker self-fencing on control-plane loss (`rockstream-runtime/src/fence.rs:20-159`),
  and checkpoint-based recovery (`rockstream-runtime/src/recovery.rs:178-260`).
  "Validate running the worker pool on Spot" becomes a **SimRuntime test**
  injecting sudden worker-kill faults (mimicking a 2-minute Spot reclaim
  notice with no graceful drain) and asserting the v0.31 recovery SLOs
  (failure detection ≤5s p99, reassignment ≤30s p99) still hold — not new
  recovery machinery.
- **No v0.31 TCO benchmark exists.** `sign-offs/v0.31.md` and
  `.claude/v0.31-{plan,evidence}.md` document **recovery SLO validation**
  (failure detection/reassignment/freshness under induced partitions), not
  a cost benchmark. P1 ("compared to v0.31") is therefore not "re-run an
  existing v0.31 benchmark" — it is **build a new TCO benchmark now** that
  models two configurations: a "v0.31-era" baseline (single-tier standard
  storage, 100% on-demand compute — the architecture as it stood at v0.31,
  before any tiering/Spot support existed) and the v0.45 optimized
  configuration (S3 Express One Zone for `shard_meta/`, Standard-IA for aged
  SSTs, Spot-priced compute mix), both priced through the same
  `estimated_cost_per_hour` engine built in Slice C3, and asserts >50%
  reduction.
- **No `PRIMARY KEY`/`DEFAULT`/`gen_random_uuid`/`IDENTITY` parsing exists**
  in `CREATE TABLE` (`server.rs:2609-2658`, `:6338`+ column-list parser) —
  confirmed via grep, zero hits for any of these. `INSERT ... RETURNING`
  for server-assigned keys (P10) therefore needs a **minimal** schema
  addition: a column can declare `DEFAULT gen_random_uuid()` or
  `GENERATED ALWAYS AS IDENTITY` (bounded to exactly these two forms — no
  general expression-default engine, since no Proof claim needs more), plus
  the point-read-back flow DESIGN.md §12.8.2 already fully specifies.
- **`SET rockstream.*` handling today only covers `session_wait_for`/
  `session_wait_for_timeout_ms`** (`server.rs:2954-2966`). `max_staleness`,
  `write_fence`, `after_fence` have zero references anywhere in `crates/`.

## 3. Vertical Slices

Each slice ends in a green test (unit, or the existing wire-protocol
`gateway_proof_tests.rs`-style integration test, or LFS/MinIO harness as
noted). Grouped by workstream; workstreams are independent of each other
(no cross-group dependencies) so they can be built and tested in any order,
but **within** a group the listed order is a dependency chain.

### Group A — OLTP/Analytical Session Ergonomics (gateway-only)

1. **A1 — `SET rockstream.max_staleness`.** Add `max_staleness` to
   `SessionState`; extend the existing `SET rockstream.*` parser
   (`server.rs:2954`) to accept `'<duration>'`/`'0'`/`'none'`; before pinning
   the frontier on `SELECT`, compare wall-clock age of the last published
   cluster frontier against the bound; emit `RS-2018` NOTICE (never blocks)
   when exceeded; add `frontier_age_ms` to response metadata; add
   `session_staleness_exceeded_total`/`session_frontier_age_ms` metrics;
   setting `max_staleness` clears `session_wait_for` and vice versa (mutual
   exclusion per §12.8.3); `SHOW rockstream.session_mode` reports the active
   mode. *Green test*: wire-protocol test setting `max_staleness='10s'`,
   forcing a stale frontier, asserting the NOTICE fires, the query still
   returns (never blocks), and `frontier_age_ms` is present and accurate;
   companion test for the mutual-exclusion behavior with `session_wait_for`.
2. **A2 — `rockstream.write_fence()` / `after_fence(:token)`.** Add two SQL
   functions dispatched by the gateway (not full UDF infra — hardcoded
   recognized function names, consistent with existing gateway dispatch
   style): `write_fence()` returns the caller session's current
   `last_written_epoch` as an opaque token; `after_fence(:token)` in a
   `WHERE` clause (or as a query modifier) applies `wait_for = token` for
   that query only, reusing the existing `wait_for` code path from §12.4/
   §12.8.1 — no new distributed machinery. *Green test*: two-connection
   wire-protocol test — session 1 writes and calls `write_fence()`, session
   2 uses `after_fence(:token)` and observes the write is visible
   (`gateway_proof_tests.rs`-style, following the existing cross-session
   freshness-token test pattern from §12.4).
3. **A3 — `INSERT ... RETURNING` for server-assigned keys.** Extend the
   `CREATE TABLE` column-list parser (`server.rs:6338`) to recognize
   `DEFAULT gen_random_uuid()` and `GENERATED ALWAYS AS IDENTITY` (sequence,
   process-local atomic counter is sufficient — no cross-shard sequence
   coordination needed per DESIGN's "no new distributed machinery" framing
   for this feature, since sequences are scoped to a single logical table
   whose writes are already serialized through one internal source
   connector). On `INSERT` without an explicit value for such a column,
   generate the value before the `WriteBatch` commit; extend
   `parse_insert`'s `RETURNING` handling to, for these generated columns,
   execute the point-read-back flow (§12.8.2 steps 1–4: commit → wait for
   frontier via `last_written_epoch` → point `SELECT` by PK → return
   projected columns) instead of echoing a literal. *Green test*:
   wire-protocol test creating a table with a `DEFAULT gen_random_uuid()`
   PK, inserting without specifying it, asserting `RETURNING` returns a
   real generated UUID (not null/literal-echo) that matches a subsequent
   `SELECT`; companion test for the `IDENTITY` sequence case, and a
   multi-row-insert case asserting one generated value per row in insertion
   order (per the existing constraints table).

### Group B — `EXPLAIN INCREMENTAL` Wire-Protocol Wiring

4. **B1 — Gateway dispatch rewrite.** Replace the stub at `server.rs:1441-1491`
   with real dispatch: parse `EXPLAIN INCREMENTAL [VERBOSE|ANALYZE|ESTIMATE]
   <view-or-select>`; for the plain/VERBOSE/ANALYZE forms call
   `SqlFrontend::explain_incremental_for_sql` (extended per B2/B3 below to
   accept a verbosity level); for ESTIMATE call
   `explain_incremental_estimate_text`. Return the formatted text as a
   single-column `QueryResponse` row-stream (matching existing text-response
   patterns elsewhere in the gateway). *Green test*: `explain_shows_...`
   style wire-protocol test asserting `EXPLAIN INCREMENTAL <view>` output is
   **byte-for-byte** equal to calling `explain_incremental_for_sql`
   directly (this is P3's literal wording) — extends the existing
   `explain_names_pushdown_effect`/`explain_shows_sink_target_for_sunk_view_via_wire`
   test file (`gateway_proof_tests.rs`).
5. **B2 — VERBOSE formatter (new code in `rockstream-sql`).** Add
   `explain_incremental_verbose(plan: &PlanNode, ...) -> String` alongside
   the existing Level-1 formatter, adding merge-law annotations (already
   available via `MergeLawId`/`LawMetricKey`), combiner status, per-operator
   shard counts, parallelism utilisation, workload memory (from
   `workload_memory_bytes`), and frontier timestamps. *Green test*: unit
   test asserting VERBOSE output is a strict superset of Level-1 output
   (contains all Level-1 lines) plus the additional annotations, for a
   multi-operator plan tree (join + aggregate + exchange), mirroring the
   existing `explain_incremental_tumble_window`/`explain_incremental_topk`
   test style in `explain_incremental.rs`.
6. **B3 — ANALYZE formatter + real stats wiring.** Add
   `explain_incremental_analyze(plan, stats: &[OperatorStats]) -> String`.
   Replace `collect_operator_stats`'s hardcoded return
   (`service.rs:136-147`) with real aggregation from `MetricRegistry`'s
   existing per-operator counters (rows/s from throughput counters, state
   reads/RMW ratio from the existing `rmw_avoided`/`rmw_required` maps, p99
   latency from existing histograms, DLQ entries from existing DLQ
   counters) over the trailing 60s window — no new distributed RPC, just
   real data instead of a constant. *Green test*: unit test driving known
   counter values through `MetricRegistry`, calling
   `collect_operator_stats`, and asserting the returned `OperatorStats`
   reflects the driven values (not the old hardcoded `12500.0`/`120`/etc.);
   wire-protocol test asserting `EXPLAIN INCREMENTAL ANALYZE <view>`
   reflects live traffic driven through the view in the same test.

### Group C — Resource Usage Visibility & Cost

7. **C1 — `rockstream_catalog.view_resource_usage`/`workload_resource_usage`
   + `SHOW RESOURCE USAGE` dispatch.** Add two new in-memory catalog-stub
   tables (`catalog_stubs.rs`, following the exact `CatalogSinkEntry`
   pattern from v0.44) populated per-view/per-workload from existing
   `MetricRegistry` fields (`workload_memory_bytes`, `state_budget_bytes`,
   SLO-compliance/degraded-reason data already tracked per §14.10). Add
   gateway dispatch for `SHOW RESOURCE USAGE`, `SHOW RESOURCE USAGE FOR
   WORKLOAD <name>`, `SHOW CLUSTER RESOURCE USAGE`, each rendering as a
   result set matching the catalog table's columns (so P4's "matching
   `view_resource_usage`" is true by construction — same data source, two
   presentation paths). *Green test*: wire-protocol test creating a
   workload + view, driving state/memory usage, then asserting `SHOW
   RESOURCE USAGE` and `SELECT * FROM rockstream_catalog.view_resource_usage`
   return matching state-bytes/memory/SLO figures.
8. **C2 — Real `write_amplification_ratio`/`segment_cache_hit_ratio`/
   `segment_cache_bytes_used` metrics.** Add these as genuine
   `MetricRegistry` fields (per-shard for write-amp, per-worker for
   segment-cache), updated on the compaction cycle and segment-cache
   read/evict hot paths respectively (reusing the exact calculation already
   proven correct in `minio_budget.rs`'s one-off test math, now made a
   continuously-updated counter/gauge instead of a one-shot computation).
   *Green test*: unit test driving a compaction cycle and cache
   hits/misses, asserting the new `MetricRegistry` getters return the
   expected ratio/byte values; Prometheus-output test asserting both metric
   names appear in `/metrics` scrape output.
9. **C3 — `[pricing]` config + `estimated_cost_per_hour`.** Add `[pricing]`
   parsing to the `rockstream.toml` config loader (object-store request/
   storage/egress unit costs, compute $/core-hour, Spot-vs-on-demand mix —
   unit costs only, no billing-API integration, exactly per DESIGN.md
   §14.19). Add an `estimated_cost_per_hour` computation applying this
   pricing table to `object_store_request_duration_seconds` + bytes
   transferred + worker compute-hours + Spot mix (all already collected);
   wire it as a column on both `view_resource_usage`/`workload_resource_usage`
   and in `SHOW RESOURCE USAGE` output; **null** (not a guessed value) when
   `[pricing]` is absent. *Green test*: unit test asserting
   `estimated_cost_per_hour` is `NULL`/absent with no `[pricing]` block, a
   defined non-null value once configured, and that the value changes when
   a workload's `MEMORY_LIMIT` or shard count changes (P7, literal wording)
   — table-driven test with two configs and an inequality assertion.

### Group D — `pipeline_id` Metrics Cardinality (LRU working set)

10. **D1 — Bounded per-pipeline metric labeling.** Promote the
    already-transitively-available `lru` crate to a direct dependency of
    `rockstream-types`. Add a `pipeline_id`-labeled metric (or set of
    metrics — whichever per-pipeline breakdown this version's other slices
    need, e.g. per-pipeline state bytes for C1) to `MetricRegistry`, backed
    by an `LruCache<PipelineId, ...>` capped at 256 entries; on insertion
    past capacity, evict the least-recently-active pipeline and roll its
    contribution into an aggregate `pipeline_id="other"` bucket rather than
    dropping it or refusing the new pipeline. No functional ceiling is
    introduced anywhere (confirmed none exists today — see §2). *Green
    test*: unit test creating 300 synthetic pipelines' worth of metric
    activity, asserting (a) all 300 `CREATE MATERIALIZED VIEW`-equivalent
    registrations succeed (no rejection), (b) exactly ≤256 distinct
    `pipeline_id` label values plus one `"other"` value are ever emitted in
    Prometheus output, (c) the `"other"` bucket's aggregate matches the sum
    of the evicted pipelines' individual contributions.

### Group E — Nexmark CI Regression Gate

11. **E1 — Commit a baseline artifact.** No baseline file exists in-repo
    today (confirmed, no `baseline*` glob hits) despite the roadmap's claim
    it "has existed since 2026-06-25" — that date refers to when the
    Nexmark bench itself (`rockstream-ops/benches/nexmark.rs`) was
    introduced at v0.36, not a saved comparison artifact. Generate and
    commit a `criterion --save-baseline v0.36` JSON output (or equivalent
    machine-readable summary: delta-amplification ratio, propagation
    latency p50/p99) checked into the repo (e.g.
    `crates/rockstream-ops/benches/baseline/v0.36.json`) as this version's
    reference point.
12. **E2 — CI regression-gate job.** Add a `.github/workflows/ci.yml` job
    (or a new scheduled/nightly workflow) that runs the Nexmark bench,
    parses its output for delta-amplification and propagation-latency
    figures, compares against the E1 baseline, and fails the job if either
    regresses by >10%. *Green test*: a script-level test (shell/Rust harness
    invoked by the CI job) that, given a synthetic "regressed" bench output
    fixture (>10% worse) and the real baseline, asserts the comparator
    exits non-zero; and given a fixture within 10%, exits zero. This is the
    testable unit here since "CI fails on a real regression" itself can
    only be proven by the comparator's own pass/fail logic, not by an
    actual multi-day nightly run within this session.

### Group F — Storage FinOps Tiering (durability paths — need LFS *and* MinIO)

13. **F1 — `TieredObjectStore` prefix router.** A `dyn ObjectStore` wrapper
    (`rockstream-storage/src/tiered_store.rs`) holding N `(prefix_matcher,
    Arc<dyn ObjectStore>)` pairs; `get`/`put`/`list`/`delete` route by
    matching the key against `ShardPrefix::ShardMeta` vs. everything else,
    falling through to a default backend if no tier is configured (so
    existing single-backend behavior is preserved exactly when tiering is
    unconfigured — no regression for clusters that don't opt in). *Green
    test*: unit test with two `InMemory`/`LocalFileSystem` backends proving
    `shard_meta/*` keys land in backend A and all other keys land in
    backend B, both LFS-backed; MinIO-backed variant of the same test
    (two MinIO buckets standing in for two tiers) proving the routing logic
    is storage-backend-agnostic.
14. **F2 — Age-based SST tiering to Standard-IA + config surface.** Add a
    `[storage.tiering]` config block (`shard_meta_backend`,
    `cold_sst_backend`, `cold_sst_age_threshold`) parsed alongside the new
    `[pricing]` block (C3). Compacted SSTs older than the threshold are
    copied (scan-and-copy, per the "no range-deletion dependency" ground
    rule already governing all cleanup in this codebase) to the
    Standard-IA-tier backend with `Attribute::StorageClass` set, then the
    original is deleted only after the copy is verified — mirroring the
    existing scan-and-delete GC pattern from v0.44's cold-tier sink, applied
    here to internal SSTs instead of sink snapshots. *Green test*: LFS test
    proving an aged SST is copied then removed from the hot tier and
    remains fully readable from the cold tier (recovery still succeeds

### Group G — Spot/Preemptible Worker Pool Validation (coordination slice)

16. **G1 — SimRuntime preemption test.** A new seeded `SimRuntime` test
    (`buggify!("worker.spot_preemption", p)`) that kills a worker process
    abruptly mid-epoch with no graceful drain signal (modeling a 2-minute
    Spot reclaim notice expiring), then asserts: (a) the existing lease
    fencing (`shard.rs`) detects and reassigns the shard within the v0.31
    SLO (≤30s p99 reassignment), (b) checkpoint-based recovery
    (`recovery.rs`) restores the shard's state with no data loss, (c) no
    duplicate output rows are produced across the preemption boundary
    (Z-set idempotency, reusing the existing crash-recovery oracle
    pattern). This *validates* existing machinery under a new fault
    shape; it does not add a new coordination protocol.
