## 2. Vertical Slices

Each slice ends in a green test (`cargo test --workspace` plus the new
`check-invariant-pairs.sh` self-test where noted).

- **S1 — `scripts/check-invariant-pairs.sh` (the CI cross-check tool).**
  Parses every `always assertion NAME:` / `always eventually assertion NAME:`
  / `exists assertion NAME:` line out of `formal/*.fizz`, extracts the leading
  `M<n>_(S|L)<n>` / `COV_M<n>` token(s) from `NAME` (a name may encode two IDs,
  e.g. `M2_S3_SinglePublisherSafety` → `M2-S3`; `COV_M4` → `COV-M4`), converts
  underscores to hyphens, and greps `crates/` for a comment containing that
  exact hyphenated ID. An ID is satisfied by either (a) a real `assert!`/
  `debug_assert!` site referencing it, or (b) a `// INVARIANT-BY-CONSTRUCTION:
  <ID> — <reason>` comment. Missing coverage on any invariant modeled in a
  `.fizz` file → exit 1 with the missing-ID list; full coverage → exit 0.
  Wired into `.github/workflows/ci.yml`'s existing `check` job, immediately
  after `check-error-codes.sh`.
- **S2 — Self-test harness for S1.** `scripts/check-invariant-pairs.test.sh`:
  copies `crates/` + `formal/` into a temp dir, deletes the `M2-S3` (and,
  separately, `M4-S1`) ID references from the copy, runs the script against
  the mutated copy and asserts exit code 1 (the deliberately-reverted
  assertion-removal case the roadmap's Proof column names explicitly); then
  runs the script against the real, unmodified tree and asserts exit code 0.
  Invoked as its own CI step so a regression in the script itself is caught,
  not just a regression in invariant coverage.
- **S3 — Frontier-lease CAS store (`crates/rockstream-control/src/
  frontier.rs`, new `FrontierLeaseStore`).** Backed by the control SlateDB
  (same `ShardDb`-style backing store already used for shard leases/catalog),
  keyed on `frontier/leader`. Mirrors `formal/m2_frontier_agg.fizz`'s
  `ObjectStore.cas_lease`/`write_frontier`: `acquire_publisher_lease(
  aggregator_id, current_fence_token) -> Result<LeaseToken, FrontierLeaseError>`
  (CAS on the stored fence token; monotonically-increasing token minted on
  success, mirroring `ShardManager::mint_token`'s pattern) and
  `publish_frontier(token, frontier)` (rejects with a stale-token error if
  `token < store's fence_token`, mirroring the FizzBee model's
  `write_frontier`). New error codes `RS-8002` (stale fencing token — publish
  rejected) and `RS-8003` (sync-flush-before-lease-handoff-read violation),
  registered in `crates/rockstream-types/src/error_code.rs` next to the
  existing `RS-8001`.
- **S4 — `M2-S3` runtime assertion.** `assert_valid_publisher(aggregator_id,
  held_token, current_fence_token)` in `frontier.rs`, called before every
  `publish_frontier` CAS attempt — panics with `RS-8002` on a stale token,
  following the exact `assert_valid_writer`/`assert_single_lease_holder`
  documentation convention already established in
  `crates/rockstream-runtime/src/fence.rs` (module-level `| FizzBee invariant
  | Rust assertion |` table, inline "M2-S3 paired assertion:" comment, panic
  message prefixed `RS-8002: M2-S3 violation — …`).
- **S5 — `sync:true`-flush-before-lease-handoff-read assertion.**
  `assert_flush_before_lease_handoff_read(...)` in `frontier.rs`: every
  `publish_frontier` write goes through the control SlateDB's
  `WriteBatchOptions { sync: true }` path (DESIGN.md §3.2 "Synchronous
  frontier writes"), and a newly-elected publisher's first post-acquisition
  read of the published frontier asserts the prior write it observes was
  flushed synchronously — panics with `RS-8003` on violation. This is the
  second half of the FIZZBEE_TEST_PLAN.md §3.7 M2-S3/S4 row's prescribed pair.
- **S6 — Wire `FrontierAggregator` to the lease store.** Add `is_publisher`/
  `lease_token` fields (mirroring the FizzBee model's `@state(ephemeral=...)`
  fields exactly) and an `acquire_lease()`/`try_publish()` pair that only
  publishes when `S4`'s assertion holds; a lost CAS demotes the aggregator to
  follower (`is_publisher = false`) rather than panicking, matching the
  model's `PublishFrontier` action (`else: self.is_publisher = False;
  fencing_occurred = True`).
- **S7 — Durability tests for the new `frontier/leader` CAS path** (S3–S6
  introduce new durable state — see §4 below for the required LFS+MinIO pair).
- **S8 — Coordination test: 3-aggregator stale-publisher scenario** (S3–S6
  introduce a new distributed-coordination path — see §5 below).
- **S9 — Invariant triage** for the seven IDs the roadmap names as currently
  uncovered (`M1-S1`, `M1-S3`, `M1-S4`, `M1-S5`, `M4-S4`, `M5-S1` — confirmed
  by a live `grep -rl` sweep of `crates/` finding **zero** files referencing
  any of these six IDs today, plus `M2-S3` which S3–S6 above now cover):
  - **`M1-S1`** (`WriteBatch` atomicity) — `INVARIANT-BY-CONSTRUCTION` comment
    in `crates/rockstream-storage/src/shard_db.rs::write_batch`: the method
    builds one `slatedb::WriteBatch` and calls `self.db.write(inner)` exactly
    once, so a torn intermediate is structurally unobservable — no redundant
    runtime `assert!` needed, matching the `M2-S1`/`S2` precedent the roadmap
    names as the model for this escape hatch.
  - **`M1-S3`/`M1-S4`** (CALM cluster-commit monotonicity/verifiability) —
    investigate at Implement time whether `crates/rockstream-runtime` has (or
    needs) a concrete comparison point between an object-store-only-derived
    `cluster_committed` (reading only per-shard `frontier_key`s) and the
    control-plane's own view at a checkpoint boundary; add a real
    `assert_eq!`/`assert!` there if such a comparison point exists in the
    recovery/checkpoint path, else an `INVARIANT-BY-CONSTRUCTION` comment
    explaining why no separate control-plane cache exists that could diverge
    (there is currently no cached `cluster_committed` outside of what
    `FrontierAggregator::compute_meet` derives fresh from shard reports each
    time — likely structural, to be confirmed against the real recovery code).
  - **`M1-S5`** (idempotent replay) — attach the ID to the existing
    crash-replay equality check backing `test_recovery_bit_identical_lfs`/
    `_minio` (`crates/rockstream-runtime/tests/`), as a real `assert_eq!` on
    the replayed state, not just a doc comment.
  - **`M4-S4`** (no self-fence assert fires on an object-store-only partition)
    — `INVARIANT-BY-CONSTRUCTION` comment at the control-plane-reachability
    gate that decides self-fencing (`crates/rockstream-runtime/src/fence.rs`'s
    `SelfFenceGuard`/`must_self_fence()` path) and at
    `crates/rockstream-sim/src/brownout.rs`'s `ObjectStoreBrownoutGuard`,
    explaining that fencing is structurally gated on control-plane
    reachability alone, so an object-store-only partition can never reach the
    panic path — proven by `test_checkpoint_under_slow_input`'s absence of a
    panic, not by an assertion.
  - **`M5-S1`** (no duplicates under partial-write fault) — label fix only:
    `assert_commit_pointer_atomic` in
    `crates/rockstream-connectors/src/sink_connector.rs` already implements
    both `M5-S1` and `M5-S3` per FIZZBEE_TEST_PLAN.md §3.7's own row, but its
    doc comments/table entry/panic string only ever say `M5-S3`. Add the
    `M5-S1` reference alongside every existing `M5-S3` reference in
    `sink_connector.rs` and `object_store_sink.rs` (no new code path).

## 4. Durability Slices

**New durability path**: the `frontier/leader` fencing-token CAS record and
the synchronously-flushed published-frontier value, both introduced by S3–S6.
This is new durable state that did not exist before this version (today's
`FrontierAggregator` is purely in-memory, per-process, with no persisted
lease) and therefore needs both required tests per the Phase 2 rule:

- **SlateDB/LFS test**: `frontier_lease_tests.rs::
  frontier_leader_lease_cas_survives_restart_lfs` — LocalFileSystem-backed
  control SlateDB; a publisher acquires the lease, publishes, crashes; a
  second aggregator recovers, acquires with a strictly higher token, and its
  first read observes the crashed publisher's last (synchronously-flushed)
  write — never a stale value.
- **MinIO (S3, TestContainers) test**: `frontier_lease_tests.rs::
  frontier_leader_lease_cas_survives_restart_minio_tc` — identical assertion
  against a real MinIO container.
- **Focused sync-flush regression** (both backends):
  `frontier_lease_tests.rs::sync_flush_before_lease_handoff_read_{lfs,
  minio_tc}` — directly exercises S5's `assert_flush_before_lease_handoff_read`
  panic path by forcing an unflushed write ahead of a lease handoff and
  asserting it panics with `RS-8003`, mirroring the existing
  `commit_panics_via_assert_commit_pointer_atomic_on_truncated_write` pattern
  in `object_store_sink.rs`.

## 5. Coordination Slices

**New distributed-coordination path**: frontier-aggregator publisher election
and fencing (S3–S6). Gets a seeded `SimRuntime` test with `buggify!()`,
directly proving the roadmap's explicit Proof clause:

- **`three_frontier_aggregators_stale_publisher_never_republishes`**
  (`crates/rockstream-sim/tests/`): three simulated `FrontierAggregator`
  instances contend for the same `frontier/leader` CAS record.
  `buggify!("frontier.stale_publish_race", p)` forces a fenced (superseded)
  aggregator to attempt a late `publish_frontier` call *after* a new leader's
  CAS has already succeeded and minted a higher token. Asserts, across seeds,
  that the stale attempt is always rejected (`RS-8002`, S4's assertion
  firing) and that `store.published_frontier` is never regressed by it — this
  is the exact "a real 3-aggregator `SimRuntime` scenario proves a
  stale-fenced publisher can never re-publish a frontier after a new leader's
  token supersedes it" claim from the roadmap's Proof column.
- The FizzBee model (`formal/m2_frontier_agg.fizz`, already green,
  `M2_S3_SinglePublisherSafety`) is the formal half of this proof; the
  SimRuntime test above is its paired runtime/simulator commitment, per the
  same pattern used for M4/M7 elsewhere in this roadmap.
