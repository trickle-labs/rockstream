# v0.65.1 Plan — Concurrent Maintenance and Group Commit

**Version**: v0.65.1  
**Phase**: Phase 2 — Plan (Complete)  
**Target Scope**: After the v0.65 recovery contract is proven, schedule independent branches of the view dependency graph concurrently. Keep one ordered execution owner per shard and bound concurrency. Reduce the gateway commit lock's scope only after preserving dependent-view ordering and consistent reads. Feed multiple complete logical epochs into the existing physical commit group. Flush at a byte limit or a bounded delay for the oldest pending epoch, including idle traffic. Reserve time for persistence within the freshness budget. Bound pending bytes and acknowledgment waiters. Advance frontiers and acknowledge durability only after all required writes and durable flushes succeed; never expose partial dependencies or later epochs across a failed commit. Compare one and twenty views under light and sustained load. Require exact results through crash, retry, stale-owner, and write-failure cases. Publish lock wait, flushes per epoch, throughput, and read, commit, and freshness p99. Batching must demonstrate a benefit without violating the selected latency targets.

v0.65.1 establishes concurrent view maintenance, physical group commit batching, and narrowed gateway lock contention:

1. **View Dependency Graph & Concurrent Branch Scheduling ([`crates/rockstream-ops/src/compile.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/compile.rs), [`live_exec.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/live_exec.rs), [`pipeline.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/pipeline.rs), [`crates/rockstream-runtime/src/shard_actor.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-runtime/src/shard_actor.rs))**:
   - Inventory and trace dependency graph execution across all active views.
   - Separate independent branches (views having disjoint dependencies or branching from the same parent) from sequential dependency paths (derived views consuming another view's output).
   - Schedule independent branches with bounded task concurrency (`MAX_CONCURRENT_BRANCH_TASKS = 16`), ensuring every dependent node executes strictly after its upstream input deltas are fully computed.
   - Maintain exactly one ordered execution owner per shard; concurrent branch execution operates as worker tasks within that shard's ownership lease.
   - Implement fail-fast branch cancellation: failure in any branch halts the remaining tasks and prevents publication of that entire logical epoch.

2. **Gateway Commit Lock Narrowing & Read Snapshot Consistency ([`crates/rockstream-gateway/src/server.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-gateway/src/server.rs))**:
   - Trace every acquisition of `shard_commit_lock` across SQL DML execution, pgoutput source ingestion, transaction commits, and catalog operations.
   - Narrow the critical section of `shard_commit_lock` to cover only epoch allocation, shard state registration, and physical commit staging, releasing the lock during independent branch delta computation and non-conflicting preparation.
   - Maintain strict parity between SQL client writes and pgoutput CDC stream ingestion under the narrowed lock regime.
   - Guarantee consistent read snapshot isolation: readers querying materialized views observe only fully committed dependency-consistent epochs; intermediate branch states are never queryable.

3. **PhysicalCommitGroup Multi-Epoch Coalescing & Group Commit ([`crates/rockstream-ops/src/group_commit.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/group_commit.rs))**:
   - Extend [`PhysicalCommitGroup`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/group_commit.rs#L187) to ingest multiple complete logical epochs concurrently rather than immediately executing a physical commit per epoch.
   - Preserve monotonic ordering of pending logical epochs within [`BTreeMap<Epoch, WriteBatch>`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/group_commit.rs#L189).
   - Retain ordered write-batch merging and atomic durable write/flush behavior across all batched epochs.
   - Ensure complete error recovery: on physical write or flush failure, restore pending epoch batches so retries or diagnostic handlers can act safely without torn state.

4. **Delay-Based & Byte-Threshold Flush Triggers with Idle Traffic Guarantee ([`crates/rockstream-ops/src/group_commit.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/group_commit.rs))**:
   - Introduce dual trigger mechanisms for physical flushes:
     1. Pending bytes limit (`MAX_GROUP_COMMIT_PENDING_BYTES = 8 MiB`): immediate flush when accumulated uncommitted batches exceed the byte threshold.
     2. Oldest-epoch delay timer (`DEFAULT_GROUP_COMMIT_MAX_DELAY_MS = 10 ms`): scheduled flush when the oldest pending epoch reaches its deadline.
   - Decouple the deadline timer from incoming traffic: run an independent asynchronous timer so single-epoch or low-volume idle traffic flushes strictly within the delay bound.
   - Reserve sufficient persistence time within the overall freshness SLO budget (accounting for storage fsync latency).

5. **Ordered Monotonic Frontier Advancement & Durability Acknowledgments ([`crates/rockstream-gateway/src/server.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-gateway/src/server.rs), [`crates/rockstream-runtime/src/client.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-runtime/src/client.rs))**:
   - Advance shard frontiers and dispatch durability acknowledgments (e.g. pgwire `COMMIT` OK, source LSN commits) strictly *after* physical `write_batch()` and `flush()` succeed.
   - Enforce fail-stop frontier ordering: a failed commit halts frontier progression; subsequent epochs can never be published across a prior failed commit.
   - Issue updated [`FreshnessToken`](file:///Users/grove/projects/rockstream/crates/rockstream-gateway/src/session.rs)s only upon verified durable flush.

6. **Crash Injection, Stale-Owner Fencing, and Idempotent Retry Safety ([`crates/rockstream-gateway/src/server.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-gateway/src/server.rs), [`crates/rockstream-runtime/src/shard_actor.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-runtime/src/shard_actor.rs))**:
   - Verify shard owner fencing: validate that stale worker instances or expired lease tokens cannot commit epochs or corrupt the physical commit queue.
   - Leverage v0.65 idempotency metadata (`ShardDb::put_idempotency_key`) to deduplicate retried client transactions post-recovery without duplicate side effects.
   - Subject the system to hard crashes (`SIGKILL`) during concurrent branch computation and during physical commit flush, verifying exact bit-identical state recovery upon process restart.

7. **Operational Limits, Queues, Waiters, and Admission Control ([`crates/rockstream-ops/src/group_commit.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-ops/src/group_commit.rs), [`crates/rockstream-runtime/src/shard_actor.rs`](file:///Users/grove/projects/rockstream/crates/rockstream-runtime/src/shard_actor.rs))**:
   - Enforce explicit named upper bounds:
     - `MAX_GROUP_COMMIT_PENDING_BYTES = 8 MiB`
     - `PHYSICAL_COMMIT_GROUP_MAX_EPOCHS = 64`
     - `MAX_GROUP_COMMIT_WAITERS = 1,024`
     - `MAX_CONCURRENT_BRANCH_TASKS = 16`
     - `DEFAULT_GROUP_COMMIT_MAX_DELAY_MS = 10 ms`
   - Apply proactive admission control: reject excess epoch submissions before allocation with `RS-1015` (`group_commit_full`) or `RS-5003` (`state_budget_exceeded`).
   - Clean up cancelled waiters without resource leakage or deadlocks.

8. **Workload Benchmarking & Performance Gate Qualification (1-View vs 20-Views) ([`benchmarks/`](file:///Users/grove/projects/rockstream/benchmarks/), [`crates/rockstream-cli/`](file:///Users/grove/projects/rockstream/crates/rockstream-cli/))**:
   - Benchmark 1-view and 20-view topologies under both light load (idle/single-epoch) and sustained write load.
   - Measure and publish: lock wait duration, physical flushes per epoch, committed transaction throughput, and p99 latencies for reads, commits, and end-to-end view freshness.
   - Prove batching efficiency: group commit demonstrates measured flushes/epoch reduction and throughput gains without exceeding frozen p99 latency targets.

### Non-Negotiable Ground Rules

- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag or config property on the same `rockstream` binary. `main` remains runnable through it.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters, asserted by test.
- Unbounded in-memory accumulation is never acceptable. Every new queue, buffer, or scan window needs a named upper bound, a fill-level metric, and a backpressure or error path.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass. Do not use `--no-verify`. Fix root causes.
- Make only changes this version requires. No speculative features outside IVM engine + Postgres wire layer.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals.**
