## 6. Real-Cluster Chaos/SLO Soak Contract

**New test:** `crates/rockstream-sim/tests/real_cluster_chaos_soak_tests.rs`,
reusing the role-based unified-binary fixture shape in
`crates/rockstream-sim/tests/shard_migration_tc_tests.rs:39-145`. It boots
separate control, gateway, and at least two worker containers plus real Kafka
and MinIO in one TestContainers network. It must never substitute the
in-process `chaos_tests` simulation for this proof.

The deterministic schedule uses a documented seed and records event timestamps:

1. sustain Kafka ingestion into a materialized view backed by MinIO;
2. kill one worker, verify catch-up, then restart/rejoin it;
3. partition and restore a worker/control network link;
4. inject a bounded MinIO brownout until source credits exhaust, then recover;
5. kill a control node/worker during active load; and
6. compare the complete final view Z-set and source offsets with the batch
   oracle (zero loss and zero duplicates).

The test must write a stable JSON and Markdown summary containing seed,
schedule, rows submitted/committed, complete output digest, failure-detection
p99, shard-reassignment p99, freshness-recovery p99, steady-state throughput,
and pass/fail target values. The workflow uploads both artifacts and appends
the Markdown summary to the job summary.

Absolute targets are documented in `DESIGN.md` and asserted by the test, not
compared to a baseline: failure detection ≤ 5 s, shard reassignment ≤ 30 s,
freshness recovery ≤ 60 s, zero loss, zero duplicates, and a nonzero documented
minimum sustained throughput chosen with the fixture's fixed record shape.
The threshold, load size, duration, worker count, and seed are constants in
the test and are included verbatim in the published summary; no environment
default may silently weaken them.

Add a dedicated CI workflow/job for this TestContainers suite, run manually
and on its schedule, with a required PR run whenever the fixture, chaos
runtime, connectors, storage, control, runtime, gateway, or formal-edge files
change. Docker/image unavailability must be a CI failure for this job, never a
passing skip.

This is validation of existing Kafka/MinIO durability paths, not a new
commit/replay/checkpoint/compaction/WAL mechanism. S4 nevertheless commits to
both the LFS and MinIO recovery tests above. If implementation changes a
durability mechanism, it must add both an LFS and MinIO TestContainers test
before merge.

## 7. Coordination and Boundedness Commitments

`EDGE-QUOTA` and `EDGE-LATE` are distributed-ordering paths. Their
`edge_case_recovery_tests.rs` cases run seeded `SimRuntime` schedules with
named `buggify!()` points for reservation/release and watermark/message order;
the failing seed is emitted and replayable. Source failure, brownout, and
misconfiguration are deterministic local lifecycle paths and need no invented
coordination protocol.

No new unbounded structure is allowed. Brownout buffering retains a named
epoch cap, exposes the pending/buffered epoch fill metric, and returns
backpressure at the cap; source polling consumes explicit credits. The chaos
fixture itself uses fixed load count/duration and bounded result collection.
