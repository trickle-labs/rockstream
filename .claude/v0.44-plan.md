# v0.44 Plan — Cold-Tier Sinks (Iceberg / Delta)

## Roadmap row (verbatim reference)

- **Focus**: Cold-Tier Sinks
- **Scope**: Iceberg and Delta sinks exporting periodic columnar Parquet
  snapshots to object storage. DDL surface (DESIGN.md §13.6.1): `CREATE SINK
  <name> FOR VIEW <view> TO ICEBERG|DELTA '<path>' WITH
  (snapshot_interval_epochs, snapshot_interval_ms, parquet_row_group_bytes,
  format_version, partition_by, catalog = filesystem|glue|rest|hive|ducklake,
  ...)`, documented in `docs/`. Plus cold-snapshot GC (DESIGN.md §13.6.2.1):
  `cold_snapshot_retention_count` / `cold_snapshot_retention_duration`,
  whichever-first expiry, "never delete a file referenced by a retained
  snapshot" safety guarantee.
- **Proof** (decomposed into checkable claims, P1–P7):
  - P1: External engines can query RockStream-generated Iceberg (and, per
    Scope, Delta) tables with zero data corruption.
  - P2: `partial_write_probability` fault injection passes without any
    duplicate or missing rows in the sink output.
  - P3: `docs/` documents `CREATE SINK` end-to-end with a runnable example.
  - P4: `EXPLAIN INCREMENTAL` on a sunk view shows the sink target.
  - P5: Cold-snapshot GC expires snapshots beyond
    `cold_snapshot_retention_count`/`cold_snapshot_retention_duration`
    (whichever first) and emits `cold_gc_bytes_reclaimed`/
    `cold_gc_last_run_epoch`.
  - P6: `cold_gc_safety_tests.rs` proves a data file shared by a retained and
    an expired snapshot is never deleted.
  - P7: `cold_gc_safety_tests.rs` proves GC never runs concurrently with a
    snapshot commit.
- **Backends**: Unit, LFS, MinIO, TC.

## 2. Codebase reality check (binding constraints on the plan below)

Direct inspection of the repository (not just DESIGN.md) found:

- `CREATE SINK` (and `CREATE SOURCE`) DDL **does not exist anywhere in Rust
  code today** — only `docs/language-features.md` mentions it aspirationally.
  Gateway DDL dispatch (`crates/rockstream-gateway/src/server.rs`) is a flat
  `ql.starts_with("create view ")` / `"create table "` / `"create index "`
  chain, each delegating to a `handle_create_*` method — **no general SQL
  parser** is used for DDL. `CREATE SINK` must follow this exact pattern:
  add `ql.starts_with("create sink ")` → `handle_create_sink`, with a
  hand-written `WITH (...)` option parser (key=value, `ARRAY[...]`, string/
  numeric literals) — no new SQL-parsing dependency needed.
- `rockstream_catalog.connectors` (mentioned in DESIGN.md §12.6) is **not**
  wired as a queryable system view anywhere in the gateway. Building a
  general system-catalog SQL surface is out of scope for v0.44 (no Proof
  claim requires it — P4 only requires `EXPLAIN INCREMENTAL` to show the sink
  target, and P3 only requires docs+DDL). Sinks will be registered in an
  in-memory `CatalogSinkEntry` list in `catalog_stubs.rs`, mirroring the
  existing `CatalogIndexEntry` pattern, sufficient for `EXPLAIN` lookup and
  connector lifecycle. Building the full `rockstream_catalog.connectors` SQL
  view is explicitly **not** part of this version (no proof claim needs it;
  adding it would be a drive-by scope expansion).
- The gateway's `EXPLAIN <query>` handler (`server.rs` ~line 1436) is
  confirmed to be exactly the "one-line pushdown/index-annotation stub"
  that v0.45's own roadmap row describes as disconnected from
  `rockstream-sql::explain_incremental`. **v0.44 must only add a sink-target
  annotation line to this existing stub** (same pattern as the existing
  `index_note` block) — the full rewire to the real `explain_incremental`
  library is v0.45's scope and must not be pulled forward here.
- `should_flush(bytes_buffered, epochs_buffered)` is designed (DESIGN.md
  §13.3.1/§13.6.2) but **has no Rust implementation** — it must be added to
  the `SinkConnector` trait (or a new `TieredSinkConnector` extension) as
  part of this version, since the whole snapshot-interval trigger depends on
  it.
- No `parquet`, `iceberg`, `deltalake`, or Avro crate is currently a
  dependency (workspace `Cargo.toml` only has `arrow`, `object_store`,
  `datafusion`). `parquet` v58.3.0 is already vendored transitively (via
  `datafusion`/`arrow`), so adding it as a **direct** dependency is
  version-safe.
- The Iceberg spec requires manifest and manifest-list files in **Avro**,
  not JSON — hand-rolling Avro plus the full v2 metadata/partition-spec/
  optimistic-concurrency-commit protocol correctly is high-risk for the
  "zero data corruption" / "queryable by external engines" proof claim (P1).
  Per the "prefer ecosystem tools" rule, this plan uses the official
  `iceberg` crate (`apache/iceberg-rust`, v0.9.x, mature: 74k LOC, storage-s3
  feature) for Iceberg table writes, and the official `deltalake` crate
  (`delta-rs`, v0.32.x) for Delta writes. Both crates accept a `dyn
  object_store::ObjectStore` — the **same crate already used** throughout
  this codebase — as their storage backend, so `partial_write_probability`
  fault injection composes cleanly (see Slice 2 below) without needing the
  crates to know about `buggify!`.
- Catalog registration backends: `iceberg-catalog-rest` and
  `iceberg-catalog-glue` (official, from the same `iceberg-rust` project) are
  used for `catalog = rest|glue`. `iceberg-catalog-hive` (official) is used
  for `catalog = hive` — avoids hand-rolling the Thrift binary protocol.
  `deltalake`'s `glue` feature covers Delta+Glue. For `catalog = ducklake`,
  no official Rust SDK exists; the only candidate (`ducklake` crate,
  `ducklake-sdk`, v0.0.9, ~180 total downloads, pre-1.0, sqlite/postgres/
  mysql-backed) is immature. This plan uses it behind the same
  `CatalogRegistrar` trait with its `sqlite` feature only (a local,
  self-contained catalog file — no external service dependency), and
  explicitly documents the immaturity risk in `docs/`. `catalog = filesystem`
  (the default) needs no external crate: it is simply "don't call a
  `CatalogRegistrar`", matching DESIGN.md's own description.

## 3. Vertical Slices

Each slice ends in a green test runnable via `cargo test` (unit) or the
LFS/MinIO harness already established by `partial_write_recovery_tests.rs`.

1. **`CREATE SINK` DDL parsing + validation** — `handle_create_sink` in
   `server.rs`: parses `FOR VIEW <view> TO ICEBERG|DELTA '<path>' WITH
   (...)`, validates the referenced view exists, validates `catalog` is one
   of the five allowed values, and validates required numeric/array option
   types. Malformed DDL returns a new `RS-4007` parse error (hard error, not
   silent corruption — same rule the v0.42.2 multi-row-INSERT fix
   established). *Green test*: `handle_create_sink` unit tests for valid
   DDL (registers a `CatalogSinkEntry`) and for each malformed-input case
   (unknown view, bad `catalog` value, malformed `WITH` clause) returning
   `RS-4007`.
2. **`FaultInjectingObjectStore` wrapper** — a `dyn ObjectStore` decorator
   (`crates/rockstream-connectors/src/fault_injecting_store.rs`) that
   truncates bytes on `put()`/`put_opts()` with `partial_write_probability`,
   gated by `buggify!("object_store.partial_write", p)` exactly like
   `ObjectStoreSink` (v0.43) — reused for *both* the Iceberg and Delta
   writers so P2 (fault injection) covers both formats through one
   mechanism instead of two bespoke ones. *Green test*: unit test proving
   `put()` is byte-identical when probability is 0, and truncated when the
   fault fires under a seeded RNG (mirrors `object_store_sink.rs`'s
   `write_final` test style).
3. **Cold-tier `should_flush` + pending-buffer wiring** — add
   `should_flush(&self, bytes_buffered: u64, epochs_buffered: u64) -> bool`
   to `SinkConnector` (default: `true`, preserving existing sinks'
   behavior), and a `snapshot_interval_epochs`/`snapshot_interval_ms`-driven
   override on the new cold-tier sink type. Buffered rows are staged in
   `connector/{id}/pending_buffer` per DESIGN.md §13.6.2's exactly-once
   guarantee. *Green test*: unit test driving N epochs with
   `snapshot_interval_epochs=3` and asserting flush triggers exactly on
   epochs 3, 6, 9, buffering (not flushing) in between.
4. **Iceberg writer (filesystem catalog only)** — `IcebergSink` wraps the
   `iceberg` crate's `Transaction`/`FileIO` writer over
   `FaultInjectingObjectStore`; converts the epoch's committed Z-set rows to
   an Arrow `RecordBatch`, writes Parquet data files
   (`parquet_row_group_bytes` respected via `ArrowWriter` row-group sizing),
   commits a new snapshot via optimistic-concurrency `metadata.json` swap,
   updates `last_snapshot_epoch`. Implements the existing `SinkConnector`
   4-phase protocol (`pre_commit`/`commit`/`abort`/`recover`) so it composes
   with the same epoch-commit loop as `ObjectStoreSink`. *Green test*: unit
   test writing 5 snapshots then reading them back via the `iceberg` crate's
   own table-scan API, asserting row-for-row equality with the source rows
   (this **is** the "incremental == batch" oracle property for this
   version — see §4).
5. **Iceberg crash-recovery + partial-write fault (LFS + MinIO)** — new
   `iceberg_sink_recovery_tests.rs`, structured like
   `partial_write_recovery_tests.rs`: drives N epochs through
   `IcebergSink` backed by (a) `LocalFileSystem`, (b) MinIO via
   `testcontainers`, with `partial_write_probability=0.5` armed on the
   `FaultInjectingObjectStore`. *Green test*: after recovery, an external
   read (via the `iceberg` crate's scan API, standing in for
   DuckDB/Trino/Spark) returns exactly the expected rows with no
   duplicates and no missing rows — this is P1 + P2's direct proof.
6. **Delta writer (filesystem catalog only)** — `DeltaSink` using the
   `deltalake` crate over the same `FaultInjectingObjectStore`, mirroring
   slice 4/5's structure (its own `deltalake_sink_recovery_tests.rs`, LFS +
   MinIO, same fault-injection + external-read-back assertions). *Green
   test*: same shape as slice 5, for Delta.
7. **`partition_by` support** — thread `partition_by` (array of column
   expressions, e.g. `region`, `date_trunc('day', created_at)`) into both
   writers' partition specs. *Green test*: write partitioned data across 3
   distinct partition values, confirm the external read-back groups rows
   under the correct partition directories/partition-spec values.
8. **Catalog registration: `filesystem` (default) + `rest`** — wire the
   `catalog` DDL option; `rest` uses `iceberg-catalog-rest`. Catalog-call
   failure sets `CATALOG_WARN` (visible on the `CatalogSinkEntry`) without
   blocking IVM, and retries on the next successful flush (DESIGN.md
   §13.6.5's Failure isolation rule). *Green test*: a tiny in-process HTTP
   listener (std `TcpListener`, no new mocking dependency) stands in for a
   REST catalog; one test proves successful registration, one proves a
   500/timeout response sets `CATALOG_WARN` and does not fail the sink's
   `commit`, and a third proves the next flush retries and clears
   `CATALOG_WARN`.
9. **Catalog registration: `glue`, `hive`, `ducklake`** — same
   `CatalogRegistrar` trait, backed by `iceberg-catalog-glue` /
   `deltalake`'s `glue` feature, `iceberg-catalog-hive`, and the `ducklake`
   crate's `sqlite` feature respectively. Since no live Glue/Hive/MotherDuck
   service is available in CI, these are unit-tested by injecting a fake
   transport/local catalog file rather than a new TestContainers image (no
   Proof claim requires round-tripping against a real Glue/Hive/DuckLake
   service — only the DDL surface and the generic failure-isolation
   behavior from slice 8, which each backend shares via the same trait).
   *Green test*: one registration-success + one registration-failure test
   per backend, asserting the same `CATALOG_WARN`/retry contract as slice 8.
10. **`EXPLAIN INCREMENTAL` sink-target annotation (P4)** — extend the
    existing one-line `EXPLAIN` stub (`server.rs` ~1436) with a
    `sink_note` block, structurally identical to the existing `index_note`
    block: if the queried view has a registered `CatalogSinkEntry`, append
    `\nsink_target: name='<n>' format=ICEBERG|DELTA path='<path>'
    last_snapshot_epoch=<N> state=<OK|CATALOG_WARN>`. **Explicitly not**
    wiring the full `explain_incremental` library — that stays v0.45 scope.
    *Green test*: `EXPLAIN <sunk view>` returns a string containing
    `sink_target: name='...'`; `EXPLAIN <un-sunk view>` does not.
11. **Cold-snapshot GC (P5, P6, P7)** — `cold_gc` module: after each
    successful snapshot commit, evaluate retention
    (`cold_snapshot_retention_count` / `cold_snapshot_retention_duration`,
    whichever bound is reached first, defaults 32 / 7d per DESIGN.md
    §13.6.2.1), then scan-and-delete (never a range delete) manifests/data
    files not referenced by any retained snapshot, update `metadata.json` to
    drop expired snapshot entries, and emit `cold_gc_bytes_reclaimed` /
    `cold_gc_last_run_epoch` metrics. GC acquires the same per-sink commit
    lock the flush path uses, so it structurally cannot run concurrently
    with a snapshot commit (P7). New `cold_gc_safety_tests.rs` (LFS + MinIO,
    per the Durability Slices rule in §5): (a) a data file shared by a
    retained snapshot and an otherwise-expired snapshot is never deleted
    (P6a); (b) re-running GC after a simulated crash mid-delete is
    idempotent and deletes nothing extra (P6b, matches the "GC is
    idempotent" safety guarantee); (c) a seeded coordination test spawning
    GC and a snapshot commit concurrently (buggify-gated interleaving,
    mirroring the `sim_coordination` module in
    `partial_write_recovery_tests.rs`) asserts the commit lock serializes
    them — no snapshot is ever partially visible to GC (P7).
12. **Docs (P3)** — `docs/language-features.md`'s existing forward-looking
    "roadmap items" line for `CREATE SINK ... TO ICEBERG` is replaced with a
    real, runnable end-to-end example (create a view, attach an Iceberg
    sink, query it from DuckDB via `iceberg_scan`), plus a new
    `docs/cold-tier-sinks.md` documenting the full `WITH` option surface,
    retention/GC behavior and defaults, catalog backend matrix (mirroring
    DESIGN.md §13.6.5's table), and the `ducklake` maturity caveat from §2
    above.

## 4. Test Commitments (oracle property tests)

No new **IVM operator** (in the differential-dataflow/circuit sense) is
introduced by this version — cold-tier sinks are a connector, not a
relational operator, so the literal "incremental == batch" operator oracle
does not apply verbatim. The closest equivalent, and the one this plan
commits to as the binding oracle property for this version, is:

> **Sink oracle property**: querying the latest committed Iceberg/Delta
> snapshot for a view via an external reader must return exactly the same
> rows as directly reading the view's current committed IVM state through
> the existing gateway (`SELECT * FROM <view>`), for every snapshot boundary
> exercised in the recovery tests (slices 5 and 6).

This is asserted in slices 4, 5, 6, and 11 above (row-for-row equality
between the sink's external read-back and the source-of-truth committed
rows). It is the direct, literal proof of P1 ("zero data corruption").

All four rows reuse the exact LFS/MinIO harness pattern established by
v0.43's `partial_write_recovery_tests.rs` (real `LocalFileSystem` +
`testcontainers` MinIO, deterministic seeded RNG fault injection — no new
test infrastructure needed).

## 6. Coordination Slices

New distributed-coordination path: **GC running concurrently with a
snapshot commit on the same sink** (DESIGN.md §13.6.2.1's "GC never runs
concurrently with a snapshot commit" safety guarantee, P7). Per the ground
rules, this gets a seeded test with `buggify!()` annotations:
`cold_gc_safety_tests.rs`'s coordination test (slice 11c above), modeled
directly on the existing `sim_coordination` module in
`partial_write_recovery_tests.rs` — multiple seeds, `buggify_init`/
`buggify_disable`, asserting the commit lock always serializes GC and
flush regardless of interleaving.

No new FizzBee model is added. The v0.18 binding requirement ("model-check
the cold-tier exactly-once commit protocol in FizzBee before any cold-tier
sink code is written") was already discharged by v0.43's
`formal/m5_cold_tier_sink.fizz` (M5-S1/S2/S3, M5-L1, all green). v0.44's
Proof column does not request a new or extended formal model for GC — only
`cold_gc_safety_tests.rs` — so adding one would be scope not required by
this version's contract.
