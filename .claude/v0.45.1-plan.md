# v0.45.1 Plan — Workload Quotas, Priority Admission Control & Multi-Tenancy

## Roadmap row (verbatim reference, decomposed)

- **Focus**: Workload Quotas, Priority Admission Control & Multi-Tenancy.
- **Scope** (NEW_ROADMAP.md line 603, condensed to deliverables):
  1. Wire `rockstream-types::workload`'s data model into a **real
     control-plane workload catalog** (durable, not in-memory-only) and the
     gateway: `CREATE WORKLOAD <name> WITH (MEMORY_LIMIT=..., MAX_PARALLELISM=...,
     PRIORITY=..., FRESHNESS_SLO=...)`, `ALTER WORKLOAD ... SET (...)`,
     `DROP WORKLOAD`, `SHOW WORKLOAD STATUS` (DESIGN.md §14.13).
  2. Per-workload `MEMORY_LIMIT` transitions over-budget views to
     `OVER_BUDGET_RELAXED`, **independently of (and nested inside)** the
     existing global `state_budget_gb` floor, which remains the cluster-wide
     backstop.
  3. `MAX_PARALLELISM` caps the existing per-operator auto-tuner (v0.30) on a
     per-workload basis.
  4. `PRIORITY`-driven admission control (§14.16) pauses or defers
     lower-priority workloads' views under contention instead of degrading
     every pipeline on the cluster equally.
  5. This is the substrate the v0.55 admin CLI's `workload {list,show,create,
     alter,drop}` / `cluster {status,workers,quotas}` commands assume exists.
- **Proof** (roadmap's literal Proof column, split into checkable claims):
  - **P1**: Two workloads (`PRIORITY=HIGH`, `PRIORITY=LOW`) sharing one
    deliberately under-provisioned cluster: under sustained contention the
    low-priority workload's views transition to `PAUSED`/`OVER_BUDGET_RELAXED`.
  - **P2**: Under that same contention, the high-priority workload keeps
    meeting its `FRESHNESS_SLO`.
  - **P3**: A view that exceeds its own workload's `MEMORY_LIMIT` (but not
    the global budget) transitions to `OVER_BUDGET_RELAXED`.
  - **P4**: That `OVER_BUDGET_RELAXED` state is visible in
    `SHOW WORKLOAD STATUS`.
  - **P5**: Every quota decision (memory-limit transition, parallelism-cap
    application) is audited (§14.11).
  - **P6**: Every admission-control pause is audited (§14.11).
  - **P7** *(from Scope, not a one-line Proof clause but binding per the
    Ground Rules — "if Scope requires it, it is implemented now, in full")*:
    the full `CREATE WORKLOAD`/`ALTER WORKLOAD`/`DROP WORKLOAD`/
    `SHOW WORKLOAD STATUS` DDL surface works end-to-end, including the new
    `MAX_PARALLELISM` and `PRIORITY` options (only `MEMORY_LIMIT` and
    `FRESHNESS_SLO_MS` are parsed by the existing `CREATE WORKLOAD` stub
    today — see Reality Check below).
  - **P8** *(from Scope)*: `MAX_PARALLELISM` actually caps the v0.30
    auto-tuner's scale-up ceiling on a per-workload basis (never exceeded
    regardless of cluster-wide `max_parallelism`).
  - **P9** *(from Scope)*: the workload catalog is **durable** — survives a
    process restart via the control-plane store, not just in-memory
    (`CatalogStubs` today is process-lifetime only).
- **Backends**: Unit, LFS, TC. *(No MinIO in the roadmap's own Backends
  column for this row — but per Ground Rules, "for every new durability
  path, pre-commit to both a SlateDB LFS test and a MinIO test." The new
  workload-catalog durability path introduced here is a `ShardDb`-backed
  catalog entry — identical mechanism to the existing view/table/index/sink
  catalog entries, which already have both LFS and MinIO catalog tests in
  `crates/rockstream-sql/tests/lfs_catalog.rs`. To stay consistent with that
  precedent and the non-negotiable durability ground rule, the plan below
  adds a MinIO variant for the new workload-catalog persistence test even
  though the roadmap's Backends column omits it — this is required
  durability coverage, not scope creep, since it reuses the exact same
  `ShardDb`/`CatalogKeyEncoder` mechanism already MinIO-tested for views.)*

## 2. Codebase Reality Check (binding constraints on the plan below)

Direct inspection of `crates/` (not just DESIGN.md or the roadmap's own
framing) found the following, which shape every vertical slice below:

- **The workload data model is not "entirely unused" — it's partially
  wired, in-memory only.** `crates/rockstream-types/src/workload.rs`
  defines `WorkloadDef { name, freshness_slo, memory_limit, priority }` —
  note **no `max_parallelism` field exists yet**, contrary to what a
  literal reading of the roadmap might suggest is just "wiring". This field
  must be added.
- **`CREATE WORKLOAD` already exists but only parses two of four options.**
  `crates/rockstream-gateway/src/server.rs:6803` (`parse_create_workload`)
  parses `memory_limit` and `freshness_slo_ms` only; `priority` and
  `max_parallelism` are silently ignored (no `match` arm — falls into
  `_ => {}`). `handle_create_workload` (line 2864) calls
  `CatalogStubs::add_workload`, which is **in-memory only**
  (`crates/rockstream-gateway/src/catalog_stubs.rs:254` — plain `HashMap`,
  no `ShardDb` write, no restart durability). There is **no `ALTER
  WORKLOAD`, no `DROP WORKLOAD`, no `SHOW WORKLOAD STATUS`** dispatch arm
  anywhere in `server.rs`'s `dispatch_sync`.
- **`OVER_BUDGET_RELAXED` does not exist as a code symbol anywhere.**
  `crates/rockstream-types/src/view_lifecycle.rs`'s `ViewState` enum has
  only `Running | Paused | BackfillingFromEpoch(u64)`. The existing
  `workload_resource_usage_entries()` function
  (`catalog_stubs.rs:859-925`, shipped v0.45) computes a `degraded_reason`
  string and flips `slo_compliant = false` **for the read-only
  `SHOW RESOURCE USAGE` report** when `memory_bytes > memory_limit_bytes` —
  but this is purely an on-read computed annotation; it does **not**
  mutate any actual view lifecycle state. `OVER_BUDGET_RELAXED` must be
  added as a new `ViewState` variant and the transition into/out of it must
  be a real, persisted state change (driving `SHOW WORKLOAD STATUS` output
  directly, not recomputed from scratch each query), while the existing
  read-only `degraded_reason` heuristic in resource-usage reporting is left
  untouched (different, pre-existing, already-shipped surface).
- **A per-workload memory-accounting primitive already exists but is
  wired nowhere.** `crates/rockstream-types/src/state_budget.rs` has a
  fully-implemented, unit-tested `WorkloadBudget` (keyed by `WorkloadId`,
  atomic `try_acquire`/`release`, 80%/95% notice/warning thresholds) and
  `StateBudget::new_with_workload(...)` that nests an operator budget
  inside a workload budget and rejects/releases correctly when either is
  exceeded — this is **exactly** the "independently of (and nested inside)
  the existing global `state_budget_gb` floor" mechanism the Scope asks
  for. But grepping the whole workspace, `WorkloadBudget`/`WorkloadId` are
  referenced **only** inside `state_budget.rs` itself — no production code
  constructs or wires one. This version's job is to *wire* this
  already-correct primitive to real view/operator state accounting and to
  the `OVER_BUDGET_RELAXED` transition, not to redesign the budget
  arithmetic.
- **The v0.30 auto-tuner is itself only SimRuntime-validated, not wired
  into the live runtime.** Every non-test call site of `AutoTuner::new`/
  `AutoTuner::new_with_state` is in `crates/rockstream-sim/src/spike.rs` or
  `#[cfg(test)]` blocks — **zero** production call sites in
  `rockstream-runtime` or `rockstream-gateway`. `AutotunerConfig.
  max_parallelism` (default 32) is the ceiling `adjust_parallelism` clamps
  to (`auto_tuner.rs:142`). Consistent with the existing v0.30 precedent
  (algorithm proven correct in `SimRuntime`, not live-wired), this version
  adds the **per-workload cap** at the same SimRuntime-provable layer:
  extend `AutotunerConfig`/`AutoTuner` construction to accept an optional
  workload `max_parallelism` and clamp the effective ceiling to
  `min(cluster_config.max_parallelism, workload.max_parallelism)`. Full
  live-runtime wiring of the auto-tuner is *out of this version's scope*
  because it was never in scope for v0.30 either — extending that scope now
  would be a drive-by expansion the Ground Rules forbid ("make only changes
  this version requires").
- **No admission-control subsystem exists at all today.** Grepped for
  "admission" across `crates/` — no hits outside DESIGN.md prose. This is
  wholly new: a component that (a) gates `CREATE MATERIALIZED VIEW` /
  `CREATE WORKLOAD` requests that would push cluster or per-workload
  utilization over a threshold, and (b) under contention, pauses the
  lowest-priority workload's views first (reusing the existing
  `ViewState::Paused` variant — no new pause mechanism needed, just a new
  *trigger* for it).
- **The audit log is an existing file-backed JSONL log, already used by
  `create_view`/`create_workload`/`refresh_materialized_view`.**
  `crates/rockstream-control/src/audit.rs`'s `FileAuditLog::append()` is
  the established mechanism (`crates/rockstream-gateway/src/server.rs`
  lines ~2852-2858, 2882-2888, 2920-2925 already call it for those three
  actions). DESIGN.md §14.11 describes an idealized `control:
  audit/{ulid}` SlateDB-backed schema, but the codebase's actual,
  already-shipped precedent is the JSONL file log — this version follows
  that established precedent for quota/admission audit events rather than
  introducing a second, inconsistent audit mechanism (which would be a
  drive-by architectural change outside this version's two-pillar scope).
- **`CatalogType` (control-plane catalog key type byte) has no `Workload`
  variant.** `crates/rockstream-storage/src/keys.rs:512` enumerates
  `Pipeline | Source | View | Table | Schema | Connector | Index` (bytes
  `0x10`–`0x16`). A `Workload = 0x17` variant must be added for durable
  persistence, following the exact same `CatalogKeyEncoder::encode(...)` +
  `ShardDb` pattern `SchemaCatalog::register_view`/`load_all_views` already
  use for views (`crates/rockstream-sql/src/catalog.rs`).
- **`ViewStatus` (view_lifecycle.rs) already carries workload-inherited
  `freshness_slo_ms`/`memory_limit_bytes` and `workload_name`,** built in a
  prior version for `SHOW VIEW STATUS FOR NAMESPACE`. This version reuses
  `ViewStatus`/`ViewState` rather than inventing a parallel status type for
  `SHOW WORKLOAD STATUS`.

## 3. Vertical Slices

### Group A — Durable control-plane workload catalog

1. **A1 — `CatalogType::Workload` + `WorkloadCatalog`.** Add the `0x17`
   variant to `CatalogType` (`rockstream-storage/src/keys.rs`). Add a
   `WorkloadCatalog` type in `rockstream-sql` (or a new
   `rockstream-sql/src/workload_catalog.rs`) mirroring `SchemaCatalog`:
   `register_workload`/`load_all_workloads`/`update_workload`/
   `remove_workload`, all backed by `ShardDb` via
   `CatalogKeyEncoder::encode(CatalogType::Workload, namespace_id,
   object_id)`, JSON-serializing `WorkloadDef`. *Green test*: LFS test
   (`ShardDb::builder` over a `TempDir`) proving a registered workload
   survives a fresh `ShardDb` re-open (restart durability) with identical
   `WorkloadDef` fields; a MinIO variant of the same test
   (`#[ignore = "requires Docker / MinIO TestContainers"]`, named
   `..._minio_tc`, in the same test file per the existing
   `lfs_catalog.rs` convention) proving the same over a TestContainers
   MinIO bucket.
2. **A2 — Wire `CatalogStubs` to `WorkloadCatalog` for durability.**
   `add_workload`/`get_workload`/`list_workloads` in
   `catalog_stubs.rs:310-330` currently only touch the in-memory
   `HashMap`. Extend `CatalogStubs` to hold an optional
   `Arc<WorkloadCatalog>` and, when present, write-through on
   `add_workload` and load from it on `CatalogStubs::new`/startup — same
   dual-layer pattern (fast in-memory cache + durable backing store)
   already used for the view catalog's `SchemaCatalog`/`load_all_views`
   interplay with `CatalogStubs.views`. *Green test*: gateway integration
   test that creates a workload, restarts the gateway process's
   `CatalogStubs` (simulating a fresh boot against the same `ShardDb`
   path), and asserts `SHOW WORKLOAD STATUS` / `get_workload` return the
   identical definition.

### Group B — Full DDL surface

3. **B1 — Extend `parse_create_workload` for `PRIORITY` and
   `MAX_PARALLELISM`.** Add `max_parallelism: Option<u32>` to
   `WorkloadDef` (+ `with_max_parallelism` builder, +round-trip
   serde test, mirroring the existing `with_memory_limit`/
   `with_freshness_slo` pattern in `workload.rs`). Add `"priority"` and
   `"max_parallelism"` match arms to `parse_create_workload`
   (`server.rs:6828`), parsing `PRIORITY = HIGH|LOW|DEFAULT|<u8>` (reusing
   `WorkloadPriority::{HIGH,DEFAULT,LOW}` constants for the named forms)
   and `MAX_PARALLELISM = <u32>`. *Green test*: wire-protocol test issuing
   `CREATE WORKLOAD fast WITH (MEMORY_LIMIT=1048576, FRESHNESS_SLO_MS=500,
   PRIORITY=HIGH, MAX_PARALLELISM=8)` and asserting all four fields land
   correctly via `SHOW WORKLOAD STATUS` (B3).
4. **B2 — `ALTER WORKLOAD <name> SET (...)` and `DROP WORKLOAD <name>`.**
   New `handle_alter_workload`/`handle_drop_workload` in `server.rs`,
   dispatched from new `ql.starts_with("alter workload ")`/
   `ql.starts_with("drop workload ")` arms alongside the existing
   `create workload ` arm (`server.rs:1224-1226`). `ALTER` re-parses the
   `SET (...)` body with the same option-parsing logic as B1 and applies
   only the specified fields (existing fields left unchanged) via a new
   `CatalogStubs::update_workload`. `DROP` removes the workload
   (`CatalogStubs::remove_workload` + `WorkloadCatalog::remove_workload`)
   and returns `RS-1005 workload.not_found` if it has active view
   assignments... **decision needed on drop-with-assignments semantics**
   — resolved as: `DROP WORKLOAD` fails with a new distinct error
   (`RS-1007 workload.has_assigned_views`) if any view is still assigned,
   requiring the operator to reassign or drop those views first (safer
   default, consistent with the existing view-dependency-cycle rejection
   pattern already used for `CREATE VIEW`). Both actions call
   `FileAuditLog::append` (`workload.altered`/`workload.dropped`),
   matching the existing `create_workload` audit call. *Green test*:
   wire-protocol tests for successful alter (each of the 4 fields
   individually and combined), alter-of-nonexistent-workload error,
   successful drop, drop-with-assigned-view error, drop-then-recreate.
5. **B3 — `SHOW WORKLOAD STATUS` / `SHOW WORKLOAD STATUS FOR <name>`.**
   New dispatch arm returning one row per workload:
   `workload_name, priority, max_parallelism, memory_limit_bytes,
   freshness_slo_ms, view_count, over_budget_relaxed_view_count,
   paused_view_count` — reusing the existing `CatalogResponse::Rows` +
   `catalog_resp_to_response` plumbing that `SHOW RESOURCE USAGE`
   (`server.rs:1819-1859`) already establishes as the template. *Green
   test*: wire-protocol test asserting column values match the underlying
   `CatalogStubs` state exactly (same "both paths read the same
   underlying data" style as v0.45's `resource_usage_show_matches_
   catalog_table`).

### Group C — Per-workload `MEMORY_LIMIT` enforcement → `OVER_BUDGET_RELAXED`

6. **C1 — `ViewState::OverBudgetRelaxed` variant.** Add to
   `view_lifecycle.rs`'s `ViewState` enum (with `Display` arm
   `"OVER_BUDGET_RELAXED"`, `is_over_budget_relaxed()` predicate). *Green
   test*: enum round-trip/serialize/predicate tests matching the existing
   `view_state_*` test style in the same file.
7. **C2 — Wire `WorkloadBudget` into real per-view state accounting and
   the `OverBudgetRelaxed` transition.** When a view assigned to a
   workload with a `MEMORY_LIMIT` accumulates state bytes (existing
   `op_state_bytes`/`pipeline_state_bytes` metrics plumbing in
   `catalog_stubs.rs`), route the acquisition through a
   `StateBudget::new_with_workload(...)` backed by a per-workload
   `WorkloadBudget` (constructed once per workload from its
   `memory_limit`, looked up/created lazily in `CatalogStubs`). On
   `try_acquire` failure attributable to the **workload** budget
   specifically (not the view's own/global budget), transition that
   view's `ViewState` to `OverBudgetRelaxed` and record an
   `AuditEvent::now("system", "workload.memory_limit_exceeded",
   view_name)` via `FileAuditLog`. On subsequent release bringing usage
   back under the limit, transition back to `Running`. Critically, this
   path is independent of the existing global `state_budget_gb`
   (`read_state_budget()`/`set_state_budget()` in `metrics.rs`) — a view
   can breach its workload's `MEMORY_LIMIT` while the cluster-wide budget
   still has headroom, and vice versa; both checks run, either can
   trigger a transition, and the workload-level `OverBudgetRelaxed` must
   not be conflated with the existing global-budget behavior. *Green
   test*: unit test proving (a) a view within its workload's
   `MEMORY_LIMIT` and within the global `state_budget_gb` stays `Running`;
   (b) a view whose *workload* aggregate exceeds `MEMORY_LIMIT` while the
   global budget still has headroom transitions to `OverBudgetRelaxed`
   (this is the literal wording of Proof claim P3); (c) releasing state
   back under the workload limit returns it to `Running`; (d) the
   transition and reversion are both audited (P5).
8. **C3 — Surface in `SHOW WORKLOAD STATUS`.** B3's query includes the
   count of views currently `OverBudgetRelaxed` per workload, satisfying
   P4 directly.

### Group D — Per-workload `MAX_PARALLELISM` cap on the v0.30 auto-tuner

9. **D1 — Workload-scoped `AutotunerConfig` clamp.** Add a constructor
   (e.g. `AutoTuner::new_for_workload(config: AutotunerConfig, workload:
   &WorkloadDef)`) that clamps the effective `max_parallelism` to
   `min(config.max_parallelism, workload.max_parallelism.unwrap_or(u32::MAX))`
   before storing it, so `adjust_parallelism`'s existing
   `.min(self.config.max_parallelism)` clamp (`auto_tuner.rs:142`)
   transparently respects the tighter workload cap with **zero changes**
   to `adjust_parallelism`'s own logic (proving the existing algorithm is
   reused unchanged, per the Ground Rules' "no drive-by refactors"). *Green
   test*: SimRuntime-style unit test (co-located with the existing
   `auto_tuner.rs` `#[cfg(test)]` module, matching its deterministic-trace
   assertion style) driving `adjust_parallelism` with a workload capped at
   `MAX_PARALLELISM=4` against a cluster `AutotunerConfig::default()`
   (cluster ceiling 32) under sustained high `epoch_ms_p95`, asserting
   `current_parallelism` never exceeds 4 even though the cluster-wide
   config would otherwise allow scaling to 32 — this is Proof claim P8,
   literal wording ("caps ... on a per-workload basis").

### Group E — `PRIORITY`-driven admission control (§14.16) — new subsystem

10. **E1 — `AdmissionController`.** New type (likely
    `rockstream-gateway/src/admission.rs` or `rockstream-control`) that,
    given the current cluster/workload utilization (via existing
    `read_state_budget()`/`WorkloadBudget::current_bytes()`/existing
    freshness-lag metrics) and a requested action (new `CREATE MATERIALIZED
    VIEW`, new `CREATE WORKLOAD`, or a periodic contention check), decides:
    (a) whether to admit the request outright, (b) whether to reject it
    with a distinct new error code (reserve the next free code after the
    existing highest-numbered code in the connector-occupied `RS-4xxx`
    range is **not** reused — this version allocates fresh, currently-
    unused codes; exact numbers finalized in Phase 3 against
    `error_code.rs`'s live registry to guarantee CI's uniqueness check
    passes), or (c) which lower-`PRIORITY` workload's views to pause
    (reusing `ViewState::Paused` — no new pause mechanism). Every decision
    (admit/reject/pause) calls `FileAuditLog::append` with action
    `admission_control.paused`/`admission_control.rejected` (P6).
11. **E2 — Contention trigger wiring.** The admission controller's
    "pause under contention" check runs whenever a workload's aggregate
    `WorkloadBudget` utilization crosses a threshold (reusing the
    existing 80%/95% notice/warning percentages already computed inside
    `WorkloadBudget::try_acquire`/`release` in `state_budget.rs`, rather
    than inventing new thresholds) **and** a higher-priority workload is
    concurrently requesting capacity. Ties are broken by `WorkloadPriority`
    ordering (lower value = higher priority, already `Ord`-derived on
    `WorkloadPriority`). *Green test*: covered by the coordination slice
    below (F1), since this is inherently a multi-workload, contention-
    dependent behavior best proven under a seeded scenario rather than an
    isolated unit test.

### Group F — Two-workload contention scenario (the roadmap's literal Proof scenario)

12. **F1 — Seeded `SimRuntime` HIGH-vs-LOW contention test.** New test
    (e.g. `crates/rockstream-sim/tests/workload_admission_control.rs`,
    matching the `control_sim.rs`/`buggify_init(seed)` style already
    established): construct two workloads (`PRIORITY=HIGH`,
    `PRIORITY=LOW`), each with views assigned, on a cluster whose
    aggregate `WorkloadBudget`/global `state_budget_gb` is deliberately
    sized below the combined demand of both workloads' state growth.
    Drive simulated state growth on both workloads' views concurrently
    (with `buggify!("admission.contention_timing", p)` jittering the
    order of growth events, per the Ground Rules' seeded-fault-injection
    requirement for new coordination paths) and assert: (a) the
    low-priority workload's views transition to `Paused` and/or
    `OverBudgetRelaxed` (P1, literal wording); (b) the high-priority
    workload's views remain `Running` and their tracked freshness lag
    stays within their `FRESHNESS_SLO` throughout (P2, literal wording);
    (c) every pause/quota-transition event appears in the audit log
    (P5/P6); (d) re-running with a different seed produces the same
    qualitative outcome (HIGH always wins contention over LOW) —
    determinism check consistent with this codebase's existing
    `buggify`/seeded-replay conventions.

## 5. Durability Slices (new durability paths → SlateDB LFS + MinIO test, both)

| New durability path | LFS test | MinIO test |
|---|---|---|
| Durable workload catalog (`CatalogType::Workload`, A1) | ✅ restart-survival round-trip test | ✅ same, over TestContainers MinIO (`register_workload_survives_restart_minio_tc`, `#[ignore]`-gated per existing convention) |

No other slice introduces a new commit/replay/checkpoint/compaction/WAL
path. Groups B (DDL dispatch), C (in-memory budget/state-transition logic
— `WorkloadBudget` is a pure in-process atomic counter, not a durability
path), D (config clamp), E (admission decisions, in-process) touch no new
object-store/SlateDB surface beyond what A1/A2 already cover.

## 6. Coordination Slices (new distributed-coordination paths → seeded SimRuntime + buggify)

Only **E/F** (priority-driven admission control under contention) is a new
distributed-coordination path — this codebase has never had an admission-
control subsystem before this version. Per Ground Rule 5, **F1** is the
required seeded `SimRuntime` + `buggify!()` test, and it is the primary
vehicle proving Proof claims P1 and P2 (the roadmap's literal two-workload
contention scenario). Group D's per-workload parallelism cap (D1) is a pure
config-clamp on an existing, already-SimRuntime-proven algorithm — no new
coordination path — so it gets a deterministic unit test co-located with
the existing `auto_tuner.rs` test module, not a separate seeded scenario.
