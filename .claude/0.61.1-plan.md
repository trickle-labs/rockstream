# v0.61.1 Plan — External Performance Baseline

**Version**: v0.61.1  
**Phase**: Phase 2 — Plan  
**Target Scope**: Establish a reproducible, external, measured standalone performance baseline using release binaries through public ingestion and query interfaces. Complete measured workloads gate performance changes.

## Scope and Boundary

Roadmap reference (`ROADMAP.md` §5.2: `v0.61.1: External performance baseline`):
> **Focus**: Extend the R1 runner and its workload contract. Version new profiles without overwriting frozen evidence. Use release binaries through public ingestion and query interfaces. Treat `sample_reference_run` as a qualification-logic fixture only.
> **Required Proof**: Measure read latency, durable commit latency, and event-to-committed-result freshness separately. Set explicit p99 targets, offered load, and regression tolerances before comparing candidates. Timestamp events at scheduled generation and include generator delay, backpressure, errors, and timeouts. Keep the offered-load schedule independent of completion so overload remains visible.
> **Required Matrix**: Account for 1K/100K/10M one-key updates, 1 and 20 compatible views, 1/2/4/8 workers, concurrent ingestion and queries, beyond-RAM/compaction/restart, and overload/worker-loss/migration. Compare complete result multisets against an independent oracle at the relevant committed epoch. Reject missing required matrix cells, inactive worker processes, and synthetic measurements. Record unavailable cases as blocked, with an owning milestone. Local performance establishes local performance only; cloud cost claims require a measured deployment with dated prices.

Committed implementation plan reference: `docs/implementation-plans/v0.61.1.md`.  
Shared implementation and evidence rules: `docs/implementation-plans/README.md`.

v0.61.1 establishes the external performance baseline infrastructure, contract freezing, metric decoupling, matrix accounting, and standalone measurement:

1. **Versioned Workload Profile & Frozen Contract Contract**:
   - Establish a new versioned profile (`benchmarks/r1-local/profile-v0611.toml` / `MBP-M5Pro-48GB-v2`) and frozen thresholds (`benchmarks/r1-local/thresholds-v0611.toml`) without modifying or overwriting prior frozen evidence (`MBP-M5Pro-48GB-v1`).
   - Freeze payload size (128 bytes), state size, view count (1 and 20), durability mode (`Durable`), offered-load schedule, separate p99 latency targets, regression tolerances, run duration, repetition policy (5 alternating A/B pairs), and sustainable-throughput rule before measurement.
   - Define the allowed write-amplification variation for "approximately constant" from the workload contract, not post-hoc after seeing results.
   - Record hardware environment, storage backend, Git commit revision, binary SHA-256 digests, and exact command invocations.

2. **Independent Offered-Load Schedule & Metric Decoupling**:
   - Drive release processes exclusively through public ingestion and query interfaces (pgwire TCP).
   - Timestamp scheduled event generation and enforce offered load on an independent clock, completely decoupled from response completion.
   - Bound generator queues (max 10,000 pending events); record drops, backpressure, generator delay, errors, timeouts, and unfinished requests rather than silently throttling offered load.
   - Measure and report three separate p99 metrics:
     - **Read latency p99**: Client query execution round-trip time.
     - **Durable commit latency p99**: Time from transaction submission to durable storage commit acknowledgment.
     - **Event-to-correct-committed-result freshness p99**: Time from scheduled event timestamp to correct committed output multiset visibility.

3. **Complete Result Multiset Comparison & Adversarial Oracle Validation**:
   - Query complete result multisets from the gateway and compare with an independent oracle (SQLite reference engine) at the relevant committed epoch.
   - Enforce that a visibility marker or single-row probe alone is insufficient to establish freshness.
   - Adversarial oracle validation suite: validate that the oracle and harness reject deliberate wrong-value, duplicate-row, missing-row, and stale-epoch results.

4. **Experiment Matrix Accounting & Standalone Measurements**:
   - Account for every cell in the required 6-area experiment matrix:
     1. One-key updates at 1K, 100K, and 10M groups: measure runnable standalone cells against frozen state-write rule; report lookup cost separately; assign unavailable large-state cells to v0.67.1 with concrete blocker.
     2. 1 and 20 compatible views: measure runnable standalone cells; assign shared-execution benefit comparison to v0.67 with concrete blocker.
     3. 1, 2, 4, and 8 workers: measure standalone 1-worker cell; assign 2, 4, 8 distributed workers to v0.67 with host resource limits identified.
     4. Concurrent ingestion and queries: measure mixed standalone load; report separate read-p99 and freshness results against frozen targets.
     5. Beyond-RAM, compaction, and restart: measure runnable standalone compaction and restart cells; assign beyond-RAM cells to v0.67.1.
     6. Overload, worker loss, and migration: measure standalone overload with explicit pressure, exact results, and recovery timing; assign worker loss to v0.67 and migration to v0.68.
   - Observe actual worker process PIDs and activity via OS telemetry; reject inactive or fake workers.
   - Do not score a partially populated required matrix as complete; unmeasured cells must carry explicit blockers and milestone owners.

5. **Negative Qualification Harness Integrity Tests**:
   - Negative test fixtures proving that qualification fails if:
     - Any required matrix cell is missing without an owning milestone and concrete blocker.
     - Worker PIDs are inactive, fabricated, or mock-based.
     - Synthetic samples (`sample_reference_run`) are submitted in place of release binary runs.
     - Oracle multiset comparison detects value, cardinality, or epoch discrepancies.
     - Digest or binary checksum verification fails.

6. **Comprehensive Metric Collection & Cost Model Reporting**:
   - Record state writes, intermediate rows, network bytes, and object-store requests per committed input change.
   - Record RSS, queue age, control-node load, physical flushes per logical epoch, and repeated-run variation (CV <= 0.15 across 5 pairs).
   - Report cost per million changes formula:
     `total hourly infrastructure cost * 1_000_000 / (sustainable committed changes per second * 3600)`.
   - Explicitly distinguish local developer run metrics from cloud production cost claims.

### Non-Negotiable Ground Rules

- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag on the same `rockstream` binary. `main` remains runnable through it.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters, asserted by test.
- Unbounded in-memory accumulation is never acceptable. Every new buffer, batch, or result accumulator has a named upper bound and error/backpressure path.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass. Do not use `--no-verify`. Fix root causes.
- Make only changes this version requires. No speculative features outside IVM engine + Postgres wire layer.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals.**
