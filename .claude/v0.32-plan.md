## Vertical Slices

### S1 — Catalog & DDL plumbing

**What:** Add `CatalogType::Index` to the key encoder; add `IndexEntry` struct
(name, table, index_cols, pk_cols, optional where_pred, state:
`IndexState { Building | Ready }`); register error codes RS-2014 / RS-2015 /
RS-2016 in `rockstream-errors`; parse `CREATE INDEX`, `DROP INDEX`, and
`REBUILD INDEX` SQL in the SQL frontend.

**Exit test (green):** Unit test: `CREATE INDEX` statement parses without
error; `IndexEntry` round-trips through `SchemaCatalog` (serialize/deserialize
with LFS backend); RS-2014/RS-2015/RS-2016 codes exist in the error registry
and return actionable `next_steps`.

### S2 — `PlanNode::IndexArrange` and lowering

**What:** Add `PlanNode::IndexArrange { input: Box<PlanNode>, index_cols:
Vec<usize>, pk_cols: Vec<usize>, filter_pred: Option<Expr> }` to
`rockstream-plan`. Lower `CREATE INDEX` DDL → `IndexArrange → ViewSink` plan
(internally named `__idx_<name>`). The arrangement key is
`(index_col_bytes, pk_bytes)` → `row_bytes`, stored in `view_output/__idx_<name>/`
via point writes only (no range deletion). `SHOW VIEWS` must not list
`__idx_*` names.

**Exit test (green):** Unit test: `PlanNode::IndexArrange` round-trips through
serde; a lowered `CREATE INDEX` plan stores the correct `IndexArrange` node;
`SHOW VIEWS` output excludes `__idx_*` names.

### S3 — `IndexArrangeOp` incremental operator (oracle property test pre-committed)

**Oracle pre-commitment:** Before writing the operator, commit the test:
`incremental_index_arrange_equals_batch` — runs `IndexArrangeOp` over a random
sequence of insert/update/delete Z-set deltas; verifies the resulting
`(index_key, pk) → row` arrangement equals a batch scan of the accumulated
base-table state, sorted and arranged identically.

**What:** Implement `IndexArrangeOp` in `rockstream-ops`:
- Accepts Z-set deltas; for each `(row, weight)` extracts `(index_cols, pk_cols, row_bytes)`.
- Point-writes `(index_key_bytes ++ pk_bytes) → row_bytes` to `view_output/__idx_<name>/`.
- On delete (negative weight) performs a point-delete (no range delete; test asserts this).
- Fill-level metric: `index_arrange_row_count` gauge, upper-bounded by `max_arrangement_rows` config.
- Backpressure: existing credit system starves the source if fill exceeds bound.

**Exit test (green):** Oracle property test passes ≥100k scenarios.

---

### S4 — Online backfill: `BUILDING → READY` transition (LFS + MinIO tests pre-committed)

**Durability pre-commitment:**
- LFS test: `index_backfill_lfs_crash_restart` — backfill in-progress, crash mid-way (kill via SimRuntime fault); on restart the index resumes from its persisted frontier without duplicating or skipping rows; final arrangement is bit-identical to a full backfill without crash.
- MinIO test: `index_backfill_minio_tc` — same path against a TestContainers MinIO instance (skipped if Docker unavailable).

**What:** When `CREATE INDEX` is processed, the index state is `BUILDING`.
The IVM engine runs `IndexArrangeOp` in snapshot-bootstrap mode (one-shot
scan of base-table `view_output/` checkpoint emitting each row at weight `+1`).
Live deltas arriving during backfill are applied normally after the snapshot
epochs complete. Once the index frontier ≥ base-table frontier, the state
transitions to `READY` and is written to the catalog. The planner does not use
`BUILDING` indexes; a query that touches a `BUILDING` index logs RS-2014 as an
audit event (not surfaced to the caller).

**Exit test (green):** LFS crash-restart test passes; `BUILDING → READY`
transition fires exactly once; post-transition arrangement is bit-identical to
a single-pass batch arrangement.

### S5 — Planner index-selection and `EXPLAIN` output

**What:** In `rockstream-sql`'s query optimizer, add an index-scan rewrite
rule:
1. Detect `WHERE col = ?` (exact equality) or `WHERE col = ? AND ...` patterns
   where `col` matches an index column.
2. If an `READY` index exists, estimated selectivity < `index_prefer_selectivity_threshold`
   (default 0.01), and the index frontier satisfies the query's freshness token
   → rewrite to `IndexScanPath(index_name, key_value)`.
3. If index is `BUILDING`: fall back to shard scan, emit RS-2014 audit event.
4. If index frontier lags base table by > `index_max_lag_ms`: fall back, emit
   RS-2015 audit event.
5. If index name conflicts at `CREATE INDEX` time: return RS-2016 error.

`EXPLAIN` emits `index_scan(<index_name>, <col> = <val>)` or `shard_scan(<table>)`
and the selectivity estimate used.

**Exit test (green):** Unit tests:
- `planner_chooses_index_for_selective_predicate`: assert `EXPLAIN` output contains `index_scan(...)`.
- `planner_falls_back_for_non_selective_predicate`: selectivity ≥ threshold → `shard_scan(...)`.
- `planner_falls_back_for_building_index`: RS-2014 audit event emitted.
- `planner_falls_back_for_lagging_index`: RS-2015 audit event emitted.
- `create_index_name_conflict`: RS-2016 error returned.

### S6 — Point-lookup execution path (LFS + MinIO + TC tests pre-committed)

**Durability pre-commitment:**
- LFS test: `index_point_lookup_lfs` — create index on LFS-backed shard, run
  100 point lookups on indexed column; assert all return correct rows.
- MinIO test: `index_point_lookup_minio_tc` — same against TestContainers MinIO
  (skipped if Docker unavailable).

**What:** Gateway `ViewReader` gains an `IndexScanStrategy` that does a bounded
prefix scan on `view_output/__idx_<name>/` keyed by `index_key_bytes`.
Returns matching rows without scanning unrelated shards.

**Exit test (green):** LFS point-lookup test; correctness for multi-row
matches (multiple PKs with same index key value).

### S7 — Partial indexes

**What:** `CREATE INDEX active_orders ON orders (customer_id) WHERE status = 'active'`
stores `filter_pred` in `IndexEntry`; `IndexArrangeOp` applies the filter before
the arrange step; planner uses the partial index only when the query's `WHERE`
clause implies the index predicate (i.e. query predicate ⊇ index predicate).

**Exit test (green):** Unit test `partial_index_only_indexes_matching_rows`:
insert rows with `status = 'active'` and `status = 'inactive'`; index only
contains active rows; planner uses partial index for matching query, falls back
for non-matching query.

---

### S8 — `DROP INDEX` and `REBUILD INDEX`

**What:**
- `DROP INDEX`: removes `IndexEntry` from catalog; tears down `IndexArrangeOp`;
  arrangement state is GC'd by frontier-aware compaction filter (no range
  delete; compaction filter removes entries after index frontier is closed).
- `REBUILD INDEX`: transitions state back to `BUILDING` and re-runs backfill from
  current base-table checkpoint.

**Exit test (green):**
- `drop_index_removes_catalog_entry_and_state`: after drop, SHOW INDEX returns
  nothing; subsequent query uses shard scan.
- `rebuild_index_produces_same_arrangement_as_create`: rebuild from checkpoint;
  final arrangement is bit-identical to a fresh CREATE INDEX.

---

### S9 — Index state budget and `EXPLAIN INCREMENTAL ESTIMATE`

**What:**
- Index arrangement state bytes count against `state_budget_gb` quota.
- `EXPLAIN INCREMENTAL ESTIMATE` reports projected index state size.
- `rockstream.views` system table rows with `view_type = 'INDEX'` include
  `state_bytes` and `frontier_lag_ms` columns.

**Exit test (green):** Unit test `explain_estimate_reports_index_state_size`:
assert EXPLAIN output includes `estimated_index_state_bytes` for a table with
known row count and column cardinality.

### S10 — End-to-end single-digit-ms point lookup proof (TC + LFS + MinIO)

**What:** End-to-end TestContainers integration test:
1. Start RockStream cluster, create base table, insert 1M rows (via COPY).
2. `CREATE INDEX idx ON t (customer_id)` — wait for READY.
3. Run 200 concurrent point lookups `WHERE customer_id = ?` (varied keys).
4. Assert p99 latency < 10 ms.
5. Verify `EXPLAIN` shows `index_scan(idx, customer_id = ?)`.

LFS variant: 100k rows, p99 < 10 ms in-process (no network).
MinIO variant: same as LFS but against TestContainers MinIO (skipped if Docker
unavailable).

**Exit test (green):** `proof_secondary_index_point_lookup_under_10ms_p99` passes.
