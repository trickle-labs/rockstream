# v0.46 Plan — Online Shard Migration & Elasticity

Scope (NEW_ROADMAP.md v0.46, Phase 13): model-check the shard-migration
protocol in FizzBee before any Rust code (`formal/m6_shard_migration.fizz`,
binding pre-implementation rule from v0.18); implement DESIGN.md
§10.1–§10.4's full migration state machine (`PLANNED → SNAPSHOTTING →
COPYING → DUAL_WRITING → CATCHING_UP → FENCING_OLD → CUTOVER → VERIFYING →
GC_ELIGIBLE → DONE`, with per-state timeout budgets and `ABORTED` rollback)
for online shard add/remove; implement §10.7's worker-drain protocol
(`DRAINING → DECOMMISSIONED`); close the Phase 4 real-network exit-criteria
waiver with a real ≥4-host TC cluster test.

## 2. Vertical Slices

Each slice ends in a green test before the next begins.

**0. S0 — `formal/m6_shard_migration.fizz` authored and green (binding
   pre-implementation gate; FIZZBEE_TEST_PLAN.md §4.6 names this as a
   required v0.46 deliverable, including the §3.7-style mapping rows and
   role/action write-up).**
   Roles (per `formal/conventions.md`): `Bucket` (ghost/logical, folded
   into `Shard` state — no separate role needed since buckets are only
   ever referenced as a set owned by a `Shard`, per §7.1's "buckets, not
   keys, are the unit of migration"), `Shard` (×`NUM_SHARDS ≤ 3`, donor and
   recipient are just two instances), `ControlPlane` (owns
   `migration_state`, the `bucket_map_version`, and issues fencing epochs —
   composed with the existing M4 self-fencing predicate rather than
   re-modeling it), `Consumer` (ghost downstream frontier tracker for
   `GC_ELIGIBLE` gating). State-space bounds per conventions.md
   (`NUM_WORKERS ≤ 3`, `NUM_SHARDS ≤ 3`, `MAX_EPOCH ≤ 3`,
   `MAX_CHECKPOINT ≤ 2`); the 10-state machine plus `ABORTED` is modeled as
   an explicit enum with guarded transitions matching the DESIGN.md §10.2
   table exactly (no state is collapsed — `GC_ELIGIBLE` must stay distinct
   from `DONE` to make M6-S3 checkable as a real precondition, not an
   already-satisfied one).
   Invariants: **M6-S1** (safety) — at most one shard is ever authoritative
   for a given bucket at any committed epoch (no dual-writer window); a
   bucket is authoritative on the donor for every state through
   `FENCING_OLD` and on the recipient from `CUTOVER` onward, with no state
   where both or neither claim authority. **M6-S2** (safety) — every write
   accepted during `DUAL_WRITING` is present in the recipient's state by
   `CATCHING_UP`'s exit (no lost writes across `DUAL_WRITING`→`CUTOVER`).
   **M6-S3** (safety) — `migration_state = GC_ELIGIBLE` is never entered
   while the ghost `consumer_frontier < cutover_epoch`. **M6-L1**
   (liveness, `liveness: nondeterministic`) — from any non-`DONE`,
   non-`ABORTED` state, the model always eventually reaches `DONE` or
   `ABORTED` (no stuck migration). **COV-M6** — `exists` assertions that
   the model actually reaches `DUAL_WRITING`, `ABORTED` (from at least two
   different pre-abort states, matching the "kill mid-`DUAL_WRITING`
   *and* mid-`CUTOVER`" proof claim), and `GC_ELIGIBLE`/`DONE`.
   Test: `make verify` green in CI; `fizz formal/m6_shard_migration.fizz`
   passes locally at CI-fast bounds. Any counterexample is archived in
   `formal/findings.md` and replayed as a permanent seeded `SimRuntime`
   regression test in Slice 6 below (per the ground rules — this is not
   optional if the checker finds one).

**1. Durable migration record type + store.**
   New `rockstream_types::migration::{MigrationState, MigrationRecord,
   BucketSet}` (mirrors the existing `rockstream_types::lease::ShardLease`
   shape) and a new `rockstream_control::migration::MigrationPersistentStore`
   (mirrors `ShardPersistentStore`/`RaftPersistentStore`'s
   load/save-under-a-versioned-key pattern) persisting one record per
   migration under `topology/migration/{migration_id}` in the control
   catalog's object-store-backed storage. Each of the 10
   states + `ABORTED` round-trips through (de)serialization; transitions
   are idempotent (re-applying the same transition to an already-updated
   record is a no-op, not an error) and each transition emits an audit
   event via the existing `rockstream_control::audit` module.
   Test: `migration_record_tests.rs` — unit tests for every legal
   transition, idempotent re-application, and illegal-transition rejection
   (e.g. `PLANNED → CUTOVER` directly is rejected).

**2. `MigrationCoordinator`: `PLANNED → SNAPSHOTTING → COPYING`.**
   New `rockstream_control::migration::MigrationCoordinator` drives
   `PLANNED` (compute donor/recipient shards, bucket set, source frontier
   `F_plan`, target `bucket_map_version`) → `SNAPSHOTTING` (reuses the
   existing `CheckpointCoordinator` to pin a `SlateDB` checkpoint on every
   donor shard at `F_plan`) → `COPYING` (recipient ingests via the existing
   `ShardReader`/`DbReader`, verified by comparing recipient arrangement
   state against the donor checkpoint). Each state's default timeout
   budget from the DESIGN.md §10.2 table is enforced; exceeding it emits
   `RS-1030 migration.state_timeout` and transitions to `ABORTED`.
   Test: `shard_migration_state_machine_tests.rs` —
   `snapshotting_pins_donor_checkpoint_at_f_plan`,
   `copying_recipient_matches_donor_checkpoint`,
   `state_timeout_transitions_to_aborted`.

**3. `DUAL_WRITING → CATCHING_UP → FENCING_OLD`: dual-write routing and
   fencing.**
   `bucket_map_version` bump routes new writes for migrating buckets to
   *both* donor and recipient through the exchange
   (`rockstream-runtime`'s exchange receiver already rejects stale
   `bucket_map_version` frames per §7.1 — this slice adds the "route to
   both" fan-out for the migrating bucket set specifically, gated by
   migration state, not a general dual-write mode). `CATCHING_UP` tracks
   recipient frontier catch-up against `cutover_lag_budget` (default
   100 ms). `FENCING_OLD` bumps `bucket_map_version` again via the
   existing `ShardManager` fencing-token mechanism so old-version writes
   are rejected at the receiver.
   Test: `dual_write_zero_loss_tests.rs` — a synthetic write stream is
   replayed through a real donor+recipient pair; asserts every write
   accepted during `DUAL_WRITING` is present in recipient state by
   `CATCHING_UP`'s exit (this is the oracle proof for M6-S2, not just the
   FizzBee model — `incremental (migrating) == batch (non-migrating)`
   final state).

**4. `CUTOVER → VERIFYING → GC_ELIGIBLE → DONE`: cutover, scan-compare
   verification, and frontier-gated cleanup.**
   `CUTOVER` waits for every reader/exchange-receiver/gateway to observe
   the new `bucket_map_version` (bounded by its 60 s timeout).
   `VERIFYING` runs a full scan-compare (bounded by `verify_sample_rate`,
   default 1.0 for buckets ≤ 1 GB) between donor and recipient state at
   the cutover epoch; any divergence aborts back to `DUAL_WRITING` per
   DESIGN.md's rollback rule. `GC_ELIGIBLE` is gated on the migration's
   consumer frontier (reusing the existing `FrontierAggregator`'s
   per-operator input-frontier tracking, minimum over every downstream
   operator reading the migrated buckets) passing the cutover epoch —
   **no donor cleanup, scan-and-delete or otherwise, may start before
   this**, satisfying the "no SlateDB range-delete dependency" ground
   rule (cleanup here is bucket-key-prefix scan-and-delete, never a range
   API). `DONE` closes the record and moves it to a history keyspace.
   Test: `shard_migration_state_machine_tests.rs` (continued) —
   `verifying_scan_compare_detects_divergence_and_aborts`,
   `gc_eligible_blocked_until_consumer_frontier_passes_cutover`,
   `done_cleanup_is_scan_and_delete_never_range_delete` (asserts the
   cleanup call site only ever issues point/prefix deletes, grepped
   against the `SlateDB` API surface used).

**5. Worker-drain protocol wiring (§10.7): `DRAINING → DECOMMISSIONED`.**
   Wires up the existing-but-dead `WorkerLifecycleState::Draining`/
   `BeginDrain`/`Decommissioned` types for real: `ControlService` handles
   an operator-initiated drain request by marking the worker `DRAINING`
   (no new shard assignments — `PlacementAlgorithm`/`ShardScheduler`
   already skip non-`Active` workers structurally once this state is
   threaded through `TopologyCatalog`) and enqueuing a Slice 2–4 migration
   for every shard the worker holds. Once `shards_remaining == 0`, the
   worker transitions to `Decommissioned`. Corrects the stale "(v0.38
   drain protocol)" doc comment in `topology.rs` to reference this
   version.
   Test: `worker_drain_tests.rs` — `draining_worker_receives_no_new_shards`,
   `drain_completes_after_all_shards_migrate`,
   `decommissioned_worker_removed_from_topology_after_grace_period`.

**6. Coordination fault-injection: kill donor mid-`DUAL_WRITING` and
   mid-`CUTOVER`.**
   `SimRuntime` seeded tests (per Coordination Slices below) that inject a
   donor-process kill at each of these two points and assert the
   migration recovers to either `ABORTED` (with the prior
   `bucket_map_version` restored and no partial recipient state left
   dangling) or a completed `DONE` — never a stuck `migration_state` or a
   bucket simultaneously claimed authoritative by both donor and
   recipient. If S0's FizzBee run surfaces a counterexample, its exact
   schedule is replayed here as a permanent regression seed.
   Test: `shard_migration_sim_tests.rs` —
   `donor_killed_mid_dual_writing_recovers_sim`,
   `donor_killed_mid_cutover_recovers_sim`.

**7. Real ≥4-host cluster TC test: live migration, zero loss.**
   Extends `crates/rockstream-sim/tests/control_plane_ha_tests.rs`'s `tc`
   module pattern (real `rockstream` binary containers, real Docker
   network) to a 4-container topology: 1 control node + 1 donor worker +
   1 recipient worker + 1 gateway/driver host issuing continuous
   reads/writes. Migrates a live bucket range from donor to recipient;
   a scan comparing donor/recipient state at cutover confirms zero reads
   or writes lost. This is the real-network test that closes the Phase 4
   waiver (§1 above) — its pass is the specific evidence cited in the
   sign-off for "the previously-waived Phase 4 real-network commitment is
   marked closed."
   Test: `shard_migration_tc_tests.rs::live_migration_zero_loss_tc`.

**8. Real TC fault-injection drills: donor kill mid-migration, worker
   drain zero-downtime.**
   Same 4-host TC cluster: (a) kills the donor container mid-`DUAL_WRITING`
   and, in a separate run, mid-`CUTOVER`, asserting the same
   `ABORTED`-or-`DONE` recovery as Slice 6 but against real processes and a
   real network, not simulation; (b) `rockstream cluster workers drain
   <id>` (new CLI stub, ahead of the full v0.55 admin CLI surface) against
   a worker holding live shards, asserting the drain completes with zero
   shard downtime (continuous read/write driver observes no gap).
   Test: `shard_migration_tc_tests.rs::donor_killed_mid_dual_writing_tc`,
   `::donor_killed_mid_cutover_tc`,
   `worker_drain_tc_tests.rs::drain_completes_zero_downtime_tc`.

**9. Documentation and roadmap closure.**
   `FIZZBEE_TEST_PLAN.md` §4.6 gains M6's detailed role/action write-up and
   §3.7 mapping rows (matching the M1–M5/M7 precedent); its §4.7 summary
   table row for Phase 13 is updated from "pending" to done.
   `NEW_ROADMAP.md`'s v0.46 row status is set to `✅ Done`. This slice has
   no new test of its own — it is verified by a human diff read at
   sign-off, per the Common Definition of Done's documentation-accuracy
   precedent (v0.45.5).

## 4. Durability Slices

New durable paths introduced this version, each requiring both an LFS and
a MinIO (S3, TestContainers) test:

1. **`MigrationPersistentStore`** (`topology/migration/{migration_id}`,
   Slice 1) — did not exist before this version.
   - LFS test: `migration_record_durability_tests.rs::
     migration_record_survives_restart_lfs` — a migration record at
     `DUAL_WRITING` "restarts" (fresh store instance, same on-disk
     directory) and recovers identical state.
   - MinIO test: `migration_record_durability_tests.rs::
     migration_record_survives_restart_minio_tc` — same assertion against
     a real MinIO container, mirroring
     `raft_state_durability_tests.rs`'s established pattern.

2. **Worker lifecycle `DRAINING`/`DECOMMISSIONED` state**, once persisted
   as part of Slice 5 (today's `TopologyCatalog` is in-memory-only; this
   version makes the drain state durable so a control-plane restart
   mid-drain doesn't silently reset a draining worker back to `Active`).
   - LFS test: `worker_drain_durability_tests.rs::
     draining_state_survives_restart_lfs`.
   - MinIO test: `worker_drain_durability_tests.rs::
     draining_state_survives_restart_minio_tc`.

No other new durable state is introduced (checkpoint/`DbReader` reuse
existing, already-tested durability paths from v0.20/v0.43).

## 5. Coordination Slices

New distributed-coordination paths introduced this version, each requiring
at least one seeded `SimRuntime` test with `buggify!()` annotations:

1. **The migration state machine itself** (Slices 2–4): a distributed
   protocol coordinating donor, recipient, and the control plane across a
   real network boundary. Seeded test:
   `shard_migration_sim_tests.rs::migration_converges_under_buggify_seed`
   — runs the full `PLANNED → … → DONE` happy path with `buggify!()`
   injecting message delay/reordering on the donor↔recipient and
   donor↔control channels, asserting the migration still reaches `DONE`
   (or a clean `ABORTED`) and never a stuck or dual-authoritative state.
2. **Donor-kill fault injection** (Slice 6): `shard_migration_sim_tests.rs::
   donor_killed_mid_dual_writing_recovers_sim`,
   `::donor_killed_mid_cutover_recovers_sim` — both seeded, both required
   by the roadmap's explicit "killing the donor mid-`DUAL_WRITING` and
   mid-`CUTOVER` both recover correctly" proof claim.
3. **Worker drain** (Slice 5): `worker_drain_sim_tests.rs::
   drain_converges_under_buggify_seed` — seeded `SimRuntime` test injecting
   delay/reordering on the drain-migration fan-out, asserting every shard
   eventually migrates and the worker reaches `Decommissioned`.

Any FizzBee (S0) counterexample is replayed as an additional permanent
seed in whichever of the above files matches its failure shape, per the
ground rules — not a new, separate obligation.
