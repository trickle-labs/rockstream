# v0.48 Plan — Advanced DML & Scatter Pruning

Prerequisite phases 0–1 complete: `sign-offs/v0.47.md` is fully checked off
(`.claude/v0.47-evidence.md`, "Nothing deferred"). NEW_ROADMAP.md row read
(line 920, Phase 14 — Network Efficiency & Advanced DML).

## Proof obligations (restated as checkable assertions)

1. `UPDATE ... RETURNING` and `DELETE ... RETURNING` are implemented with true
   read-modify-write semantics (the gateway reads existing row state before
   the write, per DESIGN.md §12.8.2/§13.5.2), and each returns the correct
   row set: `UPDATE ... RETURNING` returns the post-update row, `DELETE ...
   RETURNING` returns the pre-delete row that no longer exists after commit.
2. Frontier summaries piggyback `ShardColumnStats` (min/max bounds + a
   budget-capped Bloom filter per column) at each cluster checkpoint
   (DESIGN.md §8.7), published to the control-plane catalog.
3. Multi-shard point reads safely bypass **>90%** of shards based on these
   frontier-summary Bloom filters/min-max bounds — the single Proof-column
   claim for this version.
4. Pruning is provably safe: a Bloom false positive may waste a round-trip,
   but a false negative (a shard holding a matching row gets pruned) must be
   impossible by construction — proven by an oracle property test comparing
   pruned vs. full scatter-read output.
5. Ground rules: no SlateDB range deletion on any new persistence path; every
   new buffer (including the Bloom filter's own byte budget) has a named
   upper bound + fill-level metric + backpressure/error path; stats staleness
   never blocks a query (falls back to full scatter with a warning notice);
   `cargo test --workspace` has no regressions; `make e2e` passes.

## 2. Vertical Slices

Each slice ends in a green test. Track A (DML) and Track B (scatter pruning)
are independent and can proceed in parallel; Track B's gateway-integration
slices (10–13) depend on Track B's checkpoint/persistence slices (7–9)
existing first.

### Track A — `UPDATE ... RETURNING` / `DELETE ... RETURNING`

#### Slice A1 — Parse `RETURNING` clause for `UPDATE`/`DELETE`
- Extend `parse_update`/`parse_delete` (`crates/rockstream-gateway/src/
  server.rs`) to accept an optional trailing `RETURNING <col[, col...]>` or
  `RETURNING *`, mirroring `parse_insert`'s existing `RETURNING` handling.
  Malformed clauses (e.g. `RETURNING` with no columns, trailing garbage)
  return a new `RS_2022` (`write.malformed_returning_clause`), continuing the
  `RS_2056`-style "next_steps" convention already used for malformed VALUES
  lists.
- Test: `parse_update_tests`/`parse_delete_tests` (unit, in `server.rs`) —
  `update_returning_star_parses`, `delete_returning_column_list_parses`,
  `update_malformed_returning_clause_returns_rs2022`.

#### Slice A2 — `UPDATE` becomes true read-modify-write
- Before buffering, `handle_update` reads the existing row via
  `shard_db.get(view_output/{table}/{old_row_key})` (old key built from the
  `WHERE` equality pairs, as today). If not found → zero rows affected,
  `Tag::new("UPDATE 0")`, empty `RETURNING` result set (no `DmlOp` buffered).
  If found, merge the `SET` pairs into the existing row's full column map
  (using the catalog's declared column list) to build the **complete** new
  row — this closes the current gap where `new_tsv` is built only from `SET`
  columns and silently drops every untouched column, which DESIGN.md's
  read-modify-write requirement makes a correctness bug once `RETURNING`
  exists to expose it.
- `DmlOp::Update` keeps its existing shape (`old_row_key`, `old_tsv`,
  `new_row_key`, `new_tsv`) — `new_tsv` now always carries the full merged
  row, not just the `SET` columns.
- Test: `update_read_modify_write_preserves_untouched_columns` (new
  integration test in `gateway_proof_tests.rs`) — `UPDATE` sets one column,
  asserts a subsequent `SELECT *` still returns the other, unmodified
  columns; `update_of_nonexistent_row_returns_zero_rows_no_write`.

#### Slice A3 — `UPDATE ... RETURNING` read-back
- Reuses the existing `needs_read_back` / `wait_for_epoch` / point-read
  pattern already built for `INSERT ... RETURNING` (server.rs lines
  ~4185–4243): after commit and frontier-advance wait, point-read
  `view_output/{table}/{new_row_key}` and project the requested (or `*`)
  columns. Matches `INSERT`'s existing behavior of only performing the
  read-back outside an explicit transaction block (`!in_explicit_block`);
  inside an explicit block, the write is buffered and `RETURNING` is
  resolved at the eventual `COMMIT`, exactly as `INSERT ... RETURNING`
  already does.
- Test: `update_returning_returns_new_row_after_commit`,
  `update_returning_star_returns_all_columns`,
  `update_returning_inside_explicit_transaction_resolves_at_commit`.

#### Slice A4 — `DELETE` captures pre-image before the write
- `handle_delete` reads the existing row via `shard_db.get()` **before**
  enqueueing the op — this is the literal "read old state before the write"
  DESIGN.md §12.8.2 calls for, and the reason `DELETE ... RETURNING` cannot
  reuse `INSERT`'s post-commit-read-back pattern (the row will be gone).
  Only performed when a `RETURNING` clause is present, to avoid an extra read
  on every plain `DELETE`. If the row does not exist → zero rows affected,
  `Tag::new("DELETE 0")`, empty `RETURNING`, no `DmlOp` buffered.
- Extend `DmlOp::Delete` with a new optional field, `returning_tsv:
  Option<String>`, populated only when `RETURNING` was requested — used
  solely for post-commit projection, never touched by the `WriteBatch`
  construction path. `byte_size()` is updated to account for it (still
  inside the existing 64 MiB `WRITE_BUFFER_LIMIT_BYTES` bound — no new
  buffer, an existing bounded one gains a field).
- Test: `delete_returning_returns_row_that_existed_before_delete`,
  `delete_of_nonexistent_row_returns_zero_rows_no_write`,
  `write_buffer_accounts_delete_returning_capture_bytes` (extends the
  existing `WriteBuffer` byte-accounting tests).

#### Slice A5 — `DELETE ... RETURNING` projection + rollback semantics
- After commit, project the captured `returning_tsv` pre-image directly (no
  re-read — the row is gone from `view_output` once the `WriteBatch`
  commits).
- `ROLLBACK` (and `ROLLBACK TO SAVEPOINT`) discard buffered `DmlOp::Delete`
  entries — including their captured `returning_tsv` — through the existing
  `WriteBuffer` discard mechanism; no client-visible `RETURNING` output is
  ever produced before an actual `COMMIT`.
- Test: `delete_returning_discarded_on_rollback` (asserts the row is still
  present via `SELECT` after `ROLLBACK`, and no `RETURNING` rows were sent
  before the abandoned commit), `savepoint_rollback_discards_buffered_
  delete_returning_capture`.

#### Slice A6 — Oracle property tests (incremental == batch for the view path)
- Both `UPDATE` and `DELETE` feed `crate::view_materializer::
  materialize_views` (server.rs), which incrementally recomputes every view
  transitively depending on the touched table. The corrected full-row
  `UPDATE` semantics (Slice A2) and the pre-image-aware `DELETE` path must
  not change this: a dependent view's incrementally maintained state must
  stay bit-identical to a from-scratch batch recompute.
- **Oracle property test (pre-committed per ground rules, before Slices A2/
  A4 land):** `oracle_update_returning_incremental_equals_batch` and
  `oracle_delete_returning_incremental_equals_batch`
  (`crates/rockstream-oracle`, extending the existing `INSERT`-oracle
  harness pattern) — randomized sequences of `INSERT`/`UPDATE ... RETURNING`/
  `DELETE ... RETURNING` against a base table with a dependent aggregate
  view; incremental view state after each statement equals a full batch
  recompute from the base table's current contents.

### Track B — Scatter Pruning via Frontier-Summary Column Statistics

#### Slice B7 — `ShardColumnStats`/`ColumnStats` types + config
- Add `ShardColumnStats`/`ColumnStats` (per DESIGN.md §8.7's exact struct
  shape) to `crates/rockstream-types/src/frontier.rs`, alongside
  `WorkerFrontierSummary` (piggyback sibling, not a merge into it — DESIGN.md
  is explicit these are separate messages at different update cadences).
  `col_stats: Vec<ColumnStats>` per non-partition-key column nominated for
  skipping; `bloom_filter: Option<Bytes>` using a blocked-Bloom or XOR filter
  representation.
- New `ScatterPruningConfig` in `crates/rockstream-types/src/config.rs`
  (added to `ClusterConfig`, same pattern as `SkewSplitConfig`):
  `shard_bloom_budget_bytes` (default 65536 = 64 KB, **named upper bound**),
  `shard_stats_max_age_checkpoints` (default 5, matching DESIGN.md's "5 ×
  checkpoint_interval").
- Bloom-filter fill-level metric: `shard_bloom_filter_bytes_used` (per
  shard/column); backpressure/error path: once a column's filter would
  exceed `shard_bloom_budget_bytes`, the builder degrades to a smaller/
  higher-false-positive-rate filter rather than growing unboundedly (never a
  hard error — pruning is optimization-only, so degrading gracefully is the
  correct "error path" here).
- Register `RS_2017` (`shard_stats.too_stale` — Slice B11) and `RS_2022`
  (`write.malformed_returning_clause` — Slice A1) in `error_code.rs`,
  continuing the existing 20xx block after `RS_2021`. Fix `RS_2013`'s doc
  comment to match its DESIGN.md-documented purpose
  (`transaction.returning_key_not_found`), used first by Slices A3/A5.
- Test: `shard_column_stats_roundtrip_tests` (serde roundtrip),
  `bloom_filter_never_exceeds_budget_bytes_at_high_cardinality` (the named
  bound + fill-level + backpressure/error-path ground rule, proven directly),
  `config_scatter_pruning_defaults_roundtrip` (extends
  `config.rs`'s existing `test_config_roundtrip`).

#### Slice B8 — Compute + persist `ShardColumnStats` at cluster checkpoint
- Piggyback stats computation onto `CheckpointCoordinator::
  record_shard_checkpoint` (`crates/rockstream-control/src/checkpoint.rs`):
  for each nominated column, scan the shard's current `view_output/*` range
  once per checkpoint (not per-write) to compute min/max bytes, build the
  budget-capped Bloom filter, track `null_count`, and update the
  `HyperLogLog/v1` (`0x0008`) sketch already used elsewhere for NDV
  estimation.
- Persist to the control-plane catalog key
  `control: topology/shard_stats/{view_id}/{shard_id} → ShardColumnStats`,
  overwritten (not versioned) each checkpoint — a single key per
  `(view, shard)`, so there is no historical-version cleanup path and
  therefore no range-delete surface to introduce.
- Test: `checkpoint_persists_shard_column_stats_to_control_catalog`,
  `shard_stats_write_is_put_not_range_delete` (ground-rule assertion, same
  style as `commit_write_batch_uses_no_range_delete`).

#### Slice B9 — Durability (LFS + MinIO)
- `shard_column_stats_durability_tests.rs::stats_survive_lfs_restart` —
  checkpoint writes stats, process restarts, stats read back bit-identical
  from the control-plane catalog.
- `shard_column_stats_durability_tests.rs::stats_survive_minio_tc_restart`
  — same proof against MinIO via TestContainers (feature-gated, same
  `docker_available()`-style guard as existing MinIO TC tests).
- Both include the two standing ground-rule assertions every new durability
  path in this codebase carries: scan-and-delete-not-range-delete (Slice B8)
  and named-bound-with-fill-level-metric (`shard_bloom_filter_bytes_used`,
  Slice B7).

#### Slice B10 — Gateway planner integration: shard pruning
- New `plan_scatter_shards` helper (`crates/rockstream-gateway/src/
  multi_shard_reader.rs` or a sibling module) reads cached `shard_stats` from
  the gateway's control-plane `DbReader` and evaluates each equality/range
  `WHERE` predicate per candidate shard, per DESIGN.md §8.7's exact rule: `if
  predicate_val < min_bytes || predicate_val > max_bytes → prune`; `if the
  Bloom test returns false for an equality predicate → prune`; otherwise
  include. `MultiShardReader::scatter_read` is called with the pruned shard
  subset instead of all shards.
- `EXPLAIN` (server.rs `explain_...` block) gains a
  `shard_scan: k/n shards (pruned by column statistics on <cols>)` note,
  mirroring the existing `index_note`/`sink_note` annotation pattern.
- Metrics (via the existing `generate_prometheus_metrics()` pipeline):
  `scatter_shards_total`, `scatter_shards_pruned_total`,
  `shard_bloom_false_positive_total`.
- Test: `scatter_planner_prunes_shards_outside_min_max_bounds`,
  `scatter_planner_prunes_shards_via_bloom_negative`,
  `explain_reports_pruned_shard_count`,
  `scatter_pruning_metrics_exported_correctly`.

#### Slice B11 — Stats-freshness guard
- If a view's `shard_stats` are older than `shard_stats_max_age_checkpoints`
  checkpoints, the gateway skips pruning for that view entirely and falls
  back to a full scatter, emitting `RS-2017 shard_stats.too_stale` as a
  non-blocking warning `NOTICE` (never fails the query — same posture as the
  existing `RS-2018`/`session_max_staleness` NOTICE pattern).
- Test: `stale_shard_stats_falls_back_to_full_scatter_with_warning`
  (asserts full shard set scanned + `RS-2017` NOTICE present + correct
  results still returned).

#### Slice B12 — Secondary-index-sourced stats
- When `CREATE INDEX` (shipped v0.32) completes a build, publish the
  resulting arrangement's precise min/max bounds and exact Bloom filter for
  the indexed column directly into `shard_stats` at the index's own
  completion, then keep it updated at every subsequent checkpoint (Slice
  B8's normal path) — satisfying DESIGN.md §8.7's "Secondary indexes provide
  high-quality stats" note without waiting a full checkpoint interval after
  `CREATE INDEX` finishes.
- Test: `create_index_publishes_precise_stats_immediately`,
  `indexed_column_stats_are_exact_not_probabilistic` (asserts zero false
  positives for an indexed column vs. the budget-capped approximate Bloom
  used for non-indexed columns).

#### Slice B13 — Headline proof test: >90% shard bypass
- `proof_multi_shard_point_read_prunes_over_90_percent_of_shards`
  (`gateway_proof_tests.rs`, LFS backend): construct 100+ shards, populate a
  column with well-separated per-shard value ranges, issue a multi-shard
  point-lookup `WHERE` predicate matching exactly one shard's range/Bloom
  filter, assert `scatter_shards_pruned_total / scatter_shards_total > 0.90`
  and that the single correct row is still returned.
- **Oracle property test (pre-committed per ground rules, before Slice B10
  lands):** `scatter_pruning_result_set_equals_full_scatter_result_set`
  (`crates/rockstream-oracle`) — for randomized shard-value distributions,
  predicates, and Bloom false-positive-rate settings, the pruned scatter-read
  result set is always identical to the full (unpruned) scatter-read result
  set. This is the test that proves "safely": false positives cost an extra
  scanned shard but never an extra/missing row; false negatives (which would
  silently drop matching rows) are asserted absent by construction, not just
  empirically.
