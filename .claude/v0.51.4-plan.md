## 3. Vertical Slices

Ordered by dependency. Slice 0 (delta capture) is the foundation every other
slice needs and is provable in isolation against the existing stateless views
(q0–q2). Slices 1–6 (operator-family compilation) are independent of each
other and can land in any order, but each is gated on Slice 0. Slice 7 (CASE/
scalar-function lowering) is independent of 1–6. Slice 8 (retire the dual

Slice 9 (regression benchmark + CI gate) depends on Slice 0 and Slice 8.

### Slice 0 — Per-commit delta capture (replaces full-table rescan)

- Change `handle_commit`'s compiled-view refresh (`server.rs:4216-4224`,
  calling into `recompute_compiled_view`) to pass the **actual row-level
  delta** produced by the commit's `WriteBatch` (the rows just
  inserted/updated/deleted on the changed base table, already known to the
  commit handler — it built that `WriteBatch`) as the pipeline's input
  `ArrowZSet`, with correct signed weights (`+1` insert, `-1` delete, paired
  `-1`/`+1` for update), instead of `scan_relation_rows_bounded`'s full-table
  re-read with uniform weight `1`.
- `recompute_compiled_view` (`server.rs:1088-1142`) is rewritten to accept
  this delta batch directly; `scan_relation_rows_bounded` and
  `COMMIT_COMPILED_VIEW_ROWS_SCANNED_TOTAL`'s "count full-table rows" meaning
  are retired. A new counter, `COMMIT_VIEW_REFRESH_DELTA_ROWS_TOTAL`, counts
  only the rows actually fed into the pipeline per commit — this is the
  counter Slice 9's proportionality benchmark asserts against.
- For the currently-compiled stateless shapes (`Source→[Filter]→[Project|Map]→ViewSink`,
  i.e. q0–q2 today), this is a pure behavior-preserving change: `FilterOp`/
  `ProjectOp`/`MapOp` are already linear (DBSP linear-operator rule — `ΔF(Δx)
  = F(Δx)`), so running them on the true delta instead of a full snapshot
  produces the same final materialized state, verified by the exit test.
- Exit test: `crates/rockstream-gateway/tests/unified_data_plane_tests.rs::
  commit_refresh_is_proportional_to_delta_not_table_size` — populate a
  compiled `Source→Filter→Project→ViewSink` view (e.g. q1-shaped) with 10,000
  rows via one commit, assert `COMMIT_VIEW_REFRESH_DELTA_ROWS_TOTAL` is
  ~10,000 after that commit; then commit a single additional row and assert
  the counter increases by exactly 1 (not by ~10,001), proving the refresh
  cost no longer scales with table size. A second assertion re-runs
  `insert_commit_select_round_trip_serviced_by_real_operator_dag` (existing,
  v0.51.3) unmodified to confirm no regression in output correctness.

### Slice 1 — Stateful executor scaffold + `Aggregate` compilation

- New module `crates/rockstream-ops/src/live_exec.rs`: a `StatefulPipeline`
  that generalizes `LinearPipeline` (`pipeline.rs:22-`) to host a mix of
  stateless operators (`FilterOp`/`ProjectOp`/`MapOp`, unchanged) and
  stateful operators addressed by a persisted `OperatorId` (reusing the exact
  `OperatorId` assignment convention `DiffCtx::next_op_id` already
  establishes for EXPLAIN, so operator ids stay consistent between `EXPLAIN`
  output and live execution). `StatefulPipeline::process(delta: ArrowZSet) ->
  Result<ArrowZSet, OpError>` threads the delta through each stage in order,
  loading each stateful operator's arrangement from storage before
  processing and persisting it after (reusing each operator's existing
  `load_from_storage`/`persist_state` pair — `AggregateOp::load_from_storage`/
  `persist_agg_state`, `aggregate.rs:238`/`:681`).
- Extend `compile_plan` (`compile.rs:94-123`)'s `other =>` arm: for
  `PlanNode::Aggregate { input, group_by, aggregates }`, recursively compile
  `input` (may itself be stateless or another stateful node — see Slices
  2–6), then push `AggregateOp::new(op_id)` onto the `StatefulPipeline`.
- Exit test: `crates/rockstream-sql/tests/nexmark/main.rs::test_nexmark_q4_q9_lfs`
  (existing) stays green for **q4's aggregate half** in isolation is not
  possible without Slice 3 (join) — so this slice's own exit test is new:
  `crates/rockstream-gateway/tests/live_exec_aggregate_tests.rs::
  compiled_aggregate_view_matches_batch_oracle_across_commits` — a
  `CREATE MATERIALIZED VIEW ... SELECT category, SUM(price) FROM bid GROUP BY category`
  shaped view (no join, so provable standalone), driven over pgwire across
  insert/update/delete commits, compared against a DataFusion oracle
  recompute after each commit.

## 4. Test Commitments (new operators)

Per the ground rules ("pre-commit to its oracle property test
(`incremental == batch`) before writing the operator"): the *operators*
themselves (`AggregateOp`, `JoinOp`, `OuterJoinOp`, `WindowOp`, `TopKOp`,
`DistinctOp`, `SessionWindowOp`) are **not new** — all pre-exist and were
individually oracle-proven correct since v0.7–v0.14/v0.50 (`time_window.rs`
unit tests, `rockstream-oracle`'s `aggregate_oracle.rs`/`window_oracle.rs`/
`sql_fuzzer.rs`). What is new in Slices 1–6 is wiring live, gateway-submitted
SQL to these existing operators for the first time — the oracle-property
commitment for each is therefore an **end-to-end wiring proof** (live pgwire
path output == DataFusion batch oracle), not a from-scratch operator-semantics
proof:

- Slice 1 (`Aggregate`): `compiled_aggregate_view_matches_batch_oracle_across_commits`.
- Slice 2 (`TumbleWindow`/`HopWindow`): `compiled_tumbling_view_matches_batch_oracle`.
- Slice 3 (`InnerJoin`/`OuterJoin`): `compiled_join_view_matches_batch_oracle_when_either_side_commits`.
- Slice 4 (`Window`/`TopK`): `compiled_topk_view_matches_batch_oracle`.
- Slice 5 (`Distinct`): `compiled_count_distinct_view_matches_batch_oracle`.
- Slice 6 (`SessionWindow`): the existing `nexmark_q11_session_bit_identical_to_batch_oracle`
  plus the new differently-worded-query test.

The one genuinely **new** piece of evaluation logic (not a pre-existing,
oracle-proven operator gaining new wiring) is Slice 7's `Expr::Case`/scalar-UDF
evaluation — this gets its own from-scratch oracle test,
`case_and_scalar_udf_eval_matches_datafusion_oracle`, pre-committed before
implementation per the ground rules, since no prior version proved this
expression evaluation correct against anything.

## 6. Coordination Slices

No new distributed-coordination path is introduced. This version's execution
model remains single-shard, single-process (`--role all`, per v0.51.3's own
Coordination Slices finding, unchanged) — `StatefulPipeline` runs
synchronously within the same commit handler that already holds the shard's
epoch/frontier fencing (M1–M4, unchanged since v0.4). Feeding a true row-level
delta (Slice 0) instead of a full-table rescan changes *what* is computed
within a commit, not *when* a commit is fenced or ordered relative to other
commits — the frontier/lease/fencing state machines in
`rockstream-control`/`rockstream-runtime/src/fence.rs`/`recovery.rs` are
untouched by this plan. Per the ground rules' own scoping precedent
(v0.51.3's Coordination Slices), no new `SimRuntime`/`buggify!()` test is
owed by this version's Scope; the existing FizzBee-paired regression suite
(Slice 10) is re-run unmodified as the coordination proof, matching the
roadmap's statement that this version needs no new FizzBee model.
