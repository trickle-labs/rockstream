### Slice 1 — M4 Self-Fencing FizzBee Model (D6.1–D6.2)

**Goal**: Write and verify `formal/m4_self_fencing.fizz` **before** the Rust
implementation, as required by FIZZBEE_TEST_PLAN.md §4.3. M4 is modeled first
(before M3) because M3 composes on top of a correct single-writer guarantee.

**Changes**:
- [NEW] `formal/m4_self_fencing.fizz`: Roles `Worker`×2–3, `Shard`,
  `ControlPlane`, `ObjectStore`. State: `Worker.can_reach_control` flag,
  `Shard.fence_epoch` integer (CAS on every commit), `ControlPlane.leases` map,
  `ControlPlane.dead_workers` set. Actions: `worker_commit` (CAS on
  `fence_epoch`), `mark_dead` (failure-detector), `self_fence` (gated on
  `can_reach_control == False` for `self_fence_after` steps), `grant_lease`,
  `lose_control_contact`. `CheckpointCoordinator` role composed with M1's
  `cluster_committed` predicate (a shard's checkpoint is committed only after
  `ControlPlane.checkpoint_index` records it). Invariants: M4-S1…S4, M4-L1…L2
  (`liveness: nondeterministic`), COV-M4.
- [MODIFY] `formal/findings.md`: Add D6.1/D6.2 section with M4 model results
  and any counterexamples found during modeling.
- [MODIFY] `FIZZBEE_TEST_PLAN.md` §3.6: Add M4-S1…S4, M4-S2 paired-assertion
  rows (fence-epoch rejection, single lease holder, self-fence deadline,
  object-store-only block).

**Test**: `rtk make verify` — M4 spec green (M4-S1…S4 safety, M4-L1…L2
liveness, COV-M4 coverage assertion all pass).

### Slice 4 — Checkpoint Coordinator (Control Plane)

**Goal**: Implement `CheckpointCoordinator` in `rockstream-control` following
DESIGN.md §11.2.

**Changes**:
- [NEW] `crates/rockstream-control/src/checkpoint.rs`:
  `CheckpointCoordinator` struct. Steps:
  1. Generate fresh `CheckpointId`.
  2. Inject `CheckpointBarrier` into every source operator.
  3. Track per-shard barrier-aligned confirmations.
  4. When all shards report their `PerShardCheckpoint`, atomically write
     `control: checkpoints/{checkpoint_id}` with the full
     `ClusterCheckpoint` manifest.
  5. Release old checkpoints beyond retention horizon; trigger SlateDB GC.
- [MODIFY] `crates/rockstream-control/src/lib.rs`: Wire
  `CheckpointCoordinator` into the control-plane service loop.
- Named upper bound: `checkpoint_alignment_max_credits` config key; fill-level
  metric `checkpoint_alignment_buffer_credits_used`.

**Test (LFS)**: `test_checkpoint_alignment_bounded_lfs` — run coordinator with
one fast and one slow source; verify alignment buffer never exceeds credit
limit; verify coordinator emits `RECOVERING` (not panic/OOM) on alignment
timeout.

### Slice 6 — Recovery Driver

**Goal**: Implement the recovery driver following DESIGN.md §11.3: open shards
via `DbReader` pinned to the latest committed cluster checkpoint, bring up
writers, re-elect leases.

**Changes**:
- [NEW] `crates/rockstream-runtime/src/recovery.rs`: `RecoveryDriver` struct.
  Steps:
  1. Fetch latest committed `ClusterCheckpoint` from control plane.
  2. For each shard, open `ShardDbReader` (wrapping `DbReader`) pinned to its
     `shard_checkpoint_id`.
  3. Transition each shard from reader to writer (acquire lease via
     `fence_epoch` CAS).
  4. Resume source connectors from offsets recorded in `control:
     connector/`.
  5. Emit `recovery_progress` metric (fraction of shards recovered).
- Named upper bound: recovery is bounded by `shard_recovery_budget` SLO
  (DESIGN.md §11.5).

**Test (LFS)**: `test_recovery_bit_identical_lfs` — checkpoint a pipeline,
simulate crash, recover via `RecoveryDriver`, assert output state is
bit-identical to pre-crash state.
