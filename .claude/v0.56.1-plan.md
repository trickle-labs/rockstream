# v0.56.1 — Disaster Recovery: Checkpoint Export & Restore Into a New Cluster

## Scope and non-negotiable outcome

Export the latest **M3-committed** cluster checkpoint to a different object-store
bucket/account/region, then restore it into a freshly provisioned cluster using
only that export. The restored cluster must reproduce every committed view
bit-identically. Exporting an object-store prefix while writes continue is not
an acceptable implementation: the export is defined by one committed checkpoint
manifest and its referenced immutable shard snapshots.

The operator surface remains one binary:

- `rockstream checkpoint export --destination <file://...|s3://...>`
- `rockstream checkpoint restore --source <file://...|s3://...> --storage <url> --yes`

`restore` replaces the current local placeholder restore semantics. It needs no
surviving source control-plane process. Neither command is SQL/pgwire work, so
the aggregate, join, window, type, and SQL-dispatch matrices are not applicable.

## Data and resource contract

1. An export selects one latest committed `ClusterCheckpoint` *after* its M3
   manifest is durable. It captures the manifest, the exact SlateDB objects
   reachable from each listed `shard_checkpoint_id`, and the control/catalog,
   topology, lease, connector-offset, and source-resume records belonging to
   that committed epoch.
2. Write those copies under a new immutable export generation. Store the
   ordered object name, byte length, and digest in bounded records, then write
   the terminal export manifest/commit marker **last**. A missing marker,
   missing object, length mismatch, digest mismatch, malformed manifest, or a
   shard/control epoch mismatch is `RS-5035` and is never restored.
3. Copy sequentially. `MAX_CHECKPOINT_EXPORT_OBJECTS_IN_FLIGHT = 1` and
   `MAX_CHECKPOINT_EXPORT_SCAN_WINDOW = 1024` are named hard bounds. Export
   `checkpoint_export_objects_in_flight` and
   `checkpoint_export_copy_progress` (`copied/total`) metrics. A concurrent
   request that cannot acquire the one copy permit fails with actionable
   `RS-5035`; no queue accumulates. Interrupted copies are resumable only when
   every already-written object validates against the same generation inventory.
4. Restore verifies the complete committed export before publishing any
   recoverable target state. It writes a fresh target generation, verifies it,
   and publishes the target bootstrap/active-generation pointer last. A failed
   restore therefore leaves no openable partial cluster. It uses point/object
   copy and scan only: no SlateDB range deletion or prefix-as-snapshot shortcut.
5. Both commands require the existing Admin policy and produce success and
   denial audit events. The response includes checkpoint id, source/destination,
   object/byte totals, and status in text and JSON so tests can assert the full
   output.

## Vertical slices

1. **Commit-bound export model and integrity format**
   - Add the minimal durable export-generation record/terminal marker and
     `RS-5035` registration. Reuse the existing object-store URL builder.
   - Add exact snapshot-id plumbing; fix the recovery/export reader gap so a
     `PerShardCheckpoint` actually selects its named durable snapshot.
   - Add `MAX_CHECKPOINT_EXPORT_OBJECTS_IN_FLIGHT`,
     `MAX_CHECKPOINT_EXPORT_SCAN_WINDOW`, progress/in-flight metrics, and
     permit-exhaustion error path.
   - Green tests: bounded scan/copy trace, generation digest validation,
     snapshot-id selection, and `export_restore_uses_no_slatedb_range_deletion`.

2. **M3-consistent export, interruption, and coordination proof**
   - Export only the latest M3-committed manifest; include every required
     control and shard object for that manifest. Copy into an immutable
     destination generation and publish the terminal marker last.
   - Make retry resume validated objects only; it must never promote a mixed
     epoch.
   - Add the seeded `SimRuntime` scenario with registered `buggify!()` points
     `dr.export.after_m3_selection` and `dr.export.before_terminal_marker`.
     The test uses `SimRuntime::new(0x56_01_0001)`, focuses each point, and
     asserts the exact committed/exported epoch and inventory.
   - Green tests: the SimRuntime test plus LFS export interruption/retry test.

3. **Fresh-cluster restore and durability proof**
   - Validate all export artifacts before publishing any target generation;
     restore control/catalog/topology/connector resume state and every shard
     snapshot without consulting a source control plane.
   - Rebuild the fresh bootstrap pointer last, recover through the real
     `RecoveryDriver`, and compare complete sorted rows and epoch metadata for
     each view.
   - Green tests: all six LFS/MinIO+TC matrix cells for bit identity, sustained
     writes, and truncation fail-closed behavior. This is the required LFS and
     MinIO durability coverage for both export and restore paths.

4. **CLI, audit, runbook, and measured drill**
   - Replace the placeholder local restore command with `export` and
     export-source `restore`; require `--yes` for restore, preserve Admin
     enforcement, and emit exact structured/text responses and audit events.
   - Update `docs/cli.md`; add `docs/disaster-recovery.md` with full-region-loss
     steps, export schedule, fresh-cluster restore commands, verification,
     periodic drill recommendation, and RPO/RTO values recorded from the drill
     rather than predeclared targets.
   - The runbook test must execute its documented command sequence and assert
     the full resulting transcript/artifacts. It is forbidden to use an
     unlisted helper or private script.
   - Green tests: exact CLI/documentation test and runbook drill test.
