## 1. Resolved Contract Choices

1. **Canonical Source DDL / API Contract & Authoritative Ownership (Step 1, V070-01)**:
   - **Syntax & Schema**:
     ```sql
     CREATE SOURCE <source_name> TYPE kafka (
       bootstrap_servers = '...',
       topic = '...',
       group_id = '...',
       offset_policy = 'earliest',
       schema_policy = 'strict',
       credential_ref = 'vault://kafka/...',
       poll_max_records = '5000',
       poll_max_bytes = '16777216',
       idle_partition_timeout_ms = '50'
     ) FORMAT json;
     ```
     (with standard Kafka aliases `bootstrap.servers` and `group.id` supported seamlessly).
   - **Authoritative Ownership**: The SQL DDL / API path owns the canonical source definition. `rockstream.toml` configuration files supply environment and worker budget bindings, but cannot act as an independent mutable source owner.
   - **Enforced Source Fields**:
     1. Broker bootstrap endpoints (`bootstrap_servers` or `bootstrap.servers`)
     2. Topic name (`topic`)
     3. Consumer group identifier (`group_id` or `group.id`)
     4. Offset reset policy (`offset_policy`: `earliest` | `latest`; default `earliest`)
     5. Schema policy (`schema_policy`: `strict` | `evolve` | `error`; default `strict`)
     6. Credential reference (`credential_ref` or `secret`; inline credentials such as `password = '...'` or SASL plain secrets are rejected with `RS-4008`)
     7. Formats supported: `json`, `avro`, `csv`
   - **Pre-Ingestion Validation**:
     - Broker reachability, topic existence, group authorization, and credential resolution are validated *before* admitting the source. Missing topic or unreachable broker fails closed with `RS-4001` / `RS-4008`.
   - **Persisted Source Record Versioning**:
     - Persisted in catalog storage (`ShardDb`) as `SourceRecordV1` with explicit version tag `1`. Records with unknown versions are rejected with `RS-2025` / `RS-4008`.

2. **Cluster, Topic, Partition, and Offset Identity Contract (Step 2, V070-02)**:
   - **Persisted Identity Quad**:
     $$\text{SourceIdentity} = (\text{cluster\_id}, \text{topic}, \text{partition}, \text{offset})$$
   - **Incarnation Tracking**:
     - Established from broker cluster metadata (`cluster_id`) and topic incarnation (topic UUID or partition metadata epoch).
     - If cluster identity cannot be verified or differs from catalog state, reject unsafe reuse with `RS-4015`.
   - **Incompatible Identity Changes & Rebuild Decisions**:
     - Topic recreation (different topic UUID / epoch), changed broker cluster ID, reduced partition count, malformed token, or `OffsetOutOfRange` MUST NEVER silently reuse old offsets.
     - The connector halts ingestion and enters `BLOCKED` status with `RS-4015` / `RS-4017`, requiring an explicit operator reset/rebuild decision (`ALTER SOURCE <name> RESET OFFSET ...` or source rebuild).
   - **Uniform Stored Offset Semantics Frozen**:
     - Stored offsets name the **NEXT** record to be fetched/applied (i.e. high watermark of consumed records, so if record at offset $N$ was durably committed, the stored offset is $N+1$). This convention is strictly enforced across `OffsetToken`, catalog storage, checkpoint persistence, and broker commit.

3. **Durable Epoch / Offset Commit Semantics (Step 3, V070-03)**:
   - **Core Invariant**:
     $$\text{Kafka offset considered committed} \iff \text{corresponding RockStream epoch is durable in SlateDB}$$
   - **Acknowledgement Boundary**:
     - Broker acknowledgement via `KafkaSource::commit_offset` (`CommitMode::Sync`) follows the durable epoch write in SlateDB.
   - **Crash and Replay Boundaries**:
     - *Crash before persistence*: Unpersisted in-memory batches are discarded upon crash; restart resumes from the last durable offset.
     - *Crash after persistence but before broker acknowledgement*: On restart, RockStream recovers durable offsets from `ShardDb`; replayed Kafka records (offset $< \text{durable\_offset}$) are detected and deduplicated with zero duplicate logical writes to materialized views.
     - *Broker commit failure*: If `commit_offset` returns an error from the broker, the durable epoch outcome in SlateDB remains valid and visible to queries; the failure is recorded as a retryable acknowledgment task rather than rolling back visible data.

4. **Multi-Partition Epoch Assembly and Bounded Idle Partitions (Step 4, V070-04)**:
   - **Partition Contribution**:
     - Records from all currently assigned active partitions are assembled into a single logical RockStream epoch.
   - **Assembly Bounds**:
     - `max_epoch_batch_records = 5,000` records
     - `max_epoch_batch_bytes = 16 MiB`
     - `max_epoch_assembly_ms = 100 ms`
     - `idle_partition_timeout_ms = 50 ms`
   - **Idle Partition Rule**:
     - Idle partitions (partitions with no available records within `idle_partition_timeout_ms`) MUST NOT cause an unbounded global wait. When active partitions have accumulated records or the timeout expires, the assembly window closes.
     - Progress is recorded per-partition: active partitions advance their durable offsets; idle partitions retain their existing offsets.
   - **Ordering and Visibility**:
     - Per-partition sequential order is strictly preserved. All partition deltas within the epoch become atomically visible to queries at the epoch commit boundary.

5. **Consumer Group Rebalance and Partition Revocation Protocol (Step 5, V070-05)**:
   - **Revocation Protocol**:
     - When partitions are revoked by Kafka consumer group rebalance, the source immediately halts admission of new records for those partitions.
     - Stale assignment generations are fenced using an assignment generation counter; records delivered from stale generations are rejected.
   - **In-Flight Work Disposition**:
     - In-flight epochs already persisted to SlateDB proceed to durable completion; uncommitted in-flight buffers for revoked partitions are discarded cleanly.
   - **Reassignment & Resumption**:
     - Newly assigned partitions seek strictly to durable offsets recovered from `ShardDb`, ensuring no record gap and no duplicate processing.
   - **Waiters and Retries**:
     - Revocation waiters and consumer retries are bounded by `rebalance_timeout_ms = 10,000 ms`.

6. **Bounded Poison-Record Handling & DLQ Diagnostics (Step 6, V070-06)**:
   - **Default Disposition**:
     - Fail closed: ingestion blocks and reports with an actionable error code (`RS-1003` / `RS-4014`) rather than silently skipping unparseable records.
   - **Configured DLQ Quarantine Policy**:
     - When DLQ policy is active, poison records (malformed JSON, schema decode failures, oversized records) are routed to the persistent DLQ store and quarantined.
   - **Six Mandatory Diagnostic Fields**:
     1. `topic`: topic name
     2. `partition`: partition index
     3. `offset`: record offset
     4. `error`: specific error code (e.g. `RS-1003`) and reason
     5. `schema`: target table/source schema definition
     6. `payload_digest`: cryptographic SHA-256 digest of the raw payload
   - **Safe Payload Redaction**:
     - Diagnostic outputs and status queries redact sensitive tokens, passwords, and PII; raw payload is safely truncated/hashed.
   - **Capacity Ceilings**:
     - `max_dlq_capacity = 10,000` entries. If DLQ reaches capacity, ingestion pauses and fails closed with `RS-4014` (`dlq_capacity_exhausted`), preventing unbounded memory growth or infinite retry loops.

7. **Worker Budgets, Backpressure, and Truthful Lag (Step 7, V070-07)**:
   - **Named Limits**:
     - `max_poll_records = 5,000` records
     - `max_poll_bytes = 16 MiB`
     - `max_source_buffer_bytes = 64 MiB`
     - `max_in_flight_epochs = 16`
   - **Flow Control via Broker Pause/Resume**:
     - When downstream queues fill or worker memory exceeds budget, the consumer pauses partition consumption via `rdkafka::consumer::Consumer::pause`.
     - Polling resumes via `resume` once worker memory clears below the low-water mark.
   - **Truthful Lag Reporting**:
     $$\text{partition\_lag} = \text{high\_watermark} - \text{durable\_offset}$$
     $$\text{total\_source\_lag} = \sum_{\text{partitions}} \text{partition\_lag}$$
     Reported truthfully in `SHOW SOURCE STATUS` alongside partition assignments, buffer fill level, and active consumer group generation.

8. **Generated Project Template Structure (`rockstream project new events --template kafka`) (Step 1 & 8, V070-01, V070-08)**:
   - Restore `--template kafka` in [`crates/rockstream-cli/src/init.rs`](file:///Users/grove/projects/rockstream2/crates/rockstream-cli/src/init.rs):
     - Remove the error block rejecting `kafka`.
     - Scaffolds a complete, self-contained project:
       - `rockstream.toml`: deployment configuration pointing to Kafka brokers and setting worker budgets.
       - `docker-compose.yaml`: reproducible Redpanda / Kafka single-node service with automated topic creation.
       - `schema.sql`: canonical `CREATE SOURCE events_source TYPE kafka (...) FORMAT json;` and materialized view definitions.
       - `produce-events.sh`: executable script publishing multi-partition seed records.
       - `queries.sql`: queries verifying materialized view maintenance.
       - `scripts/verify.sh`: fresh-directory release binary verification script.
   - Operates against release binaries without manual edits or mock fixtures.

9. **Connector Performance Envelope, Large State, and Worker Movement (Step 9, V070-09)**:
   - Workload profile: 10,000 msg/s sustained multi-partition ingestion.
   - Maintained state > configured worker budget (backed by v0.67.1 demand-loaded spillable arrangements).
   - Latency targets: `freshness_p99 <= 100 ms`, `commit_p99 <= 25 ms`, `read_p99 <= 10 ms`.
   - Worker RSS strictly bounded under continuous streaming; zero leaks.
   - Bounded recovery time following broker interruption or consumer restart.
