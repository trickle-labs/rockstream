# v0.59.24 Plan — Final Horizontal Scale & Performance Qualification

## Scope and Boundary

Roadmap row (`NEW_ROADMAP.md:1848`):
> **Focus**: Final Horizontal Scale & Performance Qualification
> **Scope**: **Blocking v0.59 qualification gate; this version changes no engine architecture.** At the start of this version, create `v1.0.0-rc.1` from one protected source SHA and publish the exact signed binary and image artifacts to be qualified. Freeze their digests, toolchain, lockfile, deployment topology, configuration, workload corpus, fault policy, hardware identity, and v0.59.23 thresholds before measurement. Run Kafka/PostgreSQL CDC → real RockStream workers → incremental operators → SlateDB/MinIO → PGWire/Kafka sink on fixed reference hardware at 1, 2, 4, and 8 workers. Exercise uniform and high-cardinality aggregation, factorized and unfactorized shuffle-heavy joins, correlated shared windows, Zipf skew with a sustained 50× hot key, state substantially larger than worker RAM, 120% offered-load recovery, worker loss, online split and micro-migration, checkpoint alignment, and compaction pressure. Requalify the v0.47 elasticity claims and every v0.59.5–v0.59.9 architecture gate through the final v0.59.10 observability and v0.59.23 capacity surfaces. Profile operator CPU, useful work, lock wait, Arrow encode/decode, key construction, SlateDB and object-store I/O, shuffle, checkpoint, compaction, cache, and gateway work. A candidate-identity change creates the next RC number. A qualification-input change creates a new `QualificationProfile` revision and `QualificationRun` for the same candidate. Any threshold change invalidates prior qualification evidence and requires a complete rerun, but does not create a new RC unless the candidate artifacts also changed. A failure that requires redesign returns to the owning architecture version and invalidates affected downstream evidence; thresholds are never relaxed inside the gate to make a candidate pass.
> **Proof**: An external benchmark/oracle harness that imports no RockStream crate timestamps generated changes, independently computes complete expected materialized-view multisets, queries PGWire, and consumes Kafka sink output. Maximum sustainable throughput follows the binding benchmark contract and must hold for 30 minutes with p99 freshness ≤1 second, bounded memory, queues, checkpoint backlog, and compaction debt, the declared checkpoint and compaction cycles complete, and no wrong results, lost changes, duplicate sink outputs, failed or rejected committed writes, or OOMs. Proof requires every absolute floor and ceiling frozen by v0.59.23 **and** ≥1.7×, ≥3.2×, and ≥5.6× single-worker sustainable throughput at 2, 4, and 8 workers for partitionable uniform aggregation; ≥4× at 8 workers for the shuffle-heavy join; no worker above 1.5× median sustained CPU under uniform load; hot-key mitigation recovering ≥80% of corresponding non-skew throughput without manual intervention; online split or migration with zero incorrect results and ≤20% temporary throughput loss; and automatic freshness recovery after five minutes at 120% offered load. One-row changes against 1K, 100K, and 10M-state arrangements remain approximately constant in state mutations and SlateDB writes; state larger than RAM remains inside its declared freshness SLO. Raw measurements record throughput, scale factor, p50/p95/p99 freshness, query latency, CPU/core, RSS, shared and private state bytes, spill, cache hit rate, network bytes, object-store requests, checkpoint duration, logical and physical write amplification, queue depth, compaction debt, and per-worker load. Harness mutations must fail when two declared workers are one process, WorkerIds repeat, one worker performs all useful work, a declared worker owns no shard, the generator saturates, the sink consumer falls behind, a result is stale but otherwise correct, output is duplicated or lost, raw timestamps are replaced by constants, a required workload is skipped, or CPU affinity or hardware identity changes mid-run. Inputs, environment, candidate digests, raw observations, and regenerated summaries are immutable evidence; every external bottleneck is demonstrated and quantified; constants or manually supplied samples cannot satisfy a result; future candidates regress by no more than 10% sustainable throughput or p99 freshness without explicit baseline approval.
> **Backends**: `Unit, LFS, MinIO, Postgres, Kafka, multi-process TC/Kubernetes, fixed multi-host performance environment`
> **Dependencies**: `v0.59.9, v0.59.23` (proof dependencies: `v0.59.2, v0.59.5, v0.59.6, v0.59.7, v0.59.8, v0.59.9, R2, v0.59.17, v0.59.18, v0.59.20, v0.59.21, v0.59.22, v0.59.23`)

v0.59.24 is the pure, blocking qualification gate for the v0.59 technical preview. It establishes and enforces the definitive multi-worker production performance contract:

1. **Exact-Artifact Identity & Candidate Freeze (`v1.0.0-rc.1`)**:
   - Create `CandidateIdentity` with semantic version `1.0.0`, candidate ID `rc.1`, protected commit SHA, lockfile digest, toolchain version, and compiler flags.
   - Freeze all deployment topologies, configurations, reference hardware identities, workload corpora, and the v0.59.23 sealed `CapacityThresholdManifest` before benchmarking.
   - Implement `QualificationProfile`, `QualificationRun`, and `QualificationEvidenceManifest` types in `crates/rockstream-types/src/qualification.rs`.
   - Immutable evidence binding: any candidate identity mutation generates the next RC (`rc.2`); any environment or threshold modification produces a new run for the candidate.

2. **Process-Isolated Multi-Worker Benchmark Orchestration (1, 2, 4, 8 Workers)**:
   - Benchmark live clusters across real OS processes with strict process isolation via `ProcessIsolationAuditor` (distinct OS PIDs, cgroups v2, distinct `WorkerId`s).
   - Ingest data via PostgreSQL CDC and Kafka, process through distributed incremental operators and shared arrangements, persist to SlateDB and MinIO/LFS, and consume through PGWire and Kafka sinks.
   - Enforce scaling speedup gates: ≥1.7× (2w), ≥3.2× (4w), and ≥5.6× (8w) single-worker sustainable throughput for partitionable uniform aggregation; ≥4.0× at 8 workers for shuffle-heavy joins; no worker >1.5× median sustained CPU.

3. **External Independent Oracle Verification**:
   - Independent oracle harness (`MultisetOracle`) importing no internal engine crates independently computes exact materialized-view multisets.
   - 30-minute sustained qualification runs proving zero wrong results, zero lost changes, zero duplicate sink deliveries, zero rejected writes, and zero OOMs with p99 freshness ≤1.0s.

4. **Extreme Stress & Fault Invariants**:
   - **Zipf Skew (50× Hot Key)**: Hot-key mitigation automatically recovers ≥80% of non-skew throughput.
   - **State Larger Than Worker RAM**: Constant write amplification across 1K, 100K, and 10M-state arrangements; p99 freshness remains inside declared SLO.
   - **Overload Recovery**: 120% offered load for 5 minutes converges back to p99 freshness ≤1.0s within 5 minutes of load normalization.
   - **Online Split & Micro-Migration**: Shard migration with zero data loss and ≤20% temporary throughput loss.
   - **Worker Eviction**: Abrupt and graceful worker loss with clean lease handoff and zero inconsistent results.

5. **Anti-Cheat Harness Mutation Invalidation Suite**:
   - Enforce fail-closed harness behavior across 11 deliberate mutations (single-process simulation, duplicate WorkerIds, idle worker, unowned shard, generator saturation, consumer lag, stale results, duplicate/lost sink outputs, constant timestamps, skipped workloads, mid-run affinity/hardware shifts).

6. **Automated Qualification Release Gate**:
   - `rockstream qualify` CLI command orchestrating qualification runs and evaluating `QualificationReleaseGate` against immutable raw evidence chunks, rejecting candidates with regressions >10%.

### Non-Negotiable Ground Rules

- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag on the same `rockstream` binary.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters, asserted by test.
- Unbounded in-memory accumulation is never acceptable: all buffers, queues, metrics batches, and sample streams have named bounds and metrics.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass; no `--no-verify`. Fix root causes.
- **This version changes no engine architecture.** Zero changes to query execution, planning, or physical storage layout.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals** overlapping this scope.

### Explicitly Out of Scope

- No engine architecture redesigns or physical format modifications.
- No promotion to `v1.0.0` (v0.59.24 qualifies `v1.0.0-rc.1`; final promotion is an unscheduled release operation).
- Post-v0.59.24 roadmap programs (v0.60–v0.64 typed semantics, v0.65–v0.69 essential operators, v0.70–v0.75 temporal analytics, v0.76–v0.81 recursion, v0.82–v0.86 durable time, v0.87–v0.92 serializable transactions, v0.93–v0.102 multi-region).
- No dynamic shard auto-resizing controller (deferred from v0.42.3 to post-v1 scale control).
- No GCP KMS / HashiCorp Vault providers (deferred from v0.55.1 to security provider follow-up).
- Commissioned third-party independent security audit report (v0.55.2 external artifact).
