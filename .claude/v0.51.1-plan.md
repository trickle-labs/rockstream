# v0.51.1 Plan — PostgreSQL-Standard Write & DDL Semantics

Roadmap row: `NEW_ROADMAP.md:1009`. Prior version: v0.51 (`NEW_ROADMAP.md:929`,
Hot-Path Compute Optimizations, ✅ done — WAL elision + backpressure coupling;
no scope overlap with v0.51.1). Phase 15.5 (`NEW_ROADMAP.md:1120`) covers
v0.51.1–v0.51.6 closing the "impressive internals, fragile front door" gap
found in the 2026-07-19 live `psql` review (`IMPLEMENTATION_STATUS_20260719.md`).

Scope is entirely inside `crates/rockstream-gateway` (pgwire session/commit
logic). No IVM operator, DAG, or `rockstream-runtime`/`rockstream-ops`/
`rockstream-diff` code is touched — those crates remain dev-dependencies only
of the gateway per the "two disconnected data planes" finding
(`NEW_ROADMAP.md:974-994`); reconnecting them is out of scope, reserved for
v0.51.4+.

## 1. Deferred-Item Audit

Scanned all 61 `sign-offs/v*.md` files (v0.1–v0.51) for deferred/postponed/
out-of-scope items overlapping autocommit, idempotency envelope, immediate MV
population, or no-column-list INSERT.

**Result: none found.** All four v0.51.1 items are newly-discovered gaps from
the 2026-07-19 live end-to-end `psql` review, not prior deferrals:

- Autocommit — buffered-until-COMMIT was the original design (not previously
  flagged as a gap).
- Idempotency envelope (RS-2007) — v0.24 shipped idempotency as
  client-mandatory; `NEW_IMPLEMENTATION_PLAN.md` Phase 7.2 always scoped it to
  "a direct write to a non-idempotent aggregate," but no sign-off flagged the
  over-broad enforcement as deferred work.
- Immediate MV population — v0.24/v0.42 shipped `view_materializer.rs` batch
  re-evaluation on commit; initial-population-on-CREATE was never scheduled
  or deferred, just never built.
- No-column-list INSERT — v0.42.2 (`sign-offs/v0.42.2.md:28-32`) fixed
  multi-row *tuple-splitting* detection only; it left the column-order
  resolution stage unfixed and did not flag it as deferred.

No pickup work from prior versions is required beyond the four Scope items
themselves.

## 3. Vertical Slices

Each slice ends in a green test and is independently committable/revertable.
Order matters: Slice 2 (server-generated envelope) must land before Slice 3
(implicit autocommit), because generalizing autocommit to every statement
means every un-RETURNING write now also goes through the idempotency gate —
without Slice 2 first, this would make **every** autocommitted write fail
with RS-2007, a regression. Slice 1 and Slice 4 are independent and can be
done in any order relative to 2/3.

### Slice 1 — No-column-list multi-row INSERT fix (independent, do first — lowest risk)
- Fix `parse_insert`/`handle_insert` (`server.rs:4199-4213`, `4237-4240`) so
  that when `cols` is empty, positional values are resolved against
  `catalog.get_table(&table)`'s declared column order before building
  `value_map`, instead of falling back to the empty `cols` list.
- If the table's catalog schema cannot be resolved at all (unknown table),
  fall through to the existing `RS-2056` malformed-row error path — do not
  invent a new error code.
- Exit test: `insert_no_column_list_multi_row_tests.rs` (new file) green.

### Slice 2 — Server-generated idempotency envelope (do second)
- Replace the hard error at `server.rs:3573-3580`: when both
  `idempotency_key` and `source_epoch_envelope` are `None`, generate a fresh
  random 16-byte key server-side (e.g. via the same key-hash type used for
  `SET rockstream.idempotency_key`, sourced from a CSPRNG, not derived from
  row content — it must be unique per commit, not a content hash) and treat
  it as `idempotency_key = Some(generated)` for the rest of the function.
- Skip the "prior-commit replay" lookup (`3581-3598`) for server-generated
  keys — they are freshly minted per commit and can never collide with a
  previous one, so the `get_idempotency_epoch` call is unnecessary for this
  path (avoids a wasted read on the hot path). Only run the replay-check
  branch when the key came from an explicit client `SET`.
- Explicit `SET rockstream.idempotency_key`/`source_epoch` continues to work
  exactly as today (unchanged code path) and remains the mechanism a client
  uses for a dedup guarantee spanning an explicit multi-statement
  transaction.
- Update `error.rs:32-34` doc-comment and `DESIGN.md:1524` sentence to state
  that a write with neither idempotency mechanism set now gets a
  server-generated envelope, not a rejection. Do not delete the `RS-2007`
  enum variant/SQLSTATE — retain it for protocol/documentation stability
  even if it becomes unreachable from the normal write-commit path (no other
  reachable trigger was found in the codebase for this variant).
- Update the existing test `missing_idempotency_key_returns_rs2007`
  (`gateway_proof_tests.rs:1679`) to assert the **new** required behavior
  (commit now succeeds and the row is visible) — this is a spec change
  mandated by this version's Scope, not a forbidden test-weakening; rename it
  to `missing_idempotency_key_autogenerates_envelope_and_commits`.
- New test: explicit `SET rockstream.idempotency_key` set once before two
  `INSERT`s inside an explicit `BEGIN...COMMIT` still dedupes a replayed
  identical commit (regression-locks the "spans an explicit multi-statement
  transaction" guarantee called out in Scope).
- Exit test: both tests above green.

### Slice 3 — Implicit autocommit (do third, depends on Slice 2)
- Generalize the `if returning { if !in_explicit_block { handle_commit() } }`
  gate in `handle_insert` (`server.rs:4263-4278`), `handle_update`
  (`~4559-4570`), and `handle_delete` (`~4707` region) to
  `if !in_explicit_block { handle_commit() }` unconditionally — i.e. drop the
  `returning` precondition so every statement outside an explicit `BEGIN`
  autocommits on success, matching standard PostgreSQL, while an explicit
  `BEGIN…COMMIT`/`ROLLBACK` block keeps buffering exactly as today (no change
  to that branch).
- Verify `handle_commit`'s no-op/idle behavior (`3543-3546`,
  `Response::TransactionEnd` even with no `conn_id`) is unaffected — it is
  already reused as-is.
- New test: bare `INSERT` (no `RETURNING`, no explicit `BEGIN`, no `SET`)
  followed by a `SELECT` in a **separate simple-query round-trip** returns
  the row — this is the core Gap-1 regression test.
- New test: same for `UPDATE`/`DELETE` without `RETURNING`.
- Regression test: explicit `BEGIN; INSERT; INSERT;` (no `COMMIT` yet)
  followed by `SELECT` in a separate round-trip still returns **zero** rows
  (buffering preserved) — locks in that explicit blocks are unaffected.
- Exit test: all four green, plus full existing `transaction_savepoint_tests.rs`
  suite (`91,155,212,275,304`) still green.

### Slice 4 — Immediate materialized-view population (independent, do last)
- In `handle_create_view` (`server.rs:2805-2888`), after
  `catalog.add_view_with_deps(...)` succeeds for a `CREATE MATERIALIZED
  VIEW` (not a plain `CREATE VIEW` — those are not materialized and stay
  lazy), call `view_materializer::materialize_views(catalog, shard_db,
  changed_tables)` once, synchronously, with `changed_tables` = the view's
  own source tables, **before** returning the `CREATE MATERIALIZED VIEW`
  response to the client. Reuses the exact same materializer entry point
  already called post-COMMIT (`server.rs:3674-3675`, `view_materializer.rs:43-52`)
  — no new materialization logic, no change to `rewrite_session_sql`
  (out of scope, reserved for v0.51.4).
- New test: `CREATE TABLE` + populate + `COMMIT`, then
  `CREATE MATERIALIZED VIEW mv AS SELECT ...`, then immediately (same
  connection, no further write) `SELECT * FROM mv` returns the current
  source data — no second commit required to see it.
- Regression test: a further `INSERT`+commit into the source table after
  `CREATE MATERIALIZED VIEW` still updates `mv` on the next commit (existing
  post-commit materialization path unchanged).
- Exit test: both green.

### Slice 5 — End-to-end transcript + full regression (closes the version)
- New test file `postgres_standard_transcript_tests.rs`: replay the exact
  `IMPLEMENTATION_STATUS_20260719.md` transcript verbatim — vanilla
  autocommitting connection, no `SET`, no explicit `COMMIT` —
  `CREATE TABLE t (id int, name text); INSERT INTO t VALUES (1, 'alice');
  SELECT * FROM t;` returns exactly the one row.
- Full run: `crates/rockstream-gateway/tests/gateway_proof_tests.rs` (all
  102 pre-existing tests + the renamed/updated one) green, plus all new test
  files from Slices 1–4.
- Exit: this is the version's overall Proof gate.

## 4. Test Commitments (new operators)

No new IVM operator is introduced in this version — all four Scope items are
gateway wire-protocol/session semantics changes (autocommit, idempotency
envelope generation, materializer-invocation timing, INSERT column
resolution), not new DBSP/Z-set operators. The oracle property test

## 5. Durability Slices

Every changed commit/DDL path must be proven on both SlateDB LFS and MinIO
(S3, via TestContainers) backends, per the standard two-backend durability
requirement:

| Durability path (this version) | LFS test | MinIO/TC test |
|---|---|---|
| Autocommitted write persisted without explicit COMMIT (Slice 3) | `autocommit_durability_lfs_tests.rs::bare_insert_persists_across_reconnect_lfs` | `autocommit_durability_minio_tests.rs::bare_insert_persists_across_reconnect_minio` |
| Server-generated idempotency key persisted via `put_idempotency_key` (Slice 2) | `idempotency_envelope_durability_lfs_tests.rs::autogenerated_key_persisted_lfs` | `idempotency_envelope_durability_minio_tests.rs::autogenerated_key_persisted_minio` |
| Immediate `view_output/{view}/` write on CREATE MATERIALIZED VIEW (Slice 4) | `mv_immediate_population_durability_lfs_tests.rs::mv_output_persisted_before_next_commit_lfs` | `mv_immediate_population_durability_minio_tests.rs::mv_output_persisted_before_next_commit_minio` |
| Correctly-resolved (non-NULL) row values for no-column-list INSERT (Slice 1) | `insert_no_column_list_durability_lfs_tests.rs::positional_values_persisted_lfs` | `insert_no_column_list_durability_minio_tests.rs::positional_values_persisted_minio` |

Each LFS/MinIO pair asserts: write → (process restart / new `ShardDb` handle
against the same backend, simulating recovery) → read back the same,
correctly-populated data. Follows the existing pattern used by prior
durability test files in `crates/rockstream-gateway/tests/` (e.g.
`delete_returning_durability_tests.rs`).

## 6. Coordination Slices

Not applicable. All four Scope items are single-session, single-shard
gateway logic (`crates/rockstream-gateway/src/server.rs`, `session.rs`,
`view_materializer.rs`); none introduces cross-shard or cross-node
distributed coordination. (`get_idempotency_epoch(0, key_hash)` and
`put_idempotency_key(batch, 0, ...)` use a hardcoded shard index `0` — no new
multi-shard fan-out is added.) No `SimRuntime`/`buggify!()` test is owed by
this version. If a future v0.51.x slice reconnects the gateway to the
multi-shard `rockstream-runtime` IVM engine (per the "two disconnected data
planes" finding), that version will owe its own coordination-slice tests.
