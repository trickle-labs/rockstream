# v0.45.2 Plan — M7 Control-Plane HA Model & 3/5-Node Raft Group

Source: `NEW_ROADMAP.md` row (Phase 12.5, v0.45.2 — "M7 control-plane HA model
(pre-implementation)") plus the 2026-07-11 architecture-review scheduling-risk
note (lines 987–1005) and the Phase 0–1 orient proof-obligation list (already
confirmed). Prerequisite confirmed: `sign-offs/v0.45.1.md` is complete (all
boxes checked, zero deferrals).

**Scope, as agreed at Orient**: author `formal/m7_control_plane_ha.fizz`
(safety M7-S1…M7-S3, liveness M7-L1, coverage COV-M7) **and** implement the
real 3/5-node Raft-elected control-plane writer described in DESIGN.md §3
("Tier 3 Raft bootstrap") — both in the same version, per the roadmap row as
currently written. This plan treats a green FizzBee model as the primary path
and documents the roadmap's own split-contingency as a fallback (§0 below).

**⚠️ Scheduling-risk flag (carried forward, not resolved by this plan)**: the
2026-07-11 architecture review explicitly warns that v0.45.2 (like v0.46)
collapses "model-check in FizzBee" and "implement the coordination protocol"
into one ~6-person-week version, unlike M1–M5, each of which got a dedicated
pre-implementation modeling version. It cites M4's own history — an exhaustive
state space that did not terminate at committed bounds and needed three
follow-up sub-versions (v0.42.1–v0.42.3) — as the cautionary precedent, and
recommends splitting into a model-only version + an implementation version
"if the model's state space does not terminate quickly at CI-fast bounds."

**My judgment as plan-writer**: M7's state space has one point in its favor
relative to M4 (Raft leader election among 3 nodes with small term bounds is
one of the most model-checked protocols in the literature and is generally
tractable at CI-fast bounds with symmetry reduction) and one point against it
(M7-S3 explicitly *composes* with M4's own fencing predicate — the same
predicate whose model already took three sub-versions to close — and the
roadmap allows up to 5 control nodes, not 3). Net assessment: **complexity is
plausibly comparable to M4's**, so the split contingency below is a real,
not theoretical, risk. Slice 0 (§2) is sequenced first and explicitly
time-boxed so this is discovered before any Raft implementation code is
written, matching the roadmap's own recommendation.

### §0 — Split contingency (fallback path, not the primary plan)

If `formal/m7_control_plane_ha.fizz` (Slice 0) does not reach a green
CI-fast-bounds result after reasonable tuning (tightening `NUM_CONTROL_NODES`
to 3, `MAX_TERM` to 2–3, applying symmetry reduction to control-node
instances, and wrapping non-interesting sub-steps in `atomic` per
FIZZBEE_TEST_PLAN.md §2.3's state-space tactics) within the time-box normally
budgeted for a CI-fast model (matching M1–M5's precedent):

1. Stop before Slice 1. Do not begin the Raft implementation.
2. Record the counterexample or non-termination in `formal/findings.md`.
3. Recommend to the roadmap owner that v0.45.2 be split exactly as v0.43/v0.44
   were for M5: a model-only v0.45.2 (this slice only, closed with its own
   sign-off) followed by a new implementation version for the Raft group
   (inserted immediately after, analogous to v0.44 following v0.43).
4. Everything below this line (Slices 1–6) becomes the scope of that follow-up
   implementation version instead of this one.

This plan proceeds assuming the primary (green-model) path, per instruction,
with this section as the documented fallback.

## 2. Vertical Slices

Each slice ends in a green test before the next begins. Slice 0 gates all
others (§0 contingency).

**0. S0 — `formal/m7_control_plane_ha.fizz` authored and green (binding
   pre-implementation gate).**
   Roles (per FIZZBEE_TEST_PLAN.md §2.1 conventions): `ControlNode`
   (symmetric, ×3, `NUM_CONTROL_NODES ≤ 3`) carrying `current_term`,
   `voted_for`, `role ∈ {Follower, Candidate, Leader}`, and a
   `leadership_fence_token`; `ObjectStore` (reused CAS-capable role, models
   the control SlateDB); `Worker`/`Shard` roles reused from
   `formal/m4_self_fencing.fizz` for the M7-S3 composition. Actions:
   `request_vote`, `grant_vote`, `become_leader` (requires majority),
   `heartbeat`, `step_down_on_higher_term`, `write_lease_grant` /
   `write_workload_catalog` / `write_shard_assignment` (each gated on
   `role == Leader`), composed shard-fence write reusing M4's
   `commit_epoch`/fence-check action.
   Safety: **M7-S1** (`always`: at most one `ControlNode` has
   `role == Leader` with an unfenced `leadership_fence_token` at any
   term-instant — no dual leader); **M7-S2** (`always`: `write_lease_grant`
   / `write_workload_catalog` / `write_shard_assignment` only succeeds when
   the acting node's `role == Leader` at a term the `ObjectStore` accepts —
   modeled as a `oneof` rejection branch for any non-leader attempt); **M7-S3**
   (`always`, composed with M4: a shard's `fence_epoch` write is only
   accepted from the current control leader's term, and a leadership change
   (term increment) strictly invalidates any in-flight fence write from the
   deposed leader, mirroring M2-S4's synchronous-flush pattern applied to
   the control-leader token instead of the frontier-publisher token).
   Liveness: **M7-L1** (`always eventually`, `liveness: nondeterministic`
   per M2-L2/M4-L1 precedent: after any leader crash or partition, some
   `ControlNode` eventually becomes `Leader` and resumes accepting writes).
   Coverage: **COV-M7** (`exists`: a state where the leader crashes mid-term,
   a new leader is elected at a higher term, and the stale leader's
   in-flight lease/catalog/shard-assignment write is rejected).
   Add `m7_control_plane_ha` to `Makefile`'s `verify`/`verify-relaxed`
   targets and to the CI `formal-verify` hard-gate step (no
   `continue-on-error`, matching the v0.42.3 hard-gate contract). Add a new
   `### 3.8 M7 — Control-Plane Raft Leader Election` section to
   `FIZZBEE_TEST_PLAN.md` and an M7 row to Appendix A's spec inventory.
   **Green test**: `fizz formal/m7_control_plane_ha.fizz` passes locally and
   via `make verify`, at `NUM_CONTROL_NODES=3`, small `MAX_TERM` bound,
   within CI-fast time. *(If this does not terminate/pass — see §0.)*

**1. S1 — 3-node Raft group bootstrap in `rockstream-control`.**
   Wire a vetted Raft implementation (subject to `DEPENDENCY_POLICY.md`'s
   normal vetting) into `rockstream start --role=control [--bootstrap]` per
   DESIGN.md §3's "Tier 3 Raft bootstrap" contract: first node starts with
   `--bootstrap`; subsequent nodes join via the same `--control` URL; once a
   quorum forms, the elected leader opens the control SlateDB as the sole
   writer, followers serve `DbReader` fan-out. Raft term/vote/log state is
   persisted through the existing control SlateDB (new keys, e.g.
   `control: raft/term`, `control: raft/vote`, `control: raft/log/*`) —
   this is a **new durability path** (see §4).
   Paired asserts: `assert_single_control_leader(term, node_id, …)` in
   `rockstream-control` (mirrors M7-S1).
   **Green test**: seeded `SimRuntime` scenario
   (`rockstream-sim/tests/control_plane_ha_tests.rs::three_node_raft_elects_single_leader`)
   asserting exactly one leader across seeds; real 3-node TestContainers
   cluster test (`control_plane_ha_tests.rs::three_node_tc_cluster_boots_and_elects_leader`,
   `#[ignore]`-gated per the existing MinIO/TC convention) asserting
   `cluster status` (or equivalent) reports exactly one leader after
   bootstrap.

**2. S2 — Leader-only write gating (M7-S2).**
   Add a `require_leader()` guard in front of the three write paths named in
   the Proof column — lease grant, `CREATE WORKLOAD`/workload-catalog write
   (from v0.45.1's `WorkloadCatalog`), and shard-assignment write — checked
   against the node's current Raft role + leadership fence token before the
   write reaches control SlateDB. A rejected non-leader attempt returns a
   new registered `RS-XXXX` code (e.g. `RS-1731 control.not_leader`) with
   actionable `next_steps` text and is audited.
   Paired assert: `assert_write_requires_leadership(role, term, …)` in
   `rockstream-control`.
   **Green test**: integration test issuing each of the three write kinds
   against a deliberately-demoted (follower) node, asserting `RS-1731` and
   an audit entry for each; seeded `SimRuntime` test using
   `buggify!("control.stale_leader_write", p)` to force an in-flight write
   from a node that loses leadership mid-request, asserting rejection.

**3. S3 — No dual-leader window / M7-S3 fencing composition with M4.**
   Extend the shard fence-epoch token (`rockstream-runtime/src/fence.rs`,
   M4's existing mechanism) to be derived from
   `(raft_term, control_leader_id)` so a control-leadership change strictly
   invalidates any in-flight shard-fence write issued under the old term —
   the control-plane analogue of M2-S4's synchronous-flush guarantee.
   Paired assert: `assert_valid_control_leader_epoch(term, leader_id, …)`
   alongside M4's existing `assert_valid_writer`.
   **Green test**: seeded `SimRuntime` scenario combining a forced control
   leadership change (`buggify!("control.leader_crash", p)`) with an
   in-flight shard-fence/shard-assignment write, across multiple seeds,
   asserting the stale leader's write is rejected and **no split-brain shard
   grant occurs** (two different workers never both hold a valid lease for
   the same shard during the transition) — this directly proves the "no
   split-brain shard grants occur" Proof claim in the CI-fast SimRuntime
   half of its two-test requirement.

**4. S4 — Real 3-node leader-kill recovery drill + §11.5-budget-bound
   resumption.**
   TestContainers 3-node control-plane cluster; kill the leader process
   mid-run; assert (a) a new leader is elected (reusing S1's election
   check), (b) shard leasing (the existing lease-grant path) resumes within
   the existing DESIGN.md §11.5 recovery-time budgets — reusing the same
   budget envelope already codified for worker-shard recovery
   (`failure_detection_seconds ≤ 5s`-class detection,
   `shard_recovery_seconds ≤ 30s`-class reassignment) applied here to
   control-plane leader failover, and (c) frontier publication (§3.2's
   elected publisher, which depends on the control SlateDB being writable
   again) resumes within the same budget envelope, and (d) no split-brain
   shard grant occurs during the real-cluster transition (cross-checking
   S3's SimRuntime-only assertion against real process kill/restart).
   Mirror the identical fault as a seeded `SimRuntime` scenario
   (`buggify!("control.leader_crash", p)`) for CI-fast, every-PR coverage of
   the same property, satisfying the roadmap's explicit "verified by both a
   `SimRuntime` scenario and a TestContainers drill" requirement.
   **Green test**:
   `control_plane_ha_tests.rs::leader_kill_recovers_within_budget_tc` (TC,
   `#[ignore]`-gated) and `::leader_kill_recovers_within_budget_sim`
   (`SimRuntime`, multi-seed), both asserting new-leader election, shard-lease
   resumption, and frontier-publication resumption each land within the
   §11.5-derived budget, and zero dual shard grants are observed.

**5. S5 — Rolling restart durability (worker lease + workload quota state
   never dropped).**
   Drive a one-at-a-time restart of all three control nodes (TC) while
   workers hold active shard leases and workloads (v0.45.1) have live quota
   state; assert after each individual node's restart that every worker's
   lease-holder identity/TTL is unchanged or validly renewed, and every
   workload's quota/catalog state is byte-identical pre/post the full
   rolling-restart cycle. Because S1 introduced a new durable Raft
   term/vote/log path, add its own LFS + MinIO durability tests (see §4).
   **Green test**:
   `control_plane_ha_tests.rs::rolling_restart_preserves_worker_leases_and_quotas_tc`
   (TC) plus a `SimRuntime`-seeded equivalent for CI-fast coverage; plus
   `raft_state_durability_tests.rs::raft_term_vote_log_survive_restart_lfs`
   and `::raft_term_vote_log_survive_restart_minio_tc` for the new
   Raft-state durability path.

**6. S6 — Close the loop / sign-off.**
   Populate `FIZZBEE_TEST_PLAN.md` §3.7's mapping table with the new M7 rows
   (M7-S1…S3, M7-L1, COV-M7, each paired to its `rockstream-control`/
   `rockstream-runtime` assert and test, per the §6 mapping below). Run full
   `cargo test --workspace` and `make verify`. Write `sign-offs/v0.45.2.md`.
   **Green test**: full workspace suite + `make verify`, both green.

## 4. Durability Slices

**New durability path**: Raft term/vote/log persistence through the control
SlateDB, introduced in S1 (`control: raft/term`, `control: raft/vote`,
`control: raft/log/*` keys). This is new durable state that did not exist
before this version and therefore needs both required tests per the Phase 2
rule:

- **SlateDB/LFS test**: `raft_state_durability_tests.rs::raft_term_vote_log_survive_restart_lfs`
  — LocalFileSystem-backed control SlateDB, restart a control node process,
  assert `current_term`/`voted_for`/log entries are recovered identically.
- **MinIO (S3, TestContainers) test**: `raft_state_durability_tests.rs::raft_term_vote_log_survive_restart_minio_tc`
  — same assertion against a real MinIO container.

The existing control-SlateDB catalog/lease/shard-assignment writes (S2, S3)
reuse the *existing* durability path already covered by prior LFS/MinIO tests
(v0.45.1's `lfs_catalog.rs` and earlier control-plane tests) — extending
*who may write* to it (leader-only gating) does not open a new durability
surface requiring its own paired slice; only the new Raft-log storage does.

## 5. Coordination Slices

Every new distributed-coordination path in this version gets at least one
seeded `SimRuntime` test with `buggify!()`:

- **3-node Raft leader election** (S1): `buggify!()`-free baseline seeded
  scenario plus fault-injected variants forming the group under induced
  message delay/loss, asserting single-leader convergence across seeds.
- **`control.stale_leader_write` fault** (S2): seeded test forcing a write
  attempt from a node mid-losing leadership, asserting rejection.
- **`control.leader_crash` fault** (S3, S4): seeded scenario combining a
  forced leader crash with an in-flight shard-fence write and, separately,
  full leader-kill recovery timing, asserting no split-brain grant and
  budget-bound recovery across seeds.
- **Rolling restart** (S5): seeded scenario driving all three simulated
  control nodes through sequential restart while workers hold leases and
  workloads hold quota state, asserting neither is dropped.

The M7 FizzBee model (S0) is the formal (non-`SimRuntime`) half of this
coordination proof; `COV-M7` is the FizzBee-side commitment, and the four
bullets above are its paired runtime/simulator commitments, together with
the TestContainers drills in S1/S4/S5 required by the roadmap's explicit
"verified by both a `SimRuntime` scenario and a TestContainers drill" clause.
