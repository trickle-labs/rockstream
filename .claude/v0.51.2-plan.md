**Scoping decision (documented, not a deferral):** because v0.51.3's real
`rockstream-runtime` DAG connection does not exist yet, `CREATE INDEX`'s
automatic backfill in this version builds a **gateway-local** index
arrangement — scanning the target table/view's already-materialized
`view_output/{table}/` rows and writing the exact same
`0x03‖op_id(BE8)‖col_val(BE8)` binary layout `maybe_index_point_lookup`
already reads — and assigns a locally-minted monotonic `op_id` (a new
`AtomicU64` counter in `CatalogStubs`, not a real `IndexArrangeOp`). This
satisfies the Proof claim (`CREATE INDEX` reaching `Ready` measurably
accelerates a point lookup) using the wire format already shipped and tested
in v0.32, without inventing DAG/operator plumbing that belongs to v0.51.3.
The private `MARK INDEX ... READY` command is **retained** unchanged (existing
tests in `gateway_proof_tests.rs` still use it to inject synthetic
already-backed indexes) but `CREATE INDEX` no longer **depends** on it for
standard operation.

## 3. Vertical Slices

Each slice ends in a green test. Slices 1–3 share one engine change (query-time
DataFusion re-execution) and are ordered by risk; Slice 4 (EXPLAIN) is
independent; Slice 5 (real CREATE INDEX backfill) is independent of 1–4 but
depends on the bounded-scan helper introduced in Slice 1.

### Slice 1 — Query-time WHERE predicate evaluation via DataFusion (do first)
- Add a new gateway-local helper, `query_time_datafusion_select(catalog,
  shard_db, raw_sql, referenced_tables) -> Result<Vec<RecordBatch>, _>`, that:
  builds a fresh `SessionContext` (mirrors `view_materializer.rs:94`), for each
  referenced table/view scans its `view_output/{name}/` prefix in `shard_db`
  bounded by a hard cap (`MAX_QUERY_TIME_ROWS`, e.g. 1_000_000 rows — a named
  upper bound per the ground rules; exceeding it returns a new `RS-2xxx`
  "query result set too large for query-time execution" error rather than
  buffering unboundedly), converts rows to a `RecordBatch` via the *existing*
  `tsv_to_record_batch` (reused, not duplicated), registers it as a `MemTable`
  via `ctx.register_table`, then runs the **client's original SQL text**
  (not just the view-definition SQL) through `ctx.sql(raw_sql).await`.
- Wire this into `read_view_response`'s dispatch point (`server.rs:2117-2187`):
  when the ad hoc query's `WHERE`/`GROUP BY`/`JOIN`/subquery/CTE cannot be
  satisfied by the existing raw-byte-scan + sort + limit path (i.e. the query
  is anything beyond plain column projection/`ORDER BY`/`LIMIT`), route
  through `query_time_datafusion_select` instead of the legacy raw scan.
  Plain projection-only queries keep the existing fast raw-scan path
  unchanged (no regression risk, no perf regression for the common case).
- New metric: `QUERY_TIME_DATAFUSION_ROWS_SCANNED_TOTAL` (fill-level style
  counter, mirrors `SESSION_WAIT_FOR_TRIGGERED_TOTAL`'s `AtomicU64` pattern at
  `server.rs:2098`) so the bounded-scan cap has an observable fill level.
- Exit test: `query_time_execution_tests.rs::select_with_where_predicate_filters_rows`
  — live pgwire round-trip (`tokio-postgres` test client, matching
  `gateway_proof_tests.rs`'s harness) against a table with mixed `region`
  values; `SELECT * FROM v WHERE region = 'US'` returns only the `US` rows.

### Slice 2 — Ad hoc two-table JOIN (depends on Slice 1's engine)
- Extend the referenced-tables resolution so a query naming two catalog
  tables/views in its `FROM`/`JOIN` clauses (not just the single-name
  fast path) registers **both** as `MemTable`s in the same `SessionContext`
  before calling `ctx.sql`. DataFusion's own SQL planner then evaluates the
  join — no join-specific code is written here beyond registering the second
  table.
- Exit test: `query_time_execution_tests.rs::ad_hoc_two_table_join_matches_oracle`
  — two base tables (e.g. `orders`, `customers`), an ad hoc
  `SELECT o.id, c.name FROM orders o JOIN customers c ON o.customer_id = c.id`
  issued live over pgwire (not baked into any view definition), asserted
  against a hand-computed expected result set.

### Slice 3 — Ad hoc GROUP BY/aggregate, subqueries, CTEs (depends on Slice 1)
- No new code beyond Slice 1's dispatch: once the client's raw SQL text is
  run through `ctx.sql` with real data registered, DataFusion natively
  evaluates `GROUP BY`, aggregates, scalar/`IN` subqueries, and `WITH` CTEs.
  This slice is test-only — it proves the engine change from Slice 1
  generalizes correctly.
- Exit tests (`query_time_execution_tests.rs`):
  - `ad_hoc_group_by_matches_oracle` — ad hoc
    `SELECT region, COUNT(*) FROM t GROUP BY region` (not a view definition),
    asserted against a hand-computed per-group count.
  - `ad_hoc_subquery_matches_oracle` — `SELECT * FROM t WHERE id IN (SELECT
    id FROM t2 WHERE flag = true)`.
  - `ad_hoc_cte_matches_oracle` — `WITH recent AS (SELECT * FROM t WHERE ...)
    SELECT * FROM recent`.

### Slice 4 — Standard `EXPLAIN <query>` real plan (independent of 1–3)
- Replace the string-concatenation stub (`server.rs:1624-1721`) for bare
  `EXPLAIN <query>` (not `EXPLAIN INCREMENTAL`, which is untouched) with a
  real DataFusion plan: build the same `SessionContext` + `MemTable`
  registration as Slice 1 (reused helper), run
  `ctx.sql(&format!("EXPLAIN {inner_sql}")).await` (DataFusion's own
  `EXPLAIN` support), and stream DataFusion's real `plan_type`/`plan` rows
  back as the `QUERY PLAN` result set instead of the synthetic text.
  Preserve the existing index/sink/shard annotation notes
  (`index_note`/`sink_note`/`shard_note`, `server.rs:1636-1698`) by appending
  them as extra rows after DataFusion's real plan — no information is lost,
  the fabricated one-line "Plan: SeqScan → …" text is what's removed.
- Exit test: `query_time_execution_tests.rs::plain_explain_returns_real_plan_tree`
  — `EXPLAIN SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id
  WHERE c.region = 'US'` returns a multi-row plan naming real DataFusion node
  types (`Filter`, `Inner Join`, `TableScan`, etc. — asserted by substring
  match on DataFusion's actual `Display` output, not a hand-written string).
- Regression test: `EXPLAIN INCREMENTAL SELECT ...` output is byte-for-byte
  unchanged from the pre-existing `gateway_proof_tests.rs` assertions (no
  new test needed — existing suite proves this if still green).

### Slice 5 — Real `CREATE INDEX` automatic backfill + Ready transition (independent, do last)
- In `handle_create_index` (`server.rs:3206-3280`), after `catalog.add_index`
  succeeds with `state: Building`, synchronously run a new
  `backfill_index(catalog, shard_db, &index_name)` routine (standard
  PostgreSQL `CREATE INDEX` blocks the issuing session until done — no
  `CONCURRENTLY` support is in this version's Scope):
  - Scans `view_output/{table}/` in **bounded batches** (e.g. 10,000 rows per
    batch — named upper bound; a table exceeding a hard cap, e.g.
    1,000,000 rows, fails backfill with a new `RS-2xxx`
    "index_backfill_row_limit_exceeded" error and the index catalog entry is
    removed, not left stuck in `Building` forever — this is the required
    backpressure/error path).
  - For each row, decodes the indexed column's value (reuses the existing
    fixed-width i64 decode already used by `maybe_index_point_lookup`,
    `server.rs:2496-2512`), and writes `0x03‖op_id(BE8)‖col_val(BE8)` →
    row bytes into `shard_db` — the exact layout the existing point-lookup
    reader already consumes.
  - Mints a fresh `op_id` from a new `AtomicU64` counter on `CatalogStubs`
    (not derived from any runtime-DAG concept — see the scoping decision in
    §2) and calls the existing `catalog.mark_index_ready(&name, op_id)`
    (`catalog_stubs.rs:608`) once the scan completes — no protocol change to
    that function.
  - New metric: `INDEX_BACKFILL_ROWS_PROCESSED_TOTAL` (counter) and
    `INDEX_BACKFILL_IN_PROGRESS_COUNT` (gauge, `AtomicU64`, incremented before
    the scan loop, decremented after) so the backfill's fill level is
    observable, per the ground rules.
  - Extend `extract_where_equality` (or add a sibling
    `extract_where_range(q) -> Option<(String, RangeOp, i64)>` for
    `<`/`<=`/`>`/`>=`/`BETWEEN`) and extend `maybe_index_point_lookup`'s
    matching logic (or add `maybe_index_range_lookup`) to scan a bounded
    sub-range of the `0x03‖op_id‖…` prefix instead of a single exact key —
    this is the "range-lookup accelerator" half of the roadmap's Scope
    wording (today's function is point-lookup-only).
- Exit tests (`create_index_query_planning_tests.rs`, new file):
  - `create_index_reaches_ready_automatically_without_mark_index` — issues
    plain `CREATE INDEX idx ON t(col)` over live pgwire with **no** `MARK
    INDEX` command anywhere in the test, then polls (or synchronously
    observes, since backfill is synchronous) that the index catalog state is
    `Ready`.
  - `create_index_point_lookup_under_10ms_p99` — matches v0.32's bar
    (`sign-offs/v0.32.md`'s `proof_secondary_index_point_lookup_under_10ms_p99`,
    p99 < 10 ms): after `CREATE INDEX` reaches `Ready`, a matching
    `SELECT ... WHERE col = ?` point lookup is measured at p99 < 10 ms over
    N repeated lookups, **and** a scan-count assertion (e.g. a
    debug/test-only row-touched counter) proves the lookup touched O(1) rows,
    not the full table — satisfying "measurably avoids a full-table scan."
  - `create_index_range_lookup_returns_correct_rows` — `WHERE col > x AND col
    < y`-equivalent (single bounded range predicate) returns the correct
    subset via the new range-lookup path.
  - `create_index_backfill_row_limit_exceeded_returns_error` — a table over
    the hard cap fails backfill with the new `RS-2xxx` code, and the index
    entry does not remain stuck in `Building`.

## 4. Test Commitments (new operators)

No new IVM/DBSP operator is introduced in this version — Slices 1–4 reuse
`view_materializer.rs`'s existing DataFusion-`MemTable` pattern purely at
query time (read-only, no new streaming operator, no arranged state), and
Slice 5's index backfill is a one-time gateway-local scan-and-write, not a
continuously-maintained incremental operator. The `incremental == batch`
oracle property test therefore does not literally apply. The roadmap's
"oracle-matching results" language for ad hoc JOIN/GROUP BY (Slices 2–3) is
satisfied instead by correctness tests asserting the ad hoc query's live
pgwire result is byte-identical to a hand-computed expected result set over
the same fixture data — the same standard this codebase already applies to
`view_materializer.rs`'s own batch-recompute correctness (no oracle regression
introduced by reusing that exact code path at query time).

## 5. Durability Slices

Slices 1–4 are **read-only** query-time execution against already-durable
`view_output/` data (no new commit/replay/checkpoint/compaction/WAL path is
introduced — the underlying data's durability is already proven by
pre-existing `*_durability_lfs_tests.rs`/`*_durability_minio_tests.rs` files).
No new durability slice is owed for Slices 1–4.

Slice 5 (`CREATE INDEX` automatic backfill) **does** introduce a new durable
artifact — the `0x03‖op_id‖…` index-arrangement bytes plus the catalog's
`Building`→`Ready`/`op_id` state — and owes both backends:

| Durability path (this version) | LFS test | MinIO/TC test |
|---|---|---|
| `CREATE INDEX`'s backfilled `0x03‖op_id‖col_val` index bytes persist and remain point-lookup-servable across a reconnect / new `ShardDb` handle against the same backend | `create_index_backfill_durability_lfs_tests.rs::backfilled_index_persists_across_reconnect_lfs` | `create_index_backfill_durability_minio_tests.rs::backfilled_index_persists_across_reconnect_minio` |
| The catalog's `Ready` state + minted `op_id` for an index survive process restart (re-opened against the same backend) so a post-restart point lookup still uses the index path, not a fallback full scan | `create_index_backfill_durability_lfs_tests.rs::index_ready_state_persists_across_restart_lfs` | `create_index_backfill_durability_minio_tests.rs::index_ready_state_persists_across_restart_minio` |

Follows the existing pattern in `crates/rockstream-gateway/tests/` (e.g.
`mv_immediate_population_durability_lfs_tests.rs` / `_minio_tests.rs`).

## 6. Coordination Slices

Not applicable. All three Scope items (query-time DataFusion execution,
standard `EXPLAIN`, `CREATE INDEX` backfill) operate against the gateway's
single local `shard_db` (hardcoded shard index `0`, same boundary noted by
`sign-offs/v0.51.1.md`) — no cross-shard fan-out, no cross-node coordination,
no new distributed-coordination path is introduced. No `SimRuntime`/
`buggify!()` test is owed by this version. Real multi-shard index
arrangement (backed by an actual `IndexArrangeOp` in the unified data plane)
is reserved for v0.51.3+, which will owe its own coordination-slice tests
when it lands.
