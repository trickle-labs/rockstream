### Gap B (minor, documented deviation) — `CatalogView.op_id` remains `Option<u64>`

Slice 8 specifies changing `CatalogView.op_id` from `Option<u64>` to `u64`
(non-optional). It is still `Option<u64>` (`catalog_stubs.rs:166`). Reading
the current `handle_create_view` (`server.rs:3352` `let compiled_op_id:
Option<u64> = ...`), the `None` case is now reached only when the current
process has **no local `ShardDb`** (a standalone `--role gateway` process in
a multi-shard topology, served via `ViewReader` scatter-read) — a
legitimate, documented architectural case, not the old silent-fallback-on-
compile-failure behavior. A real compile failure on a process that *does*
have a local shard now returns a hard `RS-1019` error (confirmed above,
`server.rs:3421` `Err(e) => return Ok(vec![Response::Error(...RS-1019...)])`).
So the *intent* of Slice 8 (no silent fallback on failure) is met; the
literal type-signature change to non-optional is not. Flagging as a
deviation for the record, not blocking. (Exact current line numbers:
`server.rs:3352` for the `let compiled_op_id` binding, `server.rs:3423` for
the `Err(e) =>` arm returning the `RS-1019` error.)

### Gap A — Durability Slices: FIXED, with a real underlying bug found and fixed

Wrote and **ran** all 4 required Durability Slice test files (LFS only —
MinIO/TestContainers counterparts not yet written, see §6):

- `crates/rockstream-gateway/tests/live_exec_aggregate_durability_lfs_tests.rs::compiled_aggregate_state_persists_across_restart_lfs`
- `crates/rockstream-gateway/tests/live_exec_tumble_window_durability_lfs_tests.rs::compiled_tumble_window_state_persists_across_restart_lfs`
- `crates/rockstream-gateway/tests/live_exec_join_durability_lfs_tests.rs::compiled_join_state_persists_across_restart_lfs`
- `crates/rockstream-gateway/tests/live_exec_session_window_durability_lfs_tests.rs::compiled_session_window_state_persists_across_restart_lfs`

`cargo test -p rockstream-gateway --test live_exec_{aggregate,tumble_window,join,session_window}_durability_lfs_tests`
→ **4 passed** (all 4 suites).

Writing these tests surfaced a real, previously-undiscovered defect: there
was **no startup recovery path at all** for compiled views.
`GatewayHandler.compiled_views` (the process-local `DashMap` populated only
by `handle_create_view`) was silently empty after every restart, even
though `CatalogView.op_id` (durable) still reported the view as compiled —
so a restarted gateway kept serving stale `SELECT` output and **silently
dropped every subsequent commit's effect on that view** (verified: my first
draft of the aggregate test failed with the post-restart insert having zero
effect, before any fix was applied). Fixed by:

- `GatewayHandler::recover_compiled_views()` (new) — recompiles every
  catalog-registered view at startup (`serve()`/`serve_background()`),
  reusing its existing `op_id` (`rockstream_ops::compile_plan_with_sink_id`,
  new) and reproducing its exact internal stage ids deterministically from
  the view name (`rockstream_ops::live_exec::with_view_id_scope`, new —
  replaces the old process-lifetime global atomic counter for internal
  stateful-stage ids, which could never reproduce the same ids across a
  restart).
- New in-place `restore_in_place`/`restore` methods on `AggregateOp`,
  `TumbleWindowOp`, `SessionWindowOp`, `JoinOp`, `Stage`,
  `StatefulPipeline`, `JoinPipeline` — the pre-existing `load_from_storage`
  functions return a *new* instance, useless once an op is already `Arc`'d
  inside a live pipeline.
- Fixed a **second** latent bug found via the tumble-window test:
  `TumbleWindowOp`'s restore didn't reconstruct `prev_output`/`finalized`
  (diff-baseline bookkeeping), causing a touched window to re-emit its
  *entire* content as new inserts instead of a real delta, double-counting
  downstream — fixed by reconstructing both from invariants during restore.
- Fixed a **third** latent bug found via the session-window test:
  `GroupKeyPacker` (composite `GROUP BY` key surrogate-id interning, needed
  for `GROUP BY bidder, SESSION(...)`) had no persistence at all — a
  surrogate remap after restart looked like a brand-new group, duplicating
  output rows. Added `GroupKeyPacker::persist`/`restore_in_place`.

`OuterJoinOp`/`HopWindowOp`/`WindowOp`/`TopKOp`/`DistinctOp` restore remain
documented no-ops — not required by this version's Durability Slices.

## 9. Gap-Fixing Follow-Up Session #3 (2026-08-01): pre-existing nexmark_retraction gap

`cargo test -p rockstream-oracle --test nexmark_retraction` (a pre-existing,
v0.36 test suite — not new to this version, but exercising the composite
`GROUP BY`+`TumbleWindow` live-exec path for the first time) surfaced a
real, serious, generically-applicable correctness bug:
`TumbleWindowOp`/`HopWindowOp`/`SessionWindowOp::process_epoch` (in
`crates/rockstream-ops/src/time_window.rs`) dropped **retractions**
(DELETE/UPDATE effects) of rows in already-finalized/late windows using the
same late-data policy meant only for new arrivals — since the initial
view backfill loads all data in one batch (immediately advancing the
watermark and closing every window), any subsequent DELETE/UPDATE against a
windowed view was silently swallowed, permanently freezing stale data.
**Fixed**: both checks now only apply to positive-weight (new) rows; a
retraction always reopens its target window so the existing diff logic
recomputes and re-emits the correction. Verified via targeted
instrumentation tracing real retract/insert events through
`GroupKeyPacker`/`AggregateOp`/`TopKOp`, and via 2 new regression tests
(`retraction_reopens_finalized_window_without_disturbing_other_groups` in
`time_window.rs`, plus a full-pipeline equivalent and a many-windows/
multi-retraction variant in `live_exec.rs`). Confirmed **zero regressions**:
`cargo test -p rockstream-ops --lib` (160 passed, was 157) and `--tests`
(233 passed, unchanged).

**A second, still-unresolved bug remains**: even after the above fix,
`test_nexmark_q4_q9_retraction_lfs` (view q5) and
`test_nexmark_q12_q22_retraction_lfs` (view q12) still fail — the symptom
*inverted* from over-counting (stale duplicate rows) to under-counting
(entirely valid, untouched groups vanish from the final view, 8 rows in
each test). Ruled out via evidence: TopK tie-break ambiguity (q12 has no
TopK at all and shows the same symptom), `TopKOp` itself dropping rows
(traced one vanished group through `TopKOp` — it never retracted rows it
shouldn't have), and DML `WHERE`-clause ambiguity (instrumented every DML
statement's `CommandComplete` row count — every UPDATE/DELETE affected
exactly 1 row). **3 targeted isolated-operator repro attempts (single
retraction in one finalized window; many windows with simultaneous
multi-window retraction; full `TumbleWindow -> KeyPack -> Aggregate ->
KeyUnpack` pipeline) all pass correctly** — the bug does not reproduce
outside the full SQL/gateway/materialization stack, meaning the remaining
defect is likely in the sink/materialization write path, or in how the
compiled q5/q12 pipeline differs from the hand-built repro (column
ordering, the tumble-window `display_scale` multiplication, or a
persistence/reload interaction) rather than in `TumbleWindowOp`,
`AggregateOp`, `GroupKeyPacker`, or `TopKOp` in isolation. Full findings,
ruled-out theories, and next steps are recorded in
`/memories/repo/implement-version-pipeline.md` (repo-scoped agent memory).

**Conclusion: v0.51.4 sign-off remains blocked.** One real, valuable,
regression-free correctness fix has been made and is included in this
commit. `cargo test -p rockstream-oracle --test nexmark_retraction` still
reports 4 passed / 2 failed. Per the sign-off ground rules ("nothing may be
deferred"), Phase 5 (Sign Off) has not been run and should not be run until
the remaining bug is found and fixed, or the test scope is explicitly
descoped with the user's sign-off.
