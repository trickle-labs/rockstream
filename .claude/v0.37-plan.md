## Vertical Slices

### S1 — SSL Negotiation & Parameter Status Startup Messages

**What:**
- Intercept connection initialization/startup protocol in the TCP serve loop.
- When an `SSLRequest` (represented by magic code `80877103` in the startup packet) is received, write `'N'` (ascii 78) to the connection and flush, so TLS-first clients (like `tokio-postgres` and standard `psql`) downgrade to plaintext gracefully.
- Extend pgwire's parameter provider or add manual `ParameterStatus` response messages in `StartupHandler::on_startup` for:
  - `server_version` (`"14.9 (RockStream)"`)
  - `integer_datetimes` (`"on"`)
  - `standard_conforming_strings` (`"on"`)
  - `DateStyle` (`"ISO, YMD"`)
  - `IntervalStyle` (`"postgres"`)
  - `client_encoding` (`"UTF8"`)

**Exit test (green):**
- Integration test `test_ssl_negotiation_downgrade` in `gateway_extended_query_tests.rs` connects to the gateway using an SSL-first connection, asserts it downgrades, and verifies startup parameters are returned.

---

### S2 — Stateful `PreparedStatementCache` with Parameter Inference & Casting

**What:**
- Implement `PreparedStatementCache` replacing `NoopQueryParser`.
- The cache maps statement name $\to$ SQL text + inferred parameter types (OIDs).
- Parameter type inference:
  - Parse SQL with sqlparser-rs to find `$N` placeholders and any explicit `$N::type` casts (e.g. `$1::INT4`).
  - Match logical plans from DataFusion to infer parameter types based on schema types of referenced columns if not explicitly cast.
- Enforce an upper bound limit on the statement cache (`MAX_PREPARED_STATEMENTS_PER_CONNECTION = 1000`) with appropriate metric and error path returning standard PostgreSQL error codes (e.g., `53200` out of memory/resources).
- Support `DEALLOCATE [ALL]` and `DEALLOCATE <statement_name>` query handling, clearing them from the stateful cache.

**Exit test (green):**
- Integration test `test_prepared_statement_caching_and_deallocate` registers and prepares statements with casts, asserts correct cached parameter type mapping, and verifies `DEALLOCATE` clears them.

---

### S3 — Describe Statement & Describe Portal Implementation

**What:**
- Implement `do_describe_statement`: returns `ParameterDescription` with parameter OIDs, followed by `RowDescription` containing field/column definitions (OIDs, formats, names).
- Implement `do_describe_portal`: returns `RowDescription` containing output field descriptions for the portal.
- Correctly map Arrow/DataFusion types to PG type OIDs in `Describe` responses.

**Exit test (green):**
- Integration test `test_describe_statement_and_portal` describes statements and portals and asserts that correct parameter types and row schemas are returned.

---

### S4 — Parse/Bind/Execute/Close/Sync/Flush State machine & Pipeline Semantics

**What:**
- Implement the full extended query protocol state machine in `ExtendedQueryHandler`:
  - `Parse`: stores prepared statement SQL and inferred types.
  - `Bind`: binds parameters to a prepared statement creating a portal.
  - `Execute`: executes a portal query.
  - `Close`: closes portal or prepared statement.
  - `Sync`: flushes buffered responses and sends `ReadyForQuery`, resetting/finishing the pipeline even if errors occurred (abort-on-error semantics).
  - `Flush`: flushes buffered client messages without sending `ReadyForQuery`.

**Exit test (green):**
- Integration test `test_extended_query_pipeline` verifies that the full Parse $\to$ Bind $\to$ Describe $\to$ Execute $\to$ Sync flow executes correctly and respects pipelining.

---

### S5 — Portal Suspension with `max_rows`

**What:**
- Implement portal suspension inside `do_query`/`on_execute`:
  - If `max_rows > 0` and the query returns more rows than `max_rows`, emit exactly `max_rows` data rows followed by a `PortalSuspended` message.
  - The portal state must be preserved (e.g. index/offset in the row stream) so the subsequent `Execute` on the same portal resumes execution from the exact next row.
  - An `Execute` with `max_rows = 0` returns all remaining rows.

**Exit test (green):**
- Integration test `test_portal_suspension_max_rows` executes a query over 1,000 rows with `max_rows = 10`, asserts exactly 10 rows and `PortalSuspended` are returned, and a subsequent execute resumes and retrieves the rest.

---

### S6 — Multi-Statement Simple Queries & Empty Queries

**What:**
- Semicolon-separated simple queries: support executing queries like `"SELECT 1; SELECT 2"`, where each individual query statement is parsed, executed, and produces its own `CommandComplete` response in order.
- Empty query / whitespace-only query: return `EmptyQueryResponse`.

**Exit test (green):**
- Integration test `test_multi_statement_and_empty_queries` executes multi-statement simple query and asserts multiple result sets/completed tags, and verifies empty query returns `EmptyQueryResponse`.

---

### S7 — End-to-End Driver & ORM Verification

**What:**
- Create `crates/rockstream-gateway/tests/gateway_extended_query_tests.rs`.
- Write end-to-end integration tests using `tokio-postgres` driver performing `.prepare()` and `.query()` with typed parameters, asserting correct rows are returned.
- Implement tests verifying standard `psql` extended query scenarios (e.g. `psql -c '\d my_view'`).

**Exit test (green):**
- Run `rtk cargo test -p rockstream-gateway --test gateway_extended_query_tests` and ensure all tests pass.
