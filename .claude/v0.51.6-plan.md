# v0.51.6 Plan — Session-State Bounding, Isolation-Level Honesty & Aggregate Correctness

Roadmap row: `NEW_ROADMAP.md:1014`. Prior version: v0.51.5 (Gateway-Facing
TLS Termination & Binary Wire Format), `sign-offs/v0.51.5.md` complete, all
12 boxes checked ("Nothing deferred to a later version"). Scope this version
(three independent fixes, all within the wire-protocol pillar):

1. Bound per-connection prepared-statement/portal cache state with LRU
   eviction (today hard-capped at 1000/connection with a hard error, no
   eviction) and guarantee **all** per-connection session-state maps are
   cleaned up on abnormal (dropped-TCP) disconnect, not just the graceful
   `DISCARD ALL`/`RESET ALL` path already covered since v0.37/v0.39.
2. Make `REPEATABLE READ` honest: either genuinely pin/hold the transaction's
   vector frontier for its duration, or reject it with a documented `RS-XXXX`
   code the same honest way `SERIALIZABLE` already is (`RS-2003`).
3. Fix `avg` to use correct floating-point/numeric division instead of
   truncating integer division.

## 1. Deferred-Item Audit

Scanned every `sign-offs/v*.md` (v0.1–v0.51.5, 106 files) for
deferred/postponed/out-of-scope items overlapping "prepared statement",
"portal", "session state", "abnormal disconnect", "REPEATABLE READ",
"isolation level", "frontier", or "avg"/"average":

- `sign-offs/v0.37.md` (Extended Query Protocol) — implemented prepared
  statement caching, portal suspension, and the 1000/connection hard limits
  (`RS-2600`/`RS-2601`), and states explicitly: *"All extended query
  protocol, prepared statement caching, parameter inference, describe stubs,
  portal suspension, and SSL downgrade mechanisms have been implemented and
  fully verified ... No items have been deferred to a later version."* No
  explicit deferral of LRU eviction or abnormal-disconnect cleanup — these
  are latent gaps in v0.37's narrower proof scope (a hard cap satisfies "the
  system doesn't crash," not "the system never surfaces a spurious limit
  error to a well-behaved long-lived client"), not a named deferral.
- `sign-offs/v0.39.md` (Session/Transaction State Machine) — implemented
  `DISCARD ALL`/`RESET ALL` clearing session state on the graceful path only;
  no mention of the TCP-drop path at all, and no deferral recorded.
- No sign-off anywhere mentions `REPEATABLE READ` enforcement, frontier
  pinning across a whole transaction, or `avg`'s division semantics as an
  explicit deferred item. `NEW_IMPLEMENTATION_PLAN.md` §7.1 documents the
  *design intent* for `REPEATABLE READ` ("`BEGIN` captures a vector frontier
  held for the transaction") but no version's sign-off claims this was ever
  built or deferred — it is simply unimplemented design debt, first
  discovered as a live gap during this version's own orientation (see §2).

**Result: no prior version recorded an explicit deferred/out-of-scope item
that overlaps this version's Scope.** All three gaps this version closes are
latent, never-previously-flagged debt, not named deferrals to pick up.

## 2. Current-State Findings (from code)

**A. Prepared statement / portal cache (`crates/rockstream-gateway/src/server.rs`)**

- `GatewayHandler` holds four connection-keyed `DashMap`s that must all be
  emptied when a connection ends: `prepared_statements` (name-set, line
  ~1355), `active_portals` (name-set, ~1356), `portal_states` (buffered rows,
  ~1357), plus `sessions` (`session.rs` `SessionInfo`), `write_buffers`, and
  `copy_states`.
- `on_parse`/`on_bind` (~6965, ~7016) hard-cap each connection's statements
  and portals at a literal `1000`, returning `RS-2600`/`RS-2601` once
  exceeded — no LRU eviction exists today. The actual `Statement`/`Portal`
  objects live in pgwire's own `client.portal_store()` (per-TCP-connection,
  dies with the connection); `rm_statement`/`rm_portal` (used today in
  `on_close`, ~7061/~7069) are the exact primitives an eviction path needs.
- Graceful cleanup: `handle_discard_all` (~5115) clears `copy_states`,
  `portal_states`, `prepared_statements`, `active_portals`, and resets (but
  does not remove) the `sessions` entry. `DEALLOCATE ALL` (~2092) clears
  `prepared_statements`/`active_portals`/`portal_states` only.
- Abnormal-disconnect cleanup: `serve()`/`serve_background()` (~7888,
  ~7923) run cleanup code unconditionally after
  `pgwire::tokio::process_socket()` returns — on **both** graceful close and
  I/O error/EOF (dropped TCP) — but today that cleanup only covers
  `notify_registry.unsubscribe_all` and `pending_notifies.remove`. It is
  **missing** `prepared_statements.remove`, `active_portals.remove`,
  `portal_states.retain(|k,_| k.0 != cid)`, `sessions.remove`,
  `write_buffers.remove`, and `copy_states.remove`. This exact spot is the
  single correct hook — it already fires unconditionally on every
  disconnect path, so no new hook needs inventing.

**B. `REPEATABLE READ` (`crates/rockstream-gateway/src/session.rs`,
`server.rs`)**

- `session.rs` already has `IsolationLevel::RepeatableRead`, a
  `pinned_frontier: Option<u64>` field, `begin()` (~221, captures
  `current_frontier` into `pinned_frontier` only when the level is
  `RepeatableRead`), and `effective_frontier()` (~264, returns
  `pinned_frontier.or(current_frontier)`).
- `server.rs`'s `BEGIN` handler (~2344) passes the live epoch into
  `session.begin(current_frontier)`, so `pinned_frontier` **is** captured
  correctly at `BEGIN` time.
- However, `effective_frontier()` is **never called anywhere** outside
  `session.rs`'s own definition — confirmed by exhaustive grep. The live
  view read path, `read_compiled_view_rows()` (~1660), calls
  `rockstream_ops::read_view_output(shard_db, op_id, ...)` with **no epoch
  or frontier argument at all** — it always reads the current live state.
  There is no point-in-time / as-of-epoch read capability anywhere in the
  compiled-view read path for **any** isolation level, not just
  `REPEATABLE READ` — `READ COMMITTED`'s own documented "each statement pins
  the latest published vector frontier" (`NEW_IMPLEMENTATION_PLAN.md` §7.1)
  is equally unimplemented in the read path.
  `MultiShardReader` (`multi_shard_reader.rs`) does carry a `pinned_frontier`
  field end-to-end and is fully unit-tested in isolation, but it is
  **never constructed from `server.rs`** — it is unused/unwired
  infrastructure, not a partially-wired feature.
- **Decision**: genuinely pinning `REPEATABLE READ`'s frontier for the
  duration of a transaction requires adding an entirely new as-of-epoch read
  capability across the compiled-view materialization/read path (`ShardDb`
  read, `read_view_output`, `MultiShardReader` wiring, DataFusion ad-hoc scan
  path) that does not exist today for *any* isolation level — a
  multi-crate, multi-slice undertaking on its own that is out of proportion
  to a point release also carrying the prepared-statement-LRU and `avg`
  fixes, and orthogonal to those two pillars-scoped fixes. The roadmap row
  explicitly offers rejection ("the same honest way `SERIALIZABLE` already
  is") as an equally acceptable resolution of the Proof claim ("either...
  or..., never silently accepted-but-unenforced"). This plan takes the
  **reject** path: `REPEATABLE READ` returns a new, documented `RS-2004`
  error, exactly mirroring `SERIALIZABLE`'s `RS-2003` (same file, same
  `ql.contains("isolation")` dispatch site in `dispatch_sync` at ~2148, and
  the `SET TRANSACTION ISOLATION LEVEL` handler at ~2796). This is honest
  (no silent no-op), scoped, and consistent with the ground rule against
  scope outside the two pillars. The now-dead `pinned_frontier`/
  `effective_frontier`/`IsolationLevel::RepeatableRead` plumbing is removed
  as part of this slice (ground rules forbid speculative/dead code) — real
  snapshot-pinned reads remain a legitimate, larger, future-version project
  if `REPEATABLE READ` is ever un-rejected.

**C. `avg` aggregate (`crates/rockstream-ops/src/aggregate.rs`,
`compile.rs`, `sink.rs`, `crates/rockstream-oracle/src/aggregate_oracle.rs`)**

- `AggregateOp`'s output schema is 4 `Int64` columns `(k, sum_v, count,
  avg_v)`; `avg_v` is computed with plain integer division (`old_sum /
  old_count` ~348, `new_sum / new_count` ~358, plus incremental-restate
  paths ~611/~618) and is explicitly documented and tested as truncating
  (`avg_truncates_toward_zero`, ~968–979).
- The persisted state format (`ShardDb` `op_state` namespace, documented at
  the top of `aggregate.rs`) stores only `(sum: i64, count: i64)` — the
  truncating `avg_v` itself is *not* persisted, it is recomputed from
  `(sum, count)` on every emit. This means fixing the division does **not**
  change the persisted state encoding — no migration of existing on-disk
  state is needed — but it **does** change the *output row* schema (`avg_v`
  must become `Float8`/`Numeric` instead of `Int64`), which flows through
  `sink.rs`'s row encoder/decoder (`TAG_INT64` vs. a new `TAG_FLOAT64` tag)
  and `column_values_to_tsv_bytes`, both of which currently assume `avg_v`
  is `Int64`.
  This *is* a durability-relevant change (the on-disk row encoding for the
  aggregate operator's output rows changes), so it is treated as a
  Durability Slice (§5), even though the intermediate `(sum, count)` state
  encoding itself is untouched.
- `rockstream-types/src/laws/sum_count.rs`'s `aggregate_avg()` already does
  correct `f64` division (`sum as f64 / count as f64`) — this exists as a
  standalone law-of-large-numbers helper, unused by `AggregateOp` itself, and
  is not the code path a live `SELECT avg(...)` exercises today.
  `rockstream-oracle/src/aggregate_oracle.rs`'s oracle also currently encodes
  `sum / count` (truncating) as its reference semantics and must be updated
  in lock-step so the oracle's "batch" reference matches the new
  incremental semantics (`incremental == batch` — ground rule 3).
- `compile.rs` (~664) routes `AggregateFunc::Avg` to output column index 3;
  unaffected by the type change other than downstream schema plumbing.

## 3. Vertical Slices

- **Slice 1 — LRU eviction for prepared statements/portals.** Replace the
  hard `HashSet<String>` cap-and-reject in `on_parse`/`on_bind` with an
  order-tracked bounded structure (`lru` crate, added as a dependency —
  ecosystem tool over hand-rolled) capped at a new named constant
  `MAX_PREPARED_STATEMENTS_PER_CONN = 1000` /
  `MAX_PORTALS_PER_CONN = 1000` (unchanged limit value, changed behavior:
  evict-oldest instead of error). On eviction, call
  `client.portal_store().rm_statement(&evicted_name)` /
  `rm_portal(&evicted_name)` so the pgwire-side store and our tracking map
  stay consistent. Add fill-level metrics
  `PREPARED_STATEMENTS_EVICTED_COUNT` / `PORTALS_EVICTED_COUNT` (following
  the existing `PREPARED_STATEMENTS_COUNT`/`PORTALS_COUNT` atomic-counter
  convention) so eviction pressure is observable.
  Green test: `prepared_statement_lru_tests.rs` —
  `opening_10k_statements_without_discard_stays_bounded_with_lru_eviction`
  (open 10,000 named prepared statements on one connection without
  `DISCARD ALL`; assert peak per-connection statement count never exceeds
  the bound, no `RS-2600` error is ever returned, and the eviction counter
  increases; then re-execute the most-recently-used statement to confirm it
  was not evicted, and a long-unused one to confirm it correctly
  re-`PARSE`s/errors as `StatementNotFound` since it *was* evicted).

- **Slice 2 — Abnormal-disconnect cleanup of all per-connection state.** In
  the existing unconditional post-`process_socket` cleanup block in both
  `serve()` and `serve_background()`, add
  `prepared_statements.remove(&cid)`, `active_portals.remove(&cid)`,
  `portal_states.retain(|k, _| k.0 != cid)`, `sessions.remove(&cid)`,
  `write_buffers.remove(&cid)`, `copy_states.remove(&cid)`, decrementing
  `PREPARED_STATEMENTS_COUNT`/`PORTALS_COUNT` by the removed counts so the
  fill-level metrics stay accurate across disconnects.
  Green test: `abnormal_disconnect_cleanup_tests.rs` —
  `tcp_level_kill_of_many_connections_shows_zero_session_state_growth` (open
  N connections, each `PREPARE`s several statements and opens portals with
  no `DISCARD ALL`, then kill each connection at the raw-socket level, e.g.
  `TcpStream::shutdown`/drop without the pgwire `Terminate` message, per the
  Backends column's "TC" = raw-socket test convention established in
  v0.51.5's `gateway_tls_tests.rs`); assert all five per-connection maps
  return to empty/zero and the fill-level metrics return to their
  pre-connections baseline after cleanup runs.

- **Slice 3 — Reject `REPEATABLE READ` honestly with `RS-2004`.** Add
  `GatewayError::RepeatableReadNotSupported` to `error.rs`
  (`[RS-2004] isolation.repeatable_read_not_supported: REPEATABLE READ
  isolation is not supported; use READ COMMITTED`), mirroring `RS-2003`'s
  exact structure/SQLSTATE mapping. Extend the existing `ql.contains(...) &&
  ql.contains("isolation")` check in `dispatch_sync` (~2148) to also match
  `"repeatable read"`, and the `SET TRANSACTION ISOLATION LEVEL` handler
  (~2796) to return the new error there too (both `BEGIN ISOLATION LEVEL
  REPEATABLE READ` and `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`
  forms, matching how `SERIALIZABLE` is already caught in both forms via the
  shared `dispatch_sync` check). Remove now-dead code:
  `IsolationLevel::RepeatableRead` variant, `pinned_frontier` field,
  `begin()`'s frontier-capture branch, and `effective_frontier()` in
  `session.rs` (never called; ground rules forbid dead/speculative code).
  Green tests, both new and updated:
  - `repeatable_read_tests.rs::begin_isolation_level_repeatable_read_returns_rs2004`
    and `::set_transaction_isolation_level_repeatable_read_returns_rs2004`
    (mirroring the existing `SERIALIZABLE` coverage pattern).
  - Update `golden_wire_tests.rs`'s existing `BEGIN ISOLATION LEVEL
    SERIALIZABLE` golden-capture test comment/assertions if it incidentally
    exercises `REPEATABLE READ` phrasing (verify at implementation time; if
    not, no change needed there).
  - `session.rs` unit tests referencing the removed `RepeatableRead`
    variant/fields are deleted or updated as part of this slice.

- **Slice 4 — Fix `avg` to correct floating-point division.** Change
  `aggregate.rs`'s output schema `avg_v` from `DataType::Int64` to
  `DataType::Float64`, and its computation from `old_sum / old_count` /
  `new_sum / new_count` (and the two incremental-restate call sites) to
  `old_sum as f64 / old_count as f64` / `new_sum as f64 / new_count as f64`
  (matching `sum_count.rs`'s existing correct `aggregate_avg()` helper's
  semantics — reuse that helper directly rather than re-deriving the
  division inline, per "use ecosystem/existing code" preference). Update
  `sink.rs`'s row encoder/decoder to add a `TAG_FLOAT64` tag (alongside the
  existing `TAG_INT64`/`TAG_UTF8`) for the changed `avg_v` column, and
  `column_values_to_tsv_bytes`/whatever wire-schema-inference path
  (`arrow_type_to_pg_oid`) reports the view column type, so `avg_v` is
  reported as `Float8`/`Numeric` rather than `Int8`/`Utf8` over the wire.
  Update `rockstream-oracle/src/aggregate_oracle.rs`'s reference semantics
  from `sum / count` to `sum as f64 / count as f64` so oracle "batch"
  results match the new incremental semantics (ground rule 3 — oracle
  property test pre-committed *before* the operator change, run first
  against the old code to confirm it now fails, then against the new code
  to confirm it passes).
  Green tests:
  - Update `aggregate.rs`'s own `avg_truncates_toward_zero` test → rename/
    replace with `avg_computes_correct_fractional_average` asserting
    `-21.0 / 3.0 == -7.0` (exact in this case) and a genuinely fractional
    case, e.g. sum=10, count=3 → `avg_v == 10.0/3.0` (not `3`).
  - New `avg_aggregate_precision_tests.rs` (live end-to-end,
    `crates/rockstream-gateway/tests/`): `SELECT avg(qty) FROM t` over rows
    whose true mean is fractional (e.g. `qty ∈ {1,2,4}` → mean `7/3`)
    returns the correct fractional value through the wire protocol, not a
    truncated integer; includes a negative-mean case and a case where the
    true mean is an exact integer (regression: must still be exactly correct,
    not off due to floating rounding for reasonably small integers).
  - Update `rockstream-oracle`'s `oracle_aggregate_100k` proptest and
    `oracle_datafusion_validates_batch_reference` to assert `f64`
    incremental-vs-batch equality (with an epsilon tolerance consistent
    with `sum_count.rs`'s existing `f64::EPSILON`-based test) instead of
    exact `i64` equality.
  - `nexmark/main.rs`'s AVG queries (currently `CAST`-wrapped to `BIGINT`)
    are checked for compatibility at implementation time; if any assert
    exact integer AVG results without an explicit cast, they are updated to
    match the corrected semantics — not deferred.

## 4. Test Commitments (new operators)

No new IVM operator is introduced. `AggregateOp` (Slice 4) is an existing
operator whose *arithmetic* changes, not its shape or incremental algorithm
— the DBSP retract/insert delta rule is unchanged, only the final division
performed on the retained `(sum, count)` state. Per ground rule 3, this
still requires an oracle property test proving `incremental == batch` under
the new semantics: `rockstream-oracle`'s existing `oracle_aggregate_100k`
(100k-case proptest) is updated in Slice 4 to compute its reference `avg` as
`sum as f64 / count as f64` and assert incremental/batch equality within
`f64::EPSILON`, re-run to confirm it fails against the pre-fix truncating
code and passes against the post-fix code. `IVM.md` was searched
(`rtk grep -i "avg\|repeatable read\|prepared statement" IVM.md`) — no
avg-specific invariant beyond the standard DBSP delta rule already covered
by the existing oracle harness, and no isolation-level content, confirming
no additional IVM-level obligation beyond the updated oracle test.

## 5. Durability Slices

Only Slice 4 (`avg`) touches a durability path: the aggregate operator's
persisted-then-replayed **output row** encoding changes shape (`avg_v`
`Int64`→`Float64`; the intermediate `(sum, count)` state format written to
the `op_state` namespace is unchanged, so no state-migration path is
needed — see §2C). Per the ground rules, this new/changed encoding gets
both a SlateDB LFS test and a MinIO (S3, TestContainers) test:

- `avg_aggregate_durability_lfs_tests.rs` (new, `rockstream-ops` or
  `rockstream-gateway` per the existing `live_exec_aggregate_durability_lfs_tests.rs`
  sibling pattern): commit a fractional-average-producing workload against a
  local-filesystem-backed `ShardDb`, restart/reload the shard, and assert the
  reloaded `avg_v` is still the correct `f64` value (not reinterpreted as a
  stale `Int64` tag) — proving the new `TAG_FLOAT64` row encoding survives a
  real WAL-replay/checkpoint-reload cycle, not just an in-memory computation.
- `avg_aggregate_durability_minio_tests.rs` (new, TestContainers-backed real
  MinIO S3 object store, mirroring the existing MinIO test harness pattern
  used elsewhere in the repo for object-store-backed durability tests): same
  scenario as the LFS test, against a real S3-compatible backend, confirming
  the encoding round-trips through actual object-store SST flush/read, not
  just local disk.

Slices 1–3 (prepared-statement LRU, abnormal-disconnect cleanup, `REPEATABLE
READ` rejection) touch only in-memory, per-connection gateway state — none
of the `DashMap`s involved (`prepared_statements`, `active_portals`,
`portal_states`, `sessions`, `write_buffers`, `copy_states`) are persisted to
`ShardDb`/SlateDB/object storage, and rejecting an isolation level at parse
time never reaches `ShardDb`. No new commit/replay/checkpoint/compaction/WAL
path is introduced by Slices 1–3, so no LFS/MinIO test pair is owed for them,
consistent with the roadmap row's Backends column listing `MinIO` as
relevant to this version specifically because of the `avg` durability change,
not the session-state work.

## 6. Coordination Slices

No new distributed-coordination path is introduced. Slices 1–3 are entirely
single-connection, single-process gateway concerns (statement/portal
lifecycle, TCP disconnect handling, isolation-level parsing) that never touch
shard leases, epoch fencing, Raft, or worker registration. Slice 4's fix is a
pure arithmetic change to an existing single-operator computation, not a new
coordination path. Per the ground rules, no new seeded `SimRuntime` test with
`buggify!()` annotations is owed by this version's Scope. (The "TC" raw-socket
test in Slice 2 exercises real concurrent TCP connections and kills, but that
is connection-lifecycle testing, not distributed coordination between
shards/workers — it uses real sockets precisely because pgwire's own
per-connection task lifecycle, not `SimRuntime`, is what is under test.)
