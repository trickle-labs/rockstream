# v0.59.14 Plan — Golden Path Complete

## Scope and Boundary

v0.59.14 implements the Golden Path Complete milestone of the Pre-v1 Product Polish track (`NEW_ROADMAP.md` v0.59.14):

1. **`rockstream init` Project Scaffolding Engine (`GP-001`)**:
   - Introduce `rockstream init [NAME] [--template <local|kafka|postgres-cdc>] [--dir <PATH>] [--force]` into `rockstream-cli`.
   - Scaffold complete, production-structured project directories containing:
     - `rockstream.toml`: Pre-configured runtime configuration matching the selected deployment topology.
     - `schema.sql`: Declarative table, source, sink, and materialized view DDL.
     - `queries.sql`: Canonical diagnostic, inspection, and verification queries.
     - `docker-compose.yaml`: Complete multi-container orchestration profile (where applicable).
     - `data/`: Seed data, streaming event batches, and mock generators.
     - `README.md`: Self-contained onboarding guide and step-by-step instructions.
     - `scripts/verify.sh` & `scripts/cleanup.sh`: Automated verification and teardown scripts.
   - Enforce fail-safe pre-flight checks: abort if target directory exists and is non-empty unless `--force` is specified; validate template identifiers; validate directory permissions.

2. **Local Standalone Template (`local`) (`GP-002`)**:
   - Single-process, zero-external-dependency project template.
   - Uses file/memory stream ingestion and SlateDB on local filesystem (LFS).
   - Establishes base tables (`orders`, `line_items`) and incremental materialized views (`sales_by_store`, `high_value_orders`).
   - Includes local seed datasets, pgwire connection verification scripts, and incremental view assertion tests.

3. **Kafka Streaming Template (`kafka`) (`GP-003`)**:
   - Distributed streaming ingestion template integrated with Apache Kafka / Redpanda.
   - Defines Kafka source and sink connectors, topic schemas (JSON / Avro), and stateful incremental aggregations over real-time events.
   - Supplies Compose profile with Redpanda/Kafka broker, schema registry, console, and continuous mock event producer.

4. **PostgreSQL CDC Template (`postgres-cdc`) (`GP-004`)**:
   - Change Data Capture (CDC) template integrating PostgreSQL logical replication (pgoutput / Debezium).
   - Replicates source transactional tables into RockStream, executes multi-table join and aggregation views, and serves low-latency results via pgwire.
   - Supplies Compose profile with PostgreSQL configured with `wal_level=logical`, replication slots, Debezium connect service, and workload generator.

5. **Maintained Compose Profiles, Verifier & Cleanup Services (`GP-005`)**:
   - Deliver tested, reproducible Docker Compose profiles (`local`, `kafka`, `postgres`, `all`) with deterministic service definitions, health checks, and restart policies.
   - Built-in `verifier` service/script that connects to RockStream over pgwire, executes test queries, compares live incremental results against the exact batch oracle result, and exits with code 0 on success or code 1 on mismatch.
   - Built-in `cleanup` service/script that idempotently stops containers, removes ephemeral networks and volumes, and restores the project directory to a clean state ready for immediate re-execution.

6. **Canonical Examples, Reference Application & Contract Distinction (`GP-006`)**:
   - Production-grade Reference Application: Real-Time E-Commerce Analytics & Fraud Detection pipeline demonstrating multi-source joins, temporal sliding aggregates, Top-K leaderboards, and retraction handling.
   - Documented contract separation:
     - `rockstream demo`: Ephemeral, zero-configuration, self-cleaning, in-memory walkthrough for immediate product evaluation.
     - `rockstream init`: Persistent, customizable, multi-service project scaffold for continuous development, testing, and production operations.

### Non-Negotiable Ground Rules
- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag on the same `rockstream` binary. `main` remains runnable.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters.
- Unbounded in-memory accumulation is never acceptable. Every queue, buffer, or scan window has a named upper bound, fill-level metric, and backpressure/error path.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass. Do not use `--no-verify`. Fix the root cause.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals** overlapping this scope.
