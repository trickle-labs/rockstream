# v0.52.2 design — Shared pgoutput source coordinator

Status: accepted implementation design for v0.52.2.

## 1. Decision

One PostgreSQL logical slot is owned by one source-scoped gateway coordinator.
The coordinator reads the ordered pgoutput stream, routes every relation in an
upstream transaction, builds one M3 `WriteBatch`, durably commits that batch,
and only then acknowledges the transaction's commit LSN to PostgreSQL.

The unit of ownership and recovery is:

```text
SourceIdentity(host, port, database, slot, publication, credential identity)
    -> one owner lease
    -> one pgoutput connection
    -> one relation-route map
    -> one active transaction buffer
    -> one source checkpoint
```

A materialized-view name is never part of this identity. Views subscribe to a
source coordinator; they do not own source connectors.

For one upstream xid, the observable write is exactly:

```text
pgoutput BEGIN ... COMMIT(commit_lsn)
                    |
                    v
             one M3 WriteBatch
               - every routed base-table mutation
               - every affected view output
               - every affected operator-state update
               - the shard frontier
               - every active dependent view's lifecycle/cursor
               - compatible relation-route/schema-history changes
               - one source checkpoint at commit_lsn
                    |
                    v
          durable ShardDb write + flush
                    |
                    v
        acknowledge commit_lsn to PostgreSQL
                    |
                    v
       point-delete this envelope's spill keys
```

The invariant is structural: no helper used by this path may commit base rows,
view output, operator state, lifecycle, frontier, or checkpoint independently.

## 2. Scope and constraints

This design changes pgoutput ownership and commit assembly. It does not add a
second transaction system, cross-shard two-phase commit, a new spill engine, or
a generic coordinator abstraction for other connectors.

All imported tables and dependent view state for one pgoutput coordinator must
reside in the same `ShardDb`. `ShardDb::write_batch` provides atomicity only
inside one SlateDB database. Source/view attachment must fail closed when it
would span shards; distributing this transaction requires a future cross-shard
protocol and is not part of v0.52.2.

The first implementation uses one shard-wide async commit lock for all gateway
writes that can mutate compiled-view state. This serializes pgoutput
coordinators with other source and direct-DML commits while their operator
state and M3 batch are built.

`ponytail: one shard-wide lock is the correctness-first ceiling; replace it
with dependency-component locks only after contention is measured.`

The existing pgoutput operation/type support remains unchanged. Unsupported
messages, streaming-in-progress transactions, prepared transactions, and
incompatible schemas fail closed rather than being partially applied.

## 3. Why the current boundary is wrong

The current gateway derives `ConnectorId` from `(source_name, view_name)` in
`source_view_connector_id`, constructs `PostgresCdcSource` per view, and keys
the live worker by `source:view`. Each runtime can therefore connect to, poll,
checkpoint, and advance the same PostgreSQL slot independently.

The current single-view `commit_bound_source_ops` also computes one compiled
view and writes one lifecycle record. Repeating that helper for N views would
produce N visibility points and could acknowledge the slot after the first
view. It must not be used in a loop for a shared transaction.

The native connector now recognizes `BEGIN`/`COMMIT`, but its relation map
contains only tuple width, its native envelope loses xid/relation identity,
and spill entries are removed while the transaction is drained, before M3
commit. Those are staging concerns that belong to the shared coordinator.

## 4. Durable source identity

### 4.1 Canonical fields

`SourceIdentityV1` contains the effective connection and slot identity:

```rust
struct SourceIdentityV1 {
    host: String,
    port: u16,
    database: String,
    slot: String,
    publication: String,
    auth_principal: String,
    credential_ref: String,
}
```

- Host is trimmed, lower-cased, and has one trailing DNS dot removed. IP
  literals use `std::net::IpAddr`'s canonical text form. DNS is not resolved.
- An omitted port becomes `5432` before identity calculation.
- Database, slot, publication, principal, and credential reference retain
  their exact configured bytes; PostgreSQL names can be case-sensitive.
- `auth_principal` is the configured PostgreSQL user. `credential_ref` is the
  stable secret identity, never the resolved secret value.
- Rotating a secret behind the same credential reference preserves identity.
  Changing an identity field requires a stopped migration/rebind; it may not
  silently start a fresh checkpoint against the old slot.

The durable byte representation is version-tagged and length-prefixed in the
field order above. `ConnectorId` is the existing stable FNV-1a 64-bit hash of
those bytes. The full canonical `SourceIdentityV1` is stored beside the hash;
loading a different preimage for the same hash is a hard collision error.

Source names map to this identity but do not alter it. Two catalog aliases with
the same identity share the same coordinator. Dropping one alias stops the
coordinator only after no alias, imported table, or dependent view remains.

### 4.2 Physical slot uniqueness

The catalog also maintains a unique binding for `(host, port, database, slot)`.
This prevents two identities that differ only by publication or credentials
from claiming the same physical slot. Registration reports the existing owner
instead of opening a second connection.

Identity-bearing source options are immutable while the coordinator is
running. Pause, drain, and an explicit rebind are required to change them.

## 5. Runtime ownership

`GatewayHandler` owns a registry keyed by the source identity hash:

```rust
pgoutput_coordinators:
    DashMap<ConnectorId, Arc<tokio::sync::Mutex<SharedPgOutputCoordinator>>>
```

The registry entry and live-worker key are source-scoped, replacing the
current `source:view` worker key. `DashMap::entry` prevents duplicate tasks in
one process.

Across processes, the coordinator runs only on the holder of the existing
writer lease for the source's `ShardDb`. The control-plane shard lease is the
cross-process fence; `SourceOwnerLease` remains the in-process fence. The
PostgreSQL connection is opened only after both recovery and lease acquisition.
Losing either lease closes the connection and forbids M3 commit or slot
acknowledgement by the old owner.

PostgreSQL slot state is an additional check, not the ownership mechanism. On
startup the coordinator validates that the slot exists, uses plugin
`pgoutput`, belongs to the configured database, and is not active elsewhere.
A missing slot may be created only for a never-checkpointed source. A missing
slot after a durable checkpoint blocks and requires the existing bounded
resnapshot workflow.

## 6. Component boundary

The gateway-specific coordinator lives in
`crates/rockstream-gateway/src/pgoutput_coordinator.rs`. Protocol decoding
stays in `rockstream-connectors`; catalog key encoding and atomic storage stay
in `rockstream-storage`.

The concrete boundary is:

```rust
struct SharedPgOutputCoordinator {
    source_identity: SourceIdentity,
    connector_id: ConnectorId,
    runtime: SourceRuntimeCoordinator<PostgresCdcSource>,
    relation_routes: RelationRoutes,
    envelope_buffer: SpillableArrangement<EnvelopeKey, EncodedChange>,
    active_envelope: Option<ActiveEnvelope>,
}

async fn commit_envelope(
    &mut self,
    envelope: CdcTransactionEnvelope,
    gateway: &GatewayHandler,
    shard_db: &ShardDb,
) -> Result<(), GatewayError>;
```

This intentionally wraps the existing `SourceRuntimeCoordinator` instead of
copying its lease, epoch, checkpoint, and acknowledgement state machine. A
pgoutput-specific runtime method exposes decoded protocol events without
exposing an independent acknowledgement path.

`PostgresCdcSource` becomes the one source-wide transport/decoder. It yields
`Begin`, `Relation`, `Insert`, `Update`, `Delete`, and `Commit` events carrying
relation id and xid context. It no longer owns a table schema, a table name, a
transaction spill arrangement, or a per-view queue.

The current SQL `peek` pagination cannot provide a bounded large-transaction
stream: every peek begins at the unacknowledged slot position. The native path
must use PostgreSQL's logical-replication stream so it can read forward while
feedback remains at the last durable commit LSN. Keepalive feedback reports
only the durable checkpoint, never the decoder's read position.

## 7. Durable relation routing

Relation routing is source catalog state, not connection-local decoder state.
Keys use the existing connector catalog namespace:

```text
connector/<source_id>/pgoutput/identity/v1
connector/<source_id>/pgoutput/relation/<relation_id_be>
connector/<source_id>/pgoutput/schema_history/<schema_version_be>
connector/<source_id>/pgoutput/blocked
connector_slot/<physical_slot_hash> -> source identity
```

Each relation record contains:

```rust
struct RelationRoute {
    version: u16,
    relation_id: u32,
    upstream_namespace: String,
    upstream_relation: String,
    imported_table_id: u64,
    imported_table_name: String,
    columns: Vec<ColumnRoute>,
    replica_identity: ReplicaIdentity,
    schema_version: u64,
}
```

The source/import DDL resolves upstream relation OIDs and persists these
records before a worker can decode tuple messages. Startup order is fixed:

1. acquire the shard/source owner fences;
2. load and verify the full source-identity record;
3. load relation routes, schemas, and blocked state;
4. recover the highest committed source checkpoint;
5. reconcile/ack PostgreSQL to that checkpoint;
6. clean stale spill records with point deletes;
7. open the live read loop and decode tuples.

An event for a publication relation that has no imported route is decoded only
far enough to skip it. It never creates a table implicitly. A relation id whose
durable namespace/name no longer matches blocks the source.

`Relation` messages update a staged copy of the route before a following tuple
is decoded. Compatible changes and their schema-history entry join the xid's
M3 batch. If the batch fails, the durable route remains old and replay sees the
same `Relation` message again.

An incompatible relation change records `BLOCKED(RS-1002)`, the xid, offending
relation metadata, and the last safe committed LSN in one metadata M3 batch.
It applies no row changes, does not advance the source checkpoint, and does not
acknowledge PostgreSQL. No tuple is decoded against the stale ordinal layout.

## 8. Envelope buffering and spill

Only one transaction may be active because pgoutput is ordered. Nested begin,
row-without-begin, commit-without-begin, xid mismatch, and a second uncommitted
envelope are coded source errors.

```rust
struct EnvelopeKey {
    xid: u32,
    sequence: u64,
}
```

Keys serialize xid and sequence in big-endian order below a source-specific
spill prefix. `EncodedChange` retains relation id, operation, old/new tuple,
and the schema version used to decode it. Sequence is assigned in wire order.
`scan_all` results are explicitly sorted by `EnvelopeKey`; hash-map iteration
order is never transaction order.

The coordinator tracks total encoded envelope bytes independently of the
arrangement's in-memory bytes:

- `POSTGRES_CDC_TRANSACTION_MEMORY_BYTES` is the spill threshold;
- `POSTGRES_CDC_MAX_TRANSACTION_BYTES` is the hard total envelope bound;
- exceeding the memory threshold spills cold changes to the existing
  `SpillableArrangement`;
- exceeding the hard bound blocks reading with `RS-4014` and never
  acknowledges the transaction.

The arrangement must be able to spill its sole resident entry when a single
change is larger than the memory threshold; retaining one over-budget entry is
not a valid bound. No new spill implementation or dependency is introduced.

On `Commit`, the coordinator scans and sorts the arrangement, reconstructs the
envelope up to the hard total bound, and builds the M3 batch. Reading spill does
not remove entries. Spill keys are point-deleted only after M3 commit and slot
acknowledgement both succeed, or after recovery has reconciled the slot and
chosen replay. Cleanup failure stops the read loop until cleanup succeeds, so
xid reuse cannot collide with stale keys. Range deletion is forbidden.

## 9. Dependency discovery and view staging

The coordinator holds the shard commit lock while it snapshots catalog
dependencies, stages operator work, and commits. The graph is traversed in
deterministic topological order with view name as the tie-breaker.

The envelope first produces a map of relation name to signed `ArrowZSet`
delta. Each reachable compiled view is processed exactly once:

1. collect all dependency deltas already present in the map;
2. for joins, pass left and right deltas together for the same xid;
3. run the compiled pipeline once;
4. append view output and operator state to the shared M3 batch;
5. add the output delta to the map for downstream views.

This handles a transaction that changes both sides of a join and prevents a
view reachable through two changed tables from running twice. It also fixes
transitive propagation: downstream views consume the staged upstream view
delta rather than searching only the original base-table DML.

Every active view attached to the source receives a lifecycle/cursor record at
the source commit LSN in the same batch, even when its filter produces no rows
or the xid changed only another imported table. Affected views additionally
contribute output and state. Batch validation rejects a missing, duplicate, or
mismatched active-view cursor before storage is called.

A newly created dependent view does not open PostgreSQL. Under the source
coordinator lock it backfills from RockStream's imported base tables, records a
cursor at the coordinator's current source checkpoint, and becomes `RUNNING`
atomically. Before that activation it is unpublished and is not an observer
covered by the active-view invariant. Dropping or pausing a view uses the same
attachment lock.

## 10. `commit_envelope` algorithm

`commit_envelope` is the only pgoutput path that constructs the visibility
batch or invokes source acknowledgement.

1. Require a complete envelope and the active source/shard lease.
2. Require `commit_lsn > source_checkpoint_lsn` and no other in-flight xid.
3. Resolve every buffered change through the restored/staged relation routes.
4. Snapshot active source attachments and compute base-table `DmlOp`s.
5. Acquire the shard-wide commit lock and allocate one global M3 epoch with
   `ShardDb::try_next_epoch`; source epochs may have gaps caused by other shard
   commits and therefore require monotonic, not `current + 1`, validation.
6. Create one `WriteBatch` and append all base-table mutations.
7. Process the affected view graph once and append every output/state update.
8. Append compatible route/schema-history changes and one shard frontier.
9. Append one lifecycle/cursor for every active attached view, all containing
   this epoch and commit LSN.
10. Append one committed source checkpoint containing the same epoch and LSN.
11. Call `ShardDb::write_batch` once and flush it. A durable prepared
    checkpoint is unnecessary for pgoutput because the unacknowledged slot is
    the replay log; this path must not create a second pre-commit M3 batch.
12. Update in-memory source epoch/checkpoint state only after the flush.
13. Acknowledge exactly `commit_lsn` to PostgreSQL. Never acknowledge a row
    LSN, decoder read LSN, or per-view cursor.
14. Point-delete this envelope's spill keys, release the buffer, publish status,
    and poll the next transaction.

An M3 or operator failure fences the coordinator. Because compiled operators
mutate in-memory state while producing their staged batch, the same process
must not retry processing after a failed M3 commit. It reloads affected
pipelines from durable state (or restarts the worker) before replay. This uses
the existing pipeline `restore` methods and avoids a second rollback model.

The existing `SourceRuntimeCoordinator` gains one pgoutput/replayable commit
entry point that accepts all lifecycle records and the caller-built batch. Its
existing generic commit methods remain for other connectors. The new entry
point reuses lease checks, checkpoint encoding, durable flush, blocked-state
handling, and acknowledgement ordering but omits the separate durable
`Prepared` write.

## 11. Recovery

Recovery always loads relation routes before starting protocol decode and
calls recovered acknowledgement before any poll.

| Crash point | Durable M3 checkpoint | PostgreSQL slot | Recovery action |
| --- | --- | --- | --- |
| During `BEGIN`/decode/spill | Previous LSN | Previous LSN | Discard stale envelope spill with point deletes after slot reconciliation; replay the whole xid. |
| After `COMMIT`, before M3 | Previous LSN | Previous LSN | Reload durable operator state and replay the whole xid. |
| M3 result unknown | Read storage | Previous or commit LSN | If the exact commit LSN is durable, acknowledge only; if the previous LSN is durable, replay; any other value blocks as concurrent-owner/corruption. |
| After M3, before ack | Commit LSN | Previous LSN | Call `acknowledge_recovered` for the commit LSN; do not rebuild or rewrite view data. |
| After ack, before spill cleanup | Commit LSN | Commit LSN | Repeat idempotent acknowledgement, then point-delete spill entries. |
| After cleanup | Commit LSN | Commit LSN | Poll strictly after the commit LSN. |

At startup, compare the durable checkpoint with PostgreSQL's confirmed slot
position:

- slot behind checkpoint: retry acknowledgement only;
- slot equal to checkpoint: continue;
- slot ahead of checkpoint: block as externally advanced/data-loss state;
- no durable checkpoint: start from the source's initial snapshot fence.

There is at most one unacknowledged M3-committed xid because the coordinator
does not poll the next envelope until acknowledgement and cleanup finish. This
makes recovery a two-value comparison rather than a durable pending queue.

Per-view lifecycle keys remain namespaced by the source-scoped `ConnectorId`.
For every active attached view, its durable cursor must equal the source
checkpoint LSN in the same batch. Recovery treats any mismatch as corruption
and blocks; it never advances or rewinds one view independently.

## 12. Snapshot and lifecycle changes

Initial PostgreSQL snapshot/fence acquisition is source-wide. One repeatable-
read snapshot imports all registered relation routes, then the shared stream
catches up from its one fence. It is not repeated per dependent view.

Existing per-view lifecycle rows remain because publication/backfill status is
view-specific, but they no longer carry independent slot ownership. `PAUSE`,
`RESUME`, and `DROP SOURCE` must address the source coordinator registry:

- pause stops reads without advancing the slot;
- resume performs full checkpoint/slot reconciliation before polling;
- drop closes the connection and removes source metadata/spill keys with
  bounded scans and point deletes only after attachments are gone;
- changing one view never calls `PostgresCdcSource::commit_offset`.

## 13. Errors and status

`SHOW SOURCES` / `SHOW SOURCE STATUS` project the shared runtime, never secret
material. At minimum they expose source identity hash, owner, slot,
publication, committed LSN, active xid, envelope bytes, in-memory bytes,
current spill bytes, attached/affected view counts, relation/schema version,
and blocked reason.

The coordinator fails closed for duplicate physical-slot ownership, an unknown
or mismatched routed relation, a breaking schema, a slot ahead of M3, a
cross-shard attachment, an over-limit envelope, stale ownership, or incomplete
view lifecycle coverage. Errors leave the slot unacknowledged.

## 14. Minimal implementation map

- `rockstream-connectors/src/postgres_cdc.rs`: keep one source-wide pgoutput
  transport and emit relation-aware protocol events; remove table/view-owned
  transaction spill and Arrow batching from the native path.
- `rockstream-connectors/src/source_runtime.rs` and `source_epoch.rs`: add the
  replayable single-batch commit path, append multiple lifecycles, accept
  monotonic global shard epochs, and acknowledge recovery before polling.
- `rockstream-ops/src/spill.rs`: allow the sole resident entry to spill so the
  named memory bound is real.
- `rockstream-gateway/src/pgoutput_coordinator.rs`: own routing, buffering,
  dependency staging, the one M3 batch, acknowledgement, and cleanup.
- `rockstream-gateway/src/server.rs`: add the source-scoped registry/worker,
  shard commit lock, attach/detach hooks, and remove per-view pgoutput worker
  construction. Other connector paths remain unchanged.
- catalog storage/status: persist identity, physical-slot binding, relation
  routes, schema history, blocked state, and source-scoped view lifecycles.

No new crate or third-party dependency is needed.

## 15. Acceptance tests

Tests assert exact rows, outputs, checkpoints, lifecycles, and call order, not
only counts.

1. Two views and three imported tables sharing one identity open one PostgreSQL
   connection and show one active slot owner.
2. Changing materialized-view names does not change source identity; changing
   host, port, database, slot, publication, principal, or credential reference
   does. Stored-preimage collision and physical-slot collision fail exactly.
3. Restart restores relation routes before the first tuple decoder call.
4. One xid changing two tables, including both sides of a join, yields the
   exact base rows, view rows, operator state, frontier, all active lifecycle
   rows, and source checkpoint in one captured `WriteBatch` call.
5. A transitive view consumes the staged parent-view delta, and a view reached
   by two changed relations executes once.
6. An unaffected active view advances its lifecycle cursor to the same source
   LSN without receiving output.
7. Injected failure before M3 exposes none of the transaction and sends no
   acknowledgement; replay produces the exact expected batch.
8. Injected failure after M3 and before acknowledgement performs acknowledgement
   only and does not execute any operator twice.
9. Unknown M3 outcome chooses ack or replay solely from the exact durable
   checkpoint comparison.
10. A transaction above the memory threshold and below the hard bound spills,
    preserves exact wire order, commits once, and point-deletes every spill key
    only after acknowledgement. A single oversized resident change also spills.
11. Cleanup tests observe point deletes and no range delete.
12. A compatible relation change and history record share the transaction
    batch; an incompatible change persists exact `BLOCKED(RS-1002)` state,
    exposes no tuple, advances no checkpoint, and sends no acknowledgement.
13. Concurrent view attachment linearizes either before the envelope (included
    in its batch) or after it (backfilled at that checkpoint); there is no gap.
14. Two source coordinators targeting one compiled join serialize through the
    shard commit lock and recover the exact durable operator state.
15. A cross-shard dependent view is rejected before a worker or connection is
    created.

The existing v0.52.2 LFS, MinIO/TestContainers, raw-pgwire, and seeded
SimRuntime matrices remain the release proof. Their atomicity oracle must also
assert one `ShardDb::write_batch` for each upstream xid and that PostgreSQL
acknowledgement occurs strictly after its successful flush.

## 16. Rejected alternatives

- **One connector per view:** cannot safely share a slot or checkpoint.
- **Fan out and commit each view separately:** exposes partial transactions and
  can acknowledge early.
- **Put only base rows/checkpoint in M3 and refresh views afterward:** violates
  the visibility invariant even if refresh is fast.
- **Use view name in source identity:** recreates per-view ownership and breaks
  recovery when views are renamed or added.
- **Delete spill while reconstructing the envelope:** loses the recovery copy
  before M3/ack outcome is known.
- **Advance the slot to the decoder read position:** can discard transactions
  that M3 never committed.
- **Add cross-shard 2PC in v0.52.2:** unnecessary for the current single-shard
  gateway path and too large to hide inside a CDC fix.
