# v0.61 Plan — Golden Path and Project Tooling

## Scope and Boundary

Roadmap reference (`ROADMAP.md` §7: `v0.61 — Golden Path and Project Tooling`):
> **Focus**: Make the first 15 minutes with RockStream reliable.
> **User outcome**: A user can execute:
> ```bash
> rockstream project new sales
> cd sales
> rockstream start
> rockstream project apply
> rockstream project verify
> ```
> and obtain a real maintained materialized view. No external `psql` installation is required. Every command uses the live PostgreSQL protocol.
> **Required Proof**: The test must build the release binary and execute the complete project workflow without direct Rust APIs. It must verify:
> `CREATE TABLE`, `CREATE MATERIALIZED VIEW`, `INSERT/import`, `SELECT exact contents`, `UPDATE`, `SELECT changed contents`, `DELETE`, `SELECT changed contents`.
> The generated README commands must themselves be executed by CI.

Committed implementation plan reference: `docs/implementation-plans/v0.61.md`.

v0.61 establishes the golden path across project generation, embedded PostgreSQL protocol tooling, live declarative schema/seed application, and structured verification:

1. **Six-File Project Contract and Versioned Manifest (`project.toml`)**:
   - Standardize `rockstream project new <name>` and `rockstream project init` to generate exactly six files:
     - `rockstream.toml`: Standalone local node configuration (LFS storage at `./storage`, gateway at `127.0.0.1:5432`).
     - `project.toml`: Versioned project manifest (version = 1, ordered apply list, seed declarations with format/table, verify query expectations).
     - `schema.sql`: DDL for base tables and incremental materialized views (`orders` table, `sales_by_store` view).
     - `data/seed.csv`: Seed records for initial ingestion (`orders` records).
     - `queries/verify.sql`: Verification query against the materialized view (`sales_by_store`).
     - `README.md`: Step-by-step golden path documentation (`project new`, `start`, `project apply`, `project verify`).
   - Validate version, referenced paths, file availability, and supported formats before execution.
   - Enforce destination safety: reject non-empty target directory unless `--force` is specified.

2. **Embedded PostgreSQL Client (`rockstream query`, `rockstream shell`)**:
   - Introduce a shared embedded pgwire client module in `crates/rockstream-cli/src/client.rs` leveraging `tokio-postgres`.
   - Never call gateway Rust internal handlers directly; communicate strictly over the live TCP pgwire protocol.
   - Implement:
     - Simple query execution (`Q` wire messages).
     - Extended / prepared query execution (`P`/`B`/`E` wire messages) with typed parameter binding.
     - Multiline REPL input with semicolon termination and command history in `rockstream shell`.
     - Output encodings: tabular (aligned plain text), JSON (array of row objects or lines), and CSV.
     - Query execution timing (`--timing`).
     - SQL-file execution (`--file <path>`).
     - RockStream error-code rendering (`RS-XXXX` extraction from PostgreSQL error fields).
     - Defined escaping, NULL representation (`NULL` in text/table, `null` in JSON, empty string or `\N` in CSV), and type-preserving formatting.

3. **Live Declarative Schema & Seed Application (`rockstream project apply`)**:
   - Establish live pgwire connection to the running node.
   - Execute manifest `[[apply]]` schema files in strict declaration order.
   - Ingest `[[seed]]` data streams (CSV format streaming) without shell pipes or external loaders.
   - Stop immediately on the first unexpected SQL error.
   - Maintain applied step metadata (in `_rockstream_project_metadata` or local state) recording completed steps.
   - Guarantee idempotency: documented repeat `apply` does not duplicate seed data (using deduplication/upsert/tracking).

4. **Structured Project Verification (`rockstream project verify`)**:
   - Execute verification queries declared in `[[verify]]` blocks in `project.toml` or `queries/verify.sql`.
   - Compare structured typed values and complete ordered rows or multisets (preserving types, NULLs, duplicate multiplicities).
   - Rejection semantics: wrong values, extra rows, missing rows, duplicate rows, missing objects, or unavailable service fail nonzero.
   - Report named verification outcome and exact difference diffs on failure.

5. **Template Simplification**:
   - Support `local` template exclusively in `rockstream project new` / `init`.
   - Remove `kafka` and `postgres-cdc` from active template choices.
   - Relocate Kafka and PostgreSQL CDC examples to `examples/experimental/` and mark them experimental until their roadmap milestones (v0.69 / v0.70).

6. **Resource Bounding & Limits**:
   - Bound SQL-file buffering (max 10 MB per file).
   - Bound seed streaming batches (max 1,000 rows / 2 MB per batch).
   - Bound shell input accumulation (max 64 KB per statement).
   - Bound query result accumulation in memory (max 10,000 rows / 16 MB before streaming or budget error).
   - Bound client connect/query timeouts (default 30s) and retry backoff.
   - Expose progress or fill levels and fail explicitly with `RS-0005`/`RS-0004` if budgets are exceeded.

### Non-Negotiable Ground Rules

- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag on the same `rockstream` binary. `main` remains runnable through it.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters, asserted by test.
- Unbounded in-memory accumulation is never acceptable. Every new buffer, batch, or result accumulator has a named upper bound and error/backpressure path.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass. Do not use `--no-verify`. Fix root causes.
- Make only changes this version requires. No speculative features outside IVM engine + Postgres wire layer.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals.**

### Explicitly Out of Scope

- Kafka template and PostgreSQL CDC template (relocated to `examples/experimental/`).
- External performance baseline (v0.61.1).
- Aggregate delta reduction (v0.61.2).
- Node lifecycle and unified `NodeConfig` (v0.62).
- Durable catalog (v0.63).
- Production clustering and multi-node coordination (v0.67+).
- Cloud deployment automation and GUI.
