# v0.47 Plan — Hot-Key Virtual Buckets, Proactive Shard Splitting & Autoscaling Signals

Prerequisite phases 0–1 complete: `sign-offs/v0.46.md` is fully checked off
(`.claude/v0.46-evidence.md`). NEW_ROADMAP.md row read (line 914, Phase 13).

## Proof obligations (restated as checkable assertions)

1. A synthetic hot key at 50× the median shard's load is detected and split
   into virtual buckets within `hot_key_factor` breach + 30s, output
   bit-identical to the non-split oracle.
2. A shard crossing `1.5 × target_shard_state_bytes` splits in the background
   with zero operator action and zero pipeline downtime.
3. A non-composable aggregate (DISTINCT) on a hot key routes to a single
   spill shard and never double-emits under bucket salting (oracle property
   test).
4. A real k8s cluster with HPA configured against the exported
   `cluster_worker_pressure` metric adds a worker within 2 minutes of a
   sustained 10× shard-demand spike and removes it within 10 minutes of the
   spike ending.
5. Architecture constraint: hot-key/re-splitting decision logic lives in
   `rockstream-control`, never `rockstream-plan`; `rockstream-plan` gains only
   the deterministic virtual-bucket `OpNode` variants + the pure
   rendezvous-hash routing function; `rockstream-control` takes a new,
   verified-safe (acyclic) dependency on `rockstream-plan`.
6. Ground rules: no SlateDB range deletion on any new cleanup path; every new
   buffer/queue has a named bound + fill-level metric + backpressure;
   `cargo test --workspace` has no regressions; `make e2e` passes.

## 2. Vertical Slices

Each slice ends in a green test before moving to the next. Ordered so later
slices build on earlier machinery (bucket routing before splitting; splitting
before the control loop; control loop before the metrics it emits).

### Slice 0 — `LawDescriptor.composable` + error-code registry additions
- Add `composable: bool` to `LawProperties`/`LawDescriptor`
  (`crates/rockstream-types/src/merge_law.rs`). Default `true` for existing
  algebraic laws (`SumCount/v1`, etc.); `WeightAdd/v1` (DISTINCT) sets
  `false`, matching DESIGN.md §10.5's exception text verbatim.
- Register `RS-5035` (`SKEW_BOUND` — SLO cannot be met without splitting an
  operator that lacks exact partial-state semantics) and `RS-5036`
  (`SKEW_BOUND_NON_COMPOSABLE` — non-composable law routed to single spill
  shard) in `crates/rockstream-types/src/error_code.rs`, continuing the 5xxx
  (control-plane/elasticity) block after `RS-5034`.
- Test: `merge_law_composable_flag_tests.rs` — `WeightAdd/v1.composable() ==
  false`, every other registered law's `composable() == true`;
  `error_code_registry_tests.rs` extended for `RS-5035`/`RS-5036`.

### Slice 1 — Virtual-bucket `OpNode` variant (rockstream-plan)
- Add `OpKind::VirtualBucketSplit { bucket_count: u16, key_prefix_len: usize
  }` and `OpKind::VirtualBucketCombine { source: OperatorId }` to
  `crates/rockstream-plan/src/lib.rs` — pure, deterministic IR nodes, no
  control-plane state.
- Add the pure salting/routing function (wraps the existing
  `rockstream_types::rendezvous::rendezvous_hash` with a per-key bucket
  salt) in `crates/rockstream-plan` — new module `crates/rockstream-plan/
  src/virtual_bucket.rs`. This is the "pure rendezvous-hash routing
  function" the architecture constraint names as rockstream-plan's only new
  surface.
- Test: `virtual_bucket_routing_tests.rs` — same key + same bucket_count
  always salts to the same bucket (determinism); salted keys distribute
  across all `B` buckets within a documented skew bound for a synthetic
  key population.

### Slice 2 — Hot-key detection (rockstream-control)
- New `crates/rockstream-control/src/skew.rs`: per-key CPU/bytes/state-write
  tracking against `hot_key_factor` (reuses/renames `ShardLoadSample` →
  extended with per-key breakdown), emits a `HotKeyReport` when a key's
  share exceeds `hot_key_factor × median` for the shard.
- This is the decision-maker DESIGN.md §10.5 names for the control plane;
  `rockstream-control/Cargo.toml` gains `rockstream-plan = { workspace =
  true }` (verified acyclic: `rockstream-plan` depends only on
  `rockstream-types`).
- Test: `hot_key_detection_tests.rs` — synthetic per-key load samples at
  50× median trip detection; below-threshold samples do not.

### Slice 3 — Bucket salting + final unsalted combiner (algebraic case)
- Wire `Slice 1`'s `OpNode` variants into the aggregate execution path
  (`crates/rockstream-ops/src/aggregate.rs`): a hot key detected by Slice 2
  is split into `B` partial-state sub-keys `(logical_key, bucket)`; the
  combiner merges partials before emitting view output.
- **Oracle property test (pre-committed per ground rules, before writing the
  operator):** `hot_key_bucket_oracle.rs` in `crates/rockstream-oracle`
  (mirrors the existing `aggregate_oracle.rs` harness) — `incremental ==
  batch`: a bucketed-and-combined aggregate produces byte-identical output
  to the same aggregate computed unsplit, across randomized insert/retract
  sequences and `B ∈ {2,4,8,16}`.

### Slice 4 — Non-composable exception (single spill shard)
- Planner checks `LawDescriptor.composable`; if `false`, routes all rows for
  the hot key to one designated spill shard (no bucket salting) and returns
  `SKEW_BOUND_NON_COMPOSABLE` (`RS-5036`) instead of splitting.
- **Oracle property test:** extend `distinct_oracle.rs` with a hot-key
  scenario — DISTINCT (`WeightAdd/v1`) on a synthetic hot key under
  concurrent epoch-boundary-crossing deltas never double-emits (the exact
  bucket-0/bucket-1 zero-crossing race described in DESIGN.md §10.5 is
  reproduced as a regression case and asserted absent).

### Slice 5 — Proactive shard splitting at `1.5 × target_shard_state_bytes`
- Per-shard footprint reporting (sum of `op_state/*` + `view_output/*`
  ranges) each epoch, feeding into `ProactiveSplitConfig` (reconciled from
  Slice-0 dead code, moved/renamed under `crates/rockstream-control/
  src/skew.rs`, doc comment fixed to "(v0.47)").
- Split mechanism reuses `MigrationCoordinator`/`BucketMapVersionTracker`
  from `crates/rockstream-control/src/migration.rs` (v0.46): pick a midpoint
  key by sampling the shard's hash range, allocate a new shard id, drive the
  existing `PLANNED → ... → DONE` state machine to copy the upper half via
  checkpoint + replay. Throttled to one split per minute per shard.
- Durability slice — see §4 below (this is a "new durability path": a new
  *trigger* for the existing migration state machine, and the split-specific
  midpoint-sampling/range-halving logic is new code that must be proven
  durable independently of v0.46's donor→recipient migration proof).

### Slice 6 — Cold-shard merge at `min_shard_state_bytes` floor
- Reverse of Slice 5: two adjacent cold shards (`state_bytes <
  min_shard_state_bytes`, default 4 GB) merge in the background, again
  riding the migration state machine (recipient absorbs donor's range).
- Test: `proactive_split_merge_tests.rs` — a shard crossing the split
  threshold splits with zero operator action (asserted via a scripted load
  injector, no CLI/API call); two shards below the merge floor merge back;
  splitting and merging never both fire on the same shard within the
  one-per-minute throttle window (rate-limit test).

### Slice 7 — Adaptive skew-splitting control loop (§14.5, fifth loop)
- New `SkewSplitConfig` (mirrors `AutotunerConfig`'s `enabled` toggle
  pattern) with `hot_key_factor`, `max_skew_buckets`, `enabled: bool` —
  independently disableable per view, satisfying the "each independently
  disableable" requirement of the loop table without needing to retrofit
  the other four loops' toggle granularity (out of scope for this version —
  not named in v0.47's Scope/Proof).
- Per-operator override lives in the existing (previously-dead)
  `TunerOverrides` struct — add `skew_buckets: Option<u16>` there rather
  than inventing a new override type.
- Decision logic (worst-shard load exceeds `hot_key_factor × median` for
  > 30s → trigger split) lives in `rockstream-control` per the architecture
  constraint; every adjustment is recorded in the audit log (§14.11,
  existing `audit.rs`) with the metric reading that triggered it, matching
  the other four loops' existing audit behavior.
- Coordination slice — see §5 below.

### Slice 8 — `cluster_worker_pressure` Prometheus export
- Compute `cluster_worker_pressure = max over pipelines of
  (demanded_shard_count / placed_shard_count)` in `rockstream-control`,
  reusing/renaming the dead `ClusterWorkerPressure` struct (doc comment
  fixed to "(v0.47)").
- Export `cluster_worker_pressure`, `demanded_shard_count`,
  `placed_shard_count` as new gauges through the existing
  `rockstream_types::metrics::generate_prometheus_metrics()` pipeline
  (already serving `crates/rockstream-cli/src/metrics_server.rs`'s
  `/metrics` endpoint — no new HTTP surface needed).
- Test: `cluster_worker_pressure_metrics_tests.rs` — gauge values track a
  scripted demanded/placed shard-count sequence exactly; `/metrics` HTTP
  body contains all three metric names with correct `# TYPE gauge` lines
  (extends the existing `metrics_server.rs` test pattern).

### Slice 9 — Real k8s HPA/KEDA integration test
- No k8s test harness exists in the repo today (confirmed: zero `kind`/`k3d`/
  `kubectl` references outside docs/prose). Build one: a new TestContainers-
  style test that requires `docker`, `kind` (or `k3d`), and `kubectl` on the
  runner (gated by the same `docker_available()`-style probe pattern as
  `worker_drain_tc_tests.rs`, extended with a `kind_available()` probe;
  `#[ignore]`-free but skips with a clear stderr message — not a silent
  no-op — when tooling is absent, matching the existing TC convention of
  never `#[ignore]`-gating away real coverage).
- Cluster: a real `kind` cluster, `rockstream:ci` image deployed as a
  Deployment + a sidecar/adapter exposing `/metrics` to a real
  `prometheus-adapter` or KEDA `ScaledObject`-compatible metric source, a
  real `HorizontalPodAutoscaler` (or `ScaledObject`) targeting
  `cluster_worker_pressure`.
- Test: `hpa_autoscale_kind_tests.rs::real_hpa_scales_out_and_in` — inject a
  sustained 10× shard-demand spike (drives `cluster_worker_pressure > 1.0`),
  assert `kubectl get hpa` / pod count grows within 2 minutes; end the
  spike, assert scale-in within 10 minutes. This is the single most
  expensive test in the plan; it runs only when `kind`+`kubectl` are present
  (same posture as the existing Docker-gated TC tests).

### Slice 10 — Architecture-constraint compliance check
- `rockstream-control/Cargo.toml` gains `rockstream-plan` (Slice 2); confirm
  no cycle: `rockstream-plan`'s own `Cargo.toml` still lists only
  `rockstream-types` + `serde` after all slices (test below fails the build
  if that ever changes).
- Test: `crate_dependency_direction_tests.rs` (new, in `rockstream-control`
  or a workspace-level script) parses `crates/rockstream-plan/Cargo.toml`
  and asserts it lists no `rockstream-ops`/`rockstream-control` dependency —
  the same class of guard `scripts/check-invariant-pairs.sh` /
  `check-error-codes.sh` already provide for other cross-cutting rules.
