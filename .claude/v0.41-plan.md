### Slice 1 — `error.rs` — New RS transaction error codes

Add five new error variants and their SQLSTATE/sqlstate_for mappings:

- `RS-2560` `InFailedSqlTransaction` — SQLSTATE `25P02` — severity `ERROR`  
  message: `"[RS-2560] transaction.in_failed_sql_transaction: query cannot run inside a failed transaction block. next_steps: Issue ROLLBACK to exit the failed block, then retry."`
- `RS-2561` `SavepointNotFound { name: String }` — SQLSTATE `3B001` — severity `ERROR`  
  message: `"[RS-2561] transaction.savepoint_not_found: savepoint '{name}' does not exist. next_steps: Use SAVEPOINT <name> to create one before ROLLBACK TO."`
- `RS-2562` `TwoPhaseNotSupported` — SQLSTATE `0A000` — severity `ERROR`  
  message: `"[RS-2562] transaction.two_phase_not_supported: PREPARE TRANSACTION / XA two-phase commit is not supported. next_steps: Use a single-phase COMMIT instead."`
- `RS-2563` `SavepointLimitExceeded { limit: usize }` — SQLSTATE `54000` — severity `ERROR`  
  message: `"[RS-2563] transaction.savepoint_limit_exceeded: per-transaction savepoint limit of {limit} exceeded. next_steps: RELEASE earlier savepoints before creating new ones."`
- `RS-2564` `NotifyChannelLimitExceeded { limit: usize }` — SQLSTATE `54000` — severity `ERROR`  
  message: `"[RS-2564] notify.channel_limit_exceeded: notify channel limit of {limit} exceeded. next_steps: UNLISTEN unused channels."`

Update `test_all_rs_codes_have_sqlstate` to include all five new variants.

**Green gate**: `test_all_rs_codes_have_sqlstate` passes (existing test updated).

### Slice 2 — `write_buffer.rs` — SavepointStack

Extend `WriteBuffer` with named savepoints:

```rust
/// Named upper bound for savepoints per transaction.
pub const MAX_SAVEPOINTS_PER_BUFFER: usize = 128;

// In WriteBuffer:
savepoints: Vec<(String, usize)>,  // (name, ops_len at save time)
```

Methods added to `WriteBuffer`:
- `create_savepoint(&mut self, name: &str) -> Result<(), GatewayError>`:  
  If already exists by name: overwrite (Postgres semantics — SAVEPOINT with existing name replaces it).  
  If `savepoints.len() == MAX_SAVEPOINTS_PER_BUFFER`: return `GatewayError::SavepointLimitExceeded`.  
  Otherwise push `(name.to_string(), self.ops.len())`.
- `release_savepoint(&mut self, name: &str) -> Result<(), GatewayError>`:  
  Find last entry with matching name; if not found return `GatewayError::SavepointNotFound`.  
  Remove that entry and all entries after it (RELEASE drops nested savepoints too — Postgres semantics).  
  Does NOT discard ops.
- `rollback_to_savepoint(&mut self, name: &str) -> Result<(), GatewayError>`:  
  Find last entry with matching name; if not found return `GatewayError::SavepointNotFound`.  
  Truncate `self.ops` to the recorded `ops_len`.  
  Recalculate `self.byte_count` by summing `op.byte_size()` on the surviving ops.  
  Remove all savepoints after (and including) the matched entry from the stack (retain the named savepoint itself so further ROLLBACK TO the same name is valid — consistent with Postgres).  
  Actually per Postgres spec: after ROLLBACK TO s, the savepoint s is NOT removed (can ROLLBACK TO s again). Remove only entries after s.
- `clear_savepoints(&mut self)`: remove all savepoints — called at COMMIT and ROLLBACK.

**Green gate**: unit tests in `write_buffer.rs`:
- `savepoint_create_rollback_to` — push 3 ops, create savepoint "s", push 2 more, rollback_to "s", assert `ops.len() == 3`, `savepoints` has "s" still present
- `savepoint_release_does_not_discard` — push 1 op, create "s", push 2 more, release "s", assert `ops.len() == 3`, `savepoints.is_empty()`
- `savepoint_not_found_returns_error` — rollback_to "nonexistent" returns `SavepointNotFound`
- `savepoint_limit_exceeded` — create MAX_SAVEPOINTS_PER_BUFFER + 1 distinct savepoints, last returns `SavepointLimitExceeded`
- `savepoint_overwrite_replaces` — create "s" at ops_len=1, push more ops, create "s" again at ops_len=3, rollback_to "s" truncates to 3 ops

### Slice 3 — `session.rs` — Transaction state machine extensions

Add fields to `SessionState`:
```rust
/// True when an explicit BEGIN block is active.
pub in_explicit_block: bool,
/// SET LOCAL overrides — cleared at COMMIT or ROLLBACK.
pub local_guc_params: HashMap<String, String>,
```
Defaults: `in_explicit_block: false`, `local_guc_params: HashMap::new()`

New methods on `SessionState`:
- `begin_explicit(&mut self)`:  
  Set `in_explicit_block = true`, `tx_status = TxStatus::InTransaction`.
- `fail_transaction(&mut self)`:  
  Set `tx_status = TxStatus::Failed` (only if `in_explicit_block`; single-statement implicit tx failures do not persist).
- `end_transaction(&mut self)` — extend existing:  
  Also clear `in_explicit_block = false`, `local_guc_params.clear()`, leave `guc_params` intact (SET LOCAL only, not SET).
- `is_in_failed_block(&self) -> bool`:  
  Returns `self.tx_status == TxStatus::Failed`.
- `effective_guc(&self, key: &str) -> Option<&str>`:  
  Check `local_guc_params` first, then `guc_params`.

**Green gate**: unit test `test_transaction_state_machine` in `session.rs`:
- New session → tx_status Idle, in_explicit_block false
- begin_explicit → InTransaction, in_explicit_block true
- fail_transaction → Failed
- end_transaction → Idle, in_explicit_block false, local_guc_params empty

### Slice 4 — `server.rs` — Aborted-transaction guard + tx status propagation

Two changes in `dispatch_async_with_conn`:

**Guard at top of dispatch (before dispatch_sync / other handlers)**:  
If `session.is_in_failed_block()` and the normalized query is NOT one of `rollback`, `rollback;`, and does NOT start with `rollback to`:
- Return `Err(PgWireError::UserError(Box::new(ErrorInfo::new("ERROR", "25P02", "[RS-2560] ..."))))`

This ensures every command in a failed block is bounced immediately.

**Error-in-block → flip to Failed**:  
Wrap the core dispatch call in a match. If an error `Err(_)` is returned AND `session.in_explicit_block`:
- Call `session.fail_transaction()`
- Re-return the error

(Single-statement errors outside an explicit block do NOT persist the Failed state — the session stays Idle.)

**BEGIN idempotency**:  
In `dispatch_sync`, when `tx_status == InTransaction` and we receive BEGIN:
- Do NOT call `begin_explicit` again
- Return `CommandComplete("BEGIN")` (Postgres issues a warning "there is already a transaction in progress" but we keep it simple in v0.41 — just succeed silently)

When `tx_status == Idle` and we receive BEGIN: call `session.begin_explicit()`, return `TransactionStart("BEGIN")`.

**END alias**:  
In `dispatch_async_with_conn`, handle `ql == "end"` || `ql == "end;"` as an alias for COMMIT.

**COMMIT / ROLLBACK set tx status**:  
After successful `handle_commit` or `handle_rollback`: call `session.end_transaction()`.
(Currently `end_transaction` is only called in some paths; audit all code paths to ensure it is called unconditionally.)

**Green gate**: unit test `test_failed_block_blocks_commands` in `gateway_proof_tests.rs`:
```
1. connect (no-shard gateway)
2. CREATE TABLE t (id BIGINT) → success
3. BEGIN → 'T' status
4. force an error (SELECT * FROM nonexistent_view) → error, status → 'E'
5. SELECT 1 → must return error with SQLSTATE 25P02
6. ROLLBACK → success, status → 'I'
7. SELECT 1 → success
```

### Slice 5 — `server.rs` — SAVEPOINT commands

In `dispatch_async_with_conn`, add handlers (after aborted-tx guard):

**`SAVEPOINT <name>`**:
- Parse: `ql.starts_with("savepoint ")` → extract name
- Require `session.in_explicit_block`; if not: return error "SAVEPOINT can only be used in transaction blocks"
- `write_buffers.entry(conn_id).or_default().create_savepoint(name)?`
- Return `CommandComplete("SAVEPOINT")`

**`RELEASE SAVEPOINT <name>`** / **`RELEASE <name>`**:
- Parse: `ql.starts_with("release savepoint ")` or `ql.starts_with("release ")`
- `write_buffers.entry(conn_id).or_default().release_savepoint(name)?`
- Return `CommandComplete("RELEASE")`

**`ROLLBACK TO SAVEPOINT <name>`** / **`ROLLBACK TO <name>`**:
- Parse: `ql.starts_with("rollback to savepoint ")` or `ql.starts_with("rollback to ")`
- `write_buffers.entry(conn_id).or_default().rollback_to_savepoint(name)?`
- If `session.tx_status == TxStatus::Failed`: reset to `TxStatus::InTransaction` (ROLLBACK TO reactivates the block)
- Return `CommandComplete("ROLLBACK")`

**`PREPARE TRANSACTION <lit>`** / **`COMMIT PREPARED <lit>`** / **`ROLLBACK PREPARED <lit>`**:
- Match `ql.starts_with("prepare transaction")` / `"commit prepared"` / `"rollback prepared"`
- Return `GatewayError::TwoPhaseNotSupported.into()` (SQLSTATE 0A000)

At `handle_commit` and `handle_rollback`: call `write_buffer.clear_savepoints()`.

**Green gate**: unit/integration test `test_savepoint_rollback_partial_write` in new `tests/transaction_savepoint_tests.rs` (LFS via `start_gateway_with_shard`):
```

BEGIN
INSERT INTO items VALUES (1, 'before')
SAVEPOINT s
INSERT INTO items VALUES (2, 'after')
ROLLBACK TO s
COMMIT
SELECT * FROM items → exactly row (1, 'before')
```

### Slice 6 — `server.rs` + `session.rs` — SET LOCAL / SET TRANSACTION

**`SET LOCAL key = value`**:  
In `dispatch_sync` SET handler, detect `ql.starts_with("set local ")`:
- Strip "local " prefix, parse `key = value` or `key TO value` as per existing SET logic
- Store in `session.local_guc_params[key] = value` (NOT `guc_params`)
- `set local` outside an explicit block: accepted but has no visible effect (Postgres: SET LOCAL outside a transaction is just like SET)
- Return `CommandComplete("SET")`

**SHOW lookup order**:  
Update the SHOW handler to check `session.local_guc_params` before `session.guc_params` before defaults (use `session.effective_guc(key)`).

**`SET TRANSACTION ISOLATION LEVEL <level>`**:  
In `dispatch_sync`, parse `"set transaction isolation level read committed"` / `"repeatable read"` / `"serializable"`:
- Update `session.isolation_level`; serializable → return RS-2003
- Return `CommandComplete("SET")`

**`SET TRANSACTION READ ONLY`** / **`SET TRANSACTION READ WRITE`**:  
Accept silently, return `CommandComplete("SET")` (no enforcement in v0.41 — RockStream is always effectively READ COMMITTED for reads and does not enforce read-only mode).

### Slice 7 — `notify_registry.rs` — LISTEN/NOTIFY channel registry

New file `src/notify_registry.rs`, added to `src/lib.rs`:

```rust
/// Max distinct notify channel names registered per gateway.
pub const MAX_NOTIFY_CHANNELS: usize = 1_000;
/// Max pending notifications per connection outbox.
pub const MAX_OUTBOX_PER_CONNECTION: usize = 10_000;
```

`NotifyRegistry` struct (no sub-crate, just `DashMap`-based):
- `subscriptions: DashMap<String, HashSet<String>>` — channel_name → set of conn_ids
- `outboxes: DashMap<String, Vec<(String, String, i32)>>` — conn_id → Vec<(channel, payload, sender_pid)>

Methods:
- `subscribe(&self, channel: &str, conn_id: &str) -> Result<(), GatewayError>`:  
  If channel not present and `subscriptions.len() == MAX_NOTIFY_CHANNELS`: return `NotifyChannelLimitExceeded`.  
  Insert conn_id into `subscriptions[channel]`.  
  Ensure `outboxes[conn_id]` entry exists (empty vec).
- `unsubscribe(&self, channel: &str, conn_id: &str)`:  
  Remove conn_id from `subscriptions[channel]`. If set becomes empty, remove the channel entry.  
  (No-op if not listening — Postgres UNLISTEN of a not-listened channel is not an error.)
- `unsubscribe_all(&self, conn_id: &str)`:  
  Remove conn_id from every channel's set; remove any emptied channel entries.  
  Remove `outboxes[conn_id]`.
- `deliver(&self, channel: &str, payload: &str, sender_pid: i32) -> usize`:  
  For each conn_id in `subscriptions[channel]` (if any):  
    If `outboxes[conn_id].len() < MAX_OUTBOX_PER_CONNECTION`: push `(channel, payload, sender_pid)`.  
  Return count actually enqueued.
- `drain_outbox(&self, conn_id: &str) -> Vec<(String, String, i32)>`:  
  `std::mem::take(&mut outboxes.entry(conn_id).or_default())`.

**Green gate**: unit tests in `notify_registry.rs`:
- `test_subscribe_deliver_drain` — subscribe A to "chan", deliver "hi", drain A → 1 entry
- `test_unsubscribe_stops_delivery` — subscribe, unsubscribe, deliver → drain empty
- `test_unsubscribe_all_clears_all_channels` — subscribe A to "c1" and "c2", unsubscribe_all(A), deliver to both → drain empty
- `test_outbox_limit_no_panic` — fill outbox to MAX_OUTBOX_PER_CONNECTION, one more deliver → drain returns exactly MAX limit items (excess dropped)

### Slice 8 — `server.rs` — LISTEN/NOTIFY dispatch + notification delivery

**Add to `GatewayServer`**:
```rust
notify_registry: Arc<NotifyRegistry>,
pending_notifies: DashMap<String, Vec<(String, String)>>,  // conn_id → [(channel, payload)]
```
Initialize `notify_registry: Arc::new(NotifyRegistry::default())` in `GatewayServer::new()` (and `start_gateway_*` helpers in tests via builder or default).

**`dispatch_sync` additions** (checked before existing handlers):
- `ql == "listen"` or `ql.starts_with("listen ")` → parse channel name, `notify_registry.subscribe(channel, conn_id)?`, return `CommandComplete("LISTEN")`
- `ql == "unlisten"` or `ql.starts_with("unlisten ")` →  
  If `ql == "unlisten *"` or `ql == "unlisten"`: `notify_registry.unsubscribe_all(conn_id)`  
  Else: parse channel, `notify_registry.unsubscribe(channel, conn_id)`, return `CommandComplete("UNLISTEN")`

**`dispatch_async_with_conn` additions**:
- `NOTIFY <channel>` / `NOTIFY <channel>, '<payload>'`:  
  Parse channel and optional payload (default `""`).  
  If `session.in_explicit_block`: push `(channel, payload)` to `pending_notifies[conn_id]`.  
  Else: `notify_registry.deliver(channel, &payload, session.backend_pid)`.  
  Return `CommandComplete("NOTIFY")`.
- `SELECT pg_notify('<chan>', '<payload>')`:  
  In `catalog_stubs.handle_query`: detect `pg_notify(` pattern, parse args, call `notify_registry.deliver(...)` (pass `notify_registry` as a new parameter to `handle_query`, or handle in `dispatch_async` before delegating).  
  Return single-row result with column `pg_notify`, value `""` (void, like Postgres).

**At `handle_commit`** — after successful flush:
- Drain `pending_notifies.remove(conn_id)` → for each `(channel, payload)`: `notify_registry.deliver(channel, &payload, session.backend_pid)`.

**At `handle_rollback`**:
- `pending_notifies.remove(conn_id)` — transactional NOTIFYs are aborted.

**Notification delivery injection** — before each `client.set_state(ReadyForQuery)` call in the extended query protocol and simple query handlers:
- Call a helper `drain_and_send_notifications(client, conn_id, &self.notify_registry).await?`
- That helper: `for (channel, payload, pid) in notify_registry.drain_outbox(conn_id) { client.send(PgWireBackendMessage::NotificationResponse(NotificationResponse::new(pid, channel, payload))).await?; }`

**DISCARD ALL extension**:
- Add `self.notify_registry.unsubscribe_all(conn_id)` and `self.pending_notifies.remove(conn_id)` inside `handle_discard_all`.

**On disconnect**:
- In the connection cleanup path (where cursors/sessions are cleaned up): `notify_registry.unsubscribe_all(conn_id)`.

**Green gate**: integration test `test_listen_notify_delivers` in new `tests/listen_notify_tests.rs`:
- Spawn in-process gateway (no shard needed)
- Connection A: `LISTEN events`
- Connection B: `NOTIFY events, 'hello'`
- Connection A: issue any query (e.g. `SELECT 1`) — receives `NotificationResponse` with channel "events", payload "hello" via tokio-postgres `connection.notifications().next()`

## Durability Slices

v0.41 savepoints are in-memory checkpoints on the write buffer; they are not individually persisted to SlateDB (only COMMIT flushes to SlateDB). The write buffer is already covered by the existing LFS `start_gateway_with_shard` tests (S9/P1, S9/P2).

New durability paths: none beyond the existing COMMIT flush path.

No new MinIO (S3, TestContainers) test required — savepoints do not add a new durability path.

## Coordination Slices

v0.41 adds no new distributed-coordination paths. LISTEN/NOTIFY is single-node (in-memory registry). No `SimRuntime`/`buggify!()` tests required.
