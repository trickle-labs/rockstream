# v0.59.23 plan - Capacity planning and estimator calibration

## Scope and boundary

The roadmap row at NEW_ROADMAP.md:1847 requires calibrated small, medium, and
large reference profiles. The profiles must measure the frozen engine and make
EXPLAIN INCREMENTAL ESTIMATE report canonical arrangement sharing and the
selected physical strategy. They must also publish guidance that users can
inspect before deployment.

This version reuses the existing rockstream binary, CLI, configuration, IVM
operators, and test-support harness. It does not add SQL syntax, a new
workspace crate, a new IVM operator, or a new distributed coordination
protocol. v0.59.24 owns the RC qualification run. v0.59.23 creates the
immutable per-reference-profile threshold manifest that v0.59.24 consumes.

The implementation must use scan-and-delete or a snapshot-safe compaction
filter for any cleanup. It must not call SlateDB range deletion.

## Capacity model and bounded collection

The model reuses ArrangementSpec and ArrangementCatalog. It uses the
ArrangementId, not a view name, as the maintained-state identity. A report
contains one private-state entry per arrangement, one shared-state entry per
ArrangementId, and one consumer entry per view. Twenty views using three
canonical arrangements therefore report three maintained arrangements and
twenty consumers. They must never report twenty maintained copies.

The model reuses the compiled join strategy from the existing compiler. A
factorized join reports bounded factor-payload state, factor-payload bytes,
and delta amplification. A classic join reports its materialized intermediate.
The report labels the strategy so a user can see why the estimates differ.

Source statistics follow DESIGN.md:773. Connector statistics win over catalog
statistics, and catalog statistics win over a marked low-confidence fallback.
The report records the source of each input and the profile revision. The
implementation must not invent a confidence value from a missing input.

Each raw measurement record includes the profile, workload digest, candidate
identity, hardware identity, arrangement identities, selected strategy, and
estimated and observed values for:

- private and shared state bytes, RSS, spill bytes, cache-hit ratio, epoch
  duration, commit-group duration, p99 freshness, and shuffle bytes;
- logical and physical writes, object-store requests, checkpoint cost, and
  compaction debt; and
- the error for every estimated value that has an observation.

Raw records stream to immutable chunks. The in-memory batch is limited by
CAPACITY_SAMPLE_BATCH_MAX = 10,000 records and
CAPACITY_SAMPLE_BATCH_BYTES_MAX = 32 MiB. The collector exports
rockstream_capacity_sample_batch_fill_ratio. At either limit it flushes before
accepting another record. If a flush fails, the profile run fails with a
capacity-recording error. It must not retain an unbounded retry queue.

The three profiles are fixed by their workload corpus and recorded hardware,
not by made-up performance results:

| Profile | Topology and arrangement shape | Required workloads |
|---|---|---|
| small | One worker, one canonical arrangement, one consumer. | Uniform aggregation and a low-cardinality window. |
| medium | Four workers, three canonical arrangements, and twenty consumers. | Shared uniform aggregation, high-cardinality aggregation, classic and factorized joins, and windows. |
| large | Eight workers with maintained state larger than the declared worker cache and RAM allowance. | State-over-RAM aggregation, a shuffle-heavy join, a window slice, and sustained Zipf hot-key traffic. |

The corpus fixes source rows, update order, random seeds, schema, view SQL,
concurrency, cache budget, spill policy, checkpoint cadence, commit-group
settings, and source and binary digests. The run records the reference
hardware before it starts. Floors and ceilings come from recorded results,
not constants chosen in this plan.

## Vertical slices and test commitments

1. Add the capacity profile schema, raw-record schema, immutable chunk writer,
   and result reducer in existing crates. Reuse CandidateIdentity from
   crates/rockstream-types/src/candidate_identity.rs:12 and EvidenceManifest
   from crates/rockstream-types/src/evidence_manifest.rs:113. End with
   capacity_profile_calibration_tests::raw_fixture_reduces_to_exact_summary.
   The test compares the full ordered summary, workload digests, and error
   ranges with the checked-in fixture.

2. Extend the existing SQL estimator. It must consume canonical arrangements,
   consumer counts, source-statistic provenance, and selected strategy. End
   with every aggregate, join, and window matrix test above green. The
   twenty-view fixture must produce exactly three maintained arrangements,
   twenty consumers, and the expected shared-byte saving. The factorized
   fixture must fail if a flat intermediate cardinality is substituted.

3. Wire the common report through PGWire and the CLI. End with
   explain_incremental_estimate_capacity_pgwire_tests::mixed_case_estimate_returns_exact_report
   and cli_capacity_estimate_tests::cli_and_pgwire_reports_match_exactly.
   The first asserts the complete PGWire text for mixed-case SQL. The second
   compares complete text and JSON reports from both entry points.

4. Run the reproducible workload corpus against the three profiles. Feed
   PostgreSQL CDC and Kafka inputs through real workers, then collect LFS and
   MinIO results. End with
   capacity_profile_connector_tests::postgres_cdc_and_kafka_emit_exact_calibration_rows
   through TestContainers, every profile-workload test above, and
   capacity_profile_calibration_tests::all_profile_metrics_and_error_ranges_are_exact.
   The latter asserts the complete ordered rows and error ranges regenerated
   from raw inputs. It fails if sharing, factorization, selectivity, skew, or
   freshness moves an estimate in the wrong direction.

5. Create the per-reference-profile threshold manifest and the generated
   capacity guidance. The manifest binds the canonical threshold payload,
   candidate identity, hardware identity, concurrency, workload digests,
   raw-record digests, absolute floors, and ceilings. It uses a SHA-256 digest
   of canonical serialized content and create-only storage. End with
   capacity_threshold_manifest_tests::sealed_manifest_rejects_any_mutation
   and capacity_guidance_determinism_tests::raw_records_regenerate_exact_guidance.
   The latter compares the full published guidance and error-range table.

6. Add release gates. A seal is accepted only when all required profile and
   workload rows exist, all values were observed, and every threshold source
   digest is present. The gates reject stale hardware, changed workload,
   missing metric, changed candidate, duplicate worker identity, one-process
   multi-worker measurement, and a modified manifest. End with
   capacity_release_gate_tests::complete_signed_profile_set_is_required.

No new operator is introduced, so no new per-operator incremental-equals-batch
property test is required. The calibration scenarios run the existing
operators and compare every final row and weight with the independent batch
oracle. That is mandatory for each scenario in slice 4.

capacity_threshold_manifest_durability_tests::cleanup_never_uses_range_delete
must assert that the new persistence path contains no SlateDB range-deletion

The collector is external benchmark instrumentation. It does not add a
runtime coordination protocol. Existing checkpoint and global-commit paths
remain unchanged. If implementation adds a cross-worker collection or sealing
protocol, it must add a seeded SimRuntime test with buggify annotations before
the change can merge. The test must compare the complete final multiset,
published frontier, and sealed manifest transcript.
