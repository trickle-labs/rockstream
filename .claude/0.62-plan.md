# v0.62 Plan — Unified Configuration and Node Lifecycle

## Scope and Boundary

Roadmap reference (`ROADMAP.md` §8: `v0.62 — Unified Configuration and Node Lifecycle`):
> **Focus**: Create one authoritative description of a RockStream node.
> **User outcome**: A single configuration file can explain exactly what the process will start and how it will behave.
> **Required Proof**: The same configuration must produce equivalent behavior when supplied by:
> - file,
> - environment,
> - CLI override.
> The test suite must prove that:
> - invalid config fails before opening service ports,
> - effective config reports origins,
> - generated project config validates cleanly,
> - every started service reaches the expected lifecycle state,
> - `Ready` is never emitted before mandatory recovery completes.

Committed implementation plan reference: `docs/implementation-plans/v0.62.md`.
Apply the shared implementation and evidence rules: `docs/implementation-plans/README.md`.

v0.62 unifies the configuration system, origin tracing, schema diagnostics, storage URL binding, and node runtime lifecycle:

1. **Authoritative `NodeConfig` Schema (`crates/rockstream-types/src/config.rs`)**:
   - Replace overlapping startup and subsystem configurations with `NodeConfig` in `rockstream-types`.
   - Top-level `version: ConfigVersion` (version = 1).
   - Exactly nine canonical configuration sections:
     - `[node]`: `role` (`all`, `control`, `worker`, `gateway`, `metrics`), `host_id`, `availability_zone`.
     - `[gateway]`: `listen_addr`, `tls`, `max_connections`, `query_timeout_secs`.
     - `[control]`: `listen_addr`, `url`, `shared_storage`, `raft` (`peers`, `node_id`, `bind`, `bootstrap`).
     - `[worker]`: `worker_id`, `execution_threads`, `segment_cache_bytes`, `max_rows_per_quantum`, `capabilities`.
     - `[storage]`: `url` (`file://...`, `s3://...`), `temp_dir`, `spill_dir`.
     - `[metrics]`: `listen_addr`, `enabled`, `scrape_interval_secs`.
     - `[auth]`: `mode` (`off`, `scram`, `md5`, `oidc`, `mtls`), `secret_path`, `admin_user`.
     - `[logging]`: `level` (`error`, `warn`, `info`, `debug`, `trace`), `format` (`text`, `json`).
     - `[runtime]`: `shutdown_timeout_secs`, `min_epoch_ms`, `checkpoint_retention_count`, `state_budget_gb`.
   - Single inventory of all existing startup options: every active option has exactly one resolved owner or an explicit deprecation.
   - Backward compatibility: legacy `RockstreamConfig` structures parse with clear migration guidance or transparent translation into `NodeConfig`.

2. **Single Override Precedence and Origin Tracking (`crates/rockstream-types/src/config_resolver.rs`)**:
   - Enforce the non-negotiable precedence hierarchy:
     `compiled defaults < configuration file < environment variables < CLI overrides`.
   - Track provenance for every field through `ConfigOrigin`:
     - `Default`: compiled-in default value.
     - `File(PathBuf)`: loaded from configuration file.
     - `Env(String)`: overridden via environment variable (e.g., `ROCKSTREAM__GATEWAY__LISTEN_ADDR`).
     - `Cli(String)`: overridden via explicit CLI flag (e.g., `--listen 127.0.0.1:5433`).
   - Implement `rockstream config print-effective --origins` output:
     - Complete rendering of the resolved `NodeConfig`.
     - Every key annotated with its source origin.
     - Strict redaction of secrets, passwords, tokens, and private keys (`[REDACTED]`).
   - Service listening addresses are first-class properties of their services (`gateway.listen_addr`, `control.listen_addr`, `metrics.listen_addr`).
   - Invariant: No startup path may recompute different defaults after resolution.

3. **Strict Validation, Typo Diagnostics & Pre-Bind Port Rejection (`crates/rockstream-types/src/config_validation.rs`)**:
   - Reject unknown sections and unknown keys in `version = 1` configurations.
   - Diagnostics provide actionable feedback: source file path, line and column numbers, unknown key name, and nearby valid keys using Levenshtein distance matching.
   - Validate version, role requirements (e.g., worker requires control URL), address parseability, authentication settings, and resource limits before binding any socket.
   - Invariant: Invalid configurations must fail fast and cleanly *before* binding or opening any service ports.

4. **Explicit Storage URLs (`crates/rockstream-types/src/config.rs`, `crates/rockstream-storage/src/`)**:
   - Replace ambiguous directory paths and raw backend strings with explicit URLs:
     - `file:///path/to/storage` (absolute file path)
     - `file://./data` (relative file path, resolved relative to configuration file base directory)
     - `s3://bucket/prefix` (S3-compatible object store)
   - Reject unimplemented schemes (e.g., `http://`, `hdfs://`, `ftp://`) with explicit diagnostics.
   - Relative file URLs resolve consistently against the documented config base directory.
   - Invariant: Inaccessible or uncreatable storage fails startup immediately with nonzero exit code; silent fallback to ephemeral in-memory state is forbidden.

5. **Unified Component Architecture & State Machine (`crates/rockstream-types/src/lifecycle.rs`, `crates/rockstream-cli/src/`)**:
   - Introduce `NodeRuntime`, `Component`, and `ComponentState` abstractions in `rockstream-cli`.
   - Canonical lifecycle states:
     `Created -> Starting -> Recovering -> Ready -> Draining -> Stopping -> Stopped -> Fatal`.
   - Core components:
     - `ControlComponent`: Manages cluster metadata, leases, and Raft consensus.
     - `WorkerComponent`: Manages data-plane execution, shard execution, and task processing.
     - `GatewayComponent`: Serves PostgreSQL wire protocol connections and query execution.
     - `MetricsComponent`: Serves Prometheus metrics and HTTP health/readiness endpoints.
     - `ConnectorSupervisor`: Manages external ingestion connectors and sources.
   - Role composition symmetry:
     `role = "all"` composes the exact same component implementations as separate single-role processes.
   - Readiness gating:
     - Health endpoint (`/healthz` or `/live`) reports process aliveness.
     - Readiness endpoint (`/readyz`) reports `false` (HTTP 503) during `Starting` and `Recovering`.
     - Readiness transitions to `true` (HTTP 200) *only* after mandatory recovery succeeds and validation passes.
     - Recovery failure transitions directly to `Fatal` (HTTP 500) and terminates startup.

6. **Production Lifecycle & Removal of No-Op Startup (`crates/rockstream-cli/src/lib.rs`, `shutdown.rs`)**:
   - Remove production sleep-based or no-op startup completion (`ROCKSTREAM_E2E_SLEEP_MS` or default 50ms sleep in `crates/rockstream-cli/src/lib.rs:1028-1033`).
   - Every server role remains alive until explicit shutdown signal (SIGINT/SIGTERM), fatal failure, or coordinator trigger.
   - Testing shortcuts such as fast-exit move strictly into the test harness or CLI flags (`--exit-after-ready` / test coordinator triggers).
   - Startup failure cleans up all already-started components within named deadlines before surfacing the error.
   - Graceful shutdown enters `Draining`, propagates deadlines to active components, and completes within `shutdown_timeout_secs`.

7. **Operational Bounding & Limits**:
   - Bounded startup requests and registration waiters (max 20 attempts / 50ms interval, 1s deadline).
   - Bounded drain waiters (timeout bounded by `shutdown_timeout_secs`, default 30s).
   - Bounded lifecycle transition event queue (max 1,024 events).
   - Bounded health diagnostic buffer (max 64 KB / 100 entries).
   - Named backpressure and failure propagation on boundary violations.

### Non-Negotiable Ground Rules

- Prefix every shell command with `rtk` (e.g. `rtk cargo test`, `rtk git status`).
- One binary, one CLI, one config: every role is a flag or config property on the same `rockstream` binary. `main` remains runnable through it.
- No code path may depend on SlateDB range deletion. Cleanup is scan-and-delete or snapshot-safe compaction filters, asserted by test.
- Unbounded in-memory accumulation is never acceptable. Every new queue, buffer, or scan window needs a named upper bound, a fill-level metric, and a backpressure or error path.
- Do not weaken, skip (`#[ignore]`), or delete tests to make a build pass. Do not use `--no-verify`. Fix root causes.
- Make only changes this version requires. No speculative features outside IVM engine + Postgres wire layer.
- **Nothing may be deferred to a later version.**
- **Pick up all prior deferrals.**
