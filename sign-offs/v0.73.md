## Legacy authorization storage inspection (not migration qualification)

See [`AclStore`](../crates/rockstream-control/src/acl.rs), [`AclEntry`](../crates/rockstream-types/src/acl.rs), [`CatalogRoleEntry`](../crates/rockstream-storage/src/catalog/mod.rs), and the [catalog transaction](../crates/rockstream-storage/src/catalog/txn.rs). No supported persisted legacy grant format is established by this source inspection. This does not establish what external deployments contain; preserve fail-closed rejection and keep the upgrade/migration case unqualified until a supported stored format is evidenced and tested.

## CLI local-adapter route gaps

Local `audit tail/query` also lack a role check, so the scoped audit-read requirement in #305 remains unqualified.

The [disaster-recovery runbook](../docs/disaster-recovery.md) documents the top-level `checkpoint export` and `checkpoint restore` commands. [The binary dispatch](../crates/rockstream-cli/src/main.rs) routes these through `StorageClient`, which performs object-store I/O but gates those operations only on the caller-provided `Role`; this adapter has no durable-principal authorization. The separate `admin checkpoint` binary route uses [`RemoteStorageAdminClient`](../crates/rockstream-cli/src/transport.rs), whose checkpoint methods return `remote_query_unavailable`, and the [management protocol](../crates/rockstream-management-proto/proto/management/v1/management.proto) has no checkpoint export/restore RPC. No supported authenticated binary path is established by this source inspection, so checkpoint coverage remains unqualified under V073-02/V073-10. Do not treat `--identity-role admin` as proof of authority; provide an authenticated route or an explicit scope decision before counting this coverage.

On the release CLI candidate based on runtime code `2aaa8c92`, `RUSTUP_TOOLCHAIN=1.99.1 rtk cargo test --locked --release -p rockstream-cli --test cli_disaster_recovery_tests checkpoint_export_restore_cli_outputs_and_audits_exactly -- --exact` passed 1 test. The test runs the documented top-level export/restore commands without management or TLS credentials, expects the caller-supplied `--identity-role admin` to authorize the operations, and checks that the caller-provided `dr-admin` label is written to local `audit.jsonl`; it also checks the viewer-role denial. This confirms legacy CLI behavior, not authenticated authorization. See the [test](../crates/rockstream-cli/tests/cli_disaster_recovery_tests.rs) and [test summary](v0.73-checkpoint-cli-boundary-2aaa8c92.log).

The same binary dispatch routes local `admin backup` operations (except `create` when a management address is configured), `admin restore`, `support bundle`, `support diagnose`, and `audit tail/query` through `StorageClient::with_identity`. `cli_identity` constructs that identity from the user and role flags; local role comparisons do not map a certificate to a durable principal. Some local actions have role checks, while audit reads, checkpoint list/show, and backup inspect/verify do not. These paths therefore establish filesystem/object-store access and legacy self-asserted role behavior, not shared durable-grant authorization. `support artifact create/download` and management-backed backup creation instead use `ManagementCliClient`, which requires a client certificate, private key, trusted CA, and TLS. `security preprovision-admin` and `security recover-admin` are explicit offline catalog operations with separate confirmation and audit behavior, not general request authentication. See [`main.rs`](../crates/rockstream-cli/src/main.rs), [`cli_identity`](../crates/rockstream-cli/src/main.rs), [`StorageClient`](../crates/rockstream-cli/src/transport.rs), and [`ManagementCliClient`](../crates/rockstream-cli/src/transport.rs). The broader CLI endpoint matrix and shared authorization remain unqualified under #301/#302/#306.
