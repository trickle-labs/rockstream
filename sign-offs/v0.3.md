# v0.3 Sign-off — SlateDB storage contract and determinism gate

**Signed off**: 2026-06-07

## Scope recap

v0.3 completes the `rockstream-storage` (`ShardDb`) contract: key encoders with
`namespace_id` in all catalog keys; `WriteBatch` builders; `DbReader` snapshot
reads; WAL tail reader with listing cache; checkpoint helpers; scan-and-delete
cleanup. No range deletion anywhere.

The **SlateDB determinism gate** is the binding proof obligation: the same
write-heavy `ShardDb` workload run twice — once against a fresh LFS tempdir and
once against a freshly-provisioned MinIO container — produces bit-identical
key-value state in both cases.

`make e2e` now exercises three backends: the no-op binary in both `--role=control`
and `--role=worker` modes, the full LFS backend integration suite, and the MinIO
TestContainers integration suite.

New integration test files added:
- `crates/rockstream-storage/tests/lfs_backend.rs` — 12 LFS tests
- `crates/rockstream-storage/tests/minio_backend.rs` — 3 MinIO / TC tests

New workspace dependencies added:
- `testcontainers = "0.23"`, `testcontainers-modules = { version = "0.11", features = ["minio"] }`
- `object_store = { version = "0.12", features = ["aws"] }` (promoted from storage-internal to workspace)
- `tempfile = "3"` (promoted to workspace)
- `reqwest`, `sha2`, `hmac`, `hex` (dev-deps for SigV4 bucket creation in MinIO tests)

## Proof obligations (NEW_ROADMAP.md v0.3 row) → evidence

The Proof column reads: *"Storage API validation suite proves only supported
SlateDB features are used. **SlateDB determinism gate**: a write-heavy `ShardDb`
workload run twice at the same seed produces bit-identical key-value state and
WAL sequence; any non-deterministic SlateDB background surface is found and
constrained before v0.4. `make e2e` brings up MinIO + 1 worker + 1 control and
tears it down."*

| # | Proof claim | Evidence |
|---|---|---|
| 1 | Storage API validation suite — only supported SlateDB features used | `lfs_backend::supported_api_surface_validation` (in `src/tests.rs`) and the 12 LFS integration tests in `tests/lfs_backend.rs`. Every path through the storage layer uses only: `get`, `put`, `delete`, `merge`, `write_batch`, `scan_prefix`, `flush`, `close`, `DbReader`. `lfs_backend::no_range_delete_method_exists` and `tests::no_range_delete_method_exists` provide compile-time + doc-level assertions that `range_delete` is not exposed. `lfs_backend::lfs_scan_and_delete_cleanup_no_range_delete` exercises the scan-and-delete pattern in the context of actual cleanup. |
| 2 | SlateDB determinism gate — LFS: same workload, two independent tempdirs, bit-identical KV state | `lfs_backend::lfs_determinism_gate_bit_identical_kv_state` — 100 puts, 8 deletes, 4×20 merge accumulations, 5 epochs of batched writes, frontier key; both tempdirs produce identical key count and identical (key, value) pairs. `lfs_backend::lfs_determinism_gate_interleaved_operations` covers interleaved puts/merges/batches/deletes across 5 epochs. |
| 3 | SlateDB determinism gate — MinIO: same workload, two independent MinIO containers, bit-identical KV state | `minio_backend::minio_determinism_gate` — 50 puts, 5 deletes, 3×10 merge accumulations, 10-key batch, flush; both MinIO containers (provisioned via TestContainers) produce identical key count and identical (key, value) pairs. | 4 | `make e2e` brings up MinIO + 1 worker + 1 control and tears it down | `minio_backend::minio_e2e_worker_and_control_roles` — opens two `ShardDb` instances against the same MinIO container (one using catalog-key namespace = "control shard", one using shard-local keys = "worker shard"); both write, read, flush, and close cleanly. `make e2e` Step 1 also runs `cargo run -- start --role=control` and `cargo run -- start --role=worker` end-to-end. |
| 5 | No non-deterministic SlateDB background surface found for sequential single-writer workloads | Two independent runs (LFS and MinIO each) of an identical sequential write workload produce bit-identical output. No background compaction, GC, or S3 ListObjects call introduces non-determinism for sequential single-writer operations. The `WalListingCache` (v0.1 code) constrains hot-path LIST calls to the initial mount. |

## Notes

- New integration test files: `tests/lfs_backend.rs` (LFS, 12 tests), `tests/minio_backend.rs` (MinIO/TC, 3 tests).
- New workspace deps: `testcontainers = "0.23"`, `testcontainers-modules = { version = "0.11", features = ["minio"] }`, `object_store = { version = "0.12", features = ["aws"] }`, `tempfile = "3"`, `reqwest`, `sha2`, `hmac`, `hex`.
- `testcontainers_modules::minio::MinIO` wraps `quay.io/minio/minio` with correct image, command, and wait condition. The test bucket is created via a hand-rolled SigV4 `CreateBucket` request to avoid needing `mc` or a separate container.
- The LFS determinism gate validates that two independent `TempDir`-backed `ShardDb` runs with the same sequential operation sequence produce bit-identical KV state — proving determinism holds at the on-disk layer, not merely in memory.
- The MinIO determinism gate validates the same property through the S3 object-store layer, proving that S3 list/get/put semantics (conditional writes, multipart, object listing) do not introduce non-determinism for sequential single-writer workloads.
- `make e2e` extended from a single no-op binary run to three steps: (1) no-op binary in both `--role=control` and `--role=worker` modes, (2) LFS backend suite, (3) MinIO backend suite via TestContainers.
- Deferred (out of scope for v0.3, by roadmap schedule): per-operator oracle tests, IVM engine (v0.4+); multi-shard exchange (v0.16+); checkpoint coordinator (v0.20+).
