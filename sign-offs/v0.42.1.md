## Background

The `<=v0.42` implementation review (2026-07-10) found the `formal-verify` CI
job had never actually worked: a wrong FizzBee release-asset download URL, a
bare-binary-only extraction that omits the `fizz` wrapper's sibling files, an
invalid PR-trigger condition (`changed_files` is an integer count, not a file
list), and `continue-on-error: true` meant no model had ever been a real gate.
Running the real toolchain for the first time found M2 genuinely green, M1
failing `M1_S5_IdempotentReplay`, and M3/M4 crashing outright.

## Proof Claims Verification

- [x] **`formal-verify` CI installer resolves the real per-OS/arch FizzBee
  release asset and installs the full `fizz` wrapper directory**
  - **Evidence**: `.github/workflows/ci.yml` `formal-verify` job's
    `Install FizzBee` step resolves `browser_download_url` from the GitHub
    Releases API (`.../releases/latest`) instead of a guessed fixed filename,
    and adds the whole extracted directory (containing `fizz`, `fizzbee`,
    `fizz.env`, `parser/`, `mbt_gen.zip`) to `$GITHUB_PATH`.
  - **Command**: manually verified via a real `fizzbee` v0.5.2 binary
    downloaded and run locally (see `formal/findings.md` "Post-v0.42 Review").

- [x] **PR trigger condition does a real diff against the merge-base**
  - **Evidence**: the `Determine whether formal verification applies` step in
    `.github/workflows/ci.yml` runs `git merge-base` + `git diff --name-only`
    and greps for `^(formal/|DESIGN\.md|crates/rockstream-(runtime|control|connectors|storage)/)`,
    replacing the invalid `contains(github.event.pull_request.changed_files, 'formal/')`
    guard.

- [x] **`formal/m1_epoch_commit.fizz`'s `M1_S5_IdempotentReplay` scoping bug
  is fixed and the spec is genuinely green**
  - **Evidence**: `CommitEpoch0`/`CommitEpoch1` now clear
    `duplicate_commit_delivered` when they fire, scoping the idempotent-replay
    check to the single state immediately after the duplicate. Result: 72
    nodes, 72 unique states, safety + liveness hold.
    See `formal/findings.md` "Post-v0.42.1 Remediation Results".
  - **Command**: `fizz formal/m1_epoch_commit.fizz`

- [x] **`formal/m3_sink_2pc.fizz`'s undefined-variable crash, Starlark
  set-literal syntax error, `sink_pending_epoch` reset bug, and unbounded-crash
  liveness starvation are all fixed and the spec is genuinely green**
  - **Evidence**: explicit role instantiation in `Init`, `ext.delivered_epochs.add(...)`
    replacing the invalid Python-style set-literal union, `SinkFinalize`
    clearing `s.sink_pending_epoch`, and a `MAX_CRASHES` bound on the crash
    actions. Result: 1,168 nodes, 1,168 unique states, all safety invariants +
    `M3_L1_DeliveryProgress` liveness hold.
    See `formal/findings.md` "Post-v0.42.1 Remediation Results".
  - **Command**: `fizz formal/m3_sink_2pc.fizz`

- [x] **`formal/m4_self_fencing.fizz`'s undefined-variable crash and a real
  heartbeat/self-fence race are fixed**
  - **Evidence**: explicit role instantiation, folding the self-fence
    transition into the same atomic step as the threshold-crossing increment
    (fixing `M4_S2_SelfFencePrecedence`), and adding `RestartWorker` so a
    terminated worker can regain eligibility. Exhaustive verification of the
    full state space does not yet terminate at this point — closed in
    v0.42.3, not this version.
    See `formal/findings.md` "Post-v0.42.1 Remediation Results".

- [x] **`continue-on-error` removed for smoke/M1/M2/M3; M4 stays
  non-blocking pending v0.42.3, and a same-day CI-robustness follow-up
  ensures a `cancelled` M4 step conclusion can never flip the whole job to
  `failure`**
  - **Evidence**: `.github/workflows/ci.yml` hard-gates smoke/M1/M2/M3;
    the first real CI run (push `2a98157`) showed the M4 step itself get a
    `cancelled` conclusion (consistent with the runner's OOM killer), which
    `continue-on-error` does not suppress. Fixed same day by running M4 under
    a per-subshell `ulimit -v` cap plus a wall-clock `timeout`, swallowing its
    exit code into a step output instead of the step's own outcome.
    See `formal/findings.md` "Post-v0.42.1 Remediation Results", item 4.
