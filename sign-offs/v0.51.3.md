## Notes

Full evidence (commands, outputs, and the exact proof mapping) is recorded in
`.claude/v0.51.3-evidence.md`. v0.51.3 closes the two-disconnected-data-planes
architecture gap at its root: `rockstream start --role all` now opens exactly
one SlateDB data plane (no separate gateway-local `<storage>/gateway-shard/`),
DML written over pgwire is registered as real input to a `rockstream-runtime`
worker's operator DAG, and `SELECT` reads the worker's `ViewSink` output
rather than a gateway-local-only table. `rockstream-gateway`'s `Cargo.toml`
now carries genuine non-dev dependencies on `rockstream-runtime`,
`rockstream-plan`, `rockstream-ops`, and `rockstream-diff`. `CREATE
VIEW`/`CREATE MATERIALIZED VIEW` issued over pgwire compiles through the real
`rockstream-sql` → `rockstream-plan` `PlanNode`/`OpNode` IR →
`rockstream-diff` → `rockstream-runtime` scheduling pipeline instead of the
standalone DataFusion `view_materializer`. This is purely a plumbing/wiring
version — view refresh incremental maintenance is deferred to v0.51.4 by
design (explicitly scoped out of this version, not an omission), and no new
FizzBee model is needed since the epoch-commit/frontier/fencing protocols
(M1–M4) are unchanged.

All 5 Proof-Mapping rows from `.claude/v0.51.3-plan.md` §7 are satisfied with
passing, live-pgwire and real-MinIO/TestContainers tests. Two pre-existing
`clippy -D warnings` violations found incidentally while finalizing sign-off
(an unused `shard_db` binding in `mv_immediate_population_durability_lfs/
minio_tests.rs`, a `sort_by` that clippy prefers as `sort_by_key` in two
`sink_multi_type_durability_*_tests.rs`/`unified_data_plane_oracle_tests.rs`
files, and an overly-complex tuple type in
`unified_data_plane_oracle_tests.rs`) were fixed as part of this sign-off so
`cargo clippy --workspace --all-targets -- -D warnings` is fully green with
zero suppressions. `cargo fmt --check` is clean after running `cargo fmt`.

A real regression was found and fixed during this sign-off's full
`cargo test --workspace` run (not present in the narrower per-crate proof
suites run during Phase 4): `crates/rockstream-gateway/src/server.rs`'s
`GatewayHandler::try_compile_view()` hardcoded `PlanNode::ViewSink { pk:
vec![0] }`, so every compiled view (including a bare passthrough like
`CREATE VIEW q0 AS SELECT * FROM bid`) was upserting on column 0 as an
implicit primary key, silently collapsing multiple rows sharing that
column's value instead of preserving `bid`'s full append-only multiset —
caught by `rockstream-oracle`'s pre-existing `test_nexmark_q0_q3_retraction_lfs`
et al. Fixed by compiling views with a full-row `pk`, tracking materialized
compiled-view state as `(row, multiplicity)` counts, emitting multiplicity
deltas on recompute, and expanding multiplicities back to duplicate rows on
`SELECT`; added `compiled_view_state_preserves_full_row_multiplicity` unit
test. Re-verified clean: `rockstream-oracle --test nexmark_retraction` (6
passed), `gateway_proof_tests` (107 passed, 1 ignored),
`unified_data_plane_tests` (2 passed), `unified_data_plane_oracle_tests` (2
passed), `sink_multi_type_tests` (3 passed), `cargo fmt --check` and
`cargo clippy --workspace --all-targets -- -D warnings` both clean.

One unrelated, pre-existing test failure was found and root-caused during the
full `cargo test --workspace` run: `rockstream-sql`'s
`test_nexmark_ingestion_lfs` (`crates/rockstream-sql/tests/nexmark/main.rs`,
introduced in v0.50, `git log` confirms it predates v0.51.3) always fails
with "person row count mismatch left: 1 right: 10" because its assertion
counts `SimpleQueryMessage::Row` messages returned by `SELECT COUNT(*) FROM
person` — which always returns exactly one row (the aggregate itself) — as
if it were the count value, instead of parsing the numeric value out of that
one row. Verified via `git stash`/A-B test that this failure is 100%
identical (same "left: 1, right: 10", same panic location) with none of
v0.51.3's changes applied, i.e. on the pre-v0.51.3 baseline — it is a
pre-existing test-assertion bug wholly unrelated to this version's Gateway↔
Runtime unification scope, not a regression introduced here, and out of
scope to fix under this version's Proof claims. Not deferred as
"incomplete work belonging to this version" — it belongs to v0.50 and is
orthogonal to any v0.51.3 Proof claim.

The full `cargo test --workspace` run is otherwise green with zero
regressions relative to the pre-v0.51.3 baseline (see Definition-of-Done
checklist above). Nothing in v0.51.3's own scope was deferred.
