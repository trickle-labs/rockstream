## Incremental changes in this PR
- Workload definition carries a persisted numeric revision; older records without one decode at revision 1.
- Conditional `ALTER WORKLOAD <name> IF REVISION <n> SET (...)` compares revision at the actual producer catalog update, returning SQLSTATE `40001` on conflict.
- The in-memory catalog compare-and-swap checks and updates under a single write lock. Conflict and overflow leave the requested definition unchanged; concurrent callers cannot both win a stale revision.
- Async conditional updates are serialized and apply the persisted definition before publication in the gateway catalog.
- Regression fixtures: revision serialization, concurrent conflict, overflow, SQL-wire conflict and restart persistence.

## Additional producer safety follow-up

All PgWire ALTER requests (including the compatibility form without `IF REVISION`) now use the same `update_workload_if_revision_async` path. A missing explicit revision uses the revision from the initial `get_workload` snapshot so another edit between that read and the write cannot be overwritten. In addition, the compatibility path cannot shrink the configured memory limit below currently accounted local reservations. The SQL syntax and existing successful sequential edits are preserved; optimistic conflicts return SQLSTATE `40001` and unsafe reductions return `54000`. A normal-client gateway test asserts a rejected 100-to-80-byte limit edit while 90 bytes remain accounted, unchanged revision and state. This is still gateway-local protection, **not distributed transactional CAS or owner acknowledgement**.
