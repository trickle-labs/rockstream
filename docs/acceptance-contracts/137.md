## Incremental changes in this PR
- Workload definition carries a persisted numeric revision; older records without one decode at revision 1.
- Conditional `ALTER WORKLOAD <name> IF REVISION <n> SET (...)` compares revision at the actual producer catalog update, returning SQLSTATE `40001` on conflict.
- The in-memory catalog compare-and-swap checks and updates under a single write lock. Conflict and overflow leave the requested definition unchanged; concurrent callers cannot both win a stale revision.
- Async conditional updates are serialized and apply the persisted definition before publication in the gateway catalog.
- Regression fixtures: revision serialization, concurrent conflict, overflow, SQL-wire conflict and restart persistence.

## Incomplete requirements that **block #137 sign-off**
- Legacy `ALTER WORKLOAD ... SET (...)` retains its SQL syntax, but the PgWire dispatcher uses the revision from its initial policy snapshot for optimistic CAS, checks current local reservations, and rejects concurrent edits. Explicit `IF REVISION` remains the client-visible contract. Cross-gateway distributed CAS and owner propagation remain unqualified.
- No verified live-owner acknowledgement protocol, effective-vs-requested policy status, frozen acknowledgement deadline, or restart/outage/failure evidence. Local memory reductions below active reservations are rejected, but remote and non-reclaimable worker allocations are not qualified.
- The async catalog backend does not provide a distributed transactional CAS; a concurrent external writer can race independently of this gateway. Multi-owner and multi-leader checks are outstanding.
- Do not close #137/#132 or claim V072 acceptance based on these focused tests.

## Follow-up regression: preserve active accounting for policy-only edits

A requested revision whose `memory_limit` is unchanged now retains the same
`WorkloadBudget` allocation object. Existing per-view `StateBudget` objects
hold `Arc` references to that object and must not be separated from a
replacement empty ledger by priority, freshness, or parallelism edits. The
`v072_policy_only_edits_preserve_live_workload_reservations` test checks
conditional revision 1→2 and legacy revision 2→3, over-budget admission
of a second view, and release/recovery without discarding the first view's
reservation.

**Still unqualified:** memory-limit-changing revisions currently rebuild
budget entries without an owner-acknowledged transfer of existing allocations.
Cross-gateway distributed compare-and-swap, actual requested/effective owner
status, and release-process load/outage/restart evidence remain unfinished.
This code-level regression must not be used to sign off #137 or parent #132.

## Additional producer safety follow-up

All PgWire ALTER requests (including the compatibility form without `IF REVISION`) now use the same `update_workload_if_revision_async` path. A missing explicit revision uses the revision from the initial `get_workload` snapshot so another edit between that read and the write cannot be overwritten. In addition, the compatibility path cannot shrink the configured memory limit below currently accounted local reservations. The SQL syntax and existing successful sequential edits are preserved; optimistic conflicts return SQLSTATE `40001` and unsafe reductions return `54000`. A normal-client gateway test asserts a rejected 100-to-80-byte limit edit while 90 bytes remain accounted, unchanged revision and state. This is still gateway-local protection, **not distributed transactional CAS or owner acknowledgement**.
