# Acceptance contract proposal — #136 committed subscription replay safety

**Status: proposed child mapping, not an issued sign-off.**
Parent: [#132](https://github.com/trickle-labs/rockstream/issues/132), acceptance v2 at commit `7a73050dbb28fdf61584d052b9521b2e7dce9835`.
Slice: [#136](https://github.com/trickle-labs/rockstream/issues/136), parent obligations v2:R6, R27–R28. Frozen source plan at `6442838183ffd913b6a24860072575aacaa9c96a`.

## Required acceptance

- Only complete, durably committed epoch frames may be published, with snapshot framing tied to the actual materialized-view read token from #135.
- Snapshot, per-epoch, retained-buffer, live stream and slow-consumer bounds fail closed before partial output.
- After process restart, lost replay, expiry, or missing retention, the server requires resnapshot unless separately qualified durable replay exists.
- Exact independent result multisets, full wire output, restart and slow-client transcripts are required.

## Contribution in this change

The in-memory registry now treats absent replay history, an invalidated complete-epoch log with no retained rows, and requests beyond its actual latest observed epoch as `[RS-2006] history.replay_unavailable`. Both `start_from_epoch` and `run_subscribe` reject these before exposing a false empty-tail success. Retained epoch replay remains ordered and preserves duplicate rows and signed retractions; an invalidated epoch cannot be resumed until actual new retained history exists. Eleven direct tests cover restart, exact replay, invalidated replay, no output before rejection, the async helper's row-limit rejection before any snapshot callback, the producer-facing PgWire reader's exact limit plus overflow rejection, unauthorized viewer rejection, aborted-transaction rejection, atomic backlog rejection before callback, and exact signed/duplicate async replay. The public async subscription helper now routes snapshots through the existing complete-snapshot row/byte check, rather than the historical unbounded callback path.

## Remaining work

This is not an authoritative durable replay protocol or an integrated snapshot token. A gateway does not have independently durable log lineage across restart. Frame start/end with actual producer materialized-view tokens, owner fencing, snapshot admission, encoded total stream bytes, actual restart/slow-client release-process evidence and earlier blocked dependencies remain incomplete. **Do not mark #136 or #132 complete.**


The PgWire `handle_subscribe` producer now asks `ViewReader` for at most `SUBSCRIBE_SNAPSHOT_MAX_ROWS + 1` rows. This bounds the number of materialized snapshot rows before the complete snapshot row/encoded-byte check, and allows that check to fail without creating a partial query stream. The reader must honor this limit; the compiled-arrangement fallback and actual committed snapshot token remain unqualified, and large individual rows still require independent encoded-byte producer accounting.


The direct PgWire `SUBSCRIBE` dispatcher now carries the real connection context into `select_access_error_response` before reading catalog state, scanning the snapshot or acquiring a stream permit. It also runs after the existing failed-transaction check; subscriptions may not bypass SQLSTATE `25P02`. This reuses the production ACL/namespace policy, not a client-side filter. End-to-end authorization, scope-specific revocation, correct committed-read-token pairing and full-process release evidence remain required.

The public asynchronous replay helper now uses `start_from_epoch` followed by the same `SubscriberHandle::poll` as PgWire to validate replay floor, consumer backlog and complete per-epoch projected-byte limits before sending callbacks. The previous direct registry-entry replay loop skipped this uniform slow-client gate. This is still in-memory replay only, not independently qualified durable history.
