# v0.64 SQL execution integrity

Status: Done

Source: [ROADMAP section 10](../../ROADMAP.md#v0-64). Apply the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.63 durable catalog and stable object identities. Define the supported SQL predicate and type subset before implementation. Unsupported expressions must return explicit capability errors without modifying state.

## Goal and public behavior

Ordinary PostgreSQL clients issue standard UPDATE and DELETE statements. Simple and extended protocols produce equivalent typed results and transactional effects.

## Implementation steps

1. Trace statement dispatch and every caller of `parse_update`, `parse_delete`, and `substitute_params` in `crates/rockstream-gateway/src/server.rs`. Route every statement through the shared PostgreSQL AST and semantic path in `crates/rockstream-sql/src/frontend.rs`, `extension.rs`, and `lower.rs`. Replace execution decisions based primarily on string prefixes; retain special syntax only through explicit parsed extensions.
2. Add typed InsertStatement, UpdateStatement, DeleteStatement, and DmlStatement representations in the SQL crate using existing expression and schema types. Lower typed predicates and assignments to logical operations. Validate relations, columns, permissions, types, and supported expressions before writes. Bound parser input, expression depth, and execution accumulators with explicit failures.
3. Implement the documented general-predicate subset, including AND predicates such as order_id = 1 AND store_id = 100. Define precedence, SQL three-valued logic, no-WHERE behavior, and unsupported expression diagnostics before coding. Replace comma-separated key/value matching in the gateway. Use existing key or scan access paths according to the validated predicate.
4. Execute each update as a retraction of the complete old row plus insertion of the complete new row in one logical commit. Preserve commit and rollback ownership in gateway session and write-buffer code. Defer maintained-view visibility until the full epoch is committed; include multi-row failures and key changes in atomicity tests.
5. Persist first-class primary-key metadata through the durable catalog. Prefer required keys on durable mutable tables. If heap-row identity remains supported, settle and document its identity and update/delete semantics before enabling it. Reject duplicate keys atomically and preserve identity across restart.
6. Define NULL, IS NULL, IS NOT NULL, typed parameters, numeric coercion, text escaping, UUID, timestamps, decimals, and booleans using existing type representations. Bind typed parameters instead of text substitution. Freeze timestamp/time-zone and decimal overflow rules before creating oracle expectations.
7. Share semantic execution across simple queries, prepared statements, and bound parameters. Implement complete UPDATE RETURNING and DELETE RETURNING results, affected-row command tags, no-match behavior, transaction commit, rollback, and materialized-view propagation.
8. Build a compatibility corpus using tokio-postgres and one ordinary external ecosystem client selected before CI integration. Compare full result rows, types, multiplicities, command tags, and exact error codes. Restart the release process after committed DML and compare the durable state with an independent oracle.

## Documentation changes

Update SQL and client documentation with predicate support, keys or explicitly supported heap semantics, parameter binding, coercion rules, RETURNING, and transaction limits. Execute published DML examples against the release binary in CI. Remove textual key/value examples from supported SQL guidance.

## Exit criteria

| ID | Acceptance condition | Intended proof |
|---|---|---|
| V064-01 | Every SQL statement follows shared AST parsing, typed validation, logical operation, and execution; textual DML dispatch no longer owns semantics. | Caller audit and parser-to-public-client corpus, including whitespace, comments, quoting, and malformed statements. |
| V064-02 | Typed INSERT, UPDATE, and DELETE honor the documented predicate subset, including multi-column AND, and reject unsupported expressions without writes. | Complete successful results and exact capability errors against independent expected state. |
| V064-03 | Multi-row UPDATE and key changes commit complete old/new deltas atomically; readers never see half-maintained dependencies. | Concurrent readers, injected write failure, and full base/view multiset comparisons. |
| V064-04 | Durable primary-key or explicitly selected heap identity semantics survive restart and duplicate-key errors leave prior state intact. | Full metadata and row identity assertions plus public negative key cases. |
| V064-05 | NULL, NULL predicates, numeric coercion, escaped text, UUID, timestamps, decimals, booleans, and typed parameters obey the frozen contract. | Type-aware corpus covering NULL values, boundaries, overflow, invalid encodings, and complete results. |
| V064-06 | Simple, prepared, and bound forms agree through tokio-postgres and the selected external client. | Same corpus compares full rows, wire types, command tags, and SQL error codes. |
| V064-07 | UPDATE RETURNING, DELETE, DELETE RETURNING, no-match UPDATE, prepared UPDATE, rollback, commit, and view propagation return exact expected results. | Explicit corpus case for each required scenario, including multi-row UPDATE and NULL predicates. |
| V064-08 | A hard process restart preserves complete committed base/view state and excludes rolled-back or failed changes. | Release-process DML crash/restart transcript and independent full-state oracle. |
| V064-09 | Oversized statements, excessive expression depth, and result or mutation limits fail with bounded work and no partial commits. | Limit-boundary tests with occupancy and exact state/error assertions. |
