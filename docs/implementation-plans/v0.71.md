# v0.71 Operational observability and diagnostics

Status: Planned

Roadmap source: [17. v0.71](../../ROADMAP.md#v0-71). Follow the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.69 PostgreSQL CDC and v0.70 Kafka sign-offs, including their v0.68 distributed lifecycle dependency. Preserve the early performance and memory instrumentation required by roadmap section 5. This release completes operator diagnosis across those paths. It does not replace their earlier evidence gates.

Reuse `crates/rockstream-cli/src/doctor.rs`, `output.rs`, and `metrics_server.rs`, `crates/rockstream-types/src/metrics.rs`, and `crates/rockstream-gateway/src/catalog_stubs.rs`. The existing `run_doctor_checks` and `run_bounded_check` already provide bounded checks, status output, error codes, and redaction. Extend their public callers instead of introducing a second diagnostic service. Existing health and catalog tests are starting points, not proof that this milestone is complete.

## Goal and public behavior

An operator can use the CLI and SQL catalog to determine system health, view currency, the cause of lag, memory ownership, shard ownership, migration blockers, and the next corrective action. Every reported value comes from authoritative durable state or an identified runtime observation. Missing and stale observations remain distinguishable from healthy zero values.

## Implementation steps

1. Define the health contract from section 17.1. Specify liveness, readiness, availability, freshness, durability, capacity, and degradation independently. Freeze their evaluation rules, stale-observation policy, sampling intervals, and timeouts before implementation. Any numerical thresholds absent from the roadmap are decisions to record before qualification, not existing promises. A live process with unavailable storage must remain live while reporting the affected durability and availability dimensions accurately.
2. Complete the section 17.2 status model through the existing types and CLI output. Map `state`, `published_frontier`, `input_frontier`, `freshness_lag`, `freshness_slo`, `state_bytes`, `memory_bytes`, `assigned_shards`, `degradation_reason`, and `blocking_operation` to their owning catalog, frontier, storage, worker, or operation records. Define units and absent-value semantics. Associate observations with their sampling time and relevant epoch. Keep published progress tied to committed visibility, including recovery, lease changes, and failed writes.
3. Extend `doctor.rs` for every section 17.3 check: configuration, filesystem and object-store access, network endpoints, PostgreSQL client connectivity, control connectivity, worker connectivity, connector connectivity, certificate validity, storage-format compatibility, catalog recovery, port conflicts, and resource limits. Use real probes with bounded deadlines and concurrency. Preserve PASS, WARN, and FAIL distinctions, stable error codes, exit status, and actionable remediation. Reject malformed options. Do not report a skipped or unreachable check as PASS. Avoid destructive probes and redact credentials in summaries, details, and remediation text.
4. Implement the small canonical SQL catalog required by section 17.4. Start from `catalog_stubs.rs` and `crates/rockstream-sql/src/catalog.rs`; trace existing query dispatch before editing. Provide authoritative relations for nodes, shards, operations, views, sources, and checkpoints, using the roadmap's `rockstream_catalog` names unless a documented compatibility decision requires an alias. Join durable ownership and operation state with runtime observations without inventing rows. Define authorization, pagination, snapshot consistency, unavailable-peer behavior, and stale data behavior. Bound scan pages and result accumulation with named limits, observable fill, and explicit overflow errors.
5. Complete section 17.5 structured logs along actual request, operation, workload, view, shard, worker, and epoch execution. Carry `request_id`, `operation_id`, `workload_id`, `view_id`, `shard_id`, `worker_id`, and `epoch` wherever those identifiers apply. Represent non-applicable identifiers explicitly in the schema rather than assigning fictional IDs. Preserve correlation through retries, worker handoff, and asynchronous completion. Bound buffering and identifier cardinality. Record any dropped-log policy and expose its counter.
6. Complete section 17.6 metrics from actual producers: ingest rows and bytes, execution rows, epoch duration, frontier lag, state size, memory, exchange bytes and backpressure, checkpoint duration, migration progress, connector lag, and errors grouped by RS code. Define units, counter reset rules, histogram boundaries, label bounds, and aggregation ownership. Cross-check measured deltas against public ingestion and committed results. Never derive real performance claims from fixture timings or synthetic resource values.
7. Add planned release-process diagnosis scenarios for source disconnection, worker unavailability, active migration, exceeded state budget, recovering view, lagging connector, and unavailable storage. Capture CLI text and JSON, SQL rows, metrics, and correlated logs before, during, and after each fault. Restart affected processes against durable state and verify the recovered status against complete query results. Include a supported public request and a meaningful failure for every newly exposed operation.

## Documentation changes

Update `docs/operator.md`, `docs/sre-operations.md`, `docs/reference/metrics.md`, `docs/reference/catalog.md`, and `docs/reference/cli.md`. Document each health dimension, status field source, doctor outcome, metric unit, and degraded-state remedy. Add executable release-binary examples that answer all seven operator questions in the roadmap. Document what cannot be observed and when an observation is stale.

## Exit criteria

Each ID requires its own code, documentation, test, and captured evidence mapping under the shared rules.

| ID | Acceptance condition | Intended proof |
| --- | --- | --- |
| V071-01 | All seven health dimensions have frozen definitions; liveness alone cannot produce workload health. | Exact health payloads under healthy operation, unavailable storage, and recovery. |
| V071-02 | All ten roadmap status fields have authoritative values or documented absent values, units, and epoch semantics. | Exact CLI and SQL records reconciled with committed query results and ownership records before and after process restart. |
| V071-03 | Every one of the twelve doctor checks executes a real bounded probe and distinguishes PASS, WARN, FAIL, and unavailable observations correctly. | Planned public-process doctor matrix with exact reports, exit codes, timeout behavior, and redaction checks. |
| V071-04 | Nodes, shards, operations, views, sources, and checkpoints have canonical queryable records without fixture substitution. | Exact full SQL rows under creation, migration, recovery, deletion, unauthorized access, and unavailable peers. |
| V071-05 | Significant requests preserve all applicable correlation identifiers through asynchronous work and retries. | Complete structured event sequences for an ingest-to-commit request and a failed migration, with bounded log-buffer evidence. |
| V071-06 | Every section 17.6 metric class measures its real producer with documented units and bounded labels. | Deterministic workload metric deltas, measured duration evidence, restart reset checks, and full exported-schema assertions. |
| V071-07 | Each of the seven required degraded scenarios reports the correct cause, affected health dimension, blocker, and corrective action in both CLI and catalog. | Planned seven-scenario release-process suite with exact before, fault, and recovery outputs. |
| V071-08 | Diagnostic queues, scans, request caches, and accumulators enforce named limits with fill observations and defined overflow behavior. | Forced limit and timeout tests plus process-level resource samples; no unbounded waits or successful truncated results. |
| V071-09 | Primary operator examples execute against the release binary, including supported and rejected protocol or schema combinations if output formats change. | CI example transcripts, versioned schema checks, and supported/rejected compatibility fixtures. |

Steps 1 through 6 correspond to the health, status, doctor, catalog, logging, and metrics criteria in order. Step 7 requires the degraded-scenario criterion. The boundedness and documentation criteria apply to every step. Every listed subcase is mandatory.
