# v0.68: Durable distributed lifecycle

Status: Planned

Roadmap sources: [14. v0.68: Durable Distributed Lifecycle](../../ROADMAP.md#v0-68), [5.6: State beyond RAM](../../ROADMAP.md#56-v0671-state-beyond-ram), and [22. Dependency Graph](../../ROADMAP.md#22-dependency-graph).
Follow the [shared implementation and evidence rules](README.md). Simulation and formal evidence supplement real shard movement; they cannot substitute for it.

## Prerequisites and scope

Require v0.66 operations, v0.67 direct transport, v0.67.1 bounded large-state recovery, durable catalog/leases, and complete standalone recovery. Manual migration, worker drain, rebalance, and failover must use one durable protocol. PostgreSQL CDC and Kafka both depend on this lifecycle gate and may proceed independently after it.

Reuse `crates/rockstream-types/src/migration.rs`, `crates/rockstream-control/src/migration.rs`, `crates/rockstream-runtime/src/migration.rs`, `crates/rockstream-control/src/skew.rs`, `placement.rs`, and `shard_stats.rs`. Existing `MigrationCoordinator::copy_bounded_chunks` scans bounded pages and flushes recipient batches. `MigrationPersistentStore::load` currently returns `Option` for both absent and unreadable records; future recovery must distinguish absence, corruption, and unavailable storage. Reuse stable partition logic in `crates/rockstream-plan/src/virtual_bucket.rs` and existing migration simulation/formal artifacts.

## Goal and public behavior

An accepted migration moves real durable state and verifies it. Restart resumes the same operation. A shard has at most one authoritative writable lease throughout movement. Pressure-driven placement preserves foreground freshness and works within the recipient budget, including state larger than RAM.

## Implementation steps

1. Bind the shared saga to `PLANNED`, `SNAPSHOTTING`, `COPYING`, `DUAL_WRITING`, `CATCHING_UP`, `FENCING_OLD`, `CUTOVER`, `VERIFYING`, `GC_ELIGIBLE`, and `DONE`, plus `ABORTED` and `FAILED`. Specify allowed transitions, terminal outcomes, retry identity, cancellation boundaries, and phase invariants before wiring executors. Management operation IDs identify the same durable saga across all entry points.
2. Apply persist-intent, idempotent-effect, persist-completion ordering to each phase. Version migration records and record copy cursors, checkpoint identities, leases, frontiers, and effect completion. Differentiate missing records from storage/corruption failures. A failed intent write prevents the side effect; a failed completion write causes safe replay, not a new operation.
3. Route manual migration, drain, rebalance, and failover through real checkpoint/copy/verify execution. Reuse bounded `copy_bounded_chunks` and storage paging, but audit checkpoint production, verification, deduplication, catch-up, and prewarming for full-state allocation. Reserve source and recipient resources before effects. Bound copy bytes, concurrent migrations, dual-write queues, retry queues, and checkpoint/verification buffers with metrics and overflow policies.
4. On control leadership/process replacement, load all active sagas and reconcile phase, completed/outstanding effects, current leases, and current frontiers. Resume safely or fail explicitly with retained authoritative state. Fence competing controllers and obsolete worker actions. Copy retries must not inflate progress or duplicate logical writes.
5. Expose actual `copied_bytes`, `total_bytes`, `copied_rows`, `estimated_rows`, `donor_frontier`, `recipient_frontier`, `lag`, `current_phase`, and `verification_progress`. Define unknown totals and estimates explicitly. Bind counters to completed durable work and persist progress sufficiently for truthful restart reporting. Do not fabricate durations.
6. Implement fenced cutover. Stop the donor's authoritative writes before publishing the recipient as sole owner. Reads and retries respect lease generation and committed frontiers. Before donor GC, verify complete recipient state and the committed frontier. Divergence retains donor data, records the exact failure, and returns to a safe repair phase. Define post-fence repair ownership before adding rollback code; never reactivate an old lease blindly.
7. Drive rebalance from stable logical partitions independent of worker count. Feed measured partition processing time, state size, queue age, and input rate into existing pressure/skew controls. Add explicit hysteresis thresholds and cooldowns to avoid repeated moves under oscillating load. Scale out only when queued work can use additional parallelism; explain indivisible hot-key limits.
8. Prewarm recipient state within its budget, then cut over with bounded recovery and foreground freshness. Qualify mergeable aggregates using partial aggregation and a combining stage. Qualify joins separately, including a hot key that cannot be divided by adding workers. Freeze pressure thresholds, cooldowns, recovery/RSS/backlog limits, and foreground latency targets before measurement.
9. Build a phase-by-process fault matrix: kill control, donor, and recipient at every binding phase, including terminal phases where restart must be idempotent. Exercise failures around each intent/effect/completion boundary, corrupted records, copy I/O failure, recipient divergence, stale requests, and quota exhaustion. Extend `formal/m6_shard_migration.fizz` and simulation tests to the actual protocol, then run equivalent release-process cases.

## Documentation changes

Publish the saga transition/repair contract, management progress meanings, durable record compatibility, cutover/GC conditions, drain and failover procedures, resource limits, and pressure policy. Include exact real migration commands, interrupted-operation recovery, large-state results, and separate aggregate/join scaling limits. Link the measured profile and formal/simulation evidence.

## Exit criteria

| ID | Acceptance condition | Required proof |
|---|---|---|
| V068-01 | All saga states and entry points use one versioned durable operation with intent persisted before every external effect. | Transition/record tests and real manual/drain/rebalance/failover traces; failed intent writes produce no effect and retried completion produces no duplicate effect. |
| V068-02 | A real shard's entire state is copied and verified through bounded production machinery. | Public management migration with ongoing SQL writes/reads; exact complete recipient multiset and committed epochs, plus bounded copy/checkpoint/verify metrics. |
| V068-03 | Control restart distinguishes absent, corrupt, and unavailable records and reconciles all active operations safely. | Full process replacement with active effects and injected store failures; exact restored operation records, phases, errors, and final data. |
| V068-04 | Progress exposes all nine roadmap fields from real work without duplicate retry accounting or invented timing. | Controlled copy/catch-up/verification steps and restart assert full management responses against storage and frontier observations. |
| V068-05 | At most one authoritative writable lease exists at every phase; divergent recipient state never permits donor GC. | Lease history and accepted-write assertions, stale-owner tests, corrupt-recipient repair, and crashes around fence/cutover/GC; exact authoritative data preserved. |
| V068-06 | Killing control, donor, or recipient at every phase loses no committed epoch and duplicates no logical write; each run reaches DONE or explicit FAILED. | Complete phase/process matrix with full post-recovery multisets, lease records, and terminal operation output. ABORTED cancellation remains separately tested and cannot replace a required fault outcome. |
| V068-07 | Large-state migration, prewarm, catch-up, and restart stay within both workers' budgets and frozen recovery/freshness limits. | Maintained state above worker memory budget, real concurrent public traffic, RSS/disk/backlog/queue-age samples, and complete output oracle through migration and restart. |
| V068-08 | Pressure decisions use all four measured partition signals and stable partitions; hysteresis/cooldowns prevent repeated moves under fluctuating load. | Oscillating/skewed-load experiments assert exact decision/placement sequences, observed cooldowns, and rejection of unhelpful scale-out. |
| V068-09 | Partial/combining aggregate execution and separate join movement retain exact weighted results with honest hot-key limits. | Frozen hot-partition profiles, full updates/deletes/NULL result checks, foreground p99, and per-worker execution evidence; no claim that an indivisible join key splits automatically. |
| V068-10 | Every queue/scan/retry/migration resource has a limit, fill metric, and deterministic failure/backpressure with safe cleanup. | Saturation, disk/storage failure, cancellation, and cooldown tests assert exact errors, retained donor safety, and resumed foreground work. |
| V068-11 | Formal, simulation, real-process, compatibility, and executable documentation evidence agree with the shipped saga. | Model invariants and simulation results plus complete real fault matrix, supported/rejected record-version cases, and per-criterion sign-off links. |

Step coverage: steps 1 through 9 map to criteria 01, 01/03, 02/10, 03/06, 04, 05, 08, 07/09, and 06/11 respectively. Documentation maps to 11.

## Verification instructions

Existing component commands include `rtk cargo test -p rockstream-control --test migration_record_durability_tests`, `rtk cargo test -p rockstream-control --test shard_migration_state_machine_tests`, and `rtk cargo test -p rockstream-sim --test sim_migration_crash_boundary_tests`. Read `formal/README.md` for the existing model runner and record the exact command used.

Build release processes with `rtk cargo build --release -p rockstream-cli`. The public phase/process driver, pressure experiment, and large-state migration profile are planned additions. Register their exact commands and fault selectors before measurement; the existing simulation/state-machine tests alone do not pass these gates.
