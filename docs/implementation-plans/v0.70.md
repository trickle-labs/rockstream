# v0.70: Kafka golden connector

Status: Planned

Roadmap sources: [16. v0.70: Kafka Golden Connector](../../ROADMAP.md#v0-70) and [22. Dependency Graph](../../ROADMAP.md#22-dependency-graph).
Follow the [shared implementation and evidence rules](README.md). This is a future qualification plan; the template becomes Supported only after every required scenario passes.

## Prerequisites and scope

Require v0.68 durable lifecycle, v0.67 direct transport, v0.67.1 state/budget proof for the claimed workload envelope, durable catalog/source identity, and v0.65 recovery. Kafka and PostgreSQL CDC are independent children of durable lifecycle. v0.69 completion is not required for Kafka implementation or sign-off.

Reuse `crates/rockstream-connectors/src/kafka_source.rs`, source DDL in `crates/rockstream-gateway/src/server.rs`, and `kafka_template_files` in `crates/rockstream-cli/src/init.rs`. `KafkaSource::refresh_assignment`, `seek_recovery_offset`, `poll_delta`, and `commit_offset` already handle pieces of consumption. The current offset token uses a partition-offset map and `commit_offset` calls the broker; prove durable epoch coordination and strengthen source identity at the shared caller. Reuse existing DLQ/backpressure mechanisms and the installed Kafka client instead of a parallel consumer framework.

## Goal and public behavior

`rockstream project new events --template kafka` provisions a reproducible Redpanda/Kafka development environment and verifies maintained views from real records. Source identity, committed offsets, replay, rebalance, idle partitions, and poison records have explicit durable and bounded behavior.

## Implementation steps

1. Freeze the source and template contract before runtime wiring. Extend the existing generated files and v0.61 project apply/verify workflow with reproducible broker configuration, topic creation, producer records, source/view definitions, and full expected results. Document credentials, topic/schema configuration, and supported broker assumptions; no fixture-backed successful verification.
2. Persist cluster, topic, partition, and offset identity with a source-record version. Determine how stable cluster/topic incarnation is established using the supported broker metadata; if identity cannot be established, reject unsafe reuse. Topic recreation, changed cluster, incompatible partition identity, malformed token, and offset-out-of-range require an explicit reset/rebuild decision rather than silently accepting old offsets. Freeze whether stored offsets name the last applied or next record and use that meaning everywhere.
3. Integrate the durable-epoch/offset contract at the shared source execution owner. An offset is committed exactly when its corresponding RockStream epoch is durable; broker acknowledgement follows that fact. Persist replay identity and offsets with required view effects. A crash after processing but before persistence discards or replays incomplete work; a crash after persistence but before Kafka acknowledgement safely replays without duplicate logical writes. Broker commit failure leaves a retryable durable outcome rather than rolling back already visible data.
4. Define how active partitions contribute records to one logical epoch. Bound batches, bytes, epoch assembly time, and pending offsets. Idle partitions must not cause a global unbounded wait. Commit the exact per-partition progress covered by durable work, preserving per-partition order and the declared cross-partition visibility contract. Freeze timeout and idle-partition rules before implementing assembly.
5. Handle consumer-group rebalance through existing assignment/recovery hooks. Stop admitting revoked partitions, fence stale assignment generations, and durably complete or discard incomplete work under the declared protocol. Resume new assignments from durable offsets. Bound revoke waiters and retries. Test revocation during an in-flight durable commit and assignment while another consumer has stale responses.
6. Define bounded poison-record handling using existing DLQ controls. Default behavior must block/report rather than silently skip. Specify retry limit, durable DLQ capacity, retention, failure behavior, and operator recovery; any configured skip/DLQ policy must expose the disposition and advance offsets only under its declared durable protocol. Report topic, partition, offset, error, schema, and payload digest with safe payload redaction. Full DLQ, oversized payload, and decode error must not accumulate memory or retry forever.
7. Propagate worker pressure through source polling and broker pause/resume. Name limits for polled bytes, record bytes, transaction/epoch buffers, retry queues, pending requests, and DLQ storage. Account under worker budgets before allocation, expose fill/queue-age/lag, and release resources on revoke, timeout, cancellation, and reconnect. Reserve capacity for commit completion and foreground reads.
8. Add real-broker release-process scenarios for multiple partitions, duplicate replay, consumer restart, broker interruption, group rebalance, poison record, large record, schema decode error, backpressure, and correct views after restart. Include idle partitions, topic recreation, unavailable broker, and crash at persistence/ack boundaries. Assert entire record/result multisets and durable per-partition offsets rather than counts.
9. Freeze the external connector profile before measurement: offered load independent of completion, record/partition/state sizes, durability, read/commit/freshness p99, RSS/queue-age/backlog ceilings, and bounded recovery. Include generator delay, broker outage/rebalance, errors, and timeouts. Validate fresh committed results with an independent produced-record oracle; do not infer correctness from observed offsets alone.

## Documentation changes

Publish the executable template, canonical source definition, cluster/topic incarnation and reset procedure, offset meaning, epoch visibility, replay and rebalance rules, idle-partition behavior, poison/DLQ policy, redaction, all limits, and recovery instructions. State Kafka independently qualified from CDC. Promote template capability status only after the full matrix passes with release binaries.

## Verification instructions

Existing baselines: `rtk cargo test -p rockstream-connectors --test kafka_source_exactly_once_tests`, `rtk cargo test -p rockstream-connectors --test kafka_source_guarantee_matrix_tests`, `rtk cargo test -p rockstream-connectors --test dlq_backpressure_threshold_tests`, and `rtk cargo test -p rockstream-gateway --test source_ddl_postgres_kafka_tests`. Inspect real-broker prerequisites and confirm broker tests actually execute. A skipped container scenario is missing evidence.

Build with `rtk cargo build --release -p rockstream-cli`. The complete generated-project driver, multi-consumer crash/rebalance matrix, and measured profile are planned additions. Register exact runnable commands and required services before qualification. Recreating a connector object or passing mock-only tests cannot satisfy the process durability or template support gates.
