# v0.73.1 Console role/API foundation

Status: Planned

Roadmap source: [19A. v0.73.1](../../ROADMAP.md#v0-73-1). Follow the
[shared implementation and evidence rules](README.md) and the
[UI-enablement qualification track](ui-enablement.md).

## Prerequisites and scope

Require v0.71 canonical observation providers, v0.72 bounded interactive
execution, and v0.73 shared security. Require UIE M0/M1 contracts and the
applicable M2 security evidence. A missing owner blocks its dependent route; a
mock adapter or unsupported response does not qualify the route.

This is the only new subsystem introduced by UI enablement. Add a
`ConsoleComponent` to the existing `rockstream` binary's composable
`Component`/`NodeRuntime` model and expose it through
`rockstream start --role console`; do not add a separate executable or parallel
console lifecycle. Reuse qualified catalog, gateway, policy,
diagnostic, resource-control, and operation owners. Do not add a console-local
catalog, ACL store, diagnostic engine, scheduler, or operation state machine.
Do not widen SQL, connector, migration, cancellation, backup, or restore
semantics.

## Goal and public behavior

A browser-class or headless client can authenticate, discover capabilities, and
use authorized public RockStream behavior through a versioned API hosted by the
console role. The browser communicates only with the console HTTPS endpoint;
pgwire, management, telemetry, and artifact storage are authenticated and
authorized internal upstreams. Every response preserves the underlying
authority, identity, boundedness, consistency, durability, eligibility, and
failure semantics.

## Implementation steps

1. Freeze the M1 `/api/v1` OpenAPI and event schemas, error mapping, stable resource identity, revision/cursor rules, exact SQL value representation, idempotency scope, stream reset behavior, and supported engine/API/client matrix. Generate TypeScript types and a client from one authoritative schema path. Schema examples and drift checks are contract tests, not product qualification.
2. Add `ConsoleComponent` to the existing `Component`/`NodeRuntime` composition and expose it through `rockstream start --role console`. Add `NodeRole::Console`, compose `ConsoleComponent` exactly once for `rockstream start --role all` once the role is qualified, and use the same startup, recovery, drain, stop, health, and shutdown coordination as every other component. Do not add a second executable or lifecycle.
3. Extend `NodeConfig` with a `[console]` section covering the HTTPS listener, authentication/session settings, upstream gateway and management targets, optional telemetry and artifact storage, and console resource limits. Resolve it through the existing compiled-default, configuration-file, environment, and CLI precedence; report redacted origins; reject unknown keys and invalid role/configuration combinations before binding. `rockstream config print-effective --origins` must include the section.

   The section should make the boundary and budgets explicit, for example:

   ```toml
   [console]
   listen_addr = "127.0.0.1:8443"
   auth_mode = "oidc"
   session_store = "durable"
   gateway_target = "https://127.0.0.1:9443"
   management_target = "https://127.0.0.1:9444"
   telemetry_target = "https://127.0.0.1:9090"
   artifact_store = "file://./artifacts"
   max_query_bytes = 8388608
   max_concurrent_queries = 16
   ```

   Field names, defaults, and supported target schemes are decisions to freeze
   in M0; the example is not an existing configuration contract.
4. Implement OIDC authorization-code flow with PKCE and server-held tokens in `ConsoleComponent`. Validate issuer, audience, signature, state, nonce, redirect target, and expiry. Use secure HttpOnly cookies with a frozen SameSite policy, CSRF and origin protection, logout, revocation, session fixation prevention, bounded session storage, and explicit role restart behavior.
5. Authenticate both the service peer and end-user actor. Use v0.73's short-lived, audience- and deployment-bound delegated assertion and intersect its allowance with current actor policy. Reauthorize long-lived work within the frozen revocation interval. Reject caller-supplied actors, roles, scopes, and stale or forged assertions.
6. Implement adapters for sessions, capabilities, canonical objects and lineage, bounded queries and subscriptions, reviewed changes, workloads, policy, secrets, observations, diagnostics, operations, and backups. Separate support, authorization, and current eligibility. Adapters reshape owner responses only; they cannot infer missing facts or replace owner-side validation and admission.
7. Enforce same-origin defaults, explicit allowed origins, content type and request limits, response/stream/export limits, rate and concurrency limits, bounded pools, deadlines, privacy/cache headers, correlation IDs, safe logs, and graceful shutdown. Authenticate streams and downloads. Reset pooled state between actors and propagate cancellation to the producer. The browser must have no direct route to an upstream interface.
8. Add release-process tests with a controlled OIDC provider and real secured gateway and management backends. Exercise complete success and failure payloads, canonical reads, bounded queries, policy decisions, operation observation, console-role/backend restart, unavailable optional telemetry, `role=all` composition, and cleanup. Retain the exact schema/client versions and process topology.

## Documentation changes

Add the console API reference, generated-client guide, authentication and
deployment configuration, browser-security boundary, capability/permission/
eligibility semantics, limits, errors, session/restart behavior, and local
headless setup. Mark routes unavailable until their owners pass. Keep UI
implementation outside primary product documentation.

## Verification instructions

Add focused component/API tests and release-process suites under
`crates/rockstream-cli/tests/`. Build with
`rtk cargo build --release -p rockstream-cli`. Run
`rockstream start --role console` and, once qualified,
`rockstream start --role all` through the generated client and independent
HTTP/protocol clients. Record exact role/configuration targets, OIDC fixture
configuration, release artifact hashes, backend revisions, and public commands in
the sign-off. Unit adapters and mock providers cannot close a route.
