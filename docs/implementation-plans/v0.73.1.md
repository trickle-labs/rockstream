# v0.73.1 Console API foundation

Status: Planned

Roadmap source: [19A. v0.73.1](../../ROADMAP.md#v0-73-1). Follow the
[shared implementation and evidence rules](README.md) and the
[UI-enablement qualification track](ui-enablement.md).

## Prerequisites and scope

Require v0.71 canonical observation providers, v0.72 bounded interactive
execution, and v0.73 shared security. Require UIE M0/M1 contracts and the
applicable M2 security evidence. A missing owner blocks its dependent route; a
mock adapter or unsupported response does not qualify the route.

This is the only new subsystem introduced by UI enablement. Add a secured,
browser-compatible HTTP API and generated client, but no UI. Reuse qualified
catalog, gateway, policy, diagnostic, resource-control, and operation owners.
Do not add a console-local catalog, ACL store, diagnostic engine, scheduler, or
operation state machine. Do not widen SQL, connector, migration, cancellation,
backup, or restore semantics.

## Goal and public behavior

A browser-class or headless client can authenticate, discover capabilities, and
use authorized public RockStream behavior through a versioned API. Every response
preserves the underlying authority, identity, boundedness, consistency,
durability, eligibility, and failure semantics.

## Implementation steps

1. Freeze the M1 `/api/v1` OpenAPI and event schemas, error mapping, stable resource identity, revision/cursor rules, exact SQL value representation, idempotency scope, stream reset behavior, and supported engine/API/client matrix. Generate TypeScript types and a client from one authoritative schema path. Schema examples and drift checks are contract tests, not product qualification.
2. Add `crates/rockstream-console` and `rockstream console serve`. Validate gateway, management, identity-provider, telemetry, artifact-store, TLS, limit, and shutdown configuration. Deployment configuration selects backend targets; requests cannot supply arbitrary upstream URLs. Package the service in release artifacts and refuse production startup against an insufficiently secured backend.
3. Implement OIDC authorization-code flow with PKCE and server-held tokens. Validate issuer, audience, signature, state, nonce, redirect target, and expiry. Use secure HttpOnly cookies with a frozen SameSite policy, CSRF and origin protection, logout, revocation, session fixation prevention, bounded session storage, and explicit restart behavior.
4. Authenticate both the service peer and end-user actor. Use v0.73's short-lived, audience- and deployment-bound delegated assertion and intersect its allowance with current actor policy. Reauthorize long-lived work within the frozen revocation interval. Reject caller-supplied actors, roles, scopes, and stale or forged assertions.
5. Implement adapters for sessions, capabilities, canonical objects and lineage, bounded queries and subscriptions, reviewed changes, workloads, policy, secrets, observations, diagnostics, operations, and backups. Separate support, authorization, and current eligibility. Adapters reshape owner responses only; they cannot infer missing facts or replace owner-side validation and admission.
6. Enforce same-origin defaults, explicit allowed origins, content type and request limits, response/stream/export limits, rate and concurrency limits, bounded pools, deadlines, privacy/cache headers, correlation IDs, safe logs, and graceful shutdown. Authenticate streams and downloads. Reset pooled state between actors and propagate cancellation to the producer.
7. Add release-process tests with a controlled OIDC provider and real secured gateway and management backends. Exercise complete success and failure payloads, canonical reads, bounded queries, policy decisions, operation observation, service/backend restart, unavailable optional telemetry, and cleanup. Retain the exact schema/client versions and process topology.

## Documentation changes

Add the console API reference, generated-client guide, authentication and
deployment configuration, browser-security boundary, capability/permission/
eligibility semantics, limits, errors, session/restart behavior, and local
headless setup. Mark routes unavailable until their owners pass. Keep UI
implementation outside primary product documentation.

| V0731-03 | Browser sessions implement the frozen OIDC, cookie, CSRF, origin, logout, revocation, fixation, expiry, and restart contract. | Controlled-provider browser-protocol tests with exact cookies, redirects, errors, session records, and post-restart behavior. |
| V0731-04 | Delegation authenticates service and actor, is audience/deployment/policy bound, and cannot be forged or widened by caller input or pooled state. | Exact allowed/denied cross-service matrix including stale policy, forged assertions, role headers, cross-user reuse, and node/client credential misuse. |
| V0731-05 | Every advertised adapter calls its authoritative v0.71-v0.73 owner and preserves permission, capability, eligibility, boundedness, consistency, and unsupported semantics. | Public HTTP responses reconciled with complete CLI/SQL/management records and owner evidence under healthy, denied, stale, unavailable, conflict, and unsupported cases. |
| V0731-06 | HTTP requests, pools, queries, streams, exports, caches, and retries enforce named limits with visible fill and explicit cleanup or overflow behavior. | Boundary and overload tests with exact errors plus producer-side memory, CPU, reservation, cancellation, disconnect, expiry, and shutdown evidence. |
| V0731-07 | Browser and download boundaries reject CSRF, malicious origins/targets, unsafe content, enumeration, cross-scope access, and secret leakage. | Adversarial HTTP matrix, exact safe logs/errors, cross-actor artifact/query tests, and secret-canary scans. |
| V0731-08 | Console restart invalidates ephemeral state predictably without changing accepted durable engine operations or their identities/outcomes. | Query/session loss and operation/change reconciliation across process destruction with exact durable records and audit correlation. |
| V0731-09 | Primary API and generated-client examples execute against the release package without private APIs or fixture-owned product state. | CI transcripts, artifact hashes, documented configuration, exact responses, and negative examples. |

V0731-01 through V0731-09 own UIE-M3 and the console-adapter portions of
UIE-M4-M9. They do not replace the owning engine/security criteria.

## Verification instructions

Add focused crate tests and release-process suites under
`crates/rockstream-console/tests/` and `crates/rockstream-cli/tests/`. Build with
`rtk cargo build --release -p rockstream-cli`. Run the final package through the
generated client and independent HTTP/protocol clients. Record exact target names,
OIDC fixture configuration, release artifact hashes, backend revisions, and public
commands in the sign-off. Unit adapters and mock providers cannot close a route.
