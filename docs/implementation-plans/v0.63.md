# v0.63 Durable catalog

Status: Done

Source: [ROADMAP section 9](../../ROADMAP.md#v0-63). Apply the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.62 lifecycle and storage configuration. Split durable-format work into reviewable subversions under the roadmap rules, but retain every obligation below in base sign-off. Metadata durability includes enough runtime reconstruction to pass the required view crash proof; v0.65 later completes all standalone recovery categories.

## Goal and public behavior

After an ungraceful process death, definitions, identities, dependencies, and compatible maintained results remain accessible through SQL catalogs and normal queries.

## Implementation steps

1. Inventory metadata ownership in `crates/rockstream-gateway/src/catalog_stubs.rs`, `crates/rockstream-sql/src/catalog.rs`, `workload_catalog.rs` in that directory, and control namespace and ACL modules. Introduce the planned CatalogStore with storage owned by existing durable storage mechanisms. Cover databases, namespaces, tables, columns, materialized views, inline views, dependencies, indexes, workloads, sources, sinks, applicable roles and grants, and compiled-plan metadata. Define the supported and inapplicable object matrix before coding; unsupported creation must fail explicitly.
2. Define a versioned record envelope with catalog_format_version, record_version, object_id, and catalog_revision. Establish compatibility rules, upgrade path, checksums, and rejection of unsupported versions before writing records. Reuse domain IDs; make allocation durable and collision-safe. TableId, ViewId, IndexId, SourceId, and WorkloadId survive rename, restart, compaction, and backup/restore.
3. Implement atomic logical CatalogTxn records containing revision, operation_id, mutations, and checksum. Route every metadata mutation through this owner. Define durable acknowledgment, retry deduplication, revision ordering, and partial-record handling. CREATE TABLE, CREATE MATERIALIZED VIEW, DROP VIEW, and CREATE INDEX must either publish the complete mutation set or none.
4. Store the planned catalog log and snapshots under the documented catalog namespace. Recover the latest valid snapshot and subsequent valid log entries to a known revision. Confirm snapshot durability before deleting covered records. Bound scan pages and pending transactions, expose progress, and continue scans to completion rather than treating a limit as EOF.
5. Persist each view's SQL, normalized SQL or AST identity, logical-plan identity, physical-plan/compiler version, state-layout version, output schema, and dependency IDs. Adapt `GatewayHandler::recover_compiled_views` in `crates/rockstream-gateway/src/server.rs` to validate compatibility and return mandatory errors. Recovery must not replace failed state restoration with an empty successful view.
6. Convert pg_catalog and information_schema handling in `catalog_stubs.rs` into projections of the same durable revision. Keep caches explicitly derived and invalidate them on revision change. Resolve references by object ID; validate dependency cycles, missing objects, and drop behavior before publishing a transaction.
7. Extend the public crash workflow to index, workload assignment, and supported source metadata. Test interrupted DDL, log append failures, damaged snapshots, incompatible plans, and replay retries. Keep management readiness false while mandatory catalog or view reconstruction is incomplete.

## Documentation changes

Document record and transaction formats, compatibility, snapshot retention, object identity, and catalog recovery. Update SQL catalog references and primary restart examples. Mark unsupported metadata categories explicitly rather than presenting them as durable.

## Exit criteria

| ID | Acceptance condition | Intended proof |
|---|---|---|
| V063-01 | Every supported metadata category has one durable owner and public projections agree with it at the same revision. | Complete object inventory and exact pg_catalog and information_schema results before and after restart. |
| V063-02 | Record envelopes include all four required identity/version fields; supported versions upgrade and unsupported combinations fail closed. | Full serialized-record fixtures and accepted/rejected compatibility tests. |
| V063-03 | IDs remain unchanged through restart, rename, compaction, and backup/restore; new IDs never collide with restored IDs. | Exact identity maps across each lifecycle operation using the catalog store and public views where exposed. |
| V063-04 | CREATE TABLE, CREATE MATERIALIZED VIEW, DROP VIEW, and CREATE INDEX publish atomic transactions and replay to the specified revision without duplicate mutations. | Kill or fail storage at each transaction boundary and compare complete catalogs and operation outcomes. |
| V063-05 | Snapshot-plus-log recovery reconstructs all records; compaction never removes the only durable copy. | Multi-page catalog fixture, interrupted snapshot and compaction tests, full reconstructed-record oracle. |
| V063-06 | All seven compiled-plan identity fields survive restart; incompatible state layouts or broken dependencies prevent Ready. | Stored plan fixtures and public failure tests with exact compatibility diagnostics. |
| V063-07 | A new process after SIGKILL returns the original definitions and exact maintained view multiset, including index, workload, and supported source cases. | Release binary SQL transcript through creation, ingestion, crash, catalog query, and complete result verification. |
| V063-08 | Corrupt records, missing referenced objects, failed writes, and exhausted transaction or scan budgets cannot produce successful partial metadata. | Negative process and storage tests assert prior revision, readiness failure, occupancy, and bounded error behavior. |
