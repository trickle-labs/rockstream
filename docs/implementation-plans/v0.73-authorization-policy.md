# v0.73 authorization policy profile

Status: approved and published v0.73 source-plan amendment (PR #310). Runtime implementation is partial, and qualification evidence remains incomplete.

This profile records the user-approved decisions for [issue #302](https://github.com/trickle-labs/rockstream/issues/302) and related v0.73 security work. PR #310 published the plan amendment; this status does not claim complete runtime implementation or qualification. Its source basis is the [roadmap](../../ROADMAP.md), [v0.73 implementation plan](v0.73.md), [UI-enablement plan](ui-enablement.md), [security contract](../security.md), [connector guarantees](../connectors.md), and the current mutation registries. The action registry follows [ROADMAP section 19.2](../../ROADMAP.md#192-persist-roles-and-grants): use four fixed presets, not a general policy language.

## Principal and login model

- A principal has a stable catalog `PrincipalId`. Login credentials map explicitly to that ID; matching names alone never merge accounts.
- OIDC login identity is the pair `(issuer, subject)`. Local SCRAM identity is a configured local username. A gateway client certificate authenticates only through an explicit mapping to a principal; its CN does not grant a role.
- Node certificates establish service identity on internal transports. A node identity cannot become a user principal or obtain user grants.
- Service-only principals may retain scoped consumer grants without an interactive login. They cannot receive the administrator or operator preset. A service identity may use a secret only for its explicitly granted consumer scope.
- Cross-process actor assertions use RS256, target the exact receiving service and deployment, expire within 60 seconds, and carry an explicit allowance intersected with the actor's current scoped policy. Use a dedicated deployment-managed signing key pair separate from TLS credentials: the gateway holds the PKCS#8 private key and control receives the matching public JWK. Missing or invalid key material fails closed; there is no production fallback key.
- Multiple login methods may map to one principal only through an explicit catalog mutation.

## Authentication modes and rejected requests

- Run all ten required negative cases through actual public release endpoints. Each case must use a supported, enabled qualification configuration; configurations need not be identical or deployment defaults. A mode may be unavailable in another configuration, but startup rejection does not substitute for a missing case. If no supported configuration can exercise a case, record it as blocked evidence.
- Failed authentication or node-identity rejection must not establish a new authenticated session. An insufficient-role denial in an existing authenticated session denies the action, preserves protected state, and is audited; it does not by itself require session teardown. An applicable protocol, revocation, or security policy may require closure.

`administrator` does not imply data access, secret use, or cluster operations. `operator` does not imply data access, secret use, or grant authority. Diagnostics and support artifacts contain sanitized operational metadata only.

`secret.use`, `checkpoint.export`, `checkpoint.restore`, and the four `backup.*` actions are explicit scoped grants outside the presets. `secret.use` is bound to the namespace, secret, and consumer identity. The service may resolve the value for that consumer, but no preset permits a caller to read secret values. A user-delegated resolution also checks the actor's current scoped policy. Checkpoint and backup operations cannot expose or download business data through operator access.

## Grant, bootstrap, and account changes

- Only a principal with `grant.manage` may create, change, or revoke a grant. Grant mutations name the target principal and exact scope; a grantor cannot increase its own authority. A grantor may revoke its own authority only if another active administrator remains.
- Each policy mutation supplies the revision it reviewed. The catalog commits only if that revision is still current; stale edits return a conflict and make no partial change.
- Provide a documented, trusted, explicitly authorized, and audited first-administrator bootstrap or preprovisioning route. Do not prescribe a particular CLI or token mechanism. Scope any temporary bootstrap credential and revoke or expire it after use. Never enable an unauthenticated listener or silently create an administrator.
- Prevent last-administrator lockout by rejecting removal, disablement, or downgrade of the last active administrator. Operators and ordinary users cannot self-grant. The trusted offline preprovision path is the only initial recovery route in this profile.
- A user password change verifies the current credential. An administrator reset writes a new verifier without retrieving the old password. Both advance the principal's authentication revision and follow the grant mutation's durable audit rules.
- A service-only principal may keep a scoped consumer grant but cannot log in interactively or administer principals, grants, secrets, or cluster operations.

## Revocation, reviewed changes, and caches

- The initial v0.73 maximum is 60 seconds from durable revocation. Reauthorize or terminate long-lived work within that interval. Deployments may be stricter; a reviewed profile change may revise the baseline before measurement, but not widen it after a failure merely to pass. A newly observed policy revision invalidates older decisions immediately; no newly admitted operation may ignore a newer revision already known at its enforcing boundary.
- Authorization cache keys include `PrincipalId`, action scope, deployment, and policy revision. Cache entries cannot cross deployment contexts.
- Pooled sessions and long-lived queries or subscriptions reauthorize within 60 seconds and terminate if the current policy denies access or cannot be refreshed.
- At apply time, recheck the grantor's authority and relevant revisions. Reject a stale review without effects; revision checks do not replace the execution-time authorization check.
- Grant, credential, and bootstrap changes are acknowledged only after the durable catalog mutation and its correlated audit record commit. Recovery restores the exact principal, grant, and revision set.

The operator preset alone never implies business-data, secret-value, or grant authority. A principal with a separate, explicitly authorized scoped grant may perform only that action under the current combined policy. Test operator-only denial separately from access through a separate grant. No grant may create a plaintext GET for an existing secret.

Support artifacts are always sanitized in qualified v0.73 workflows: no business rows, SQL literals, raw connector payloads, secret values, keys, or tokens. This does not require a non-default raw workflow or permanently ban a future separately authorized workflow. Limit each artifact to 10 MiB; allow downloads for at most 10 minutes; bind downloads to the actor and scope through opaque IDs. Deny new downloads at expiry. Limit aggregate storage to 100 MiB per deployment, reject new generation before it exceeds the budget, and do not evict unexpired artifacts. Delete retained and temporary data within 60 seconds, including after restart and before listeners open.

A backup action grant may initiate only its named operation at the granted scope; it does not grant access to backup contents or secret values.

## Compatibility mapping

Compatibility applies only to verified stored grants; a caller-presented role is not an authorization grant. Migrate supported persisted roles through explicit, versioned action mappings that retain their effective permissions. Reject unsupported legacy formats explicitly.

| Supported legacy grant | Versioned compatibility mapping | Required behavior |
| --- | --- | --- |
| `Viewer` | `data.read` on the same verified namespace/resource scope | Preserve relation reads only; do not add subscriptions, writes, or administration unless a separate stored grant provides them. |
| `PipelineOwner` | `Viewer` plus only CLI/pgwire operations currently marked `PipelineOwner`, on the same verified scopes | Preserve view/source pause/resume, schema creation, view/table/source/sink authoring, row writes, and COPY; do not widen to `Admin`-only operations. |
| `Admin` | `Viewer` and `PipelineOwner` behavior plus only CLI/pgwire operations currently marked `Admin`, and `namespace.cross_access` on the same verified scope | Preserve source/schema drop, workload/index/secret operations, namespace creation, drain/migrate, checkpoint/backup, support, and existing cross-namespace behavior. Do not equate legacy `Admin` with either new `administrator` or `operator` preset. |

Keep the documented CLI `--identity-role` flag only as a compatibility request; the authenticated principal's persisted grants decide access. The current `RoleCatalog` stores password verifiers but no role grants. `AclEntry` is currently held only in the in-memory `AclStore`, though its type documents the legacy `catalog/acl/<namespace>/<principal>` JSON form; migrate only that exact verified form through a versioned mapping if present. `CatalogRoleEntry` records durable role metadata and membership but does not establish authenticated principal authority by itself. The current CLI/pgwire mutation registries and gateway ACL callers define the operation inventory. Never infer authority from the CLI flag, role name, or `CatalogRoleEntry` membership alone; reject unrecognized stored formats.

## Audit and lost-response decisions

- When authentication has not established an actor, or a request, target, scope, operation, or before/after state does not exist, use the documented truthful verified, unverified, unknown, or not-applicable representation. Correlation comes only from listener-observed identifiers; never promote an unverified presented identity to a verified actor.
- Retain audit records for 90 days, subject to a 1 GiB deployment-wide cap. Do not evict records before retention expiry to make space. Append required audit events synchronously with their durable mutation; a failed append blocks acknowledgement. On capacity/unavailability, expose degraded health, reject the related mutation, stop admitting new authenticated sessions if their authentication event cannot be recorded, and close an existing session if its required denial event cannot be recorded. Never silently drop a required event.
- Expose authorized history through PGWire `SHOW SECURITY AUDIT [FROM <timestamp_ms>] [TO <timestamp_ms>] [AFTER <cursor>] [LIMIT <rows>]`. `FROM` and `TO` are inclusive epoch-millisecond bounds; clauses appear once in that order. Rows are ordered ascending by `(timestamp_ms, event_id)`. Each row returns a cursor formatted as `<timestamp_ms>:<unpadded base64url UTF-8 event_id>`; `AFTER` is exclusive. Pages are live keyset reads, not snapshots: records committed after a page may appear in a continuation if their key sorts after its cursor; restart from the first page to include concurrent records that sort at or before the cursor. The default page is 100 rows and the maximum is 500. Each request checks current `security.audit.read` policy for its requested time range and confirms the same policy revision at the page-read boundary; a concurrent policy change returns a retryable conflict without returning records. Retained records are paged from an ordered in-memory index in `O(log n + page_rows)` work.
- Require a client-generated UUID in `Idempotency-Key` before each security mutation and use it as the operation ID. Bind it to actor, deployment, scope, and canonical request digest. A retry with the same key and request returns the original operation; reuse with a different request has no effect. The authorized public `GET /operations/{id}` lookup returns the complete original status and result so the client can reconcile with the identity it knew before submission. Retain the reconciliation record for 90 days. Never retry a lost response as a new mutation.

## Secret and certificate compatibility decisions

- Preserve the documented `secret = '<name>'` connector input where supported, while persisting and resolving its canonical `secret://name` reference. Reject or offline-migrate unsupported legacy encrypted placeholders; do not fall back to local secret state when KMS fails.
- Preserve next-epoch connector activation and process continuity. KEK rotation retains the documented single-store, staging-failure, post-submission cancellation, and old-or-new recovery semantics.
- Preserve in-flight internal certificate reload, dual-generation CA trust during rollover, and existing stream continuity. Test active connections during rollover; rejecting an invalid new identity alone does not prove compatibility. Changing this behavior requires a separate explicit compatibility decision.

## Kafka sink qualification boundary

Do not expand the experimental Kafka sink's release tier to satisfy secret-rotation verification. Qualify rotation through a supported release-process path if one exists. Otherwise mark that sink case blocked and resolve the evidence path before sign-off. Marker-only or unsupported wiring is not proof.

## Remaining evidence gaps

These are evidence gaps, not policy decisions: a release-process bootstrap fixture, a supported sink exercise route, client-visible lost-response observation, independent durable-envelope inspection, and real multi-view/multi-partition rotation fixtures. They do not make checks pass; all planned verification remains unrun.

## Frozen implementation profile

These values are approved for the v0.73 source-plan amendment. They define the
initial qualification profile; deployments may be stricter, and a reviewed
profile change may revise a bound before measurement. A failed result cannot
be made to pass by widening a limit after measurement.

| Choice | Frozen v0.73 value |
| --- | --- |
| SCRAM | SCRAM-SHA-256 only; keep MD5 unavailable. Require the durable role store before listener startup. |
| OIDC and actor assertion algorithms/claims | RS256 only; reject `none`, HMAC, and other algorithms. Require exact OIDC `iss`, `aud`, nonempty `sub`, and `exp`; validate `nbf` when present. Actor assertions target the exact service and deployment and expire within 60 seconds. |
| OIDC request/JWKS bounds | Token ≤16 KiB; JWKS response ≤1 MiB and ≤100 keys per issuer; key cache TTL ≤60 seconds and honor any shorter issuer lifetime; 5-second fetch timeout; one in-flight refresh per issuer; at most one retry after 250 ms for transient transport failures; no stale key after expiry. |
| Authorization cache | At most 10,000 entries and 60-second TTL, matching the current ACL cache limits; invalidate immediately when the enforcing boundary observes a newer policy revision. |
| Secret resolution and audit writes | No shared plaintext secret cache or asynchronous audit queue. Resolve only at activation/next epoch, keep the existing 10-second KMS request timeout, use no automatic retry, and fail closed without local fallback. Append required audit events synchronously with the durable mutation; a failed append blocks acknowledgement and follows the capacity behavior below. |
| Bootstrap and last administrator | Preprovision the first administrator through a trusted offline deployment-state path before opening listeners. Commit principal, grant, policy revision, and audit together. Reject online removal, disablement, or downgrade of the last active administrator. If all administrator access is lost, require explicit offline recovery with operator access to durable deployment state and an audit record. This does not prescribe a CLI or token. |
| Legacy ACL mapping | Map every verified stored `Viewer`, `PipelineOwner`, and `Admin` grant through the full operation sets in the Compatibility mapping table, preserving its existing scope. Never migrate a CLI role flag or inert role metadata as authority. |
| Audit retention and capacity | Retain 90 days, with a 1 GiB deployment-wide cap. Do not evict records before retention expiry to make space. If a required audit append cannot commit, reject the related mutation and expose a degraded health state; stop admitting new authenticated sessions when authentication events cannot be durably recorded, and close an existing session when its required denial event cannot be recorded. No required event is silently dropped. |
| Audit history query | PGWire `SHOW SECURITY AUDIT`; inclusive time filters, exclusive `(timestamp_ms, event_id)` cursor, ascending order, 100-row default, 500-row maximum, and `O(log n + page_rows)` indexed reads. Recheck the current principal's permission for each requested time range. |
| Support-artifact aggregate budget | 100 MiB per deployment. Reject generation before writing when the budget would be exceeded; do not evict unexpired artifacts. Delete expired and temporary data within 60 seconds, including during startup recovery before listeners open. |
| Lost-response reconciliation | Require a client-generated UUID in `Idempotency-Key` before each security mutation. Use the same UUID as the operation ID and bind it to actor, deployment, scope, and canonical request digest. Repeating the same key and request returns the original operation; reusing the key with a different request has no effect. Provide an authorized public `GET /operations/{id}` lookup that returns the complete original status and result. Retain reconciliation records for 90 days. |

The compatibility bundle above is frozen as the behavior to preserve. The
current action inventory includes `CLI_MUTATION_POLICY`,
`PGWIRE_MUTATION_POLICY`, persisted `CatalogRoleEntry` formats, and the two
gateway ACL checks. Unsupported or unverified old forms remain explicitly
rejected until migration evidence demonstrates their exact prior permissions.
Exact externally visible errors remain governed by the existing error registry
and callers.
