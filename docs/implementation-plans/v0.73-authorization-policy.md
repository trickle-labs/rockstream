# v0.73 authorization policy proposal

Status: proposed v0.73 source/plan amendment for review. The current source contract and issue text do not yet contain these decisions; runtime behavior does not implement them, and qualification evidence remains unrun.

This proposal records the author decisions supplied for [issue #302](https://github.com/trickle-labs/rockstream/issues/302) and related v0.73 security work. It is an amendment proposal, not evidence that the decisions are already adopted in the roadmap or implementation plan. Its source basis is the [roadmap](../../ROADMAP.md), [v0.73 implementation plan](v0.73.md), [UI-enablement plan](ui-enablement.md), [security contract](../security.md), and [connector guarantees](../connectors.md). Values those sources label as proposed become profile decisions only if this amendment is adopted. The action registry still follows [ROADMAP section 19.2](../../ROADMAP.md#192-persist-roles-and-grants): use four fixed presets, not a general policy language.

## Principal and login model

- A principal has a stable catalog `PrincipalId`. Login credentials map explicitly to that ID; matching names alone never merge accounts.
- OIDC login identity is the pair `(issuer, subject)`. Local SCRAM identity is a configured local username. A gateway client certificate authenticates only through an explicit mapping to a principal; its CN does not grant a role.
- Node certificates establish service identity on internal transports. A node identity cannot become a user principal or obtain user grants.
- Service-only principals may retain scoped consumer grants without an interactive login. They cannot receive the administrator or operator preset. A service identity may use a secret only for its explicitly granted consumer scope.
- Multiple login methods may map to one principal only through an explicit catalog mutation.

## Authentication modes and rejected requests

- SCRAM, OIDC, and mTLS are all required v0.73 modes and must be enabled and qualified. A mode that cannot qualify blocks sign-off. Rejecting its selection at startup does not replace its required negative cases.
- Run all ten required negative cases through the applicable public release endpoints.
- Failed authentication establishes no application session. An authorization denial in an existing authenticated session rejects only that operation, preserves the session, creates no protected side effect, and is audited.
- A TLS peer with the wrong node identity is not accepted as an authenticated node; reject and close that node connection.

## Fixed actions and presets

Every grant carries the scope named in the action table. Multiple presets may be granted to one principal, but a preset never implies another preset.

| Action | Protected operation | Scope |
| --- | --- | --- |
| `metadata.inspect` | Inspect catalog, object definitions, and query-planning metadata without reading rows or secret values | Namespace and resource |
| `data.read` | Run row-returning SQL reads | Namespace and table/view |
| `data.write` | Insert, update, or delete rows | Namespace and table |
| `data.subscribe` | Start or continue a change stream | Namespace and view |
| `view.author` | Create, alter, or drop views | Namespace and view |
| `source.lifecycle` | Create, alter, or drop source/sink definitions | Namespace and source/sink |
| `workload.change` | Create, update, deploy, or delete a workload | Namespace and workload |
| `principal.manage` | Create, update, disable, or delete principals and login capabilities | Cluster |
| `grant.manage` | Assign or revoke fixed presets and explicit scoped grants | Target principal and exact scope |
| `auth.config.manage` | Change supported authentication-provider configuration | Cluster |
| `secret.metadata.read` | List secret identifiers, versions, and rotation status | Namespace and secret |
| `secret.manage` | Create, update, or delete a secret through write-only input | Namespace and secret |
| `secret.rotate` | Rotate a secret or its wrapping key | Namespace and secret, or cluster key |
| `secret.use` | Resolve one secret reference for its authenticated consumer; delegated calls also require the actor's current scoped policy | Namespace, secret, and consumer identity |
| `security.audit.read` | Read bounded security audit history | Cluster and time range |
| `namespace.cross_access` | Use a legacy namespace ACL grant to access a view outside the session namespace | Originating namespace ACL scope |
| `cluster.observe` | Read health, topology, capabilities, and sanitized configuration summaries | Cluster, node, or shard |
| `node.drain` | Drain a worker | Cluster and node |
| `shard.migrate` | Migrate a shard | Cluster and shard |
| `operation.cancel` | Cancel an administrative operation | Cluster and operation |
| `operation.history.read` | List or read administrative operation history | Cluster and operation |
| `diagnostics.read` | Read bounded operational diagnostics and metrics without business rows | Cluster or node |
| `support.generate` | Generate a sanitized support artifact | Cluster or node |
| `support.download` | Download an unexpired artifact bound to the requesting principal | Opaque artifact ID |
| `backup.create` | Create a backup at a configured destination | Cluster and backup destination |
| `backup.inspect` | Inspect backup metadata | Backup destination and backup ID |
| `backup.verify` | Verify a backup | Backup destination and backup ID |
| `backup.restore` | Restore a backup into a target store | Backup ID and target store |

| Preset | Actions | Scope |
| --- | --- | --- |
| `data_reader` | `metadata.inspect`, `data.read`, `data.subscribe` | Namespace and resource |
| `builder` | All `data_reader` actions, plus `data.write`, `view.author`, `source.lifecycle`, `workload.change` | Namespace and named table, view, source, sink, or workload |
| `administrator` | `principal.manage`, `grant.manage`, `auth.config.manage`, `secret.metadata.read`, `secret.manage`, `secret.rotate`, `security.audit.read` | Cluster, with secret actions additionally scoped to namespace and secret |
| `operator` | `cluster.observe`, `node.drain`, `shard.migrate`, `operation.cancel`, `operation.history.read`, `diagnostics.read`, `support.generate`, `support.download` | Cluster, node, shard, or opaque artifact ID as applicable |

`administrator` does not imply data access, secret use, or cluster operations. `operator` does not imply data access, secret use, or grant authority. Diagnostics and support artifacts contain sanitized operational metadata only.

`secret.use` and the four `backup.*` actions are explicit scoped grants outside the presets. `secret.use` is bound to the namespace, secret, and consumer identity. The service may resolve the value for that consumer, but no preset permits a caller to read secret values. A user-delegated resolution also checks the actor's current scoped policy. Backup operations cannot expose or download business data through operator access.

## Grant, bootstrap, and account changes

- Only a principal with `grant.manage` may create, change, or revoke a grant. Grant mutations name the target principal and exact scope; a grantor cannot increase its own authority. A grantor may revoke its own authority only if another active administrator remains.
- Each policy mutation supplies the revision it reviewed. The catalog commits only if that revision is still current; stale edits return a conflict and make no partial change.
- Bootstrap uses an explicit out-of-band, one-time credential through the authenticated administrative CLI. Consume it durably with the first-administrator/grant transaction and correlated audit event. Never enable an unauthenticated listener or silently create an administrator.
- At least one active, login-capable administrator must remain. A mutation cannot remove the last administrator's login capability or administrator grant. Recovery after losing that principal uses an explicit offline procedure requiring operator access to durable deployment state; operators and ordinary users cannot self-grant.
- A user password change verifies the current credential. An administrator reset writes a new verifier without retrieving the old password. Both advance the principal's authentication revision and follow the grant mutation's durable audit rules.
- A service-only principal may keep a scoped consumer grant but cannot log in interactively or administer principals, grants, secrets, or cluster operations.

## Revocation, reviewed changes, and caches

- Maximum policy staleness is 60 seconds. Revalidate or terminate long-lived work within that interval. A newly observed policy revision invalidates older decisions immediately; no newly admitted operation may ignore a newer revision already known at its enforcing boundary.
- Authorization cache keys include `PrincipalId`, action scope, deployment, and policy revision. Cache entries cannot cross deployment contexts.
- Pooled sessions and long-lived queries or subscriptions reauthorize within 60 seconds and terminate if the current policy denies access or cannot be refreshed.
- At apply time, recheck the grantor's authority and relevant revisions. Reject a stale review without effects; revision checks do not replace the execution-time authorization check.
- Grant, credential, and bootstrap changes are acknowledged only after the durable catalog mutation and its correlated audit record commit. Recovery restores the exact principal, grant, and revision set.

The operator preset alone never implies business-data, secret-value, or grant authority. A principal with a separate, explicitly authorized scoped grant may perform only that action under the current combined policy. Test operator-only denial separately from access through a separate grant.

Support artifacts are always sanitized in v0.73: no business rows, SQL literals, raw connector payloads, secret values, keys, or tokens. There is no raw artifact mode. Limit each artifact to 10 MiB and expire actor-scoped downloads after 10 minutes. At expiry, deny access and delete the artifact and temporary generation data, including after restart. Freeze an aggregate storage budget and fill/overflow behavior before qualification.

A backup action grant may initiate only its named operation at the granted scope; it does not grant access to backup contents or secret values.

## Compatibility mapping

Compatibility applies only to verified stored grants; a caller-presented role is not an authorization grant. Migrate supported persisted roles through explicit, versioned mappings that retain their effective permissions. Reject unsupported legacy formats explicitly.

| Verified legacy grant | Proposed versioned mapping | Preserved boundary |
| --- | --- | --- |
| `Viewer` | `data_reader` | Same namespace/resource scope |
| `PipelineOwner` | `data_reader` plus `builder` | Same namespace/resource scope |
| Scoped ACL `Admin` | `data_reader`, `builder`, and the legacy `namespace.cross_access` action | Preserve the verified effective permissions and namespace cross-access scope; do not infer identity, grant, secret, or cluster-operation authority |

Keep the documented CLI `--identity-role` flag only as a compatibility request; the authenticated principal's persisted grants decide access. The current `RoleCatalog` stores password verifiers but no role grants. The current `AclStore` is in memory; its entries do not provide restart-surviving grants. `CatalogRoleEntry` role definitions and memberships are not principal grants by themselves. Migrate only supported persisted role formats; reject unsupported formats explicitly and do not infer administrator or operator authority from a role name.

## Audit and lost-response decisions

- When authentication has not established an actor, or a request, target, scope, operation, or before/after state does not exist, record explicit `unknown` or `not_applicable` values. Correlation comes only from listener-observed identifiers; never promote an unverified presented identity to a verified actor.
- The client must possess or be able to derive an operation identity before a response can be lost. Retry and reconcile through the supported public path using that same identity. Server-only fault instrumentation is not client recovery evidence. If a security mutation has no client-visible operation identity, resolve that contract before claiming its recovery criterion passes.

## Secret and certificate compatibility decisions

- Preserve the documented `secret = '<name>'` connector input where supported, while persisting and resolving its canonical `secret://name` reference. Reject or offline-migrate unsupported legacy encrypted placeholders; do not fall back to local secret state when KMS fails.
- Preserve next-epoch connector activation and process continuity. KEK rotation retains the documented single-store, staging-failure, post-submission cancellation, and old-or-new recovery semantics.
- Preserve in-flight internal certificate reload, dual-generation CA trust during rollover, and existing stream continuity. Test active connections during rollover; rejecting an invalid new identity alone does not prove compatibility. Changing this behavior requires a separate explicit compatibility decision.

## Kafka sink qualification boundary

Do not expand the experimental Kafka sink's release tier to satisfy secret-rotation verification. Qualify rotation through a supported release-process path if one exists. Otherwise mark that sink case blocked and resolve the evidence path before sign-off. Marker-only or unsupported wiring is not proof.

## Remaining evidence gaps

These are evidence gaps, not policy decisions: a release-process bootstrap fixture, a supported sink exercise route, client-visible lost-response observation, independent durable-envelope inspection, and real multi-view/multi-partition rotation fixtures. They do not make checks pass; all planned verification remains unrun.

## Required implementation evidence

Before adopting this proposal, review the preset matrix, the legacy-role migrations, the 60-second bound, and the first-administrator recovery path. If adopted, prove all three authentication modes and ten required negative cases at applicable public endpoints, revision-checked concurrent edits, restart recovery, session-preserving authorization denial, pooled-session revocation, last-administrator protection, durable audit coupling, support-artifact deletion, secret rotation, and certificate rollover. Keep issues #301–#307 open until their respective acceptance evidence exists.
