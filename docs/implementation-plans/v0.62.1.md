# v0.62.1 Worker memory budgets

Status: Done

Source: [ROADMAP section 5.4](../../ROADMAP.md#54-v0621-worker-memory-budgets). Apply the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.62 NodeConfig for one worker budget configuration. Reuse existing storage caches, admission, and runtime quota mechanisms. This patch establishes production memory control; state beyond RAM and complete spill qualification remain v0.67.1 work.

## Goal and public behavior

Many shards share a worker memory budget. Admission fails or applies backpressure before allocation would exceed the budget. Foreground reads and maintenance retain reserved capacity under sustained overload.

## Implementation steps

1. Inventory all production shard construction, including initial startup, restored shards, additions, and migration destinations. Wire `WorkerStorageContext` from `crates/rockstream-storage/src/storage_context.rs` into every `ShardDbBuilder` in `shard_db.rs`. Reuse the same worker-owned block and metadata cache allocations and charge shared allocations once. Audit cache key identity across tenants, security policies, arrangements, shards, and backend objects.
2. Build the budget ledger from actual allocations: SlateDB write buffers, block and metadata caches, operator state, source buffers, exchange buffers, query work, checkpoints, and migrations. Reuse `crates/rockstream-runtime/src/quota.rs`, `crates/rockstream-gateway/src/admission.rs`, and `crates/rockstream-runtime/src/exchange/flow_control.rs` where they already enforce the relevant owner. Document accounting for transient copies and allocator overhead; logical state bytes alone cannot establish RSS safety.
3. Obtain byte permits before allocating. Define allocation ownership, release on cancellation or shard removal, oversized-request errors, source pressure propagation, and bounded retry and waiter policies. Audit existing caches for entries larger than their capacity and ensure rejection or bypass cannot allocate without a charge.
4. Reserve capacity for foreground maintenance and reads. Limit background compaction, backfill, and migration concurrency independently. Freeze budget partitions, maximum queue age, RSS tolerance, and soak duration before qualification. Invalid or mutually impossible allocations fail configuration validation.
5. Verify the pinned SlateDB version's supported local object-store disk-cache API before selecting its integration. Configure a bounded disk cache with explicit identity, location, capacity, eviction, and cleanup behavior. Shared block caches share a budget; only the object-store cache can justify cross-instance download reuse. Keep credential and tenant isolation intact. If the pinned API cannot meet the requirement, resolve the dependency change before implementation; do not claim an unsupported API exists.
6. Exercise real workers under many-shard sustained overload, including shard creation and removal, slow storage, compaction, backfill, and migration pressure where those paths are available. Record RSS, every ledger category, queue age, waiter count, disk occupancy, object requests, and foreground completion. Compare exact committed outputs and restart results against the oracle.

## Documentation changes

Extend configuration docs with worker budget ownership, all charged categories, reserves, admission errors, pressure signals, and disk-cache lifecycle. Extend the R1 contract with a versioned many-shard pressure profile and its frozen limits.

## Exit criteria

| ID | Acceptance condition | Intended proof |
|---|---|---|
| V0621-01 | Every production shard creation path receives the worker-owned caches and shared allocations are charged once. | Call-site inventory plus cache-identity and full ledger assertions during startup, restore, add, and removal. |
| V0621-02 | Every listed memory category is charged before allocation, including transient buffers, and permits return after errors or cancellation. | Allocation-boundary fixtures assert exact ledger state; oversized allocation and cancellation tests. |
| V0621-03 | Pressure reaches sources and retries, waiters, and queue age remain within frozen limits under sustained overload. | Release worker soak records offered load, pressure, RSS, category occupancy, errors, and exact committed results. |
| V0621-04 | Reserved reads and foreground maintenance complete under background pressure while compaction, backfill, and migration obey concurrency limits. | Mixed workload and stalled-background tests compare actual activity and completion with the frozen budget contract. |
| V0621-05 | The pinned supported disk-cache API enforces disk capacity and isolates cache identities across shards and tenants. | Real object-store reads test eviction, shard removal, restart, identity collisions, and bounded disk occupancy. |
| V0621-06 | Cross-instance download reuse claims are supported by object-store request measurements, and memory-cache sharing claims describe only measured behavior. | Controlled cold and warm reads with full result equality and request traces. |
| V0621-07 | Many-shard addition and removal, storage slowdown, and process restart preserve complete results without unbounded RSS or backlog. | Measured release-process pressure and recovery run with frozen RSS and queue-age limits. |

## Verification instructions

Run `rtk cargo test -p rockstream-storage --lib` and `rtk cargo test -p rockstream-ops --test operator_state_accounting_tests` for existing accounting coverage. Run `rtk cargo test -p rockstream-cli --test cluster_worker_pressure_metrics_tests` after extending it with real budget observations. Planned many-shard process and disk-cache tests must name their commands and storage prerequisites before sign-off. Unit counters alone cannot qualify bounded RSS.
