# v0.75 Stable technical preview

Status: Planned

Roadmap source: [21. v0.75](../../ROADMAP.md#v0-75). Follow the
[shared implementation and evidence rules](README.md) and the
[UI-enablement qualification track](ui-enablement.md).

## Prerequisites and scope

Require every applicable v0.60-v0.74 sign-off, including v0.73.1 and actual
distinct-artifact compatibility evidence. Require completed UIE M0-M9 evidence
and the v0.74-owned portion of M10, with no mock-only, skipped, or
infrastructure-blocked mandatory case. An incomplete prerequisite remains
incomplete; v0.75 does not absorb or waive it.

This milestone consolidates the supported contract. It may finish integration and
qualification needed for UIE M7 and M9-M11, but it does not add new SQL,
distributed, connector, migration, cancellation, backup, restore, or IAM
semantics. React or any other frontend implementation remains out of scope.

## Goal and public behavior

RockStream presents a compact, truthful, long-lived 0.x contract suitable for
serious technical evaluation and selected non-critical deployment. A frontend
engineer can complete the supported Build, Administer, and Operate journeys
through published APIs and generated types without private interfaces or fixture
state. Passing the final gate sets the program status to **Ready for UI
implementation**, not v1.0-ready.

## Implementation steps

1. Freeze the supported core surface and classify every CLI command, configuration key, SQL statement, catalog, network port, authentication mode, connector, operator, console route, and event as Supported, Experimental, Internal, Deprecated, or Removed. Remove accidental product surface or make its weaker status explicit.
2. Complete the remaining reviewed-change integration from UIE M7. Exercise materialized-view creation, supported source pause/resume, and workload changes through real compiler, catalog, connector owner, and v0.72 enforcement paths. Preserve prepare/apply revisions, idempotency, requested/effective state, audit coupling, and recovery. Reject unsupported replacement, cascade, lifecycle, and configuration behavior explicitly.
3. Expose only v0.66/v0.68-qualified management and backup operations through v0.73.1. Reuse durable operation IDs and state, authoritative preflight/eligibility, typed progress, actual executor cancellation boundaries, configured destinations, and supported restore verification. Do not enlarge migration, cancellation, backup, or live-restore capabilities.
4. Package the console service, schemas, generated client, examples, and standalone and qualified multi-process configurations with the candidate binary/container. Document TLS, OIDC, bootstrap, backend trust, optional telemetry, secrets, storage, limits, probes, and shutdown. Execute installation and local headless setup from clean release artifacts.
5. Run the frozen mixed catalog/query/subscription/admin/operation workload while ingestion, maintenance, failure, and recovery continue. Measure API latency separately from engine read, commit, and freshness latency; record sustained throughput, RSS, buffers, queue age, cancellation cleanup, and recovery. Compare direct and console paths at identical offered load. Include large catalogs, over-budget results, slow clients/storage, telemetry outage, and principal-scoped saturation without starving control or maintenance.
6. Complete adversarial qualification for untrusted input, malformed tokens, header spoofing, stale/replayed changes, resource enumeration, cross-scope search/metrics/artifact access, session expiry, CSRF, forbidden management, parser/serializer fuzz cases, and secret canaries. Resolve any finding that undermines a required isolation or integrity property.
7. Run roadmap Q1-Q8 with the exact publication artifacts. Preserve complete data, metadata, identity, observation, operation, resource, and compatibility outcomes. Run Q9 through the generated client or an independent headless HTTP client for every mandatory Build, Administer, and Operate journey, including success, denial, degradation, stale/unavailable state, conflict, cancellation, restart, and upgrade.
8. Close the UI capability map. Every first-UI interaction needs a public route, authoritative producer, permission rule, support and eligibility behavior, absence/error semantics, named limits, compatibility policy, and linked positive and negative evidence. Deferred features need a future owner and no affordance or schema claim suggesting support.
9. Publish the frontend handoff package and mechanical evidence manifest. Include versioned OpenAPI/events, generated types/client, exact examples, authentication setup, status/error semantics, capability/permission/eligibility rules, local integration setup, and contract fixtures derived from qualified behavior. Make the readiness checker reject missing, unchecked, skipped, stale, or fabricated evidence. Obtain technical, security, runtime/storage, and operational review.
10. Reset primary documentation around the supported tasks, publish explicit limitations and future 0.x compatibility expectations, and keep historical plans/evidence available without presenting them as ordinary product navigation.

## Documentation changes

## Verification instructions

Build the exact release binaries and containers intended for publication. Run
the repository's release qualification entry point after extending it for Q1-Q9,
then run `scripts/check-ui-readiness.sh` and its negative self-tests. The sign-off
must record final commands, artifact digests, revisions, process topology,
external service versions, frozen profiles, raw measurement locations, exact
result oracles, criterion mappings, and reviewer identities. Print only summary
lines for passing tests; preserve full failure output in retained artifacts.
