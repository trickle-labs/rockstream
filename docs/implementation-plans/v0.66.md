# v0.66: Real management plane

Status: Planned

Roadmap source: [12. v0.66: Real Management Plane](../../ROADMAP.md#v0-66).
Follow the [shared implementation and evidence rules](README.md). Every exit criterion below is mandatory; this document records future work, not completed qualification.

## Prerequisites and scope

Require v0.62 configuration and lifecycle, v0.63 durable metadata, and v0.65 recovery and backup proof. Management exposes real operations. v0.68 later supplies complete distributed migration semantics; v0.66 still requires real successful mutation paths and must never manufacture completion for an unavailable action. Keep management RPC, control-worker messages, row exchange, and PostgreSQL separate.

Existing ownership starts in `crates/rockstream-cli/src/transport.rs`, `cli_args.rs`, `output.rs`, and `metrics_server.rs`; control state lives in `crates/rockstream-control/src/service.rs`, `topology.rs`, `migration.rs`, and `checkpoint_export.rs`. Reuse their real state and existing protobuf/tonic dependencies. The typed management service and its protocol definitions are planned additions; decide their exact module placement before editing callers.

## Goal and public behavior

`rockstream status` and administrative commands obtain typed responses from a real management endpoint. A long-running mutation returns an operation ID after durable acceptance. `rockstream admin operation show <id>` reports actual progress, failure, or completion after client and server restarts.

## Implementation steps

1. Define the management protocol and server ownership, covering roadmap 12.1 and 12.2. Add `GetClusterStatus`, `ListNodes`, `GetNode`, `ListShards`, `GetShard`, `ListOperations`, `GetOperation`, `GetConfigSummary`, `GetCapabilities`, and `GetHealth`. Define `DrainWorker`, `MigrateShard`, `CreateBackup`, and `CancelOperation`. Publish protocol version, field meanings, unknown-object errors, unavailable-service behavior, and compatibility rejection. Configuration summaries redact credentials and use v0.62 effective configuration.
2. Map each response field to an authoritative runtime, catalog, lease, checkpoint, or operation record. Define snapshot consistency for compound status responses. Bound list pages, response bytes, concurrent requests, and retained operation history. Expose fill levels and explicit overload errors; reject invalid pagination tokens. Missing telemetry remains unknown with a reason, never a constructed healthy value.
3. Implement durable operation acceptance and lookup, covering 12.3 and 12.4. Reuse durable catalog/control storage instead of a CLI-local registry. Version records and persist `Pending`, `Running`, `Waiting`, `Succeeded`, `Failed`, or `Cancelled` with `started_at`, `updated_at`, `progress`, `phase`, `error_code`, and `next_steps`. Freeze permitted transitions and timestamp semantics before the executor runs. Only completed real effects permit `Succeeded`; storage failure prevents acceptance or advancement.
4. Implement 12.5 idempotency in the shared server path. Bind an idempotency identifier to the canonical request digest and durable operation ID before effects. Exact retries return the same operation; a changed payload under the same key returns a conflict. Serialize conflicting shard mutations and backup identity allocation. Specify retention and expired-key behavior so record cleanup cannot silently repeat an accepted effect.
5. Connect all four mutations to real executors and demonstrate a successful supported case for each. Cancellation is a durable request checked at declared safe boundaries, with a truthful waiting or rejection response after irreversible boundaries. A restart reconciles desired and completed effects before retry. Validate destination, ownership, backup configuration, and supported capability server-side. Unsupported configurations return typed failures; those failures do not substitute for required successful migration and drain demonstrations. v0.68 owns the complete phase-by-phase distributed lifecycle qualification.
6. Convert production CLI routes according to 12.6: parse, request, render. Remove worker-private RPC dispatch and duplicated business validation from these routes. Preserve meaningful process exit codes and stable structured output for automation. Deadline, connection, version, and permission failures must identify the failed operation without leaking secrets.
7. Add planned release-process tests for both standalone and a real multi-process cluster. Build a field-to-state matrix for every CLI status field and mutate its actual owner before asserting the entire response. Exercise node loss, real shard movement and drain in the cluster, backup execution, invalid requests, and restart with accepted work outstanding.

## Documentation changes

Document the endpoint configuration, protocol split, all fourteen methods, operation transitions, idempotency retention, cancellation boundaries, pagination, errors, and credentials redaction. Update CLI examples and capability claims only when the release binary executes them. Link v0.68 for complete migration qualification and explain any currently rejected action explicitly.

## Exit criteria

| ID | Acceptance condition | Required proof |
|---|---|---|
| V066-01 | All ten reads and four mutations have typed versioned contracts and real successful server paths; incompatible clients fail explicitly. | Protocol compatibility tests and release client calls assert complete success and meaningful failure responses for every method, including actual shard movement, drain, backup, and cancellation effects. |
| V066-02 | Every displayed status field changes when its actual source changes, on standalone and multi-process deployments. | Per-field mapping and before/after exact structured CLI output; no fixed topology or synthetic metrics. |
| V066-03 | Accepted operations expose all six states and six metadata fields with valid transitions and truthful terminal outcomes. | Planned operation lifecycle tests cover success, waiting, failure, cancellation, and illegal transitions with exact records. |
| V066-04 | Retrying an accepted identifier creates one effect; conflicting payloads fail, including after restart. | Concurrent retry test and full server kill/restart around durable acceptance and side-effect completion; exact IDs, records, and resulting data. |
| V066-05 | Storage failure never acknowledges unpersisted acceptance or false success; restart reconciles outstanding effects. | Inject failed operation-record writes and kill the server before and after effect completion; compare final operation and backup/shard state. |
| V066-06 | Cancellation obeys documented safe boundaries; unavailable or unsupported actions never report success. | Real executor interruption, late cancellation, nonexistent object, and unavailable worker/service tests assert exact errors and retained data. |
| V066-07 | Lists, requests, waiters, and retained operation records have named limits, fill metrics, cleanup, and deterministic overflow. | Saturation and expiry tests verify complete errors, bounded memory/queue age within a profile frozen before measurement, and recovery after pressure. |
| V066-08 | Production CLI uses management RPC and all documented examples run against release processes. | Caller review, executable documentation tests, and separate standalone/cluster transcripts; secrets absent from full outputs. |

Step coverage: steps 1 through 7 map to criteria 01, 02/07, 03/05, 04, 05/06, 08, and 02/04/05/06 respectively. Documentation maps to 01/08.

## Verification instructions

Existing component baseline: `rtk cargo test -p rockstream-cli --test management_health_endpoint_tests` and `rtk cargo test -p rockstream-control --test migration_record_durability_tests`. Build with `rtk cargo build --release -p rockstream-cli`. These tests alone do not qualify the new service.

Planned additions are the typed-contract tests, real management-process driver, per-field mutation matrix, and crash/idempotency cases above. Register their exact runnable commands and required cluster configuration in the evidence record before sign-off. Use summary-only passing test output. No required criterion may be marked passed by an unavailable executor or a mock service.
