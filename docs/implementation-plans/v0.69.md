# v0.69: PostgreSQL CDC golden connector

Status: Planned

Roadmap sources: [15. v0.69: PostgreSQL CDC Golden Connector](../../ROADMAP.md#v0-69), [5.6: State beyond RAM](../../ROADMAP.md#56-v0671-state-beyond-ram), and [22. Dependency Graph](../../ROADMAP.md#22-dependency-graph).
Follow the [shared implementation and evidence rules](README.md). The template remains unqualified until the complete real PostgreSQL scenario passes.

## Prerequisites and scope

Require v0.68 durable lifecycle and its large-state migration proof, v0.67.1 bounded state, durable source/catalog identity, v0.64 SQL integrity, and v0.65 recovery. Kafka is a sibling milestone, not a prerequisite. Reuse the project workflow from v0.61 and the authoritative configuration from v0.62.

Start in `crates/rockstream-connectors/src/postgres_cdc.rs`, `crates/rockstream-gateway/src/pgoutput_coordinator.rs`, `server.rs`, and `crates/rockstream-cli/src/init.rs`. Existing `PostgresCdcSource` has snapshot, transaction-buffer, LSN, lag, and `commit_offset` hooks; `postgres_cdc_template_files` already exists. Connect those mechanisms through the public durable execution path instead of adding a second source framework. Existing connector tests and source DDL/schema-evolution tests are starting points, not proof that the generated project is supported.

## Goal and public behavior

`rockstream project new analytics --template postgres-cdc` creates an executable project that ingests a real PostgreSQL snapshot and subsequent WAL changes into a continuously maintained view. Updates, deletes, schema identity, transaction boundaries, duplicates, and restart follow one documented contract.

## Implementation steps

1. Freeze one canonical source creation/alteration contract before connector wiring. Use the supported source DDL/API path as the source definition owner; project/config files provide deployment configuration or generate that definition, not an independent mutable source. Cover upstream endpoint, publication, replication slot, table mapping, schema policy, credential reference, and snapshot policy. Validate malformed configuration, missing publication/table, credential failure, and incompatible relation identity before ingestion. Version persisted source records and reject unsupported versions.
2. Restore the generated template through `init.rs` and the v0.61 project workflow. Provision a reproducible real PostgreSQL development service with logical replication enabled, seed data, source/view definitions, and verification commands. Credentials use references and do not appear in diagnostic output. Generated examples must run against the release binary from a fresh directory without hand edits.
3. Establish the snapshot/WAL fence using existing pgoutput/snapshot coordination. Bind snapshot identity, relation schema, source identity, and chosen LSN boundary durably. Stream the large snapshot in bounded pages while retaining or replaying WAL from the fence. Apply snapshot rows plus subsequent changes exactly once with no handoff gap or duplicate. Restart before, during, and after handoff must reconcile the same boundary or fail with an explicit resnapshot procedure.
4. Preserve upstream transaction grouping through decode, source batches, view dependencies, and durable epoch publication. A multi-row or multi-table mapped transaction becomes visible atomically within the supported contract. Freeze transaction-size limits and overflow behavior; reject or pause oversized transactions before partial publication. Do not split one upstream transaction into arbitrarily visible fragments to fit a buffer.
5. Persist received LSN, applied LSN, durable LSN, and published frontier with their source/schema identities. Integrate `commit_offset` only after the corresponding epoch and all required view effects are durable. Define monotonic relations and replay identity before enabling upstream acknowledgement. Crash between processing, persistence, publication, and slot acknowledgement must replay safely; decode or storage failure must not advance the upstream acknowledgement beyond durable state.
6. Publish a schema decision table before evolution handling. Assign `compatible`, `requires rebuild`, or `unsupported` to add-nullable-column, rename-column, type-widening, drop-referenced-column, and primary-key-change examples under concrete supported types. Test at least one genuinely compatible evolution. For rebuild/unsupported transitions, block the affected relation, retain the recoverable source position, report the exact change, and give a bounded rebuild/resnapshot recovery procedure. Unaffected relations must follow the documented isolation policy.
7. Propagate worker/source pressure to WAL consumption. Bound snapshot pages, decode and transaction bytes, in-flight epochs, retries, waiters, and reconnect buffers under the worker budget. Expose buffer fill, source lag, received/applied/durable LSN, and blocked-relation status. Distinguish internal bounds from upstream WAL retention; document slot retention exhaustion and missing-WAL recovery explicitly.
8. Add the complete TestContainers scenario using a real PostgreSQL instance and real release RockStream processes: seed a large snapshot, create source/view publicly, finish snapshot, INSERT, UPDATE, DELETE, multi-row transaction, restart RockStream, repeat transactions, disconnect/reconnect PostgreSQL, compatible evolution, incompatible evolution, and full exact result verification. Add write-during-snapshot and crash-at-handoff variations so serial success cannot hide boundary errors.
9. Freeze the connector workload profile before measurement, with state above the worker budget where claimed, payload/transaction sizes, offered load, separate read/commit/freshness p99, lag, RSS/backlog limits, and recovery time. Use scheduled event timestamps, include generator delay and pressure, and compare every committed view result with an independent upstream-history oracle. Qualify worker loss/movement under the v0.68 contract before widening supported load.

## Documentation changes

Publish the generated-project walkthrough, canonical source ownership, PostgreSQL requirements, credential references, snapshot/WAL boundary, transaction visibility, four progress fields, acknowledgement rule, schema decision table, limits, lag interpretation, and resnapshot procedure. Capability/template status changes to Supported only with complete release-process evidence. Keep examples executable in CI.

## Verification instructions

Existing baselines: `rtk cargo test -p rockstream-connectors --test postgres_cdc_exactly_once_tests`, `rtk cargo test -p rockstream-connectors --test cdc_transaction_atomicity_tests`, `rtk cargo test -p rockstream-gateway --test postgres_cdc_schema_evolution_tests`, and `rtk cargo test -p rockstream-gateway --test source_ddl_postgres_kafka_tests`. Inspect actual test service requirements; ensure container-backed cases run instead of skipping when Docker is unavailable.

Build with `rtk cargo build --release -p rockstream-cli`. The complete generated-project/process scenario and connector performance profile are planned extensions. Record exact setup, test commands, fault points, and evidence locations before qualification. Component tests and connector objects recreated in one process cannot prove restart durability.
