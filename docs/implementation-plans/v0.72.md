## Goal and public behavior

A configured workload cannot silently exhaust memory or starve another workload. Soft limits produce defined throttling or adaptation. Hard limits reject or degrade work within a bounded envelope. Operators can reproduce capacity claims and distinguish read latency, durable commit latency, and event-to-committed-result freshness. Interactive queries, previews, subscriptions, and workload changes use the same admission and accounting system.

## Implementation steps

1. Freeze the acceptance configuration before code qualification. Record workload priorities, fairness and starvation bounds, soft and hard byte limits, reserved capacity, adaptation bounds, overload duration, RSS tolerance, queue-age limit, recovery limit, offered loads, independent latency targets, repetitions, accepted noise, and per-benchmark regression thresholds. Numbers absent from the roadmap are preimplementation decisions, not current product contracts. Store these decisions in versioned benchmark profiles before collecting candidate comparisons.
2. Complete section 18.1 accounting across operator state cache, exchange buffers, source buffers, query execution, catalog and caches, checkpoint buffers, and migration buffers. Include the earlier worker-wide SlateDB write buffers, block and metadata caches, and local object-store disk cache. Trace allocation and release callers, including cancellation, errors, shard creation, shard removal, and restart. Charge shared allocations once to their owner. Reconcile per-workload and per-worker accounting with allocator overhead and measured RSS instead of pretending those totals are identical.
3. Wire section 18.2 workload limits into admission before allocation. Reuse acquisition and release guards and the distributed quota ledger. Make soft pressure reach source and exchange producers; make hard violations return bounded errors or truthful degradation. Bound retries, waiters, query results, physical commit bytes, and acknowledgement waiters. Preserve capacity for foreground maintenance, reads, and control work while limiting compaction, backfill, and migration concurrency. Test quota rollback after failed reservations and release after cancellation. Preserve exact logical epochs and durable acknowledgements.
4. Harden section 18.3 scheduling in existing execution owners. Use priority, memory pressure, freshness SLO, and available parallelism when admitting runnable work. Preserve one ordered owner per shard and dependent-view ordering. Define starvation prevention and observable scheduling decisions. Test a competing workload pair and a multi-workload set with distinct priorities, including a failing workload that must not retain another workload's capacity.
5. Implement section 18.4 bounded epoch adaptation through existing epoch and commit paths. Use ingest rate, commit latency, state pressure, and freshness SLO. Enforce configured lower and upper limits at every update and validate inconsistent configuration at startup. Define adaptation behavior for idle input, bursts, slow storage, and overload. Keep logical epoch visibility intact and reserve persistence time within the freshness target. Neither group commit nor epoch resizing may expose a partial dependency or acknowledge a failed flush.
6. Extend section 18.5 capacity profiles for filter/projection, group aggregate, high-cardinality aggregate, two-way join, window, PostgreSQL CDC, Kafka ingestion, and distributed exchange. Exercise release binaries through public ingestion and query interfaces. Keep the offered-load schedule independent of completion and timestamp scheduled generation, including generator delay, backpressure, errors, and timeouts. Compare complete result multisets with an independent oracle at the relevant committed epoch; a visibility probe is insufficient.
7. Complete every applicable section 5.2 experiment: one-key updates with 1K, 100K, and 10M groups; one and twenty compatible views; 1, 2, 4, and 8 actual workers; concurrent ingestion and queries; state larger than RAM through compaction and restart; and overload, worker loss, and migration. Measure approximately constant state writes per one-key change with separately reported lookup cost. Freeze the accepted variation before measurement. Show shared execution reducing duplicated state, writes, and computation. Show sustainable committed throughput scaling at the same freshness target, identifying host ceilings. Prove bounded RSS, storage backlog, and recovery with complete results. Reject missing cells and inactive worker processes. Any claimed non-applicable cell needs an explicit scope reason and owner; applicable blocked cells prevent sign-off.
8. Publish rows per second; p50, p95, and p99 commit latency; separate read and freshness distributions; state bytes; RSS; CPU; object-store requests; and network bytes. Also preserve section 5 evidence for state writes, intermediate rows, queue age, control-node load, physical flushes per logical epoch, and per-committed-change resource costs. Record hardware, backend, revisions, payload size, view count, state size, durability, target latency, raw samples, commands, and repeated-run variation. Version profiles without overwriting frozen evidence. `sample_reference_run` remains a qualification-logic fixture only.
9. Implement section 18.6 regression evaluation against the frozen per-benchmark noise and threshold decisions. A threshold breach requires explicit approval and evidence before acceptance; do not widen the threshold after observing a regression. Compute cost per million committed changes as total hourly infrastructure cost multiplied by 1,000,000, divided by sustainable committed changes per second multiplied by 3,600. Include gateways, control nodes, workers, storage requests, retained storage, network transfer, and compaction. Local measurements establish local performance only. Cloud claims require a measured deployment and dated prices.
10. Add planned sustained-overload process tests with many shards and competing workloads. Include shard churn, slow object storage, worker loss, active migration, compaction, backfill, connector pressure, and query load. Continue long enough to meet the frozen duration and establish bounded steady behavior. Prove no OOM, growing queues, runaway retries, or control starvation. Restart against the same state and compare complete recovered results. Unsupported large-state operators must reject explicitly rather than truncate restoration.
11. Add a producer-bounded, single-statement read-only execution path. Reject mutations and unauthorized reads in the dispatcher. Bound compilation, intermediate state, queued work, returned rows, encoded bytes, wall time, concurrency, and snapshot lifetime before or during production. Bind query handles to actor and deployment. Make cancellation, timeout, disconnect, cursor expiry, and caller shutdown reach the producer and release every reservation. Add bounded committed subscriptions with explicit snapshot and epoch framing, buffer/stream/slow-client limits, and resnapshot behavior when replay is unavailable.
12. Route workload limit, priority, parallelism, and freshness changes through revision-checked admission. Report requested and effective revisions separately, including pending or failed owners. Reject reductions below verified non-reclaimable use until the runtime can safely reclaim it. Prove accepted changes through actual scheduling, pressure, and workload behavior rather than catalog readback.
