# v0.65.1 Concurrent maintenance and group commit

Status: Planned

Source: [ROADMAP section 5.5](../../ROADMAP.md#55-v0651-concurrent-maintenance-and-group-commit). Apply the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require the complete v0.65 recovery contract and its process-failure evidence before changing commit scheduling. Use the v0.61.1 versioned baseline for comparisons. Preserve one ordered execution owner per shard and the existing physical commit group.

## Goal and public behavior

Independent view branches can execute concurrently, and complete logical epochs can share a durable physical flush. Readers and acknowledgments retain dependency-consistent committed visibility with bounded latency.

## Implementation steps

1. Trace every `shard_commit_lock` acquisition in `crates/rockstream-gateway/src/server.rs`, including SQL transactions and source ingestion. Inventory dependency graph execution in `crates/rockstream-ops/src/compile.rs`, `live_exec.rs`, and `pipeline.rs`, plus shard ownership in `crates/rockstream-runtime/src/shard_actor.rs`. Specify the order of validation, execution, state publication, persistence, frontier advancement, and acknowledgment before narrowing any lock.
2. Schedule independent branches with bounded concurrency while preserving topological dependency order. Keep one owner that orders epochs and state mutation per shard. Reuse the existing scheduler where compatible. Define cancellation, branch failure, read snapshot selection, and ownership fencing. A failed branch prevents publication of its entire logical epoch.
3. Narrow the gateway commit lock only after dependency ordering and consistent read tests pass. Concurrent branches cannot expose intermediate dependency state. Source and SQL paths must use the same durability and fencing rules.
4. Extend `PhysicalCommitGroup` in `crates/rockstream-ops/src/group_commit.rs`. Feed it multiple complete logical epochs instead of immediately calling `commit_epoch` for each one. Retain the existing ordered pending epochs and durable write/flush behavior. Audit failure restoration and retries before allowing concurrent producers.
5. Flush when pending bytes reach a named limit or the oldest epoch reaches a bounded delay. Run the delay timer independently of new arrivals so idle traffic flushes. Reserve time for persistence within the frozen freshness budget. Bound pending bytes, epoch count, acknowledgment waiters, and retry work; admission must act before excess allocation.
6. Advance frontiers and send durability acknowledgments only after every required write and durable flush succeeds. Never publish later epochs across a failed earlier commit. Fence stale owners before writes and acknowledgments. Define replay/deduplication after uncertain outcomes using v0.65 idempotency metadata.
7. Freeze one-view and twenty-view workloads under light and sustained load, durability, state size, payload, offered load, read/commit/freshness p99 targets, and regression tolerances before comparison. Measure lock wait, flushes per epoch, committed throughput, and each latency independently. Compare complete result multisets at committed epochs.
8. Inject crashes, retries, stale owners, write failures, and flush failures during branch execution and physical commit. Include idle single-epoch traffic, a slow dependency, waiter cancellation, and overload. Restore in a fresh release process and verify every acknowledged epoch plus retry behavior.

## Documentation changes

Document branch scheduling, per-shard ownership, logical versus physical commits, flush triggers, acknowledgment semantics, pressure errors, and latency configuration. Publish benchmark profiles and raw before/after evidence with the existing R1 contract.
