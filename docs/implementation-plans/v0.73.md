# v0.73 Security coherence

Status: Planned

Roadmap source: [19. v0.73](../../ROADMAP.md#v0-73). Follow the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.72 resource control, v0.71 diagnostics, v0.63 durable catalog, v0.66 management operations, and the distributed and connector paths in their dependency chain. Apply security to every advertised reachable mode and endpoint. Keep the initial authorization model narrow: concrete actions mapped to fixed data-reader, builder, administrator, and operator presets. Preserve existing `Viewer`, `PipelineOwner`, and `Admin` behavior through explicit compatibility mappings. Do not invent a generic policy language.

Start with `crates/rockstream-gateway/src/auth.rs`, `role_catalog.rs`, and `server.rs`; `crates/rockstream-types/src/identity.rs` and `secret.rs`; `crates/rockstream-runtime/src/tls.rs` and `secrets.rs`; and `crates/rockstream-control/src/secret_store.rs`. `JwtVerifier::new` currently has no default key, while `with_hs256_key` exists and `verify` documents HS256-only verification. Audit production construction and all callers instead of assuming a complete OIDC implementation. `RoleCatalog` is an existing role container; durable identity and grants still require end-to-end proof.

This plan owns
[UIE-M2 and UIE-M8](ui-enablement.md#4-criterion-ownership-and-acceptance-dependencies).
M2 is a prerequisite for the v0.73.1 console role, but the security work stays
here and retains this plan's dependency chain.

## Goal and public behavior

Every advertised authentication mode either starts with validated configuration and enforces identity or fails explicitly as unavailable. Principals and grants survive process destruction. Client identity, delegated actor identity, service identity, and node identity cannot substitute for each other. Operators do not implicitly gain business-data, secret-value, or grant authority. Source metadata uses secret references, and ordinary diagnostics and support bundles never expose secret values.

The approved v0.73 security profile, including the action registry, fixed presets, authentication and session decisions, compatibility and recovery contracts, revocation and artifact bounds, audit policy, and lost-response contract, is recorded in the [security profile](v0.73-authorization-policy.md). This profile amends the v0.73 plan; it does not establish runtime behavior or qualification evidence. All planned verification remains required.

## Implementation steps

1. Use the approved [security profile](v0.73-authorization-policy.md) for the supported mode matrix, action registry, preset permissions, legacy mappings, bootstrap, grant authority, revocation, credential validation, caches, retries, retention, artifact storage, and reconciliation. Trace CLI configuration, gateway authentication, management API authorization, control registration, worker exchange, connector credentials, and internal administrative calls. Do not label an unavailable implementation as enabled. A stricter deployment profile is allowed; revise a numeric bound only through a reviewed profile change before measurement, never after failure to make a result pass.
2. Complete section 19.1 by removing any production fallback signing secret and tracing every JWT verifier constructor and password-mode startup path. Keep explicit test keys in test-only code. Reject password configuration without a meaningful credential store before opening an apparently authenticated listener. Missing configuration, malformed key material, or failed credential-store recovery must fail closed with an actionable redacted error.
3. Complete section 19.2 by persisting principals, login capability, action grants, fixed data-reader/builder/administrator/operator presets, legacy-role mappings, and policy revisions in the v0.63 durable catalog. Reuse existing role records and catalog transactions, versioning their format when needed. Persist password verifiers instead of plaintext passwords. Authorize through shared request enforcement so SQL reads and writes, management reads and mutations, diagnostics, secret use and administration, audit access, and grant administration cannot bypass the same action decision. Operator authority must remain independent of business-data reads, secret values, and grant authority. Bootstrap only by the trusted offline preprovision route in the profile; reject removal, disablement, or downgrade of the last active administrator. Recheck grantor authority and policy revision at apply; stale reviewed changes have no effects. Invalidate pooled sessions and reauthorize or terminate long-lived work within 60 seconds of durable revocation. Acknowledge changes only after principal/grant state and correlated audit commit durably. Recover the exact principal and grant set after process destruction; deny access if durable identity state cannot be recovered.
4. Complete section 19.3 startup capability checks. SCRAM-SHA-256 requires a recovered durable role store; keep MD5 unavailable. OIDC accepts only RS256 and requires exact issuer, audience, nonempty subject, and expiration claims; validate `nbf` when present. Enforce the profile's token/JWKS sizes, key count, 60-second maximum cache TTL, 5-second fetch timeout, per-issuer singleflight, and one bounded transient retry; never use an expired key. mTLS requires a matching certificate/private key and trust roots. Validate expiration and certificate identity under the existing rustls profile. SCRAM, OIDC, and external mTLS must each be enabled and qualified in at least one supported v0.73 configuration; other configurations may reject a mode at startup. This does not waive any of the ten required release negative cases: each runs through a supported, enabled qualification configuration; startup rejection is not a substitute.
5. Complete section 19.4 as four separate enforcement paths: gateway TLS and client authentication, control-worker mTLS, worker-worker mTLS, and management API authentication. Authenticate the transport peer before trusting a claimed node or role identifier. Bind node identity to registration, assignment, and exchange authorization. Reject a valid certificate for the wrong node. Sign OIDC and delegated actor assertions with RS256; require the exact audience and deployment binding, a lifetime no longer than 60 seconds, and an allowance intersected with the actor's current scoped policy. Preserve documented in-flight certificate reload, dual-generation CA trust, and active connection/stream continuity; test live connections during rollover. Check every public and internal caller of shared identity functions. Prove that a client credential cannot register a worker, a node credential cannot acquire client administrator rights, and a service credential or caller-supplied role header cannot impersonate an actor.
6. Complete section 19.5 using `secret://name` references in configuration and source definitions while preserving supported `secret = '<name>'` connector input. Reuse the existing control secret store and worker resolution paths. Resolve secrets only where required; authorize resolution by consumer identity and, for delegated work, the actor's current scope. Persist encrypted references and envelopes rather than resolved values. Do not use a shared plaintext cache or automatic KMS retry; keep the existing 10-second KMS request timeout and fail closed on KMS failure. Define missing-secret, inaccessible-secret, and rotated-secret behavior, including already running connectors and pending operations. Preserve next-epoch credential activation and connector process continuity. Preserve complete committed connector results across retry and restart without loss or duplicated effects.
7. Complete section 19.6 audit records for authentication success and failure, authorization denial, role change, secret rotation, node identity rejection, admin operation start, and admin operation completion. Record truthful verified/unverified/unknown/not-applicable actor and request fields; correlation comes only from observed or client-known identities. Record target, result, order, and safe before/after metadata without credentials or raw tokens. Couple durable security mutations and operation state to synchronous durable audit evidence so a crash cannot leave an acknowledged unauditable change. Retain for 90 days up to the 1 GiB deployment-wide cap; do not silently discard or prematurely evict required events. On capacity/unavailability, fail the related mutation, expose degraded health, stop new session admission if authentication cannot be audited, and close a session when a required denial cannot be audited. Provide authorized, filtered, paginated audit reads.
8. Run all ten negative cases through actual public release-process endpoints in supported, enabled qualification configurations: expired certificate, wrong CA, wrong node identity, invalid password, invalid SCRAM proof, expired OIDC token, wrong issuer, wrong audience, insufficient role, and secret rotation during operation. Configurations may differ; startup rejection does not substitute for a case. Apply certificate cases to each applicable internal and external mTLS path. For rejected attempts, assert the exact protocol error and audit record, absence of a new session, and unchanged protected state. For rotation, assert the frozen old/new credential transition, exact operation outcome, audit sequence, and full committed results.
9. Add successful counterparts for every enabled mode and allowed role operation. Destroy and restart processes after grants, revocation, password change, and secret rotation. Inspect ordinary logs, error responses, doctor output, metrics labels, catalog exports, and support bundles for known test secret values, encoded variants, private keys, and raw tokens. Assert complete expected redacted records, not just absence counts. Sanitize every qualified v0.73 support workflow; enforce opaque actor/scope-bound IDs, 10 MiB per artifact, 10-minute maximum availability, 100 MiB aggregate storage, and cleanup within 60 seconds including restart. Reconcile mutations using the client-generated `Idempotency-Key` and authorized public operation lookup; never retry as a new mutation. Version changed public protocols and durable formats and prove accepted/rejected combinations.

Steps 1–2 close through the first criterion; steps 3–7 close through the matching identity, capability, boundary, secret, and audit criteria. Steps 8–9 close through the negative, redaction, boundedness, restart, and separated-authority criteria. Every subcase listed in a step is mandatory within its corresponding criterion. These criteria are the owning evidence for UIE-M2 and UIE-M8; console exposure is v0.73.1 work.

Add the planned release-process identity matrix under `crates/rockstream-cli/tests/`, with final target names and endpoint commands recorded in sign-off evidence. Build with `rtk cargo build --release -p rockstream-cli`. Existing cryptographic unit tests cannot replace network authentication, durable role recovery, rotation, or diagnostic-redaction proof. Keep complete artifacts and emit only test summaries unless a test fails.
