# v0.73 Security coherence

Status: Planned

Roadmap source: [19. v0.73](../../ROADMAP.md#v0-73). Follow the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.72 resource control, v0.71 diagnostics, v0.63 durable catalog, v0.66 management operations, and the distributed and connector paths in their dependency chain. Apply security to every advertised reachable mode and endpoint. Keep the initial role model narrow: login, admin, read, and write. Do not invent finer permissions for speculative needs.

Start with `crates/rockstream-gateway/src/auth.rs`, `role_catalog.rs`, and `server.rs`; `crates/rockstream-types/src/identity.rs` and `secret.rs`; `crates/rockstream-runtime/src/tls.rs` and `secrets.rs`; and `crates/rockstream-control/src/secret_store.rs`. `JwtVerifier::new` currently has no default key, while `with_hs256_key` exists and `verify` documents HS256-only verification. Audit production construction and all callers instead of assuming a complete OIDC implementation. `RoleCatalog` is an existing role container; durable identity and grants still require end-to-end proof.

## Goal and public behavior

Every advertised authentication mode either starts with validated configuration and enforces identity or fails explicitly as unavailable. Roles and grants survive process destruction. Client identity and node identity cannot substitute for each other. Source metadata uses secret references, and ordinary diagnostics and support bundles never expose secret values.

## Implementation steps

1. Inventory advertised modes and public entry points before implementation. Trace CLI configuration, gateway authentication, management API authorization, control registration, worker exchange, connector credentials, and internal administrative calls. Freeze the supported mode matrix, role permission matrix, bootstrap procedure, session revocation policy, certificate identity rules, JWKS cache lifetime, retry limits, credential-size limits, and audit retention policy. Numerical limits absent from the roadmap are preimplementation decisions to freeze before qualification. Do not label an unavailable implementation as enabled.
2. Complete section 19.1 by removing any production fallback signing secret and tracing every JWT verifier constructor and password-mode startup path. Keep explicit test keys in test-only code. Reject password configuration without a meaningful credential store before opening an apparently authenticated listener. Missing configuration, malformed key material, or failed credential-store recovery must fail closed with an actionable redacted error.
3. Complete section 19.2 by persisting login roles, admin roles, read roles, write roles, and grants in the v0.63 durable catalog. Reuse existing role records and catalog transactions, versioning their format when needed. Persist password verifiers instead of plaintext passwords. Authorize through shared request enforcement so SQL, management mutations, and administrative operations cannot bypass the same role decision. Define bootstrap, grant, revoke, delete, and password-change semantics for concurrent sessions. Acknowledge changes only after durable commit. Recover the exact role and grant set after process destruction; deny access if durable identity state cannot be recovered.
4. Complete section 19.3 startup capability checks. SCRAM requires an available role store. OIDC requires issuer, audience, and reachable JWKS or a valid bounded cache under the frozen cache policy. mTLS requires a certificate, private key, and trust roots. Validate key matching, expiration, supported algorithms, and trust configuration. Bound token decoding, connection handshakes, key refresh, cache entries, waiters, and retries. If a mode cannot meet its contract, reject its selection and update capability documentation. This does not waive the required OIDC and mTLS negative qualification matrix for enabled modes.
5. Complete section 19.4 as four separate enforcement paths: gateway TLS and client authentication, control-worker mTLS, worker-worker mTLS, and management API authentication. Authenticate the transport peer before trusting a claimed node or role identifier. Bind node identity to registration, assignment, and exchange authorization. Reject a valid certificate for the wrong node. Check every public and internal caller of shared identity functions. Prove that a client credential cannot register a worker and that a node credential cannot acquire client administrator rights.
6. Complete section 19.5 using `secret://name` references in configuration and source definitions. Reuse the existing control secret store and worker resolution paths. Resolve secrets only where required; authorize resolution by consumer identity. Persist references instead of resolved values. Define missing-secret, inaccessible-secret, and rotated-secret behavior, including already running connectors and pending operations. Bound resolution caches and refresh retries, invalidate stale credentials according to the frozen policy, and prevent failures from logging values. Preserve complete connector results across rotation and retry without loss or duplicated committed effects.
7. Complete section 19.6 audit records for authentication success and failure, authorization denial, role change, secret rotation, node identity rejection, admin operation start, and admin operation completion. Record actor, target, result, request and operation correlation, and ordering information without credentials or raw tokens. Couple durable security mutations and operation state to audit evidence so a crash cannot leave an acknowledged unauditable change. Define behavior when the audit destination is full or unavailable. Bound queues and retention with visible fill and explicit overflow behavior; do not silently discard required events.
8. Add a planned negative matrix through actual public release-process endpoints. Include expired certificate, wrong CA, wrong node identity, invalid password, invalid SCRAM proof, expired OIDC token, wrong issuer, wrong audience, insufficient role, and secret rotation during operation. Apply certificate cases to each applicable internal and external mTLS path. For rejected attempts, assert the exact protocol error and audit record, absence of session establishment, and unchanged protected state. For rotation, assert the frozen old/new credential transition, exact operation outcome, audit sequence, and full committed results.
9. Add successful counterparts for every enabled mode and allowed role operation. Destroy and restart processes after grants, revocation, password change, and secret rotation. Inspect ordinary logs, error responses, doctor output, metrics labels, catalog exports, and support bundles for known test secret values, encoded variants, private keys, and raw tokens. Assert complete expected redacted records, not just absence counts. Version any changed public protocol or durable format and prove accepted and rejected combinations.

## Documentation changes

Update `docs/security.md`, `docs/threat-model.md`, `docs/reference/configuration.md`, `docs/reference/cli.md`, and `docs/connectors.md`. Describe only reachable authentication modes, the exact role permissions, four identity boundaries, secret-reference setup, rotation behavior, audit access and retention, startup failures, and recovery. Execute primary examples in CI using release binaries and controlled test credentials.

## Exit criteria

| ID | Acceptance condition | Intended proof |
| --- | --- | --- |
| V073-01 | Advertised modes match the frozen capability matrix; no production fallback secret or apparently enabled empty password store remains. | Constructor/caller audit plus release startup matrix with exact accepted and rejected configurations. |
| V073-02 | Login, admin, read, and write roles and grants enforce the frozen permission matrix and survive full process destruction. | Exact role and grant records plus allowed and denied SQL, management, and admin operations before and after restart. |
| V073-03 | SCRAM, OIDC, and mTLS startup enforce every section 19.3 prerequisite for enabled modes and reject unavailable modes explicitly. | Missing role store, issuer, audience, JWKS/cache, certificate, key, and trust-root cases with exact errors and listener-state checks. |
| V073-04 | Gateway, control-worker, worker-worker, and management paths enforce distinct authenticated identities. | Planned endpoint matrix including cross-identity misuse, expired certificates, wrong CAs, and wrong-node certificates on each applicable path. |
| V073-05 | Configuration and durable source definitions retain secret references; resolution and live rotation obey the frozen access and invalidation policy. | Exact persisted metadata and running-connector results across missing secrets, denied resolution, rotation, retry, and process restart. |
| V073-06 | All eight required security event classes are auditable with correct identity, outcome, ordering, and operation correlation. | Full audit sequences for success, denial, mutation, rotation, node rejection, admin start/completion, crash, and unavailable audit storage. |
| V073-07 | Every ten-case roadmap negative scenario runs against the relevant public release endpoints; rejection cannot mutate protected state or create an authenticated session. | Explicit case-to-endpoint matrix with exact errors, unchanged durable records, complete audit events, and the defined rotation outcome. |
| V073-08 | Known secret values, tokens, keys, and encoded equivalents never appear in ordinary diagnostics or support bundles. | Complete expected redacted outputs and secret scans of logs, doctor results, errors, metrics, catalog exports, and generated bundles. |
| V073-09 | Auth, JWKS, secret resolution, and audit queues/caches enforce frozen named limits and failure policies without bypassing security. | Boundary, timeout, cache expiry, overflow, cancellation, and recovery tests with visible fill levels and exact denial behavior. |
| V073-10 | Successful authentication and authorized operations work for every enabled mode after restart; changed formats/protocols have versioned upgrade and rejection behavior. | Release-process positive matrix, exact recovered catalog and operation results, compatibility tests, and executed documentation examples. |

Steps 1–2 close through the first criterion; steps 3–7 close through the matching identity, capability, boundary, secret, and audit criteria. Steps 8–9 close through the negative, redaction, boundedness, and restart criteria. Every subcase listed in a step is mandatory within its corresponding criterion.

Use existing regression targets: `rtk cargo test -p rockstream-gateway --test auth_scram_tests`, `rtk cargo test -p rockstream-gateway --test auth_proof_tests`, `rtk cargo test -p rockstream-gateway --test gateway_mutation_authorization_tests`, `rtk cargo test -p rockstream-gateway --test live_secret_rotation_tests`, `rtk cargo test -p rockstream-control --test secrets_management_durability_tests`, `rtk cargo test -p rockstream-control --test secrets_redaction_tests`, and `rtk cargo test -p rockstream-cli --test cli_auth_enforcement_tests`.

Add the planned release-process identity matrix under `crates/rockstream-cli/tests/`, with final target names and endpoint commands recorded in sign-off evidence. Build with `rtk cargo build --release -p rockstream-cli`. Existing cryptographic unit tests cannot replace network authentication, durable role recovery, rotation, or diagnostic-redaction proof. Keep complete artifacts and emit only test summaries unless a test fails.
