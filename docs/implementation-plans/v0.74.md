# v0.74 Upgrade and compatibility

Status: Planned

Roadmap source: [20. v0.74](../../ROADMAP.md#v0-74). Follow the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.73 identity and durable grants, v0.63 catalog durability, v0.65 recovery, v0.66 operation state, and v0.68 distributed ownership and migration through the dependency chain. Preserve v0.71 diagnostics and v0.72 resource bounds during upgrades. Qualify actual v0.73 and v0.74 release binaries from distinct revisions. Tests that change advertised version fields on one binary are supporting protocol tests, not upgrade proof.

Reuse `crates/rockstream-types/src/compatibility.rs` for protocol and storage range types, `crates/rockstream-storage/src/format_migration.rs` for existing migration steps and progress, `crates/rockstream-storage/src/shard_db.rs` for format validation, and `crates/rockstream-runtime/src/exchange/service.rs` for data-plane protocol validation. Extend registration and placement through `crates/rockstream-control/src/`. Existing simulation upgrade tests and V1/V2/V3 storage migration tests provide fault patterns but do not establish the future release-pair contract.

## Goal and public behavior

Operators can determine whether versions may share durable state, register in one cluster, exchange data, restore backups, or participate in an upgrade. Compatible upgrades preserve complete committed results and durable metadata. Unsupported combinations fail before admission or state modification with an actionable error.

## Implementation steps

1. Freeze section 20.1 compatibility policy before implementation. Independently identify management protocol, control protocol, data-plane protocol, catalog format, shard/storage format, compiled-plan format, backup format, and connector cursor format. Publish readable and writable ranges plus required capability bits for each release. Keep build/package version as identity metadata, not the sole compatibility signal. Specify unknown version, malformed range, missing capability, missing marker, and unsupported future-format behavior. Any migration throughput, downtime, retry, or resource threshold absent from the roadmap is a preimplementation decision to freeze before qualification.
2. Complete section 20.2 registration handshake using the existing range types. Advertise supported protocol ranges, supported storage format ranges, capability bits, and build version. Validate the peer's authenticated identity from v0.73 before trusting its advertisement. Negotiate a concrete common version for each applicable protocol. Reject incompatible registration, placement, recovery, and data exchange before assigning work or acknowledging writes. Test overlap, disjoint ranges, mixed capability sets, unknown capabilities, stale registration, and corrupt advertisements. A readable format does not imply permission to write a newer format.
3. Implement section 20.3 forward catalog migrations as explicit versioned steps from N to N+1. Persist step identity, progress, source format, target format, and completion through the durable catalog and operation system. Make each step idempotent and resumable after actual process destruction. Advance the catalog version only after all required writes are durable. Fence concurrent or stale migration owners. Bound scan pages, write batches, retries, and accumulated results, with visible progress and explicit failure. Prove interruption before writes, between data and progress writes, before completion publication, and immediately after acknowledgement. Repeated resumes must yield the exact final catalog, including roles, grants, workload definitions, and connector metadata.
4. Complete section 20.4 shard/storage policy through existing `migrate_storage_format` and `migrate_shard_format_with_options` callers. Prefer read-old/write-current only for combinations where old readers and active mixed peers remain safe. Otherwise, retain the negotiated write format until the cluster permits promotion. If in-place migration is required, expose its durable progress, errors, and resumability through the operation system. Audit existing discovery bounds so reaching a limit reports an incomplete operation instead of a successful truncated migration. Preserve exact logical keys, values, frontiers, checkpoints, and replay behavior through compaction and restart.
5. Derive section 20.5 rolling order from the compatibility matrix and actual protocol callers. Evaluate control followers, control leader handoff, workers, and gateways as the roadmap's candidate order, then freeze the supported order and abort/resume policy. Prove mixed-version placement, lease fencing, exchange, committed reads, source progress, and management operations at every stage. Maintain complete workloads during control leadership changes and worker/gateway replacement. Bound pending work and recovery. Reject any unsupported order explicitly; do not publish an order inferred only from version names.
6. Complete section 20.6 downgrade detection at every durable-state opening path, before writes, lock-file changes that affect durable state, migrations, or catalog initialization. Return a registered actionable RS error with stored and supported versions. Cover catalog, shard, compiled plan, backup, and connector cursor formats as applicable. Preserve an exact logical-state snapshot and storage object inventory across rejected opens. Ensure the actual older binary rejects the newer state; a new binary configured with an old range is not sufficient proof. If the older release cannot reject safely, mark that downgrade unsupported and require a safe operational prevention mechanism before releasing the new format.
7. Complete section 20.7 backup portability for each promised supported pair. Create a backup with the old release, destroy its processes, and restore/read with the new release in a separate target. Preserve full data results, catalog definitions, permissions, committed frontiers, and connector cursors according to the backup contract. Do not fabricate an old backup with the new writer. Reject unsupported versions, corrupt manifests, missing objects, and incompatible cursor/plan payloads before publishing a usable restored workload. Expose partial restore failure through the operation system and support bounded safe retry.
8. Build the planned nine-case upgrade matrix: v0.73 to v0.74 standalone, mixed v0.73/v0.74 workers, control rolling upgrade, gateway rolling upgrade, catalog migration interruption, restart migration, newer-state downgrade rejection, backup from previous version, and restore under new version. Exercise release binaries with recorded hashes and revisions through public ingestion, SQL, and management interfaces. Include success and meaningful rejection for each new operation. Compare complete result multisets and durable records after each stage, not just process readiness or row counts. Preserve earlier freshness, durability, and boundedness guarantees under the frozen upgrade workload.

Record the final target names, released artifact locations, binary hashes, build commands, source revisions, storage setup, and all nine case commands before sign-off. `rtk cargo build --release -p rockstream-cli` builds the current checkout only; build the prior supported revision separately in an isolated checkout or use its verified release artifact. Retain full evidence and report only test summaries unless a test fails.
