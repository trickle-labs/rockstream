# v0.65 Complete standalone recovery, backup, and restore

Status: Planned

Source: [ROADMAP section 11](../../ROADMAP.md#v0-65). Apply the [shared implementation and evidence rules](README.md).

## Prerequisites and scope

Require v0.63 durable catalog and v0.64 SQL integrity. Prove the standalone recovery contract before v0.65.1 concurrent maintenance and group commit. Complete recovery applies now; v0.67.1 cannot defer correctness for state spanning multiple scan pages.

## Goal and public behavior

A standalone node can be hard-killed, restarted, backed up, and restored to a new filesystem path. Its exact committed state survives without dependence on the original instance's files.

## Implementation steps

1. Enumerate durable ownership and recovery order for catalog, base tables, operator state, view output, frontier/epoch, indexes, source cursors, and idempotency metadata. Trace `crates/rockstream-runtime/src/recovery.rs`, `shard_actor.rs`, `crates/rockstream-gateway/src/server.rs`, `crates/rockstream-ops/src/pipeline.rs`, and `crates/rockstream-storage/src/shard_db.rs`. Define exactly which acknowledgment establishes durable visibility and how retries resolve uncertain outcomes.
2. Implement OpeningStorage, RecoveringCatalog, RecoveringEpoch, RecoveringOperators, ValidatingState, and Ready within v0.62 lifecycle ownership. Keep management readiness false until every mandatory category validates. Turn mandatory restore warnings, skipped dependencies, or empty fallback state into explicit startup failure.
3. Audit every restore scan for continuation handling. Page to completion with bounded buffers, including aggregate, arrangement, index, sink, source cursor, and deduplication records. Record scan progress and cancellation behavior. Never treat a bounded first page as complete recovery; resource exhaustion prevents Ready.
4. Reuse `crates/rockstream-control/src/checkpoint.rs`, `checkpoint_store.rs`, and `checkpoint_export.rs` for the durable backup point. Select one consistent catalog revision, checkpoint, and frontier. Pin referenced files while copying and coordinate retention so concurrent writes or compaction cannot remove required data.
5. Define the backup manifest with format_version, catalog_revision, checkpoint_id, frontier, storage_format, complete file list, and checksum. Specify per-file verification, manifest finalization, version compatibility, and upgrade/rejection rules before implementation. Publish a complete manifest only after all required data is durable; interrupted output is not a valid backup.
6. Add `rockstream admin backup create <destination>`, `backup inspect <destination>`, `backup verify <destination>`, and `admin restore <source>` in CLI dispatch. Reuse existing checkpoint administration and disaster-recovery code. Restore only to an empty or explicitly replaceable destination, validate first, and define replacement authorization and rollback behavior before coding. Bound copy concurrency, pending bytes, retries, and verification scan windows.
7. Fail startup and backup verification on missing files, checksum mismatches, incompatible formats, incomplete manifests, and broken catalog references. Inspect may describe an invalid backup but must never imply validity. Restore must not silently repair or skip mandatory data.
8. Run crash injection during ordinary writes, view maintenance, checkpoints, catalog DDL, and backup. Restore complete backups to a new directory with the original storage inaccessible. Verify exact base rows, every view multiset, indexes, catalog identities, source cursors, idempotency behavior, and committed frontier. Retry writes around uncertain acknowledgments and prove no duplicate effects.

## Documentation changes

Update `docs/disaster-recovery.md`, configuration guidance, and executable administration examples. Publish the recovery state machine, durable acknowledgment contract, backup format, consistency point, destination rules, retention, corruption failures, and interruption cleanup. Record each supported storage backend's restore procedure.

## Exit criteria

| ID | Acceptance condition | Intended proof |
|---|---|---|
| V065-01 | All eight recovery categories reconstruct the exact acknowledged state, including cursor and idempotency behavior. | Full release-process restart oracle and subsequent retry/ingestion checks. |
| V065-02 | Startup traverses the declared recovery states, keeps readiness false, and fails closed on any mandatory recovery error. | Delayed and failed recovery process traces plus readiness responses. |
| V065-03 | Recovery reads every page of every supported state category within named memory limits. | Fixtures exceeding each scan page, exact complete recovered contents, and observed bounded buffers; truncation injection must fail. |
| V065-04 | A backup's catalog revision, checkpoint, and frontier describe one consistent logical point under concurrent writes and compaction. | Capture point recorded in the manifest and complete expected state reconstructed independently at that point. |
| V065-05 | The manifest contains every required field and file; supported formats restore and unsupported combinations reject explicitly. | Full manifest assertions and compatibility matrix including damaged, missing, and incomplete entries. |
| V065-06 | Create, inspect, verify, and restore operate through the release CLI; occupied destinations reject unless explicitly replaceable. | Complete CLI transcripts, storage-error tests, and unchanged destination assertions after refused or failed restore. |
| V065-07 | Hard kills during writes, maintenance, checkpoint, DDL, and backup produce only recoverable committed state or explicit invalid/incomplete backup errors. | Separate process kill case at each boundary, full state oracle, and retry checks. |
| V065-08 | Restore to a new filesystem path needs no original files and returns the exact catalog, base rows, view multisets, and auxiliary state. | Make original storage inaccessible before launching the restored release process and query every category. |
| V065-09 | Missing files, bad checksums, incompatible formats, incomplete manifests, and broken references fail startup or verification without successful partial recovery. | One corruption fixture per condition with exact diagnostics and false readiness. |
| V065-10 | Recovery, backup, and restore obey named byte, concurrency, waiter, retry, and scan limits with observable progress and explicit overflow behavior. | Slow-storage, cancellation, and capacity tests plus resource observations during the process suite. |
